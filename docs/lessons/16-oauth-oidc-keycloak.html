OAuth 2, OpenID Connect and Keycloak

One login for every Smart Campus module. How does the browser get a token from Keycloak, what is inside that token, and how can a service trust it without asking Keycloak every time? This lesson gives you the words and the flow you need for the identity module.

1. Who are you, and what may you do?

Story AUTH-1 says: "As a student, I want to log in once with my university account, so that I use every module without logging in again." Smart Campus has many modules (timetable, registration, grades, clubs, marketplace…) and 4 backend apps. We do not want each one to have its own password page. So we use one identity provider: a separate server whose only job is to check who people are. In Smart Campus this is Keycloak 26 (Arch ADR-2). It already runs in Compose at http://localhost:8180, still empty.

Two questions are always asked, and they are different:

Authentication (AuthN)

"Who are you?" Like the hotel reception checking your passport. Keycloak does this: it checks the password (or another factor) and says "this is student SV2026001".

Authorization (AuthZ)

"What may you do?" Like the key card that opens only your room. Our services do this: "a STUDENT may read their own grades, a LECTURER may enter grades for their own sections".

Keycloak answers the first question and gives us facts for the second (the roles). The final "yes or no" is always made in our own code (lesson 17).

2. OAuth 2 roles and what OIDC adds

OAuth 2 (RFC 6749) is a standard for one thing: letting an app get a token (a digital pass) so it can call an API for a user, without ever seeing the user's password. OAuth 2 names four roles. Here they are in Smart Campus:

OAuth 2 roleMeaningIn Smart Campus
Resource ownerThe person who owns the dataThe student or lecturer
ClientThe app that wants to call the APIThe React web app in frontend/web (planned client campus-web)
Authorization serverChecks the user and gives out tokensKeycloak (:8180)
Resource serverThe API that accepts tokensThe gateway, core-app, registration-service, notification-service

OAuth 2 alone is about access. It does not say how the client learns who logged in. OpenID Connect (OIDC) is a thin layer on top of OAuth 2 that adds exactly this. It adds three things:

  • ID token: a token for the client that says who logged in, when, and how. The web app reads it to show "Hello, An".
  • UserInfo endpoint: a URL where the client can ask for more profile facts (name, email) with the access token.
  • Discovery: one well-known URL that lists every other URL and setting. A library only needs the issuer URL and finds the rest itself.

You turn OIDC on by asking for the scope openid. A scope is a word the client sends to say what it wants (openid profile email).

curl -s http://localhost:8180/realms/campus/.well-known/openid-configuration

{
  "issuer": "http://localhost:8180/realms/campus",
  "authorization_endpoint": "http://localhost:8180/realms/campus/protocol/openid-connect/auth",

3. Authorization Code + PKCE, step by step

A flow (OAuth calls it a grant) is the dance of redirects and requests that ends with a token. The Arch (§5, "SSO login") uses the Authorization Code flow with PKCE. PKCE (say "pixie", RFC 7636) means "Proof Key for Code Exchange".

1. Web appMakes a secret code_verifier and its hash, the code_challenge
→
2. Redirect to KeycloakSends the challenge, never the verifier
→
3. Student logs inOn Keycloak's page, not ours
→
4. Back with a codeA one-time code in the URL
→
5. Code + verifier → tokensKeycloak hashes the verifier and compares

Step 1: the verifier and the challenge

The code_verifier is a long random string (43 to 128 characters). The code_challenge is its SHA-256 hash, written in base64url. The method name for this is S256. A hash works in one direction only: from the challenge, nobody can compute the verifier. Your library does this for you. This code only shows the idea:

function base64url(bytes: Uint8Array): string {
  return btoa(String.fromCharCode(...bytes))
    .replace(/\+/g, "-").replace(/\//g, "_").replace(/=+$/, "");
}

const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));   // 43 random chars, kept in memory
const hash = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(verifier));
const challenge = base64url(new Uint8Array(hash));                          // sent to Keycloak

Step 2: the redirect

GET http://localhost:8180/realms/campus/protocol/openid-connect/auth
    ?client_id=campus-web
    &response_type=code                         // "give me a code", not a token
    &scope=openid profile email
    &redirect_uri=http://localhost:5173/auth/callback
    &state=Zk3q…                                // random; checked on return (stops fake callbacks)
    &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    &code_challenge_method=S256

Steps 3 to 5: login, code, exchange

The student types the password on Keycloak's page. Our web app never sees it. Keycloak redirects back to /auth/callback?code=…&state=…. The app checks that state is the value it sent, then swaps the code for tokens:

POST http://localhost:8180/realms/campus/protocol/openid-connect/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=6c1b…                                     // one-time, valid for a short time
&redirect_uri=http://localhost:5173/auth/callback
&client_id=campus-web
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk   // the secret from step 1

→ 200 { "access_token": "eyJ…", "id_token": "eyJ…", "refresh_token": "eyJ…", "expires_in": 300 }

Keycloak hashes the verifier and compares it with the challenge from step 2. Only the app that started the login knows the verifier. So if an attacker steals the code (from browser history, a log, or a bad browser extension), the code is useless to them.

Why the implicit flow is gone

Old single-page apps used the implicit flow: Keycloak put the access token directly in the redirect URL (#access_token=…). Tokens in URLs leak into history, logs and Referer headers, and nothing proves who receives them. The OAuth security best practice (RFC 9700) says: do not use the implicit flow; use the code flow with PKCE, also for browser apps. The Resource Owner Password flow (the app collects the password itself) is also not allowed. In Keycloak we switch both off for campus-web.

Public vs confidential clients

Public client

Runs where it cannot keep a secret: in the browser, anyone can read the JavaScript. It has no client secret. PKCE protects it. Smart Campus: campus-web (planned).

Confidential client

Runs on a server and can keep a secret (from a Kubernetes Secret or .env). Smart Campus: a planned client for the SIS import job, which calls Keycloak's admin API with its own service account (section 7).

The backend apps are not clients for user login. They are resource servers: they only check tokens. Because Smart Campus is web only (map assumption 3), the user login needs just one client: the web app.

What a JWT looks like

Keycloak's tokens are JWTs (JSON Web Tokens, RFC 7519, say "jot"). A JWT is three base64url parts joined by dots: header.payload.signature.

eyJhbGciOiJSUzI1NiIsImtpZCI6IjNmY…  .  eyJpc3MiOiJodHRwOi8vbG9jYWxob3N0…  .  Qm9xL2tZ…
└──────────── header ────────────┘     └──────────── payload ───────────┘     └ signature ┘
 {"alg":"RS256","kid":"3fc…"}            the claims (JSON, NOT secret!)         made with
 which algorithm, which key              anyone can decode and read them        Keycloak's private key

The payload is only encoded, not encrypted. Anyone can read it (try jwt.io with a dev token only). The signature makes it tamper-proof: if a student changes STUDENT to SYSTEM_ADMIN, the signature no longer matches. So: never put secrets or private data (grades, phone numbers) in a token.

{
  "iss": "http://localhost:8180/realms/campus",    // issuer: who made it
  "sub": "8d0c6a6e-3f0b-4b7e-9a51-2c4e0f6b1a90",   // subject: the user's stable Keycloak id
  "aud": "campus-api",                             // audience: who it is made for
  "azp": "campus-web",                             // authorized party: the client that asked
  "exp": 1795000300,                               // expires at (seconds since 1970)
  "iat": 1795000000,                               // issued at
  "scope": "openid profile email",
  "preferred_username": "sv2026001",
  "realm_access": {
    "roles": ["STUDENT", "default-roles-campus"]   // Arch §7: roles are read from here
  }
}
ClaimWhat our services check
issMust be exactly our realm URL. A token from another realm is rejected.
audMust contain our API name. Keycloak adds it with an audience mapper (section 6).
expMust be in the future (with a small clock skew allowance).
subThe user id. Our tables store this as a UUID, never the username, because a username can change.
realm_access.rolesTurned into Spring authorities like ROLE_STUDENT (lesson 17).

5. Checking a signature with JWKS

Keycloak signs tokens with a private key that only it has. Anyone can check the signature with the matching public key. Keycloak publishes its public keys at the jwks_uri as a JWKS (JSON Web Key Set, RFC 7517). Think of a wax seal: only the king has the stamp, but everyone knows what the seal looks like.

  gateway / service                                    Keycloak
  ─────────────────                                    ────────
  1. token arrives, header says kid = "3fc…"
  2. key "3fc…" in my cache?  ── no ──► GET /realms/campus/protocol/openid-connect/certs
                                       ◄── {"keys":[{"kid":"3fc…","kty":"RSA","n":"…","e":"AQAB"}]}
  3. verify signature with that public key        (cached: NOT one call per request)
  4. check iss, aud, exp
  5. OK → continue  |  any check fails → 401

This is why the Arch says "the gateway verifies the signature with Keycloak's public keys (JWKS, cached)". Our services do not call Keycloak for each request. During the registration rush (5,000 students in one minute, NFR-1) this matters a lot.

The kid (key id) allows key rotation: Keycloak can add a new key, sign new tokens with it, and keep the old key in the JWKS until old tokens have expired. When a service sees an unknown kid, Spring Security fetches the JWKS again.

Smart Campus trap: the issuer URL inside Docker The browser reaches Keycloak at localhost:8180, so tokens say "iss": "http://localhost:8180/realms/campus". A backend app running inside Compose (the apps profile) reaches Keycloak as keycloak:8080. If the service expects the issuer keycloak:8080, every token fails. The usual fix: give Keycloak one fixed public hostname (its hostname settings), and in Spring set the expected issuer-uri to the public URL and the jwk-set-uri to the internal URL. The identity spec will decide this.

7. Accounts from the SIS (AUTH-3, AUTH-4)

AUTH-3: the academic office wants "student and lecturer accounts to exist before the semester starts". The Arch asks an open question: can Keycloak federate (read live) from a university LDAP/AD, or do we import accounts once from the SIS (Student Information System)? Decision C11: until someone answers, we import a CSV file. Map assumption 4: the SIS is a CSV fixture in dev.

student_code,full_name,email,faculty_code,cohort,role
SV2026001,Nguyễn Văn An,an.nv@student.campus.edu.vn,CNTT,K2026,STUDENT
SV2026002,Lê Thị Hoa,hoa.lt@student.campus.edu.vn,KT,K2026,STUDENT
GV0042,Trần Thị Bình,binh.tt@campus.edu.vn,CNTT,,LECTURER

The import job is a confidential client with a service account: it logs in as itself (not as a person) and has only the Keycloak admin rights it needs to manage users. For each row it:

  1. finds the user by username, or creates it with the Keycloak Admin REST API;
  2. gives the realm role from the CSV (only roles from the list of 7 are accepted);
  3. saves the profile row in the identity schema, keyed by the Keycloak sub, without roles (C9);
  4. sets a "required action" so the person chooses a password at first login.
@Service
class SisImportService {

    private final KeycloakAdmin keycloak;      // our small wrapper around the Admin REST API
    private final ProfileRepository profiles;

    ImportReport importCsv(Reader csv) {
        var report = new ImportReport();
        for (SisRow row : SisCsv.parse(csv)) {                       // bad rows are reported, not skipped silently
            String userId = keycloak.findByUsername(row.studentCode())
                    .orElseGet(() -> keycloak.createUser(row));       // run it twice: no duplicate users
            keycloak.grantRealmRole(userId, row.role());
            profiles.upsert(UUID.fromString(userId), row);           // profile only, no roles (C9)
            report.ok(row.studentCode());
        }
        return report;
    }
}

Note the word idempotent again (lesson 08): running the same CSV twice must give the same result. Admins will re-run imports.

AUTH-4 ("assign and revoke roles") is the same Admin API call, made from a small admin screen that only SYSTEM_ADMIN can use. Remember: a role change shows up only in the next access token, so within up to 5 minutes the old roles still work.

8. Global logout (AUTH-6)

AUTH-6: "log out from all devices, so a lost phone can't access my account". To understand logout, remember that there are two kinds of session:

  • the Keycloak session (a cookie on Keycloak's domain), which lets the user log in to other apps without typing the password again (that is SSO, single sign-on);
  • the tokens held by the web app.
Kind of logoutHow it worksUse in Smart Campus
RP-initiated logout (RP = relying party, the client)The web app sends the browser to Keycloak's end_session_endpoint with id_token_hint and post_logout_redirect_uri. Keycloak ends its session and sends the browser back.The normal "Log out" button
Back-channel logoutKeycloak calls each client's back-channel URL server to server with a signed logout_token. The client then ends its own session for that user.Only for clients with a server side (for example a BFF, lesson 17). A pure browser app has no URL Keycloak can call.
Log out all sessionsKeycloak removes every session of one user (Admin API or the account console). Refresh tokens stop working everywhere.AUTH-6 "log out from all devices"
GET http://localhost:8180/realms/campus/protocol/openid-connect/logout
    ?id_token_hint=eyJ…
    &post_logout_redirect_uri=http://localhost:5173/
The 5-minute gap An access token is a self-contained JWT. Our services check it without asking Keycloak, so they cannot know it was "logged out". After "log out everywhere", a stolen access token still works until exp. This is why access tokens are short (5 minutes): logout stops the refresh, and the access token dies soon after. If a module ever needs instant revocation, that is a design question for its spec (token introspection costs a call per request).

10. Common mistakes

  • Using the implicit flow or the password flow. Use Authorization Code + PKCE (S256) only. Turn the others off in the client settings.
  • Accepting any valid Keycloak token. Check iss, exp and aud. Without the audience check, a token made for some other app in the realm would work on our API.
  • Sending the ID token to the API. APIs take access tokens only.
  • Storing roles in our own table. Breaks C9: two copies will disagree.
  • Putting private data in tokens. Anyone can decode the payload.
  • Building our own login page. The password must only ever be typed into Keycloak.
  • Using the master realm for the app. It is Keycloak's own admin realm.
  • Wildcard redirect URIs in production (like *). An attacker could get the code sent to their site. List exact URLs.

    docker compose -f infra/docker-compose.yml up -d --wait

  2. Create a test realm practice by hand (it is thrown away later). Add realm roles STUDENT and LECTURER, a user sv1 with role STUDENT and a password, and a public client practice-web with redirect URI http://localhost:5173/*. Find where to require PKCE with S256.

  3. Open the discovery document and find the 5 URLs from section 2:

    curl -s http://localhost:8180/realms/practice/.well-known/openid-configuration

  4. In the client's "Client scopes" → "Evaluate" tab, generate an example access token for sv1. Find iss, sub, aud, exp and realm_access.roles. Is aud what our API would need? Which mapper would fix it?

  6. On paper: draw the PKCE flow from memory. Mark which values are secret (verifier, tokens) and which may be seen (challenge, state).

13. Test yourself

1. Why can't an attacker who steals the authorization code get tokens?

The token request needs the code_verifier. Only the hash (the challenge) travelled through the browser. The verifier stayed in the app's memory, and a hash cannot be reversed. Without it, Keycloak refuses the exchange.

2. Why is the web app a public client, and why is that OK?

All browser code can be read by anyone, so any "secret" in it is not secret. PKCE replaces the client secret with a fresh one-time secret for every login, which gives the same protection for the code exchange.

3. Why can our services check tokens without calling Keycloak?

The token is signed. With Keycloak's public key (cached from the JWKS) a service can prove the token is real and unchanged, then read the claims. That keeps Keycloak off the hot path during the registration rush.

4. Why do roles live only in Keycloak (C9)?

With one source of truth, the token always reflects the current roles (after the next refresh). A copy in our database could get out of sync, and then two parts of the system would disagree about what a person may do.

5. After "log out from all devices", why can a stolen access token still work for a short time?

Services check access tokens offline, so they do not hear about the logout. Logout stops refresh, so the token dies at exp. Short lifetimes (5 minutes) keep this window small.

6. Why must the API check aud and not only the signature?

Every client in the realm gets tokens signed with the same key. Without the audience check, a token issued for a different app would be accepted by our API, which was never the plan.
