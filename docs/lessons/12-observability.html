Observability: traces, logs, metrics

When a student says "registration was slow at 08:00", how do you find the one slow request among millions? Observability is the set of tools that let you look inside the running system and answer that question in minutes, not days.

1. Why you need this in Smart Campus

Smart Campus is not one program. One click from a student can travel through the gateway, then core-app, then Kafka, then notification-service. Each app writes its own logs, on its own machine or container. If something goes wrong, you need a way to see the whole journey.

The Architecture document sets the goal: "Find a slow request in minutes". The spec turns that into three success criteria that close in Phase 4:

IdWhat must be trueTask
B1One call to /api/v1/platform/ping?emit=true shows in Grafana/Tempo as one trace across gateway → core-app → Kafka → a consumer in notification-service.T16
B2Every app logs single-line JSON with traceId and spanId. Loki can find the logs by traceId.T17
B3Prometheus scrapes all 4 apps. The "Platform overview" dashboard shows request rate, p95 latency per route, 5xx rate, JVM memory and Kafka consumer lag. Alert rules exist for lag > 30 s and 5xx > 1%.T18

A good everyday picture: a hospital. Metrics are the heart-rate monitor (numbers over time). Logs are the nurse's notes (what happened, in words). Traces are the patient's path through the building (reception → X-ray → doctor), with the time spent in each room.

2. The three pillars

PillarWhat it isAnswersStored inQuery language
MetricsNumbers counted or measured over time (requests per second, heap size) "Is something wrong? Since when? How bad?"PrometheusPromQL
LogsText events, one line per thing that happened "What exactly happened, and with what values?"LokiLogQL

All three are shown in one UI: Grafana (port 3000). The spec chose Tempo instead of Jaeger exactly for this reason (spec Q5): one place to look.

The pillars work together. A typical investigation:

1. Metric alert5xx rate over 1% on core-app
→
2. LogsFilter ERROR lines in Loki, copy a traceId
→
3. TraceOpen it in Tempo: the Kafka send took 30 s
→
4. CauseKafka was down; the outbox retried later

The glue between them is the trace id: a 32-character hex id that is the same in the trace, in every log line of that request, and in the problem JSON the user sees.

3. OpenTelemetry in five words

OpenTelemetry (short: OTel) is an open standard plus free tools for producing traces, metrics and logs. It is not a database and not a UI. It only creates and sends the data. Five words to know:

Why a Collector in the middle? The apps only need to know one address (the Collector). If we later change Tempo for another backend, or add a second one, only the Collector config changes. No app is rebuilt.

4. Traces, spans and traceparent

A span is one timed piece of work: "handle HTTP GET /ping", "INSERT into event_publication", "send to Kafka". It has a name, a start time, a duration, some attributes (key/value facts) and a status (OK or error). Spans form a tree: each span (except the first) has a parent. All spans of one request share one trace id. The whole tree is the trace.

Trace 4bf92f3577b34da6a3ce929d0e0e4736  (the B1 request, times are made up)

gateway        GET /api/v1/platform/ping            |=================================|  41 ms
core-app         GET /api/v1/platform/ping          |=========================|          30 ms
core-app           INSERT platform.event_publication  |==|                               3 ms
core-app           campus.events publish                    |====|   (after commit)      6 ms
notification-svc     campus.events process                       |=======|               9 ms
notification-svc       INSERT notification.processed_events        |=|                   1 ms

Tempo draws exactly this kind of picture (a "waterfall"). A long bar shows you where the time went.

How does the next app know the trace id?

Each app runs in its own process. The trace id must travel with the message. This is called context propagation. The standard way is the W3C Trace Context header named traceparent:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                └ flags: 01 = sampled (keep it)
             │  │                                └ parent span id (16 hex chars)
             │  └ trace id (32 hex chars), the same for the whole journey
             └ version
BrowserGET /api/v1/platform/ping?emit=true
→
gatewaystarts the trace
adds traceparent to the HTTP call
→
core-appreads the header
adds traceparent to the Kafka record headers
→
notification-servicereads the Kafka header
continues the same trace

Kafka records have headers (small key/value pairs next to the key and value), just like HTTP. Spec decision D4 says the trace context travels in Kafka headers, not in the event payload. The business data in DomainEvent stays clean, and a replayed event does not carry fake "business" fields (see lesson 08).

Outbox and traces: a thing T16 must check Our events are sent after commit, on a background thread (the outbox, lesson 08). The agent normally carries the context into such threads, so the Kafka send joins the request's trace. But an event that the OutboxRetryJob resends 30 seconds later runs in a scheduled job, not in the request, so it will most likely appear as a separate trace. That is fine; just do not be surprised by it.

5. The Java agent, the Collector and Tempo

Attaching the agent (T16.1 to T16.3)

The JVM option -javaagent:<path to jar> loads the agent before your main method. The plan has three steps:

  1. 16.1 Pin the agent version in the root pom.xml <properties> and copy the jar (Maven artifact io.opentelemetry.javaagent:opentelemetry-javaagent) to target/otel/ with maven-dependency-plugin. No manual download, and the version is in one place.
  2. 16.2 A Maven profile, active only when the env var OTEL_EXPORTER_OTLP_ENDPOINT is set, adds -javaagent to spring-boot:run and sets service.name per app.
  3. 16.3 The shared Dockerfile copies the agent into the image. In the Compose apps profile it is switched on with JAVA_TOOL_OPTIONS.
# … stage 2: the runtime image …
COPY target/otel/opentelemetry-javaagent.jar /otel/opentelemetry-javaagent.jar
# The agent is in the image, but only used when JAVA_TOOL_OPTIONS says so.
  core-app:
    profiles: [apps]
    environment:
      JAVA_TOOL_OPTIONS: >-
        -XX:MaxRAMPercentage=75
        -javaagent:/otel/opentelemetry-javaagent.jar
      OTEL_SERVICE_NAME: core-app                        # the name you see in Tempo
      OTEL_EXPORTER_OTLP_ENDPOINT: http://otel-collector:4318

The agent is configured with OTEL_* environment variables (or -Dotel.* system properties). The most important ones:

SettingMeaning
OTEL_SERVICE_NAMEThe app's name in every span and log (core-app, gateway, …)
OTEL_EXPORTER_OTLP_ENDPOINTWhere to send OTLP data (the Collector)
OTEL_TRACES_EXPORTER, OTEL_LOGS_EXPORTER, OTEL_METRICS_EXPORTER Which signals to send. Metrics in this project go through Prometheus instead, so T16/T18 will probably turn the agent's metric export off (check the agent docs for the default).
"Builds and tests still pass with no collector running" (T16 Done when) This is why the agent is only attached when the endpoint is set. ./mvnw verify and CI never need the observability stack. Telemetry is a tool for running systems, not a build dependency.

From our fake trace id to the real one (T16.6)

Since T8, platform-starter already gives every request a trace id. But it is made up by our own filter, because no tracing existed yet:

String traceId = newTraceId();          // random UUID without dashes = 32 hex chars
MDC.put(MDC_KEY, traceId);              // "traceId" in the log context
response.setHeader(HEADER, traceId);    // X-Trace-Id response header
try {
    chain.doFilter(request, response);
} finally {
    MDC.remove(MDC_KEY);                // the thread goes back to the pool
}

The problem handler asks a TraceIdProvider interface for the id, so it does not care where the id comes from. T16.6 swaps the implementation:

public String traceId() {
    SpanContext ctx = Span.current().getSpanContext();  // OpenTelemetry API
    return ctx.isValid() ? ctx.getTraceId()             // agent attached: the real id
                         : TraceIdFilter.newTraceId();  // no agent: old behaviour
}

Without the agent, the OTel API is a "no-op" (it does nothing) and returns an invalid, all-zero id. That is why there is a fallback. The format (32 hex chars) was chosen in T8 to match, so nothing else changes.

The Collector pipeline (T16.4)

A Collector config has receivers (data in), processors (change or batch it), exporters (data out), and pipelines that connect them, one pipeline per signal type.

receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }
processors:
  batch: {}                         # send in groups, not one span at a time
exporters:
  otlp/tempo:
    endpoint: tempo:4317            # Tempo also speaks OTLP
    tls: { insecure: true }         # dev only, inside the Compose network
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp/tempo]
    # logs: added in T17 (OTLP → Loki)

Grafana gets its data sources from a provisioned file, so nobody clicks them together by hand and the setup is in Git:

apiVersion: 1
datasources:
  - name: Tempo
    type: tempo
    uid: tempo
    url: http://tempo:3200
  - name: Prometheus
    type: prometheus
    uid: prometheus
    url: http://prometheus:9090

6. JSON logs, MDC and Loki

Why JSON?

Plain text

2026-11-24 08:00:01 ERROR [core-app] Section S1 full, trace 4bf9…

A human can read it. A machine must guess where each field starts. Multi-line stack traces break into many "lines".

Structured JSON, one line

{"@timestamp":"…","log.level":"ERROR","service.name":"core-app", "message":"Section S1 full","traceId":"4bf9…","spanId":"00f0…"}

Every field has a name. Loki and Grafana can filter by traceId or level exactly. The stack trace is one field.

Spring Boot has built-in structured logging: one property switches the console output to JSON. No extra library is needed. T17.1 turns it on for non-test profiles, and T17.2 keeps plain text in tests so test output stays readable.

logging:
  structured:
    format:
      console: ecs        # built-in formats: ecs, logstash, gelf

The exact field names depend on the format you pick (ECS, Logstash or GELF). Look at a real line after T17.1 and check that the names traceId and spanId are really there (that is a "Done when" of T17).

MDC: how traceId gets into every line

MDC ("Mapped Diagnostic Context") is a small map that belongs to the current thread. Whatever you put into it, the logger can add to every line written by that thread. Think of a name badge: you put it on once at the door, and everyone you meet sees it.

  • Today (T8): our TraceIdFilter puts traceId in the MDC and removes it in finally. Threads are reused from a pool; forgetting remove would give the next request the old id.
  • After T16: the Java agent also writes the current trace and span id into the logging MDC. By default the agent uses the keys trace_id and span_id (check the agent's logger-MDC docs). T17.1 must make sure the JSON lines end up with traceId and spanId, as B2 requires.

Loki and LogQL (T17.3 to T17.5)

Loki stores logs cheaply. It does not index the full text. It indexes only a few labels (like service_name) and then scans the matching lines. In T17 the logs go app → (agent, OTLP) → Collector → Loki. Newer Loki versions accept OTLP directly; check the Loki and Collector docs for the exact exporter.

A LogQL query has two parts: a stream selector in { } (which labels), then optional filters after pipes:

# all lines of core-app that contain this trace id
{service_name="core-app"} |= "4bf92f3577b34da6a3ce929d0e0e4736"

# parse JSON fields, then keep only errors
{service_name="core-app"} | json | level="ERROR"

# number of error lines per minute, per app (LogQL can make metrics too)
sum by (service_name) (count_over_time({service_name=~".+"} |= "ERROR" [1m]))

T17.4 adds the links between the two UIs:

  • Logs → trace: a "derived field" on the Loki data source finds the trace id in a log line and turns it into a link to Tempo.
  • Trace → logs: Tempo's "trace to logs" setting opens Loki filtered by this trace id.

So the user who got a problem JSON with "traceId":"4bf9…" can give you that id, and you go straight to the trace and all its log lines.

7. Metrics: Micrometer and Prometheus

Micrometer: the metrics API of Spring

Micrometer is to metrics what SLF4J is to logs: one API in your code, many possible backends. Spring Boot Actuator already records many metrics with it (HTTP requests, JVM memory, threads, Kafka clients, connection pool). You can add your own:

TypeWhat it measuresSmart Campus example
CounterOnly goes up. Count of events.Seat requests rejected with SECTION_FULL (registration module)
GaugeA value right now; can go up or down.JVM heap used; outbox rows not yet completed
TimerHow long something takes, plus how many times.HTTP request time (http.server.requests, automatic)
Histogram (distribution)Counts values in buckets (≤ 10 ms, ≤ 50 ms, …) so you can calculate percentiles later.Request latency buckets for p95
class SeatMetrics {
    private final Counter sectionFull;

    SeatMetrics(MeterRegistry registry) {
        this.sectionFull = Counter.builder("campus.registration.section.full")
                .description("Seat requests rejected because the section was full")
                .register(registry);
    }

    void onSectionFull() { sectionFull.increment(); }
}

Prometheus pulls ("scrapes")

Prometheus is a time-series database. Every few seconds it calls an HTTP endpoint on each app and saves the numbers. This is called a scrape. With the micrometer-registry-prometheus dependency, Actuator serves that endpoint at /actuator/prometheus. Today our apps expose only health, info; T18.1 adds prometheus in the starter and turns on latency histograms for HTTP requests.

management:
  endpoints:
    web:
      exposure:
        include: health, info, prometheus
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true    # buckets, so p95 can be calculated in PromQL
scrape_configs:
  - job_name: apps-local            # apps started with spring-boot:run on your PC
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["host.docker.internal:8080", "host.docker.internal:8081",
                  "host.docker.internal:8082", "host.docker.internal:8083"]
  - job_name: apps-compose          # apps in the Compose "apps" profile
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["gateway:8080", "core-app:8081",
                  "registration-service:8082", "notification-service:8083"]

Only one of the two jobs will be UP at a time, depending on the run mode. That is expected. (Container names and ports above follow the spec; T15/T18 fix the real values.)

PromQL: rate() and histogram_quantile()

Micrometer's HTTP timer appears in Prometheus as several series, for example http_server_requests_seconds_count (number of requests), …_sum (total seconds) and …_bucket (histogram buckets, with a label le = "less or equal"). Each has labels like uri, method, status.

# Request rate: requests per second, averaged over 5 minutes, per route
sum by (uri) (rate(http_server_requests_seconds_count[5m]))

# 5xx ratio: errors / all requests (0.01 = 1%)
  sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
/ sum(rate(http_server_requests_seconds_count[5m]))

# p95 latency per route, in seconds
histogram_quantile(0.95,
  sum by (le, uri) (rate(http_server_requests_seconds_bucket[5m])))
  • A counter only grows (12 000, 12 050, …). The raw number is useless. rate(x[5m]) turns it into "per second, over the last 5 minutes". Always rate a counter before you sum it.
  • p95 ("95th percentile") = 95% of requests were faster than this. It is better than the average: an average hides the slow 5% that make students angry. The Architecture target is p95 under 500 ms during registration.
  • histogram_quantile needs the le label kept in the sum by. Forgetting le is the most common p95 mistake.

8. Dashboards, alerts, RED and cardinality

The RED method

For every service that answers requests, watch three things. They are easy to remember:

R = RateHow many requests per second?
E = ErrorsHow many of them fail (5xx)?
D = DurationHow long do they take (p95)?

The "Platform overview" dashboard (T18.5) is RED plus a few platform signals: request rate, p95 per route, 5xx rate, 429 rate (the gateway rate limiter, lesson 11), JVM heap, and Kafka consumer lag.

Dashboards as files

A Grafana dashboard is a JSON document. We do not build it by clicking and hope it survives. We save the JSON in Git and Grafana loads it at start (provisioning):

apiVersion: 1
providers:
  - name: smart-campus
    type: file
    options:
      path: /var/lib/grafana/dashboards     # infra/grafana/dashboards/ mounted here

A good workflow: build a panel in the UI, then use "Export → JSON" and save it as infra/grafana/dashboards/platform-overview.json.

Alert rules

Prometheus checks alert rules on a schedule. If the expression is true for the time in for, the alert fires. The Architecture asks for two platform alerts:

groups:
  - name: platform
    rules:
      - alert: High5xxRate
        expr: |
            sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          / sum(rate(http_server_requests_seconds_count[5m])) > 0.01
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "More than 1% of requests fail with 5xx"
      # - alert: ConsumerLagHigh   lag > 30 s, metric source decided in T18.3
Consumer lag in seconds is an open decision (T18.3 🙋) Kafka clients report lag as a number of messages (a metric like records-lag-max). The alert says 30 seconds. 1 000 messages may be 1 second of work or 10 minutes. Measuring lag in time probably needs an extra "lag exporter" container, and adding a container is "ask first" in the spec. So this is decided with the human in T18.

Before trusting the rules, T18.6 checks them with Prometheus's own tool: promtool check rules infra/prometheus/alerts.yml (run in a container).

The high-cardinality trap

Cardinality = how many different label combinations a metric has. Each combination is a separate time series stored in memory. Labels must have a small, fixed set of values.

Explodes

A label studentId, traceId, email, or the raw URL /api/v1/sections/8f3c…. 30 000 students × 20 routes × 5 statuses = 3 million series. Prometheus runs out of memory.

Safe

Labels like uri="/api/v1/sections/{id}" (the template, which Spring uses by default), method, status, service. Put ids in logs and traces, not in metric labels.

10. Common mistakes

  • Putting ids in metric labels. Student ids, trace ids and raw URLs belong in logs and traces. Metric labels must have few values.
  • Averages instead of percentiles. "Average 80 ms" can hide 5% of requests taking 4 seconds. Use p95 (and p99 for the registration rush).
  • Summing a counter without rate(). The result just grows forever and resets to zero when an app restarts.
  • Putting the trace id in the event payload. It goes in Kafka headers (D4). The agent does this for you.
  • Making the build depend on the Collector. Tests must pass with nothing listening on port 4317/4318.
  • Forgetting MDC.remove in your own filters or async code. The next request on that pooled thread gets the wrong id.
  • Logging secrets or personal data. JSON logs are easy to search, for attackers too. Never log passwords, tokens or full request bodies.
  • Building the dashboard only in the UI. It is lost with docker compose down -v. Export it to JSON in infra/grafana/dashboards/.

13. Test yourself

1. Why do we need traces at all, when every app already writes logs?

Logs are per app. Without a shared id you cannot tell which gateway line, which core-app line and which notification line belong to the same request, and you cannot see where the time went. A trace links them and shows the duration of every step.

2. Why does the trace context go in Kafka headers and not in the DomainEvent payload?

The payload is business data, versioned with schemaVersion and replayed later. Trace data is technical and only matters for this delivery. Keeping them apart keeps the event contract clean (spec D4), and the agent can handle headers with no code in our events.

3. Why is the agent attached only when OTEL_EXPORTER_OTLP_ENDPOINT is set?

So that builds, tests and CI never depend on a running Collector. T16 requires that ./mvnw verify passes with observability off. Developers who do not need traces also start faster.

4. Why use p95 and not the average latency?

An average mixes many fast requests with a few very slow ones and hides the slow ones. p95 tells you what the slowest 5% of users experience, which is what the 500 ms registration target is about.

5. A teammate adds studentId as a label on a request counter. What happens, and what should they do instead?

Each student creates new time series, so memory in Prometheus grows with the number of students (high cardinality) and queries get slow. Put the student id in logs or span attributes, and keep metric labels to small, fixed sets.

6. Why must the consumer-lag alert be measured in seconds, and why is that hard?

The rule "lag over 30 s" is about how late users get their result, which is time. Kafka clients report lag as a count of messages, and the time per message changes. Turning lag into time needs another tool (likely an extra exporter container), which is a decision for T18.3.
