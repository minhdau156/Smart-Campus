1. Why you need this in Smart Campus

Modules in Smart Campus never read each other's tables. When something happens, the module publishes an event, and other modules react. Kafka carries those events (map C2: "Kafka only", spec D5: "even inside core-app"). Kafka is also a work queue: during the registration rush, seat requests wait in registration.requests until a worker handles them.

Why Kafka and not a simple queue (Arch ADR-4)? It keeps order per key, it keeps history so read models can be rebuilt (replay), and it handles big bursts. The price: it is heavier to run and has more ideas to learn. Here they are.

2. The big picture

Think of Kafka as a set of notebooks that you can only write at the end of. Nobody erases a line. Readers keep a bookmark of how far they have read.

                          Kafka broker (one in dev, three in production)
                          ┌──────────────────────────────────────────────────┐
 producer                 │ topic "registration.events"  (6 partitions)      │
 (registration-service) ──►   partition 0: [0][1][2][3][4][5] ← new records  │
                          │   partition 1: [0][1][2]                         │
                          │   …                                              │
                          │   partition 5: [0][1][2][3]                      │
                          └──────────────────────────────────────────────────┘
                                   │ offsets: 0, 1, 2, … (position in one partition)
                                   ▼
                consumer group "timetable"      consumer group "notification"
                (its own bookmarks)             (its own bookmarks)
WordMeaning
BrokerA Kafka server. It stores records on disk and answers clients.
TopicA named stream of records, e.g. course.events. Like a notebook title.
PartitionOne slice of a topic. A topic with 6 partitions is 6 append-only logs. Partitions let many consumers work in parallel.
OffsetThe position of a record inside one partition: 0, 1, 2, … It never changes.
RecordOne message: a key, a value, headers, and a timestamp.

In Smart Campus, a record looks like this:

  • key: a string such as a studentId (chosen per topic, next section);
  • value: the JSON DomainEvent envelope (eventId, type, schemaVersion, occurredAt, aggregateId, payload);
  • headers: technical extras, like the trace context traceparent (spec D4, lesson 12). Business data never goes in headers.

3. Keys, partitions and ordering

When a producer sends a record with a key, Kafka hashes the key and picks a partition. The same key always goes to the same partition (as long as the partition count does not change). Kafka keeps order only inside one partition. So:

The key decides what stays in order All records with the same key are read in the order they were written. Records with different keys may be read in any order compared to each other.

That is why the key is chosen per topic, in shared-kernel (spec D6, built in T5):

public enum Topics {
    /** Seat requests. Not replayable: a request is a command, running it twice would act twice. */
    REGISTRATION_REQUESTS("registration.requests", 12, "sectionId",   false),
    REGISTRATION_EVENTS(  "registration.events",    6, "studentId",   true),
    COURSE_EVENTS(        "course.events",          3, "sectionId",   true),
    GRADE_EVENTS(         "grade.events",           3, "studentId",   true),
    CAMPUS_EVENTS(        "campus.events",          3, "aggregateId", true);
    …
    public String keyOf(DomainEvent<?> event) { … }  // a missing key throws (D6)
}
  • registration.requests keyed by sectionId: all requests for one section are in one partition, in arrival order. First come, first served, and the waitlist is fair.
  • registration.events keyed by studentId: one student's "enrolled", then "dropped" can never arrive swapped.
  • campus.events keyed by aggregateId: the thing that changed.
Never change the partition count of a live topic lightly More partitions = a different hash result = keys move to other partitions, and the order between old and new records of one key is lost. In Smart Campus, changing partitions, keys or names is an "Ask first" spec change.

4. The producer: acks, retries, timeouts

The producer is the client that writes records. Its most important settings:

SettingWhat it meansSmart Campus
acksWhen does the broker say "stored"? 0 = never asks, 1 = the leader wrote it, all = the leader and all in-sync copies wrote it. all, set in campus-platform-defaults.yml
enable.idempotenceThe broker drops a repeat of the same batch when the producer resends it after a timeout. Avoids duplicates from producer retries. On (Kafka's default)
retriesHow many times the producer resends a failed batch.Kafka's default (very high)
delivery.timeout.msThe total time the producer may try before it gives up and reports a failure. Kafka's default (120 s); 8 s in the test profile
key / value serializerHow the key and value become bytes. String key, byte-array value (Modulith writes the JSON itself)

Think of sending a registered letter. acks=all means you wait for the signed receipt. Idempotence means the post office throws away a second copy of the same letter you sent because you were not sure the first one arrived. But if your outbox sends a new letter later (after delivery.timeout.ms), that is a new send, and a duplicate can still appear. T7 saw exactly this. The answer is the idempotent consumer in lesson 08.

5. Consumer groups, offsets, rebalancing

Consumer groups

A consumer reads records. Consumers join a consumer group (a name, the group.id). Inside one group, each partition is given to exactly one consumer. Different groups are fully independent: each group gets every record.

topic registration.requests (12 partitions)

group "registration-worker", 3 instances:
   worker A ← partitions 0-3      worker B ← partitions 4-7      worker C ← partitions 8-11

group "timetable" on registration.events — a different group, reads everything again for itself
  • More consumers in a group = more work in parallel, up to the number of partitions. With 12 partitions, a 13th worker sits idle.
  • One partition is read by one consumer at a time, so order per key is kept.
  • In Smart Campus the group id is the consumer's name, e.g. notification, timetable. The replay script resets one group (T12).

Offsets and committing

A group remembers how far it has read by committing offsets: "for partition 3, the next record to read is 42". Kafka stores this in an internal topic. After a restart, the consumer continues from the committed offset.

Commit before processing

The app crashes after the commit but before the work → the record is skipped forever (at-most-once).

Commit after processing

The app crashes after the work but before the commit → the record is read again (at-least-once). Safe if the consumer is idempotent.

Spring Kafka turns Kafka's own auto-commit off and commits after your listener returns without an error. That gives at-least-once, which is what Smart Campus wants.

If a group has no committed offset yet (a brand-new group), auto.offset.reset decides where to start: earliest (from the oldest record) or latest (only new records, Kafka's default). A read model that must see all history wants earliest.

Rebalancing

When a consumer joins, leaves or crashes, the group rebalances: partitions are handed out again. During a rebalance, the moved partitions pause for a moment, and a record that was processed but not yet committed may be read again by the new owner. One more reason to be idempotent. Kafka notices a dead consumer when it stops sending heartbeats or stops polling for too long, so a listener that blocks for minutes can be kicked out of its group.

6. Retention: how long Kafka keeps records

Reading a record does not delete it. Kafka deletes old data only by its retention rules, per topic:

Cleanup policyWhat is keptUse
delete (default)Records younger than retention.ms (and under retention.bytes). Older segments are deleted.Event history, queues
compactAt least the latest record for each key. Older records of the same key are removed."Current value per key" tables
Smart Campus: event topics keep everything (spec D5, O5) The event topics use retention.ms=-1: never delete by age. With the full history, a read model like timetable or search can be dropped and rebuilt by reading from offset 0. Compaction was rejected because it loses history per key.

In dev, infra/docker-compose.yml also sets KAFKA_LOG_RETENTION_BYTES (about 100 MB per partition) so your laptop disk does not fill up. That size cap still deletes old data, so very old dev events can disappear.

7. Our broker: KRaft and topics in code

KRaft

Older Kafka needed a second system, ZooKeeper, to store cluster metadata. Modern Kafka uses KRaft: some Kafka nodes act as controllers and keep the metadata themselves, using the Raft agreement protocol. Kafka 4 runs only in KRaft mode. In dev, our single container is both broker and controller:

kafka:
  image: apache/kafka:4.4.0
  environment:
    KAFKA_PROCESS_ROLES: broker,controller        # one node does both jobs
    KAFKA_LISTENERS: INTERNAL://:29092,EXTERNAL://:9092,CONTROLLER://:9093
    KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:29092,EXTERNAL://localhost:9092
    KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"        # topics come from the apps
    KAFKA_LOG_RETENTION_BYTES: 104857600          # dev disk cap

Two client listeners: apps on your computer use localhost:9092, containers in the Compose network use kafka:29092. The broker tells each client which address to use next ("advertised" listener), so a wrong value here is a classic "it connects, then hangs" bug.

Topics are declared in code, never auto-created

With auto-create on, a typo like cours.events silently creates a new empty topic with default settings. So auto-create is off, and each producing app declares its topics as NewTopic beans. Spring Boot's KafkaAdmin creates any missing ones at startup. T7 does this for the probe topic:

@Bean
NewTopic probeTopic() {
    return TopicBuilder.name(ProbeTopic.NAME)        // "platform.probe"
            .partitions(ProbeTopic.PARTITIONS)       // 3
            .replicas(1)                             // one broker in dev
            .build();
}

T12 (planned) does the same for the five real topics, built from Topics, and adds unlimited retention:

@Bean
NewTopic courseEvents() {
    Topics t = Topics.COURSE_EVENTS;
    return TopicBuilder.name(t.topicName())
            .partitions(t.partitions())
            .config(TopicConfig.RETENTION_MS_CONFIG, "-1")   // keep forever (D5)
            .build();
}

core-app declares course.events, grade.events and campus.events; registration-service declares the two registration topics. The app that writes a topic owns it.

8. Spring Kafka: sending, listening, errors

Sending: KafkaTemplate

kafkaTemplate.send("course.events", sectionId, json)   // topic, key, value
        .whenComplete((result, error) -> { … });       // async: a CompletableFuture
In Smart Campus business code, do not call KafkaTemplate yourself Publish with ApplicationEventPublisher.publishEvent(new DomainEvent<>(…)) inside your transaction. Spring Modulith saves it in the outbox and calls KafkaTemplate for you after the commit, with the key from Topics (lesson 08).

Listening: @KafkaListener

package edu.campus.notification.internal;

@Component
class ProbeListener {

    private final IdempotentConsumer idempotent;     // from platform-starter (T11)

    ProbeListener(IdempotentConsumer idempotent) {   // constructor injection
        this.idempotent = idempotent;
    }

    @KafkaListener(topics = "platform.probe", groupId = "notification-probe")
    void on(ConsumerRecord<String, String> record) {
        // parse the envelope, then: insert processed_events + side effect, in ONE transaction
    }
}

Spring creates a listener container for each @KafkaListener. The container polls Kafka in a loop, calls your method for each record, and commits the offset when the method returns. If the method throws, the container's error handler decides what happens. (The group id above is an example; the T11 task decides the real one.)

Errors: retry, then dead-letter

Spring Kafka's DefaultErrorHandler retries a failed record a few times. Its default is FixedBackOff(0, 9): no pause and 9 retries, so 10 attempts in all. Then it logs the record and moves on. You can give it a back-off and a recoverer:

@Bean
DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<Object, Object> template) {
    var deadLetter = new DeadLetterPublishingRecoverer(template);   // sends to "<topic>-dlt"
    return new DefaultErrorHandler(deadLetter, new FixedBackOff(1_000L, 2L)); // 3 tries, 1 s apart
}

A dead-letter topic (DLT) is a parking place for records that keep failing (a "poison message", for example bad JSON). Without it, one bad record could block its partition forever, or be dropped with only a log line. By default Spring Kafka names it <original topic>-dlt, same partition number. Remember: our broker does not auto-create topics, so a DLT must be declared as a NewTopic too, with at least as many partitions as the original. Smart Campus has not decided its DLT setup yet; it comes with the first real consumers.

Retry only what can succeed later A database that is briefly down: retry. A payload that cannot be parsed: retrying 10 times gives the same error 10 times. Spring Kafka lets you mark exception types as "not retryable" so they go straight to the recoverer.

10. Common mistakes

  • Expecting global order. Kafka orders per partition only. If two records must stay in order, they must have the same key.
  • Sending without a key. The record lands on any partition. In Smart Campus a missing key throws on purpose (D6).
  • Doing slow work inside the listener for minutes. The consumer looks dead, the group rebalances, and records are read twice.
  • Thinking "read = deleted". Records stay until retention removes them. Other groups, and replays, read them again.
  • Reusing one group id for two different jobs. They would share the partitions and each would see only part of the records.
  • Swallowing every exception in the listener. Then failed records are committed as "done". Let real failures reach the error handler.
  • Using localhost:9092 from inside a container. Containers use kafka:29092.

11. Practice with the CLI tools

The apache/kafka image has Kafka's command-line tools in /opt/kafka/bin/ (our Compose healthcheck uses one of them). Run them inside the container with docker compose exec.

  1. Start the infrastructure and list the topics:

    docker compose -f infra/docker-compose.yml up -d --wait
docker compose -f infra/docker-compose.yml exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

  2. Start core-app in dev (it declares platform.probe), then describe the topic. Look at the partition count and the leader of each partition:

    .\mvnw.cmd -pl backend/core-app spring-boot:run
docker compose -f infra/docker-compose.yml exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic platform.probe

  3. Watch records arrive, with keys and headers. Then create a probe in another terminal:

    docker compose -f infra/docker-compose.yml exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic platform.probe --from-beginning --property print.key=true --property print.headers=true
curl.exe -X POST "http://localhost:8081/api/v1/platform/outbox-probe?note=hello"

    Create three probes. Do they always land in the same partition? Why not?

  4. See consumer groups and their lag (how far behind they are):

    docker compose -f infra/docker-compose.yml exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list
docker compose -f infra/docker-compose.yml exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group <group>

    The console consumer makes its own temporary group, so you will see something even before T11.

  5. Reset a group to the start (this is the heart of replay.sh, T12). The group must have no running consumers. Without --execute it only prints a plan (a "dry run"):

    docker compose -f infra/docker-compose.yml exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --group <group> --topic platform.probe --reset-offsets --to-earliest
# add --execute to really do it

  6. Read KafkaTestConsumer in core-app's tests. It uses assign instead of a group. Why is that better for a test that counts records?

13. Test yourself

1. Why is registration.events keyed by studentId and not by sectionId?

Consumers care about one student's history in order ("enrolled" before "dropped"). The same key puts all of one student's events in one partition, and Kafka keeps order only inside a partition.

2. registration.requests has 12 partitions. Why would a 13th worker in the same group not help?

Each partition is read by exactly one consumer of a group. 12 partitions can keep at most 12 consumers busy; the 13th gets no partition and waits.

3. Why does Spring Kafka commit offsets after the listener returns, not before?

If the app crashes in the middle, the record is read again (at-least-once) instead of being lost. Duplicates can be handled by an idempotent consumer; lost records cannot be fixed.

4. Why do our event topics use retention.ms=-1 and not compaction?

Read models must be rebuilt from the full history (replay). Compaction keeps only the newest record per key and would lose the history.

5. Why is topic auto-create turned off?

A typo would silently create a wrong topic with default partitions and retention, and events would go nowhere useful. Declaring topics in code makes the settings reviewed and repeatable.

6. The producer has idempotence on. Why can a consumer still see the same event twice?

Idempotence only removes repeats of the same producer batch. When the outbox gives up and sends the event again later, it is a new send. Rebalances can also cause a re-read. So the consumer must dedupe by eventId (lesson 08).
