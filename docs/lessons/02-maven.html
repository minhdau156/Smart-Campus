Maven multi-module builds

One command, .\mvnw.cmd verify, compiles every backend module, runs all the tests, checks the code format and the test coverage. This lesson explains how the pom.xml files make that happen, so you can read them, change them, and fix a red build.

1. What Maven does for us

Maven is a build tool for Java. You describe the project in XML files called POMs (pom.xml, "Project Object Model"). Maven then:

  • downloads libraries (dependencies) from Maven Central into a cache, ~/.m2/repository;
  • compiles the code and runs the tests;
  • packages jars, including the runnable Spring Boot jar;
  • runs checks: code format, coverage, banned libraries.

Smart Campus switched from Gradle to Maven on 2026-11-20 (spec decision Q2), because Maven's XML is easier to read: there is no code in it, only a description. The price is that XML is long. This lesson helps you find your way in it.

Maven works by convention: if you put code where it expects (src/main/java, src/test/java, src/main/resources), you write almost no configuration. The build output goes to target/ (gitignored).

2. Anatomy of a pom

Every Maven project has coordinates, like a postal address, so it can be found in a repository:

ElementSmart Campus valueMeaning
groupIdedu.campusThe organisation, like a reversed domain name
artifactIdshared-kernel, core-app …The name of this one project
version0.1.0-SNAPSHOTSNAPSHOT = work in progress, not a release
packagingpom (root) or jarWhat the build produces

A pom has a few big blocks. You will see them again and again:

pom.xml
├── <parent>                 where to inherit settings from
├── groupId / artifactId / version / packaging
├── <modules>                (root only) the sub-projects to build
├── <properties>             named values, used as ${name}
├── <dependencyManagement>   versions only: "if you use X, use version Y"
├── <dependencies>           libraries this project really uses
├── <build>
│   ├── <pluginManagement>   plugin settings, OFF until a module lists the plugin
│   └── <plugins>            plugins that really run
└── <profiles>               optional switches, turned on with -P<id>

3. Parent pom, modules, reactor

A chain of parents

A pom can have a parent. It inherits the parent's properties, dependencies, plugin settings and versions. Smart Campus has a chain of three:

spring-boot-starter-parent 4.1.3versions of hundreds of libraries and plugins, Java release, UTF-8, -parameters
→
root pom.xml (smart-campus)module list, our versions, shared build rules
→
backend/*/pom.xmlonly what this module needs
<parent>
    <groupId>edu.campus</groupId>
    <artifactId>smart-campus</artifactId>
    <version>0.1.0-SNAPSHOT</version>
    <relativePath>../../pom.xml</relativePath>   <!-- two folders up -->
</parent>
<artifactId>core-app</artifactId>

The <version> inside <parent> is the only version a child pom writes. Everything else comes from above. To see the effective pom (the final pom after all parents are merged), run .\mvnw.cmd -pl backend/core-app help:effective-pom.

Modules and the reactor

The root pom has <packaging>pom</packaging>: it builds nothing itself, it only groups modules:

<modules>
    <module>backend/shared-kernel</module>
    <module>backend/platform-starter</module>
    <module>backend/core-app</module>
</modules>

When you build from the root, Maven's reactor (the part that plans a multi-module build) reads every module, sees who depends on whom, and builds them in the right order. core-app depends on platform-starter, which depends on shared-kernel, so the order is kernel → starter → core-app. Later tasks add registration-service (T10), notification-service (T11) and gateway (T13) to this list.

Build only part of the project: -pl and -am -pl backend/core-app ("project list") builds only that module. -am ("also make") adds the modules it needs. So .\mvnw.cmd -pl backend/core-app -am verify builds kernel, starter and core-app, and skips the others. Without -am, Maven must find the other modules' jars in ~/.m2 already (from an earlier install), or it fails with "could not resolve".

4. Versions, BOMs and scopes

Properties

<properties> are named values. The root pom keeps every version in one place, with a comment that links to the official source of each number:

<properties>
    <java.version>21</java.version>                    <!-- read by the Boot parent -->
    <spring-cloud.version>2025.1.5</spring-cloud.version>
    <spring-modulith.version>2.1.3</spring-modulith.version>
    <springdoc.version>3.2.0</springdoc.version>
    <skipUTs>false</skipUTs>                            <!-- our own build switch -->
</properties>

dependencyManagement and BOMs

<dependencyManagement> is a price list, not a shopping cart. It says "if a module uses this library, use this version", but it adds nothing to any module. A BOM ("bill of materials") is a whole price list published by a project, with versions tested together. You import it with type pom + scope import:

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.modulith</groupId>
            <artifactId>spring-modulith-bom</artifactId>
            <version>${spring-modulith.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        …

We import the Spring Cloud and Spring Modulith BOMs. Spring Boot's own list comes through the parent. Result: a module writes a dependency with no version, and Maven knows which one to use.

Dependency scopes

A scope says when a library is needed:

ScopeNeeded forExample in Smart Campus
compile (default)Compile, test and run. Passed on to users of this modulespring-boot-starter-webmvc in core-app
runtimeRun and test, but not to compilepostgresql JDBC driver in core-app
testOnly test code. Never in the real jarJUnit, AssertJ, Testcontainers, jackson-databind in shared-kernel
providedCompile, but someone else gives it at run time(not used yet)
importOnly in dependencyManagement, to import a BOMSpring Cloud and Modulith BOMs

<optional>true</optional> is a related idea. In platform-starter, Spring MVC and Modulith are optional: the starter compiles against them, but an app that uses the starter does not get them automatically. Each part of the starter switches on only if the app has those libraries itself (lesson 03).

A transitive dependency is a library you get because another library needs it. See the whole tree with .\mvnw.cmd -pl backend/core-app dependency:tree.

5. Plugins and the lifecycle

Phases and goals

Maven itself does almost nothing. Plugins do the work. Each plugin has goals (jobs), like spotless:check or jacoco:report. Goals are attached to phases of the lifecycle, a fixed list of steps:

validate → compile → test-compile → test → package
         → pre-integration-test → integration-test → post-integration-test
         → verify → install → deploy

   You ask for one phase. Maven runs every phase BEFORE it too.
   ./mvnw test     = validate … test
   ./mvnw verify   = validate … test … package … integration-test … verify
   ./mvnw clean    = a separate lifecycle: delete target/

We almost always run verify: it is the "is everything OK?" command. We never run deploy (there is no artifact server).

plugins vs pluginManagement

Same idea as dependencies: <pluginManagement> prepares settings, but the plugin is off until a module lists it in <plugins>. The root pom uses this for spring-boot-maven-plugin: only runnable apps need it, and it would fail on a library like shared-kernel.

Root pom: prepared, off

<pluginManagement><plugins>
  <plugin>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
      <layers><enabled>true</enabled></layers>
    </configuration>
  </plugin>
</plugins></pluginManagement>

core-app pom: switched on

<plugins>
  <plugin>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
      <profiles><profile>dev</profile></profiles>
    </configuration>
  </plugin>
</plugins>

The plugin makes the runnable "fat" jar and gives the goal spring-boot:run. Layers split the jar into parts (libraries, loader, our code), so Docker can cache each part (lesson 05). The dev profile setting means only spring-boot:run uses the dev settings; tests never do.

6. Unit tests, ITs and profiles

Two plugins, two kinds of test

Unit tests and integration tests live in the same folder, src/test/java. The class name ending decides who runs them:

Unit testIntegration test (IT)
NameMoneyTest, PingControllerTestCoreApplicationIT, OutboxIT
Pluginmaven-surefire-pluginmaven-failsafe-plugin
Phasetestintegration-test, then fails the build in verify
Speed / needsFast, no DockerSlow, real Postgres and Kafka in Docker (Testcontainers)

Why does failsafe wait until verify to fail? So the post-integration-test phase can still clean up (stop servers, containers) after a failed IT. That is the "fail-safe" in the name.

How -DskipUTs works

Maven's standard -DskipTests skips both kinds. We wanted a way to run only the ITs, so the root pom links surefire to our own property:

<properties>
    <skipUTs>false</skipUTs>
</properties>
…
<plugin>
    <artifactId>maven-surefire-plugin</artifactId>
    <configuration>
        <skipTests>${skipUTs}</skipTests>   <!-- only surefire reads this -->
    </configuration>
</plugin>

-DskipUTs on the command line sets the property. A -D with no value means true, so surefire skips, and failsafe still runs.

Profiles: -Pexport-openapi

A Maven profile is a named block of extra settings, turned on with -P<id>. Smart Campus has one: export-openapi (T9). It writes the API documents to docs/api/:

<profile>
    <id>export-openapi</id>
    <properties>
        <skipUTs>true</skipUTs>                         <!-- no unit tests -->
        <it.test>OpenApiExportIT</it.test>              <!-- failsafe runs only this IT -->
        <failsafe.failIfNoSpecifiedTests>false</failsafe.failIfNoSpecifiedTests>
    </properties>
    …  <!-- + system property openapi.export=true: WRITE instead of compare -->
</profile>

Without the profile, the same OpenApiExportIT only compares the committed files with the live app, so a forgotten export fails the normal build. Do not confuse Maven profiles (-P) with Spring profiles (dev, test, lesson 03) or Compose profiles (apps, lesson 05): three tools, three meanings of "profile".

7. Quality gates

A gate is a check that fails the build. A red build stops bad code early, on your computer, not in review.

GatePluginWhereFails when
Code formatspotless-maven-plugin with palantir-java-formatroot pom, all modules, verifyAny Java file is not formatted. Fix: .\mvnw.cmd spotless:apply
Coveragejacoco-maven-plugin goal checkshared-kernel pom onlyTests run less than 90% of the lines
No Spring in the kernelmaven-enforcer-plugin, bannedDependenciesshared-kernel pomAny org.springframework* library reaches the classpath, even transitively
Testssurefire + failsaferoot pomAny test fails

JaCoCo works in steps: prepare-agent attaches a small helper (an "agent") to the test run that records which lines run; report writes HTML to target/site/jacoco/ (we put it in the test phase so .\mvnw.cmd test already gives it); check compares with the 90% rule. Only shared-kernel has the gate now. Each feature module's spec will set its own.

shared-kernel also builds a test-jar that holds only edu.campus.kernel.testing (the Clocks helper), so other modules' tests can use it with <type>test-jar</type> and <scope>test</scope>.

Never lower a gate to get green The spec's "Ask first" list includes "lowering a coverage gate or disabling a check". Write the missing test, or run spotless:apply. Never add -Dspotless.check.skip or @Disabled to make the build pass.

8. The wrapper and daily commands

The Maven Wrapper

Nobody installs Maven by hand. The repo has wrapper scripts: mvnw (Git Bash, Linux, macOS) and mvnw.cmd (PowerShell, cmd). On first use they download the exact Maven version written in .mvn/wrapper/maven-wrapper.properties (Maven 3.9.16) into ~/.m2/wrapper/, and check its SHA-256 fingerprint. Everyone, including CI, uses the same Maven.

Commands you will use every day

Command (PowerShell)What it does
.\mvnw.cmd verifyEverything: compile, unit tests, ITs, Spotless, coverage. Run before "done"
.\mvnw.cmd testUnit tests only. Fast, no Docker
.\mvnw.cmd verify -DskipUTsITs only (needs Docker)
.\mvnw.cmd spotless:applyFix the code format
.\mvnw.cmd -pl backend/core-app -am verifyOne module plus what it needs
.\mvnw.cmd -pl backend/core-app spring-boot:runStart core-app on port 8081 with the dev profile
.\mvnw.cmd package -DskipTestsBuild the jars quickly (used before Docker images, T15)
.\mvnw.cmd verify -Pexport-openapiRefresh docs/api/*.json
.\mvnw.cmd -pl backend/shared-kernel "-Dtest=MoneyTest" testRun one unit test class (in the module that has it; other modules would fail with "no tests matching")
.\mvnw.cmd cleanDelete all target/ folders
PowerShell and -D PowerShell can split arguments that contain dots, like -Dspring-boot.run.profiles=dev. Put such arguments in double quotes: "-Dspring-boot.run.profiles=dev".

10. Common mistakes

  • Writing a <version> in a child pom. Versions live only in the root pom (spec: "update the root pom's properties and nothing else for versions").
  • Putting a library in the root <dependencies> when you meant <dependencyManagement>. The first adds it to every module.
  • Naming an IT …Test. Surefire runs it in the fast phase, and .\mvnw.cmd test suddenly needs Docker. Integration tests end in IT.
  • Using -DskipTests to "only run ITs". It skips both. Use -DskipUTs.
  • Forgetting -am with -pl, then getting "could not resolve edu.campus:shared-kernel".
  • Using a floating version like a range or LATEST. The spec forbids it: builds must be the same tomorrow.
  • Committing target/. It is build output and is gitignored.

11. Practice

  1. Run the full build and read the "Reactor Summary" at the end. In which order were the modules built, and why?

    .\mvnw.cmd verify

  2. Look at the effective pom of core-app and find where maven-failsafe-plugin gets its version and its goals:

    .\mvnw.cmd -pl backend/core-app help:effective-pom "-Doutput=target/effective-pom.xml"

  3. Print core-app's dependency tree. Find one library you did not add yourself, and the dependency that brought it in:

    .\mvnw.cmd -pl backend/core-app -am dependency:tree

  4. Break the format of one Java file (add spaces inside a method call), run .\mvnw.cmd -pl backend/shared-kernel verify, read the error, then run spotless:apply and see it fixed.

  5. Run only the ITs, then only the unit tests, and compare the time each takes.

13. Test yourself

1. Why do the child poms have no versions for Spring libraries?

The versions come from above: the Spring Boot parent manages Boot's libraries, and the root pom imports the Spring Cloud and Modulith BOMs. One place for versions means an upgrade is one edit, and modules can never drift to different versions.

2. Why is spring-boot-maven-plugin in pluginManagement in the root pom?

Only runnable apps need it. In <plugins> it would run in every module, including the libraries shared-kernel and platform-starter, which have no main class. In pluginManagement it is prepared but off, and each app turns it on.

3. Why does failsafe report IT failures in verify, not in integration-test?

So the build can still run the post-integration-test clean-up steps after a failed IT. Stopping at once could leave servers or containers running.

4. Why do we have our own -DskipUTs?

-DskipTests stops both surefire and failsafe. We often want only the ITs (for example in CI or after a Docker change). skipUTs is wired only into surefire.

5. Why are Spring MVC and Modulith optional in platform-starter?

So the starter does not force them on every app. The gateway is not a Spring MVC app; it must not get Spring MVC just because it uses the starter. Each starter feature turns on only when the app brings the library itself.

6. Why is the coverage gate only on shared-kernel?

The kernel is shared by every app, so a bug there spreads everywhere, and it is small, plain Java that is easy to test fully. Other code gets gates when its module spec sets them.
