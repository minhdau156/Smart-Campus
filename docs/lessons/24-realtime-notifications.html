Real-time: WebSocket, push and email

1. Why you need this in Smart Campus

The notification module is the "post office" of Smart Campus. Other modules do not send emails themselves. They publish events to Kafka, and the post office decides who gets a message and how. The stories it serves:

2. Four ways to reach the browser

HTTP is "the browser asks, the server answers". The server cannot start a conversation. To send news from the server, we have four choices:

WayHow it worksGoodBad
PollingThe browser asks "anything new?" every few secondsVery simple, works everywhere, easy to cache and rate-limitSlow to notice news; many empty requests
Long pollingThe browser asks; the server waits until there is news (or a timeout), then answers; the browser asks againFaster than polling, plain HTTPMany waiting requests; tricky timeouts
Server-Sent Events (SSE)One long HTTP response; the server writes events into it. EventSource in the browserSimple, one direction, auto-reconnect built inServer → browser only; the standard EventSource cannot send an Authorization header
WebSocketAn HTTP request is "upgraded" to a two-way connection that stays openFast, both directions, low overheadStateful connections; harder with many servers and proxies

An analogy: polling is calling the shop every 5 minutes to ask "is my order ready?". WebSocket is keeping the phone line open so the shop can tell you the moment it is ready.

The Architecture document chose WebSocket with STOMP at /ws, with the user queues /user/queue/notifications and /user/queue/registration. Polling stays as a safe fallback: if the socket is closed, the page still loads the inbox with a normal GET.

3. STOMP over WebSocket in Spring

A WebSocket only moves raw text or bytes. It has no idea of "topics" or "who should get this". STOMP (Simple Text Oriented Messaging Protocol) is a small protocol on top. It adds frames such as CONNECT, SUBSCRIBE, SEND and MESSAGE, each with headers and a body, a bit like tiny HTTP messages.

Words you need:

  • Destination: an address like /topic/news or /queue/notifications.
  • Broker: the part that remembers who subscribed to which destination and delivers messages to them.
  • User destination: a destination starting with /user/. The client subscribes to /user/queue/notifications; Spring turns it into a private queue for that logged-in user only.
package edu.campus.notification.realtime;

@Configuration
@EnableWebSocketMessageBroker
class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

    private final JwtChannelInterceptor jwtInterceptor;

    WebSocketConfig(JwtChannelInterceptor jwtInterceptor) {   // constructor injection
        this.jwtInterceptor = jwtInterceptor;
    }

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws")                           // the URL the browser opens
                .setAllowedOriginPatterns("http://localhost:5173");  // the web app's origin
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.enableSimpleBroker("/queue", "/topic");      // in-memory broker (one app)
        registry.setApplicationDestinationPrefixes("/app");   // browser → @MessageMapping
        registry.setUserDestinationPrefix("/user");
    }

    @Override
    public void configureClientInboundChannel(ChannelRegistration registration) {
        registration.interceptors(jwtInterceptor);            // check the token on CONNECT
    }
}

Sending to one user from Java code is one call. The user name is the Principal name, which for a Keycloak JWT is the sub claim (the user id):

@Component
class LivePusher {
    private final SimpMessagingTemplate messaging;

    LivePusher(SimpMessagingTemplate messaging) {
        this.messaging = messaging;
    }

    void push(UUID userId, InboxItemView item) {
        // The browser subscribed to "/user/queue/notifications".
        messaging.convertAndSendToUser(userId.toString(), "/queue/notifications", item);
    }
}
The socket is a hint, not the truth If the user is offline, convertAndSendToUser just delivers to nobody. That is fine, because the message is already saved in the inbox table. When the tab opens again, it loads the inbox with a normal REST call. Never keep a message only in the WebSocket.

4. Login on /ws and the browser client

Why the token goes in the CONNECT frame

In the browser, the WebSocket API cannot add an Authorization header to the opening HTTP request. Putting the token in the URL (/ws?token=…) is risky, because URLs end up in logs. The usual answer: open the socket without a token, then send the JWT as a header inside the STOMP CONNECT frame. The server checks it before it accepts anything else.

@Component
class JwtChannelInterceptor implements ChannelInterceptor {
    private final JwtDecoder jwtDecoder;                         // checks signature + expiry (JWKS from Keycloak)
    private final JwtAuthenticationConverter converter = new JwtAuthenticationConverter();

    JwtChannelInterceptor(JwtDecoder jwtDecoder) {
        this.jwtDecoder = jwtDecoder;
    }

    @Override
    public Message<?> preSend(Message<?> message, MessageChannel channel) {
        StompHeaderAccessor stomp = MessageHeaderAccessor.getAccessor(message, StompHeaderAccessor.class);
        if (stomp != null && StompCommand.CONNECT.equals(stomp.getCommand())) {
            String header = stomp.getFirstNativeHeader("Authorization");
            if (header == null || !header.startsWith("Bearer ")) {
                throw new MessageDeliveryException("Missing token");   // connection refused
            }
            Jwt jwt = jwtDecoder.decode(header.substring(7));      // throws if bad or expired
            stomp.setUser(converter.convert(jwt));                 // Principal name = sub
        }
        return message;
    }
}

Also check SUBSCRIBE frames: a user may subscribe to their own /user/queue/… but not to someone else's raw queue. Spring Security can add rules per destination for messages too (see "Learn more").

The gateway route

The browser talks only to the gateway on :8080. Platform task T13 already plans the route /ws/** → notification-service (:8083). Spring Cloud Gateway can forward WebSocket traffic: the backend URI uses the ws:// scheme (or wss:// with TLS).

- id: notification-ws
  uri: ${NOTIFICATION_WS_URI:ws://localhost:8083}
  predicates:
    - Path=/ws/**

Watch out for idle timeouts in proxies: a quiet connection may be closed. STOMP heart-beats (small "I am alive" frames every few seconds) keep it open.

The browser client

In the web app we can use the @stomp/stompjs library. It reconnects by itself, and beforeConnect lets us put a fresh access token in every new CONNECT.

import { Client } from "@stomp/stompjs";

export function startLiveInbox(getToken: () => Promise<string>, onItem: (item: InboxItem) => void) {
  const client = new Client({
    brokerURL: `${location.origin.replace(/^http/, "ws")}/ws`,
    reconnectDelay: 5000,
    heartbeatIncoming: 10000,
    heartbeatOutgoing: 10000,
    beforeConnect: async () => {
      client.connectHeaders = { Authorization: `Bearer ${await getToken()}` };
    },
    onConnect: () => {
      client.subscribe("/user/queue/notifications", (msg) => onItem(JSON.parse(msg.body)));
    },
  });
  client.activate();
  return () => client.deactivate();
}

When a message arrives, the page can also tell TanStack Query to refetch the inbox (see lesson 14), so the list and the unread badge stay correct.

5. Many replicas: simple broker or relay

The "simple broker" lives in the memory of one app. In production the Architecture plans 2 replicas of notification-service. Now there is a problem:

  Lan's browser ──WebSocket──► replica A   (Lan's session lives here)
                                replica B   ◄── Kafka gives GradePublished for Lan to B
  B calls convertAndSendToUser("lan", …) → B has no session for Lan → message goes nowhere

Kafka splits partitions between the replicas in one consumer group, so the replica that handles the event is often not the one holding the socket. Two common fixes:

Broker relay

enableStompBrokerRelay(...) instead of enableSimpleBroker(...). Each replica forwards STOMP messages to an external STOMP broker (for example RabbitMQ with its STOMP plugin). The external broker knows all subscriptions, so any replica can send to any user. Cost: one more server to run. It is not in our Compose file today, so adding it is a spec decision.

Fan-out to every replica

The replica that saved the inbox row publishes a small "push item X to user Y" message on a channel that every replica hears (for example Redis pub/sub, which is already in Compose). Each replica pushes only if it has a local session for that user. Cost: our own code.

With one replica in dev, the simple broker is enough. SPEC-notification.md must pick the multi-replica design before production (C8).

6. Browser push and email

Browser push (Web Push)

Smart Campus is website only, no mobile app. So "push" means a browser push notification: the little pop-up that appears even when our tab is closed. The parts:

  1. Service worker: a small JavaScript file the browser keeps running in the background for our site. It receives push messages and shows them.
  2. Permission: the user must click "Allow". Ask only after they turn on push in the settings page, never on the first visit.
  3. Subscription: the browser's push service gives an address (endpoint URL and keys) for this browser. With FCM for web, the Firebase SDK gives a registration token instead. Either way, we store it as a "browser token".
  4. Sending: our server sends the message to the push service (or to FCM), which wakes the service worker.
self.addEventListener("push", (event) => {
  const data = event.data ? event.data.json() : {};
  event.waitUntil(self.registration.showNotification(data.title, {
    body: data.body,
    data: { link: data.link },            // e.g. "/grade/sections/…"
  }));
});
self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  event.waitUntil(clients.openWindow(event.notification.data.link));
});

Assumption 4 says external systems are stubbed in dev: a fake push sender. So the Java code depends on an interface, and the dev profile uses a fake that only records the message:

public interface PushSender {
    PushResult send(BrowserToken token, PushMessage message);
}

@Component
@Profile("dev")
class FakePushSender implements PushSender {
    private static final Logger log = LoggerFactory.getLogger(FakePushSender.class);

    @Override
    public PushResult send(BrowserToken token, PushMessage message) {
        log.info("FAKE PUSH to token {}…: {}", token.shortId(), message.title());  // never log the full token
        return PushResult.delivered();
    }
}

The real sender (FCM or Web Push) comes later. Its result can say "this token is dead" (the push service answers that the subscription no longer exists). Then we delete the token.

Email with Spring Mail and Mailpit

Spring Boot's mail starter gives a JavaMailSender. In dev it talks to Mailpit, a fake mail server from our Compose file: SMTP on port 1025, and a web page at http://localhost:8025 where you can read every email. No real email ever leaves your computer.

spring:
  mail:
    host: localhost
    port: 1025          # Mailpit SMTP (see infra/docker-compose.yml)
@Component
class EmailSender {
    private final JavaMailSender mail;
    private final EmailTemplates templates;

    EmailSender(JavaMailSender mail, EmailTemplates templates) {
        this.mail = mail;
        this.templates = templates;
    }

    void send(String to, NotificationType type, Map<String, Object> data, Locale locale) throws MessagingException {
        RenderedEmail email = templates.render(type, data, locale);   // vi or en
        MimeMessage message = mail.createMimeMessage();
        MimeMessageHelper helper = new MimeMessageHelper(message, true, "UTF-8");
        helper.setTo(to);
        helper.setFrom("no-reply@campus.edu");
        helper.setSubject(email.subject());
        helper.setText(email.text(), email.html());                   // plain text + HTML
        mail.send(message);
    }
}

Templates keep the words out of Java code. One template per notification type and language (for example grade-published.vi.html), filled with data from the event. Always escape user data (a title someone typed) when you put it into HTML.

7. Inbox, preferences, browser tokens

Resolution C10 says NOTI-2's tables (preferences and device tokens) are designed in the module spec. The Plan already has a notifications table. A likely shape (planned, in schema notification, no foreign keys to other schemas):

CREATE TABLE notification.notifications (            -- the inbox (NOTI-1)
    id          UUID PRIMARY KEY,
    user_id     UUID NOT NULL,                         -- bare UUID, no FK to identity
    type        TEXT NOT NULL,                         -- GRADE_PUBLISHED, CLASS_CANCELLED, …
    title       TEXT NOT NULL,
    body        TEXT NOT NULL,
    link        TEXT,
    source_event_id UUID NOT NULL UNIQUE,              -- one inbox row per event (extra safety)
    read_at     TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL
);
CREATE INDEX ON notification.notifications (user_id, created_at DESC);

CREATE TABLE notification.channel_preferences (      -- NOTI-2
    user_id  UUID NOT NULL,
    type     TEXT NOT NULL,
    channel  TEXT NOT NULL,                            -- IN_APP, PUSH, EMAIL
    enabled  BOOLEAN NOT NULL,
    PRIMARY KEY (user_id, type, channel)
);

CREATE TABLE notification.device_tokens (            -- browser tokens, not phones
    id           UUID PRIMARY KEY,
    user_id      UUID NOT NULL,
    token        TEXT NOT NULL UNIQUE,
    user_agent   TEXT,
    created_at   TIMESTAMPTZ NOT NULL,
    last_seen_at TIMESTAMPTZ NOT NULL
);

Ideas inside this design:

  • Defaults in code, rows only for changes. If a user has no row for (GRADE_PUBLISHED, EMAIL), use the default for that type. This keeps the table small.
  • Some types cannot be turned off. ANN-4 "urgent" should still arrive in the inbox. The rule lives in code, next to the defaults.
  • One user, many browsers. A student may allow push on a laptop and on a phone's browser. Each gives its own token. Delete a token when the push service says it is dead, or when the user logs out of that browser.

8. Save first, then send: retries

An email cannot be rolled back. So the consumer must not send inside its Kafka transaction. Instead it saves "what must be sent" first, and a separate worker sends later. This is the outbox idea again (lesson 08), used for email and push.

@KafkaListener(topics = "grade.events", groupId = "notification")
@Transactional
void on(DomainEvent<GradePublished> event) {
    if (!processedEvents.tryInsert(event.eventId())) {
        return;                                                    // D2: seen before
    }
    UUID studentId = event.payload().studentId();
    Notification n = inbox.add(studentId, NotificationType.GRADE_PUBLISHED, event);  // NOTI-1
    for (Channel channel : preferences.channelsFor(studentId, n.type())) {         // NOTI-2
        deliveries.schedule(n.id(), channel, clock.instant());     // status PENDING, attempts 0
    }
}                                                                  // COMMIT, nothing sent yet

A delivery worker then picks PENDING rows whose next_attempt_at has come (with FOR UPDATE SKIP LOCKED, see lesson 25), sends them, and marks them SENT. After the inbox row commits, the live WebSocket push happens too.

Exponential backoff with jitter (NOTI-3)

If Mailpit or the push service is down, do not retry every second: you would hammer a sick server. Wait longer after each failure (exponential backoff: 30 s, 1 min, 2 min, 4 min…), and add a little randomness (jitter) so thousands of failed messages do not all retry in the same second.

record Backoff(Duration base, Duration max) {
    Instant nextAttempt(Instant now, int attempts, RandomGenerator random) {
        long cap = Math.min(max.toMillis(), base.toMillis() * (1L << Math.min(attempts, 20)));
        long wait = random.nextLong(cap / 2, cap + 1);     // "equal jitter": between half and all of it
        return now.plusMillis(wait);
    }
}

Dead letters

After, say, 8 failed attempts, stop. Mark the delivery DEAD (a dead letter: a message that could not be delivered) and keep the error text. A dashboard or alert shows dead letters, and an admin can retry them by hand. The inbox row is still there, so the user does not lose the information.

The same idea exists in Kafka: if a consumer keeps failing on one record (bad data), Spring Kafka's error handler can retry with a back-off and then publish the record to a dead-letter topic. Our topics are created on purpose (auto-create is off in Compose), so a dead-letter topic must be created too.

Duplicate sends and why these consumers are not replayable

  • Duplicate event → stopped by processed_events (D2) and the unique source_event_id. One inbox row, one set of deliveries.
  • Crash after the email left but before SENT was saved → the worker sends again. This small window cannot be fully closed, because SMTP has no "undo" and no shared transaction. Keep it small: mark SENT right after each send, one row at a time. Where a provider accepts an idempotency key, pass the delivery id.
  • Replay → spec D5: consumers with external side effects are registered as non-replayable, and replay.sh refuses them. Replaying grade.events into this consumer would email every student about every old grade.

10. Common mistakes

  • Sending email inside the Kafka consumer transaction. If the commit fails after the send, the retry sends again. Save a delivery row first, send later.
  • Keeping messages only in the socket. Offline users lose them. The inbox table is the truth; the socket is a hint.
  • Putting the JWT in the WebSocket URL. URLs are logged. Send it in the STOMP CONNECT frame.
  • Using the simple broker with several replicas and wondering why some users get nothing. Use a relay or a fan-out.
  • Retrying at a fixed fast rate forever. Use backoff, jitter and a maximum, then a dead letter.
  • Asking for push permission on the first page load. Most users click "Block", and you cannot ask again easily.
  • Marking the email consumer as replayable. A replay would spam everyone.
  • Logging full tokens or email bodies with private data (grades!). Log ids.

12. Words to know

WordMeaning in simple words
WebSocketA connection that stays open so the server and browser can both send at any time.
SSEServer-Sent Events: a long HTTP response the server keeps writing into. One direction.
STOMPA small messaging protocol on top of WebSocket, with frames and destinations.
FrameOne STOMP message: a command (CONNECT, SUBSCRIBE…), headers and a body.
DestinationThe address of a message, like /user/queue/notifications.
Simple brokerSpring's in-memory message broker. Works inside one app only.
Broker relaySpring forwards STOMP to an external broker that all replicas share.
Heart-beatA tiny frame sent regularly to keep the connection alive.
Service workerA background script of a website. It receives push messages.
Web Push / FCMWays to send push messages to a browser. FCM is Google's service.
Browser tokenThe address of one browser for push messages (stored in device_tokens).
Exponential backoffWaiting twice as long after each failure.
JitterRandom extra wait so retries do not all happen at the same moment.
Dead letterA message we gave up on after many tries, kept for a human to look at.

13. Test yourself

1. Why does registration first ship a polling endpoint instead of WebSocket (C8)?

The WebSocket host is notification-service, and that module is built after registration. Polling (202 + GET …/requests/{id}) works with no new infrastructure, so registration can be finished and tested on its own. The push is added later.

2. Why is the JWT sent in the STOMP CONNECT frame and not in the URL?

The browser WebSocket API cannot set an Authorization header, and a token in the URL can leak into server and proxy logs. The CONNECT frame travels inside the open connection, and the server checks it before accepting anything else.

3. With 2 replicas and a simple broker, why do some users miss live messages?

Each simple broker knows only its own sessions. The replica that consumes the Kafka event may not be the one holding the user's socket, so the message is sent to nobody. A broker relay or a fan-out to every replica fixes it.

4. Why does the consumer save delivery rows instead of sending the email directly?

An email cannot be rolled back. If we sent inside the transaction and the commit then failed, Kafka would give the event again and we would send again. Saving first makes the decision part of the commit; sending later can be retried safely and tracked.

5. Why add jitter to the backoff?

When a mail server comes back, thousands of failed deliveries would all retry at the same moment and knock it over again. Random waits spread the retries out.

6. Why is the email/push consumer registered as non-replayable (D5)?

Replay reads every old event again. For a read model that just rebuilds rows. For a sender it would email and push every old notification to every student again.
