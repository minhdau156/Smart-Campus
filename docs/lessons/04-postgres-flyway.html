PostgreSQL, schemas and Flyway

All Smart Campus data lives in one PostgreSQL database, split into one schema per module. This lesson teaches the SQL you need, how transactions and locks keep data correct, why no foreign key may cross a schema, and how Flyway changes the database safely.

1. One database, many schemas

PostgreSQL ("Postgres") is a relational database: data is stored in tables with rows and columns, and you ask for it with SQL. Smart Campus runs Postgres 19 in Docker (image postgres:19.0-alpine3.24), with one database called campus.

Inside that database, each module gets its own schema. A schema is a named folder for tables. course.sections and registration.section_seats are in different folders. Think of one apartment building (the database) where each family (module) has a locked flat (schema).

database "campus"
├── platform      outbox (event_publication), flyway history    core_app
├── identity      course      timetable     grade                core_app
├── announcement  club        marketplace   lostfound   payment  core_app
├── registration                                                 registration_svc only
└── notification                                                 notification_svc only

database "keycloak"   (Keycloak's own tables, user keycloak)

Why not one database per module? One Postgres is simpler to run on a laptop and in CI, and still lets us split later. The schemas, separate users and the "no cross-schema foreign key" rule keep the modules as separate as if they had their own databases.

2. Tables, types, constraints, indexes

Here is a real table, the outbox table from T7:

CREATE TABLE event_publication
(
    id                     UUID                     NOT NULL,
    listener_id            TEXT                     NOT NULL,
    event_type             TEXT                     NOT NULL,
    serialized_event       TEXT                     NOT NULL,
    publication_date       TIMESTAMP WITH TIME ZONE NOT NULL,
    completion_date        TIMESTAMP WITH TIME ZONE,          -- NULL = not delivered yet
    status                 TEXT,
    completion_attempts    INT,
    last_resubmission_date TIMESTAMP WITH TIME ZONE,
    PRIMARY KEY (id)
);

CREATE INDEX event_publication_by_completion_date_idx ON event_publication (completion_date);

A timestamptz does not store a zone. It stores an exact instant (in UTC inside) and shows it in the session's time zone. That fits our rule: store Instant, convert to Asia/Ho_Chi_Minh only for display (lesson 01).

Constraints: rules the database enforces

  • PRIMARY KEY: unique and not null. Identifies a row.
  • NOT NULL: the column must have a value.
  • UNIQUE: no two rows may have the same value, e.g. UNIQUE (student_id, section_id) so a student enrolls once per section.
  • CHECK: a condition on each row, e.g. CHECK (enrolled <= capacity).
  • FOREIGN KEY … REFERENCES: the value must exist in another table. Allowed only inside the same schema (section 6).

Constraints are the last line of defence. Even if Java code has a bug, the database refuses bad data. The idempotent consumer (lesson 08) depends on a primary key to detect a repeated event.

Indexes

An index is like the index at the back of a book: it lets Postgres find rows without reading the whole table. Primary keys and UNIQUE columns get one automatically. Foreign key columns do not, so add one when you filter or join on them. Indexes make reads faster and writes a little slower, so add them for real queries, not "just in case". The outbox table indexes completion_date, because Modulith often asks for "rows not completed yet".

3. Transactions, ACID, isolation

A transaction is a group of SQL statements that succeed or fail together. In Spring, a @Transactional method is one transaction (lesson 03).

BEGIN;
INSERT INTO platform.outbox_probe (id, note, created_at) VALUES (…);
INSERT INTO platform.event_publication (…) VALUES (…);
COMMIT;          -- both rows saved. On ROLLBACK, neither.

Transactions give four promises, called ACID:

LetterPromiseIn simple words
AAtomicityAll or nothing. No half-saved enrollment.
CConsistencyConstraints hold after every commit.
IIsolationTransactions running at the same time do not see each other's unfinished work.
DDurabilityAfter COMMIT, the data survives a crash.

The whole outbox idea (spec D1) rests on A: the business row and the event row are one transaction, so an event can never exist without its data.

Isolation levels, simply

"Isolation" has levels. Stronger levels protect against more surprises, but more transactions must wait or be retried.

LevelWhat you seeUse
Read committed (Postgres default)Each statement sees data committed before that statement started. Two reads in one transaction can differ.Almost everything
Repeatable readThe whole transaction sees one snapshot, taken at its first statement.Reports that must add up
SerializableAs if transactions ran one after another. Postgres may abort one with a "serialization failure"; you must retry it.Rare, complex rules

The trap with the default level: "read, check in Java, then write" is not safe when two requests run at the same time. Both read "1 seat left", both write. The next section shows how to avoid that.

4. Locks and optimistic locking

Imagine 500 students clicking "Register" for the last seat at 08:00:00. Two ways to stay correct:

Pessimistic: lock first

SELECT enrolled, capacity
FROM registration.section_seats
WHERE section_id = ?
FOR UPDATE;          -- others wait here
-- check in Java, then UPDATE, COMMIT

Simple and safe, but every other request waits in line on that row.

Optimistic: check on write

UPDATE registration.section_seats
SET enrolled = enrolled + 1,
    version  = version + 1
WHERE section_id = ?
  AND version = ?          -- the one I read
  AND enrolled < capacity;

No waiting. If the answer is "0 rows updated", someone changed the row first: read again and retry, or answer 409 CONFLICT.

A version column is a counter that goes up on every change. It is like a document's revision number: "save only if nobody saved since I opened it". The capability map (C5) plans exactly this for the registration module: its own section_seats table with capacity, enrolled and version, fed by SectionChanged events. The real seat rush also uses Redis in front of the database (lesson 20).

5. Schemas, users and GRANT

Postgres has roles (users). A role can own schemas, and can be given rights with GRANT or lose them with REVOKE. On the first start, our init script creates one role per app and decides who owns which schema:

REVOKE ALL ON DATABASE "$POSTGRES_DB" FROM PUBLIC;   -- PUBLIC = every user
REVOKE ALL ON SCHEMA public FROM PUBLIC;

CREATE ROLE core_app         LOGIN PASSWORD '$CORE_APP_DB_PASSWORD';
CREATE ROLE registration_svc LOGIN PASSWORD '$REGISTRATION_SVC_DB_PASSWORD';
CREATE ROLE notification_svc LOGIN PASSWORD '$NOTIFICATION_SVC_DB_PASSWORD';
GRANT CONNECT ON DATABASE "$POSTGRES_DB" TO core_app, registration_svc, notification_svc;

CREATE SCHEMA course       AUTHORIZATION core_app;          -- … and the other core-app schemas
CREATE SCHEMA platform     AUTHORIZATION core_app;
CREATE SCHEMA registration AUTHORIZATION registration_svc;  -- only this user
CREATE SCHEMA notification AUTHORIZATION notification_svc;

ALTER ROLE registration_svc SET search_path = registration;
  • Owner (AUTHORIZATION): may do everything in the schema. We grant nothing to anyone else, so nobody else can even look inside.
  • search_path: where Postgres looks for a table name without a schema. For registration_svc, SELECT * FROM section_seats means registration.section_seats.
  • The script is a .sh file, not .sql, so the passwords come from infra/.env instead of being typed twice.
Smart Campus rule (spec D3: isolation enforced twice) registration-service and notification-service connect as users that can touch only their own schema: a wrong query fails at runtime with "permission denied for schema". Inside core-app (one user for many modules), Spring Modulith verify() and ArchUnit rules stop one module from using another module's tables. Task T10 proves the first part with SchemaIsolationIT (planned).

6. No foreign keys across schemas

The original plan had foreign keys like grades.enrollment_id → enrollments.id. That crosses from grade to registration, which are even in different apps. The capability map (C4) and the spec forbid it: foreign keys only within a schema.

Instead, a reference to another module's row is a bare UUID: just the id, with no database link. If a module needs more than the id, it keeps a local projection: its own small copy of the facts it needs, updated from Kafka events.

courseowns course.sections. Publishes SectionChanged (capacity, schedule)
→
Kafkacourse.events, key = sectionId
→
registrationkeeps its own section_seats (section_id as a bare UUID + capacity) and updates it

Why this is worth the extra work:

  • Modules stay independent. course can change its tables without breaking registration's queries. Only the event is the contract.
  • A service can move. registration already runs in its own app. A foreign key cannot point into another app's database anyway.
  • Read models can be rebuilt. A projection can be thrown away and replayed from Kafka (spec D5, lesson 08).

The price: the data is eventually consistent. For a short time after a change, the copy is a little behind. Each module spec decides where that is acceptable.

7. Flyway migrations

The database structure changes as the project grows. Flyway applies those changes as migrations: numbered SQL files, run once each, in order, at app startup. Like the minutes of a meeting: you never rewrite old minutes, you add new ones.

Naming and folders

src/main/resources/db/migration/<schema>/V<yyyyMMddHHmm>__<what>.sql

backend/core-app/src/main/resources/db/migration/
├── platform/
│   ├── V202611220000__baseline.sql
│   └── V202611220100__event_publication.sql
└── platform-probe/                          dev and test profiles only (T7 spike)
    └── V202611220200__outbox_probe.sql
  • V = versioned migration. Then the version, then two underscores, then a description (underscores become spaces).
  • The version is a date and time (yyyyMMddHHmm), so two developers on two branches do not pick the same number.
  • One folder per schema. A module's migrations only create or change objects in its own schema.

The history table

Flyway records each migration it ran in a schema history table, with a checksum (a fingerprint of the file). core-app's is platform.flyway_schema_history:

spring:
  flyway:
    schemas: platform
    default-schema: platform              # history table goes here
    locations: classpath:db/migration/platform

At startup Flyway compares files and history: new files run, old files must still match their checksum. Each app has its own Flyway and history: later, registration-service gets registration.flyway_schema_history (T10). How core-app will handle many module schemas is decided when the first feature module arrives.

Never edit a migration that has run If you change an applied file, its checksum changes, and Flyway refuses to start ("validate failed"). On a shared or production database you would also lose track of what really ran. To change something, write a new migration (ALTER TABLE …). On your own laptop only, you may wipe the database with docker compose … down -v.

One more T7 lesson: Spring Modulith can create its own tables, but we switched that off (spring.modulith.events.jdbc.schema-initialization.enabled: false). Flyway owns every table, so the history tells the full story.

8. JdbcTemplate (and JPA)

core-app talks to Postgres with Spring's JdbcTemplate: you write the SQL, Spring handles connections, parameters and errors. A pool (HikariCP, from spring-boot-starter-jdbc) keeps a few connections open and lends them out.

jdbc.update(
        "INSERT INTO platform.outbox_probe (id, note, created_at) VALUES (?, ?, ?)",
        probe.id(), probe.note(), Timestamp.from(probe.createdAt()));

List<OutboxProbe> probes = jdbc.query("""
        SELECT id, note, created_at
        FROM platform.outbox_probe
        ORDER BY created_at
        """,
        (rs, rowNum) -> new OutboxProbe(
                rs.getObject("id", UUID.class),
                rs.getString("note"),
                rs.getTimestamp("created_at").toInstant()));

The ? marks are parameters. The driver sends the values separately from the SQL text, so a value can never change the query. This blocks SQL injection. Never build SQL with + or formatted from user input.

JdbcTemplate (used now)

You see every query. Easy to reason about locks and transactions. Maps rows to records. More typing for big object graphs. Spring also offers JdbcClient, a newer fluent API on the same idea.

JPA / Hibernate (not used now)

Maps classes ("entities") to tables and writes SQL for you. Less typing, but hidden queries, lazy loading surprises, and entities are mutable classes, not records. A module spec may choose it later; the spec's rules (D3) already cover "JPA/JDBC access".

10. Common mistakes

  • Editing an applied migration. Write a new one.
  • A foreign key into another schema. Use a bare UUID and, if needed, a local projection.
  • Reading another module's tables "just for a test". The spec lists this under "Never".
  • "Read, check, write" without a lock or version. Two requests at the same moment both pass the check.
  • Gluing values into SQL text. Always use ? parameters.
  • timestamp without time zone for real moments. Use timestamptz.
  • Forgetting an index on a column you filter on, or adding indexes nobody uses.
  • Changing infra/.env passwords and expecting Postgres to notice. The init script only runs on an empty volume: down -v and start again.

11. Practice

  1. Start Postgres and open psql (the Postgres command-line client) inside the container. User and database come from your infra/.env:

    docker compose -f infra/docker-compose.yml up -d --wait postgres
docker compose -f infra/docker-compose.yml exec postgres psql -U postgres -d campus

  2. Explore with these psql commands:

    CommandShows
    \dn+Schemas, owners, rights
    \duRoles (users)
    \dt platform.*Tables in platform
    \d platform.event_publicationColumns, types, indexes of one table
    SELECT version, description, success FROM platform.flyway_schema_history;Which migrations ran (after core-app started once)
    \xSwitch to one-field-per-line output
    \qQuit

  3. See spec D3 with your own eyes. As the admin user you may become another role:

    SET ROLE registration_svc;
SELECT * FROM platform.event_publication;   -- permission denied for schema platform
CREATE TABLE registration.demo (id uuid PRIMARY KEY);   -- works
DROP TABLE registration.demo;
RESET ROLE;

  4. Try optimistic locking by hand. Create a scratch table in registration with capacity, enrolled, version. Open two psql windows. Read the version in both, then run the UPDATE … WHERE version = ? from section 4 in both. How many rows does the second one update? Drop the table afterwards.

  5. On paper: the grade module needs the student's name next to each grade. Where does it get it, without a foreign key into identity? Which event would keep it up to date?

13. Test yourself

1. Why do registration-service and notification-service have their own database users?

So a mistake fails loudly. Each user owns only its schema, so a query into another module's schema fails at runtime with "permission denied" instead of quietly coupling the services (spec D3).

2. Why can grade not have a foreign key to registration.enrollments?

It would tie two modules (even two apps) together at the database level: neither could change or move its tables freely, and read models could not be rebuilt. The reference is a bare UUID, and needed facts come from events into a local projection (C4).

3. Two requests both read "1 seat left" and both write. Which tool stops the double booking, and how?

A lock (SELECT … FOR UPDATE, the second waits) or optimistic locking: the UPDATE … WHERE version = ? of the second request matches 0 rows because the version changed, so it must retry or answer 409.

4. Why does Flyway refuse to start after you edit an old migration?

The file's checksum no longer matches the one stored in the history table. Flyway cannot know if the database has the old or the new structure, so it stops instead of guessing.

5. Why are migration versions dates like 202611220100?

Two developers on different branches could both pick "V3". A date and time is almost always unique and also shows the order in which changes were written.

6. Why is the outbox safe only because of transactions?

Atomicity: the business row and the event row are written in one transaction, so either both exist or neither. An event can never describe a change that was rolled back, and a saved change always has its event.
