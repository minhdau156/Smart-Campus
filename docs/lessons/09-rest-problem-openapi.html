REST APIs, problem JSON and OpenAPI

Every Smart Campus module talks to the website through HTTP and JSON. This lesson covers the rules that make all those APIs look the same: methods, status codes, URLs, validation, one error format, and API docs that are generated from the code.

1. Why you need this in Smart Campus

The website will call endpoints from 14 modules, written over many months. If course answers errors as {"error":"…"} and grade as {"message":"…"}, the frontend needs special code for each module. So the platform module fixes the shape once:

  • the same URL pattern and JSON style everywhere (Arch §7);
  • the same error body everywhere, with a stable code and a traceId (spec E1, T8);
  • API docs generated from the code, one group per module, exported to docs/api/ so the frontend can generate TypeScript types (spec A1, T9).

2. HTTP methods and status codes

REST is a style for HTTP APIs: you work with resources (things with a URL, like a course or an enrollment) using the standard HTTP methods.

MethodMeaningSafe?Idempotent?
GETRead a resource or a listYesYes
POSTCreate something, or start an actionNoNo
PUTReplace a resource with this full versionNoYes
PATCHChange some fieldsNoNot by rule
DELETERemove a resourceNoYes
  • Safe = it changes nothing on the server. Browsers, caches and crawlers may call it freely.
  • Idempotent = calling it twice has the same effect as once. "Set my phone number to X" twice is fine. "Create an enrollment" twice may create two.
Why this matters for registration and payments Networks fail. A student's browser may send the same POST again after a timeout. POST is not idempotent, so Arch §7 says: an Idempotency-Key header is required on POSTs that create enrollments, tickets or payments. The server remembers the key and answers a repeat with the first result instead of acting twice (planned in registration, club, payment; lesson 26).

Status codes you will use

CodeMeaningExample in Smart Campus
200 OKHere is the answerGET /api/v1/platform/ping
201 CreatedI made a new resource (often with a Location header)The dev-only outbox probe
202 AcceptedI got your request; the work will finish laterRegistration requests (planned)
204 No ContentDone, nothing to returnA delete
400 Bad RequestYour input is wrongVALIDATION_FAILED
401 / 403Who are you? / You may not do thisIdentity module (lesson 17)
404 Not FoundNo such resource or URLNOT_FOUND
409 ConflictThe request clashes with the current stateSECTION_FULL (planned)
429 Too Many RequestsSlow downRATE_LIMITED at the gateway (lesson 11)
500A bug or crash on our sideINTERNAL_ERROR
503 / 504A backend is down / too slow (from the gateway)Gateway errors (T13)

Rule of thumb: 4xx = the caller must change something; 5xx = we must fix something.

3. Our API conventions (Arch §7)

ConcernRuleExample
URL/api/v1/{module}/{resource}, plural nouns, no verbs/api/v1/registration/enrollments
One itemResource id in the path/api/v1/course/sections/{sectionId}
JSON field namescamelCase"sectionId", not "section_id"
TimeUTC, ISO-8601 text"2026-11-17T08:00:01Z"
Pagination?page=0&size=20&sort=createdAt,desc; the answer carries content, page, totalElementsLists of listings, notifications…
ErrorsProblem JSON with code (section 6)SECTION_FULL
DocsOpenAPI 3 from springdoc, one group per module/v3/api-docs/platform

The v1 is the API version. If we ever must break clients, a v2 path can live next to v1 for a while. The {module} part matches the module id, so the gateway can route by prefix (/api/v1/registration/** goes to registration-service).

The ping endpoint already follows the rules. Note the record, the injected Clock, and the Instant that Jackson writes as ISO-8601 UTC:

@RestController
@RequestMapping("/api/v1/platform")
class PingController {

    record Ping(String app, String version, Instant time) {}

    @GetMapping("/ping")
    Ping ping() {
        return new Ping(app, version, clock.instant());   // {"app":"core-app","version":"…","time":"2026-…Z"}
    }
}

The exact Java record for a page answer is not built yet. It will come with the first list endpoint (planned), following the field names above.

4. Checking input: Bean Validation

Jakarta Bean Validation lets you write the rules on the record itself, as annotations. Spring checks them when you mark the parameter with @Valid. (Needs spring-boot-starter-validation; platform-starter already brings it.)

package edu.campus.course;

public record NewCourse(
        @NotBlank @Size(max = 20) String code,     // "CS101"
        @NotBlank String name,
        @Min(1) @Max(30) int credits) {}

@PostMapping("/api/v1/course/courses")
@ResponseStatus(HttpStatus.CREATED)
CourseView create(@Valid @RequestBody NewCourse body) { … }

If name is blank and credits is 99, the controller method never runs. Spring throws, and our handler answers:

HTTP/1.1 400
Content-Type: application/problem+json

{
  "type": "https://campus.edu/problems/validation-failed",
  "title": "Validation failed",
  "status": 400,
  "detail": "The request has 2 invalid field(s)",
  "code": "VALIDATION_FAILED",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "errors": [
    {"field": "name",    "message": "must not be blank"},
    {"field": "credits", "message": "must be less than or equal to 30"}
  ]
}
Validation is for shape, not for business rules "Name is not blank" is shape: an annotation. "The section still has a seat" needs the database: that is business logic in the service, which throws a CampusProblem with a 409 code.

5. Slow work: 202 Accepted and polling

Some work cannot finish inside one HTTP request. In the registration rush, the server checks the seat in Redis in milliseconds, puts the request on Kafka, and a worker writes the enrollment later (Arch §5). The API says so honestly:

1. POST…/registration/requests
with Idempotency-Key
→
2. 202 Acceptedbody: request id, status PENDING
Location: …/requests/{id}
→
3. GET…/requests/{id}
every second or two
→
4. Final statusCONFIRMED or a problem such as SECTION_FULL

This is polling: the client asks again until the answer is final. Map C8 decided that registration ships with polling first; a WebSocket push is added later when notification exists (lesson 24). Names above are the planned shape; the registration spec will fix them. The frontend must show a "pending" state (ADR-7's accepted trade-off).

6. One error format: problem details

RFC 9457 "Problem Details for HTTP APIs" is a standard JSON shape for errors, sent with the media type application/problem+json. It replaced the older RFC 7807, which our spec and Arch mention: same fields, small clarifications. The standard fields:

FieldMeaningOur use
typeA URI that names the kind of problemhttps://campus.edu/problems/not-found
titleShort summary, the same every time for this type"Not found"
statusThe HTTP status, repeated in the body404
detailWhat went wrong this time, for humans"Course CS101 does not exist"
instanceOptional URI of this one occurrenceNot used

The RFC allows extension members (extra fields). We add two, on every error:

  • code: a stable machine code like SECTION_FULL. The frontend switches on this, never on detail text, which may change or be translated.
  • traceId: 32 hex characters. A student can quote it, and support finds the exact log lines. Also sent as the X-Trace-Id header (T8; T16 replaces it with the real OpenTelemetry trace id).
Never leak internals A 500 answer says only "An unexpected error occurred. Quote traceId … when you report it." The stack trace goes to the log, never to the client. ProblemJsonIT checks this with an endpoint that throws "db password is hunter2" and asserts the text does not appear.

7. How our errors are made

Three pieces, in two libraries:

public enum ProblemCode {
    INTERNAL_ERROR(500, "Internal error"),
    VALIDATION_FAILED(400, "Validation failed"),
    NOT_FOUND(404, "Not found"),
    CONFLICT(409, "Conflict"),
    RATE_LIMITED(429, "Rate limited");
    // type() = https://campus.edu/problems/ + name in kebab-case
}

Feature modules will add their own codes (for example SECTION_FULL, SCHEDULE_CONFLICT from Arch §7) when they need them. To fail a request, a service throws:

throw new CampusProblem(ProblemCode.NOT_FOUND, "Course %s does not exist".formatted(code));

CampusProblem is a plain RuntimeException in shared-kernel, with no Spring in it. The web part lives in platform-starter:

Controller / servicethrows CampusProblem, or @Valid fails, or a bug
→
CampusProblemHandler@RestControllerAdvice, extends ResponseEntityExceptionHandler
→
ProblemBody recordwritten as application/problem+json
What happenedAnswer
CampusProblemStatus, title and type from its ProblemCode; its detail
@Valid failed400 VALIDATION_FAILED + errors[]
No endpoint for the URL404 NOT_FOUND
Other Spring MVC errors (405, 415, bad JSON)Spring's status, code from it (e.g. METHOD_NOT_ALLOWED)
Anything else500 INTERNAL_ERROR, generic detail, full error logged with the traceId

An app gets all of this just by depending on platform-starter: the handler is registered by auto-configuration (lesson 03). It is also listed for @WebMvcTest, so controller slice tests see the same error JSON (PingControllerTest.wrongMethodGivesProblemJson).

8. OpenAPI docs with springdoc

OpenAPI is a standard JSON (or YAML) description of an HTTP API: every path, method, parameter, request body, response and schema. springdoc builds it at startup by reading your controllers, records and annotations. No hand-written docs that go stale.

URL on core-app (:8081)What you get
/v3/api-docs/platformThe OpenAPI JSON of the platform group
/v3/api-docs/swagger-configThe list of groups that Swagger UI shows
/swagger-ui.htmlA web page to read and try the endpoints, with a group selector

What platform-starter adds (T9)

  • A shared Problem schema (and FieldError), plus a default response on every operation pointing to it. "default" in OpenAPI means "any status not listed". So the frontend gets one Problem type for all errors (ProblemSchemaCustomizer, a GlobalOpenApiCustomizer that runs for every group).
  • A relative server URL /, so the random test port or the gateway host never ends up in the file.
  • JSON as the default answer type, not */*.

One group per module (core-app)

ModuleApiGroups asks Spring Modulith for the module list and makes one group per module (lesson 06). New modules get a group with no code change. Dev-only endpoints are hidden with @Hidden (OutboxProbeController).

The export to docs/api/

OpenApiExportIT starts the app, downloads each group, sorts the keys, pretty-prints it with \n line ends, and then:

.\mvnw.cmd verify -Pexport-openapi

Writes docs/api/core-app-<group>.json. You commit the diff. Runs only this one IT, so it is quick.

Normal .\mvnw.cmd verify

Compares and fails with "out of date. Run ./mvnw verify -Pexport-openapi" if you changed an endpoint and forgot to export.

Why sorted and pretty? So the same API gives the same bytes every time ("deterministic"). Then a git diff shows only real API changes, and two runs in a row give no diff.

Looking ahead: generated TypeScript types

In T19 (planned), npm run gen:api runs openapi-typescript on docs/api/*.json and writes types into frontend/web/src/shared/api/generated/. If a backend record changes, the frontend stops compiling until it is updated. CI also checks that the generated files are up to date. See lesson 14.

Java record + @RestController ──► springdoc ──► /v3/api-docs/<group>
        ──► OpenApiExportIT ──► docs/api/core-app-<group>.json  (committed)
        ──► openapi-typescript (T19) ──► TypeScript types the website compiles against

10. Common mistakes

  • Verbs in URLs (/api/v1/course/createCourse). Use POST /api/v1/course/courses.
  • Returning 200 with {"success": false}. Use a real status code and a problem body.
  • Building your own error JSON in a controller. Throw a CampusProblem; the handler makes the body.
  • Frontend code that checks detail text. Switch on code.
  • Local times without a zone (LocalDateTime in an API). Send Instant, which becomes UTC ISO-8601.
  • Changing an endpoint and not exporting. The build fails; run -Pexport-openapi and commit docs/api/.
  • Making a long job synchronous. If the work happens behind Kafka, answer 202 and give a status URL.

13. Test yourself

1. Why do enrollment and payment POSTs need an Idempotency-Key, but a PUT does not?

PUT is idempotent by definition: sending the same full version twice gives the same state. POST creates something each time, so a retried POST could enroll a student twice or charge twice. The key lets the server recognise the repeat.

2. Why should the frontend switch on code and not on detail?

detail is human text that changes per case and may be reworded or translated. code is a stable contract that the backend promises not to change.

3. Why does a 500 answer contain a traceId but no error message from the exception?

Exception messages can leak secrets or internals (SQL, passwords, class names). The trace id is enough for support to find the full error in the logs.

4. Registration answers 202 instead of 201. Why?

The enrollment is not created yet when the HTTP answer is sent; a worker writes it later from Kafka. 201 would be a lie. 202 plus a status URL tells the client to wait and check.

5. Why is the exported OpenAPI file sorted and pretty-printed, with a relative server URL?

So the same API always gives byte-identical files. Then git diffs show only real API changes, and the build can compare the committed file with the running app.

6. Why put the Problem schema in the OpenAPI doc at all?

The frontend generates its types from the doc. With the schema there, it gets one typed Problem for every error instead of guessing the shape.
