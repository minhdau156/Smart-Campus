2. Git basics and line endings

Git records snapshots of your project. Each snapshot is a commit: the full state of every file, plus a message, an author and a pointer to the commit before it. Think of a save point in a video game that you can always go back to.

  working folder        staging area ("index")        repository (.git)
  your edited files ──► git add ──► chosen changes ──► git commit ──► a new snapshot
         ▲                                                          │
         └──────────────── git restore / git switch ◄───────────────┘
git status                         # what changed? what is staged?
git diff                           # exact line changes not yet staged
git add backend/core-app/src/…     # stage chosen files (avoid "git add ." without looking)
git commit -m "feat(platform): …"  # save the snapshot
git log --oneline                  # short history
git push                           # send your commits to GitHub (origin)
git pull                           # get other people's commits

The staging area lets you commit only part of your changes. That keeps each commit about one thing, which makes history readable and undo safe.

Line endings on Windows

A text file ends each line with invisible characters. Windows traditionally uses CRLF (\r\n), Linux and macOS use LF (\n). If a shell script like mvnw gets CRLF, Linux (and Git Bash, and the CI runner) reads the command as sh\r and fails with a strange "not found" error. This machine has core.autocrlf=true, which would convert files to CRLF on checkout. The repo overrides it:

# Keep LF in the repo and in the working copy, so `mvnw` runs in Git Bash
# even when git's core.autocrlf is true on Windows. Windows scripts keep CRLF.
* text=auto eol=lf
*.bat text eol=crlf
*.cmd text eol=crlf

*.jar binary
*.pdf binary
*.png binary
  • * text=auto eol=lf: every text file is LF, in Git and on disk.
  • *.cmd / *.bat get CRLF in your working folder, because cmd.exe expects it (mvnw.cmd). Inside the repository Git still stores them with LF and converts on checkout.
  • binary: never convert or diff these; a converted jar or PDF would be broken.

.editorconfig says the same to your editor (end_of_line = lf), so new files start correct. .gitattributes is stronger than anyone's personal Git settings, which is why it lives in the repo.

3. Branches, merge, rebase, pull requests

A branch is a movable name that points at a commit. You work on a branch so that main stays stable. This repo does all platform work on the feature branch feat/platform, which is pushed to GitHub (origin). main still holds only the first commits.

main            A───B
                     \
feat/platform         C───D───E───F … (T1 … T9 so far)
                                     ▲ HEAD (you are here)

Merge or rebase?

When main moves on while you work, you have two ways to bring the two lines together:

Merge

main     A───B───G───────M
              \         /
feature        C───D───E

Adds one merge commit M with two parents. History is kept exactly as it happened. Safe on shared branches.

Rebase

main     A───B───G
                  \
feature            C'──D'──E'

Replays your commits on top of the new main. A straight line, but C', D', E' are new commits with new ids.

The golden rule of rebase Only rebase commits that nobody else has. Rebasing a branch that is already pushed and used by others (like feat/platform) rewrites shared history and needs a force-push. If you must, use git push --force-with-lease, which refuses to overwrite commits you have not seen.

Pull requests (PRs)

A pull request is a GitHub page that says "please merge branch X into main". It shows the diff, lets people comment line by line, and, most important for us, runs CI on the change. A red CI means "do not merge". When you merge a PR, GitHub offers three styles: a merge commit, squash (all commits become one), or rebase. For feat/platform, where every commit is already a clean task step, keeping the commits (merge or rebase) preserves the task-by-task history.

5. GitHub Actions in one picture

CI ("continuous integration") means: every push is built and tested automatically on a clean machine. "Works on my machine" is no longer enough; it must work on the CI machine. GitHub Actions is GitHub's built-in CI.

workflow  (.github/workflows/ci.yml)        ← one YAML file
 ├─ on: push, pull_request                  ← the events that start it
 ├─ job: backend    runs-on: ubuntu-24.04   ← each job = a fresh virtual machine ("runner")
 │    ├─ step: checkout the code              (jobs run in parallel by default)
 │    ├─ step: set up JDK 21
 │    └─ step: run ./mvnw verify            ← a step runs a command (run:) or an action (uses:)
 ├─ job: frontend   runs-on: ubuntu-24.04
 └─ job: security   runs-on: ubuntu-24.04
WordMeaning
WorkflowOne automated process, defined in a YAML file under .github/workflows/.
JobA group of steps that run on one runner. Jobs share nothing unless you pass artifacts.
StepOne command (run:) or one reusable action (uses:).
ActionA reusable step published by someone, like actions/checkout.
RunnerThe machine that runs a job. GitHub-hosted Ubuntu runners have Docker installed, so Testcontainers ITs work there.
CacheFiles kept between runs (Maven ~/.m2, npm cache) so downloads are not repeated.
ArtifactFiles a job uploads (test reports, coverage) so you can download them from the run page.
SecretAn encrypted value (like NVD_API_KEY) set in the repo settings, hidden in logs.

6. The Smart Campus CI workflow (T20)

Status .github/ does not exist yet. The workflow is planned in T20. The YAML below is a sketch of what the task describes; vX.Y.Z stands for the exact version T20 will pin. 
name: ci
on:
  push:
  pull_request:

concurrency:                               # T20.1: a new push cancels the older run
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read                           # least privilege for the token

jobs:
  backend:
    runs-on: ubuntu-24.04                  # a fixed image, not "latest"
    steps:
      - uses: actions/checkout@vX.Y.Z      # T20.1: every action pinned to an exact version
      - uses: actions/setup-java@vX.Y.Z
        with:
          distribution: temurin
          java-version: "21"
          cache: maven                     # caches ~/.m2/repository, keyed on pom.xml files
      - run: ./mvnw verify                 # unit + Modulith verify + Testcontainers ITs + spotless:check
      - run: ./mvnw verify -Pexport-openapi
      - run: git diff --exit-code docs/api # committed OpenAPI JSON must be up to date
      - if: always()                       # upload reports even when tests failed
        uses: actions/upload-artifact@vX.Y.Z
        with:
          name: backend-reports
          path: |
            backend/*/target/surefire-reports
            backend/*/target/failsafe-reports
            backend/*/target/site/jacoco

Notes on the choices:

  • Why Ubuntu? Testcontainers needs a Docker daemon that runs Linux containers. GitHub's Ubuntu runners have one ready. (Your own Windows machine uses Docker Desktop for the same thing.)
  • Why pin actions? @v5 is a tag the action's owner can move to new code at any time. An exact version (or, even safer, a full commit SHA) means CI runs the same code every time, the same "no floating versions" rule as the rest of the spec.
  • Why ./mvnw? The Maven Wrapper downloads the exact Maven version from .mvn/wrapper/. CI does not depend on whatever Maven the runner has.
  frontend:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@vX.Y.Z
      - uses: actions/setup-node@vX.Y.Z
        with:
          node-version: "24"
          cache: npm
          cache-dependency-path: frontend/web/package-lock.json
      - run: npm --prefix frontend/web ci
      - run: npm --prefix frontend/web run gen:api
      - run: git diff --exit-code          # generated types must be committed and current
      - run: npm --prefix frontend/web run lint
      - run: npm --prefix frontend/web run test
      - run: npm --prefix frontend/web run build

Before pushing, T20.6 checks the YAML locally with actionlint, run through its Docker image, so typos in ${{ }} expressions or unknown keys are found before GitHub sees them.

7. Security scans: Trivy and Dependency-Check

Most of the code we ship is not ours: Spring, Kafka clients, the JRE in the image, npm packages. A CVE ("Common Vulnerabilities and Exposures") is a public, numbered report of a security hole in one of them, with a CVSS score from 0 to 10. CVSS 7.0–8.9 is HIGH, 9.0–10.0 is CRITICAL. The Architecture requires dependency and image scanning in CI; T20.4 adds a security job with two tools.

ToolWhat it scansIn Smart Campus
Trivy filesystem scanLock files and build files in the repo (Maven, npm), and secrets committed by mistaketrivy fs on the checkout
Trivy image scanEverything inside a Docker image: OS packages of the base image, the JRE, the jarsThe 4 app images built from infra/docker/spring-app.Dockerfile
OWASP Dependency-CheckJava (and other) dependencies against the US National Vulnerability Database (NVD)The Maven dependencies of all modules
./mvnw package -DskipTests                       # boot jars in backend/*/target/
docker build -f infra/docker/spring-app.Dockerfile --build-arg … -t campus/core-app:ci .
#   … the same for gateway, registration-service, notification-service

trivy fs    --severity HIGH,CRITICAL --exit-code 1 --ignorefile .trivyignore .
trivy image --severity HIGH,CRITICAL --exit-code 1 --ignorefile .trivyignore campus/core-app:ci

# Dependency-Check, e.g. as a Maven plugin (T20 chooses plugin or CLI; check the docs for exact flags)
./mvnw org.owasp:dependency-check-maven:check \
    -DfailBuildOnCVSS=7 \
    -DsuppressionFile=config/dependency-check-suppressions.xml \
    -DnvdApiKey="$NVD_API_KEY"

--exit-code 1 and failBuildOnCVSS=7 are what make a finding fail the job. Without them, the scan only prints a report that nobody reads.

The NVD API key (T20.5 🙋)

Dependency-Check downloads the whole NVD database. Without an API key, the NVD limits the download speed so much that the first run can take a very long time. The human must create a key and add it as a repository secret named NVD_API_KEY. The workflow reads it as ${{ secrets.NVD_API_KEY }}; it is never written in the repo. (Caching the downloaded database between runs also helps; see the tool's docs.)

Suppression files: "reviewed" means reviewed

Sometimes a finding does not apply to us: the vulnerable function is never called, or it is a false match. Then you suppress it, in a file that is reviewed in a PR like code. The spec puts "adding a Trivy/Dependency-Check suppression" on the Ask first list.

<suppressions xmlns="https://jeremylong.github.io/DependencyCheck/dependency-suppression.1.3.xsd">
  <suppress until="2027-03-01Z">
    <notes>CVE-2026-00000 is in the XML parser's DTD feature. We never parse
           untrusted XML. Reviewed in PR #12. Re-check before the date.</notes>
    <packageUrl regex="true">^pkg:maven/org\.example/xml-lib@.*$</packageUrl>
    <cve>CVE-2026-00000</cve>
  </suppress>
</suppressions>
# CVE-2026-00000: same reason as above, reviewed in PR #12, re-check by 2027-03-01
CVE-2026-00000
Never suppress to "get green" A good suppression names one CVE and one package, explains why it does not affect us, and has an end date. The right first answer to a finding is to upgrade the dependency or the base image.

8. ADRs and the README

An ADR ("Architecture Decision Record") is a short text file that records one important decision. The format by Michael Nygard has a few parts:

Title + StatusProposed, Accepted, Deprecated, or Superseded by ADR-N
ContextThe situation and the forces: what problem, what limits
DecisionWhat we will do, in full sentences ("We will …")
ConsequencesWhat becomes easier, what becomes harder, what we accept

Why write them? Six months from now, someone (maybe you) asks "why not just call kafkaTemplate.send?". The spec and the code show what we did; the ADR shows why and what else was considered. ADRs are never edited to change a decision; a new ADR supersedes the old one, so the history stays.

# ADR 0009: Outbox = Spring Modulith Event Publication Registry

Status: Accepted (2026-11-22, Checkpoint B)

## Context
Every module must save its data and publish an event without losing it or sending a
phantom one (Arch ADR-5). Writing to PostgreSQL and Kafka separately is a dual write.

## Decision
We use Spring Modulith's Event Publication Registry (JDBC) with Kafka externalization.
Events are stored in event_publication in the business transaction and sent after commit.

## Consequences
+ No hand-written outbox table or relay; the same setup in all three backend apps.
- Delivery is at least once: consumers must deduplicate by eventId (ADR 0010).
Rejected: hand-written outbox + @Scheduled relay; Debezium.

10. Common mistakes

  • One giant commit ("lots of changes"). Make small commits, each about one thing, with a Conventional Commits message.
  • Committing secrets (infra/.env, API keys). .gitignore already excludes infra/.env; Trivy's filesystem scan also looks for secrets. A secret that was pushed must be rotated (replaced), not just deleted, because history keeps it.
  • Rebasing or force-pushing a shared branch without --force-with-lease.
  • Floating versions in CI: ubuntu-latest, @main or @v4 on actions. A run can break overnight with no change from you.
  • Ignoring a red CI "because it works locally". CI is the clean machine; it is usually right.
  • Suppressing a finding without a reason and an end date, or without asking first.
  • Editing an accepted ADR to change the decision. Write a new ADR that supersedes it.
  • A README that only works on the author's laptop. Test it from a fresh clone (T21.6).

13. Test yourself

1. Why does the repo force LF line endings with .gitattributes instead of trusting each developer's Git settings?

Personal settings differ (this machine has core.autocrlf=true). A shell script like mvnw with CRLF fails in Git Bash and on the Linux CI runner. .gitattributes lives in the repo and wins over personal settings, so every clone gets the same files.

2. Why should you not rebase feat/platform after it has been pushed?

Rebase creates new commits with new ids. Anyone (or any clone) with the old commits now has a history that no longer matches, and you need a force-push that can throw away others' work. Rebase only private, unpushed commits.

3. Why pin every action to an exact version or commit SHA?

A tag like @v4 can be moved by the action's owner, so the same workflow could run different code tomorrow, break, or even run malicious code. An exact pin makes CI repeatable and is the same "no floating versions" rule the spec uses everywhere.

4. Why do the backend ITs run on an Ubuntu runner and not on Windows?

Testcontainers needs a Docker daemon that runs Linux containers (Postgres, Kafka, Redis). GitHub's Ubuntu runners have Docker ready to use, so ./mvnw verify with ITs works there with no extra setup.

5. Why must every suppression be in a reviewed file with a reason?

Without review, suppressions become an easy way to hide real holes just to get a green build. A file in Git, with one CVE, one package, a reason and an end date, shows who accepted the risk and why, and forces a re-check later.

6. The spec already explains D1. Why also write ADR 0009?

The spec describes the current plan and changes over time. An ADR is a permanent, dated record of one decision, its context, the rejected options and the accepted trade-offs. When the decision changes, a new ADR supersedes it, so you can always see why the system looks the way it does.
