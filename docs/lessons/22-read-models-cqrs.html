Lesson 22 · Part 2: Feature modules

Read models, CQRS and iCal

A student's weekly timetable needs data from two modules: which sections they are in (registration) and when and where those sections meet (course). We are not allowed to join across schemas. So timetable keeps its own copy, built from events. This lesson shows how to build that copy correctly, and how to export it to Google Calendar.

1. Why you need this in Smart Campus

The timetable stories:

  • TT-1 (Must): a student sees their weekly timetable built from their enrolled sections, "so I know where and when to go".
  • TT-3 (Must): a lecturer sees their teaching schedule and rooms.
  • TT-6 (Could): a student exports their timetable to Google Calendar (iCal).

The data lives in other modules. In one big database you would write a single SQL join over registration.enrollments, course.sections and course.section_meetings. We cannot:

  • C4 / ADR-6: no cross-schema foreign keys, and no module reads another module's tables. "No cross-module joins; read models needed" is the trade-off the Arch accepted.
  • registration runs in a different app, with a database user that can only see its own schema (spec D3).

The Arch's answer (§4): "The timetable and search modules hold no source data of their own: they are read models rebuilt from events, so they can be dropped and replayed at any time."

2. Commands vs queries (CQRS)

A command asks the system to change something: "register me for CS101-01", "move Monday's class to room B4-305". A query only asks: "what is my week?". CQRS (Command Query Responsibility Segregation) means using different models for the two:

Write side (commands)

course and registration. Rich aggregates that protect rules (lesson 19). Normalized tables. Optimized for correct changes.

Read side (queries)

timetable. Tables shaped exactly like the screen. No business rules, just copies. Optimized for fast, simple reads.

coursepublishes SectionChanged, ScheduleChanged → course.events (key sectionId)
registrationpublishes EnrollmentConfirmed, EnrollmentDropped → registration.events (key studentId)
→
timetable consumersupdate local tables, idempotently
→
GET /api/v1/timetable/…one query in one schema

An analogy: the write side is the official land registry; the read side is the city map printed from it. The map is easy to read, may be a little behind, and can always be printed again. Note: CQRS does not mean "event sourcing". Our write side still stores normal rows; events are only how the read side learns about changes.

3. Projections and table design

A projection is code that reads events and writes a read model. It is a Kafka consumer in timetable, with the usual idempotency (timetable.processed_events, spec D2, lesson 08). Even though course and timetable both run in core-app, the projection reads from Kafka, not from an in-process listener (spec D5, C16), so it can be replayed.

Proposed tables (all in schema timetable)

-- From SectionChanged (course.events)
CREATE TABLE timetable.sections (
    section_id        UUID PRIMARY KEY,
    course_code       TEXT NOT NULL,
    course_name       TEXT NOT NULL,
    lecturer_id       UUID,
    status            TEXT NOT NULL,
    section_version   BIGINT NOT NULL,      -- newest SectionChanged we applied
    schedule_version  BIGINT NOT NULL DEFAULT 0,
    updated_at        TIMESTAMPTZ NOT NULL
);

-- From ScheduleChanged (course.events): the list is replaced as a whole
CREATE TABLE timetable.section_meetings (
    id          UUID PRIMARY KEY,           -- the meeting id from course
    section_id  UUID NOT NULL,
    starts_at   TIMESTAMPTZ NOT NULL,
    ends_at     TIMESTAMPTZ NOT NULL,
    room_code   TEXT NOT NULL,
    status      TEXT NOT NULL               -- SCHEDULED / CANCELLED
);
CREATE INDEX ON timetable.section_meetings (section_id, starts_at);

-- From EnrollmentConfirmed / EnrollmentDropped (registration.events)
CREATE TABLE timetable.student_sections (
    student_id  UUID NOT NULL,
    section_id  UUID NOT NULL,
    status      TEXT NOT NULL,              -- ENROLLED / DROPPED
    updated_at  TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (student_id, section_id)
);

Notice: no foreign keys, not even inside the timetable schema. Events from two topics arrive in any order (next section). An enrollment may arrive before the section it points to. A foreign key would reject it, and the consumer would get stuck.

The query for TT-1

SELECT s.course_code, s.course_name, m.starts_at, m.ends_at, m.room_code, m.status
  FROM timetable.student_sections ss
  LEFT JOIN timetable.sections s          ON s.section_id = ss.section_id
  LEFT JOIN timetable.section_meetings m  ON m.section_id = ss.section_id
                                         AND m.starts_at >= :weekStart
                                         AND m.starts_at <  :weekEnd
 WHERE ss.student_id = :studentId
   AND ss.status = 'ENROLLED'
 ORDER BY m.starts_at;

Joins inside one module's schema are fine. The LEFT JOINs mean "show the enrollment even if we have not received the section details yet". The UI then shows "details are on their way" for that row.

How flat should a read model be?

Small tables + local join (proposed)

A room change updates one section's meetings, not every student's rows. Reads are a three-table join on indexed columns: still fast for a few dozen rows per student.

One fully flat row per student per meeting

Reads are a plain SELECT. But a room change for a section with 200 students must update 200 × 15 rows. Use this only if measurements show reads are the bottleneck.

The lecturer view (TT-3)

The same tables answer TT-3: SELECT … FROM timetable.sections s JOIN timetable.section_meetings m … WHERE s.lecturer_id = :lecturerId. The lecturer id comes from SectionChanged. A bonus: timetable can count student_sections rows to show "38 students" next to each class. That count is local data, so it does not break C17 (which only forbids course from storing enrolled counts).

4. Out-of-order and duplicate events

Kafka keeps order only per key, inside one topic (lesson 07). Here is what that means for our projection:

EventsOrder guaranteed?Why
Two SectionChanged for section XYesSame topic, same key (sectionId)
EnrollmentConfirmed then EnrollmentDropped for student LanYesSame topic, same key (studentId)
SectionChanged for X and EnrollmentConfirmed into XNoDifferent topics, different keys, different consumers
Any event delivered twiceIt happensAt-least-once delivery (lesson 08, spec O3)

Three tools keep the read model right:

  1. Dedupe by eventId (processed_events, D2): a repeat is skipped.
  2. Tolerate missing data: write what you know; LEFT JOIN the rest.
  3. Version checks: keep the newest state, ignore older state. Events from course carry the section's version (lesson 19).

PostgreSQL's upsert (INSERT … ON CONFLICT … DO UPDATE) does "insert or update" in one statement. Adding a WHERE makes it "update only if newer":

INSERT INTO timetable.sections AS t
       (section_id, course_code, course_name, lecturer_id, status, section_version, updated_at)
VALUES (:sectionId, :courseCode, :courseName, :lecturerId, :status, :version, :now)
ON CONFLICT (section_id) DO UPDATE
   SET course_code     = EXCLUDED.course_code,
       course_name     = EXCLUDED.course_name,
       lecturer_id     = EXCLUDED.lecturer_id,
       status          = EXCLUDED.status,
       section_version = EXCLUDED.section_version,
       updated_at      = EXCLUDED.updated_at
 WHERE t.section_version < EXCLUDED.section_version;   -- older or same version: no change

EXCLUDED means "the row I tried to insert". Apply this statement once, twice or ten times: the result is the same. That is idempotent by design, a second safety net next to processed_events.

@KafkaListener(topics = "course.events", groupId = "timetable")
@Transactional
void onCourseEvent(DomainEvent<?> event) {
    if (!processedEvents.tryInsert(event.eventId())) {
        return;                                          // seen before
    }
    switch (event.type()) {
        case "SectionChanged"  -> sections.upsert(payload(event, SectionChanged.class));
        case "ScheduleChanged" -> meetings.replaceIfNewer(payload(event, ScheduleChanged.class));
        default -> { }                                   // other course events: not needed here
    }
}

replaceIfNewer first runs UPDATE timetable.sections SET schedule_version = :v WHERE section_id = :id AND schedule_version < :v. Only if that changed one row does it delete the section's meetings and insert the new list, all in the same transaction.

Unknown event types course.events will carry more event types over time. A consumer should ignore types it does not need (and still mark them processed), not crash. A changed payload shape comes with a higher schemaVersion (spec D4).

5. Eventual consistency in the UI

Eventual consistency means: the read model will match the write side soon, but not at the exact same moment. Normally the delay is milliseconds to a few seconds. If the consumer is down, it can be minutes (the platform alert fires when consumer lag is over 30 seconds, Arch §8).

Good UI for this:

  • After "Registration confirmed" (lesson 20), show a short note: "Your timetable updates in a few seconds". Do not show an error if the new class is not there yet.
  • Let the timetable query refetch when the page gets focus, or a few seconds after a confirmed registration (TanStack Query, lesson 14).
  • Show "Last updated 08:01" from updated_at, so users know how fresh the data is.
  • For rows with missing section details (the LEFT JOIN case), show a placeholder, not an empty cell.
Never make decisions from a read model The read model is for showing. registration's clash check (REG-3) must use its own data, not ask timetable, which may be seconds behind.

6. Replay: throw it away and rebuild

Because course.events and registration.events keep all history (retention.ms=-1) and are marked replayable in Topics, the timetable read model can be deleted and rebuilt (spec D5, C16, built by platform T12):

  1. Stop the timetable consumers.
  2. Delete timetable.* rows and timetable.processed_events.
  3. Reset the consumer groups to the earliest offset.
  4. Start again; every event is applied from the beginning.

Replay is how you fix a projection bug: fix the code, replay, and the data is right again. It only works if your consumer is deterministic (same events → same rows) and does not do outside side effects. Sending "your class moved" emails belongs to notification, which is not replayable. Read the full procedure in lesson 08. The search module (lesson 29) is the same pattern with OpenSearch instead of PostgreSQL tables.

7. iCalendar export (TT-6)

iCalendar (RFC 5545) is the text format that Google Calendar, Outlook and Apple Calendar all understand. Files end in .ics; the media type is text/calendar.

BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//Smart Campus//Timetable//EN
CALSCALE:GREGORIAN
BEGIN:VTIMEZONE
TZID:Asia/Ho_Chi_Minh
BEGIN:STANDARD
DTSTART:19700101T000000
TZOFFSETFROM:+0700
TZOFFSETTO:+0700
TZNAME:ICT
END:STANDARD
END:VTIMEZONE
BEGIN:VEVENT
UID:section-3f1c9a2e-slot-1@campus.edu
DTSTAMP:20270102T010000Z
DTSTART;TZID=Asia/Ho_Chi_Minh:20270104T073000
DTEND;TZID=Asia/Ho_Chi_Minh:20270104T093000
RRULE:FREQ=WEEKLY;BYDAY=MO;UNTIL=20270425T165959Z
EXDATE;TZID=Asia/Ho_Chi_Minh:20270201T073000
SUMMARY:CS101 Introduction to Programming
LOCATION:B4-201
SEQUENCE:3
END:VEVENT
END:VCALENDAR
LineMeaning
VCALENDAR / VEVENTThe file, and one event inside it. VERSION:2.0 and PRODID are required.
VTIMEZONEDescribes the time zone named in TZID. Vietnam is UTC+7 all year (no daylight saving), so it is short.
DTSTART;TZID=Asia/Ho_Chi_Minh:20270104T073000Monday 4 January 2027, 07:30 Vietnam time.
RRULE:FREQ=WEEKLY;BYDAY=MO;UNTIL=…Repeat every Monday until the end of the semester. When DTSTART has a TZID, UNTIL must be written in UTC (the Z): 25 Apr 23:59:59 in Vietnam = 16:59:59Z.
EXDATESkip this date: the class on 1 Feb is cancelled (TT-4).
UIDThe event's permanent identity. It must be stable: the same section slot gets the same UID in every export, so calendar apps update the event instead of adding a copy.
SEQUENCEGoes up each time the event changes (we can use the schedule version).
DTSTAMPWhen this file was made, in UTC. Required in every VEVENT.

A moved single class can be written as its own VEVENT with the same UID and a RECURRENCE-ID, or (simpler) we can export one VEVENT per real meeting from timetable.section_meetings, each with its own stable UID (the meeting id). The spec picks one; the second is easier to get right.

Writing the file safely

  • Lines end with CRLF (\r\n), not just \n.
  • Lines longer than 75 octets must be folded: break, then start the next line with one space. Count bytes, not characters: Vietnamese letters use several bytes in UTF-8.
  • In text values, escape \, ;, , and new lines (\\, \;, \,, \n). A course name like "Data, Algorithms" would otherwise break the line.
  • A library such as ical4j handles all of this, but it is a new dependency, which the spec says to "ask first" about. A small, well-tested writer for our few fields is also fine.

The subscription URL

A one-time download goes stale. A subscription lets Google Calendar fetch the file again by itself. But calendar apps cannot log in with Keycloak or send a JWT. So the URL itself carries a secret:

GET /api/v1/timetable/ical/8Jx2…long-random-token….ics

HTTP/1.1 200 OK
Content-Type: text/calendar; charset=utf-8
Cache-Control: private, max-age=900
  • The token is long and random (for example 32 random bytes, Base64URL). It acts like a password, so store only its hash, as you would a password.
  • The student can regenerate it (the old URL stops working) if it leaks.
  • The gateway route for this path must accept requests without a JWT (an exception to plan with the identity spec), and the per-IP rate limit still applies.
  • Put only what the student needs in the file: course, time, room. No grades, no ids of other students.
  • You cannot control how often Google refreshes a subscribed calendar; it can take hours. Tell users that the app is always the most up-to-date view.

9. Common mistakes

  • Joining another module's schema "just for reading". It breaks C4 and fails at runtime for registration's data anyway (D3).
  • Foreign keys in a read model. Events arrive out of order; the consumer gets stuck on the first missing parent.
  • Applying deltas ("seats −1") instead of state. Repeats and replays make them wrong.
  • Overwriting newer data with older events. Always compare versions.
  • Crashing on an unknown event type. Skip it and move on.
  • Using a random UID per export. Every refresh then duplicates every class in the user's calendar.
  • Forgetting the time zone in DTSTART, or writing UNTIL in local time.
  • Sending emails from a projection. A replay would send them all again.

10. Practice

  1. In a scratch table, try the versioned upsert:

    CREATE TEMP TABLE s (id INT PRIMARY KEY, name TEXT, version INT);
INSERT INTO s AS t VALUES (1, 'v2', 2)
  ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name, version = EXCLUDED.version
  WHERE t.version < EXCLUDED.version;
-- now run it with ('v1', 1), then with ('v3', 3). Which ones change the row?
SELECT * FROM s;

  2. Write down the events (with topic and key) for this story, then shuffle them across topics and check your projection still ends right: Lan enrolls in CS101-01; the admin creates CS101-01's schedule; Lan drops; Lan enrolls again; Monday's class moves room.

  3. Write the .ics for a class every Thursday 13:00–15:00 in room A2-104, from 7 January to 22 April 2027. Import it into a calendar app and check the times.

  4. Write a Java method that escapes an iCal text value and a test for "Data, Algorithms; Part 1".

  5. On paper: what should the week view show for a section whose SectionChanged has not arrived yet?

12. Test yourself

1. Why can't timetable simply join registration.enrollments with course.sections?

No module reads another module's tables (C4, ADR-6), and registration runs in a separate app whose schema core-app is not meant to touch. Joins would also tie the modules together, so one could not change or move its tables alone.

2. Why does the read model have no foreign keys, even inside its own schema?

Events from different topics have no order between them. An enrollment can arrive before its section. A foreign key would reject that row and block the consumer, while the right behaviour is to store it and fill in the details later.

3. processed_events already removes duplicates. Why also add a version check?

Defense in depth. The version check also protects against old state arriving after newer state for other reasons (for example a bug, or a replay of a partly cleaned read model), and makes each write safe on its own.

4. Why must the projection have no side effects like emails?

Replay runs every event again from the start. Writing rows again gives the same rows; sending emails again spams every student. Side effects belong to non-replayable consumers such as notification.

5. Why must the iCal UID be stable?

Calendar apps use the UID to know "this is the same event". With a stable UID, a refreshed subscription updates the class. With a new UID each time, the app adds a second copy of every class.

6. Why is the subscription URL protected by a secret token instead of a JWT?

Google Calendar fetches the URL by itself and cannot log in to Keycloak or refresh a 5-minute token. A long random token in the URL works like a password that the student can revoke by regenerating it.
