QR tickets and signed tokens

A club event has 200 seats. 600 students click "Get ticket" in the first minute. At the door, a club member scans phones with a laptop camera. How do we sell exactly 200 tickets, stop fake and copied tickets, and let each ticket in only once?

2. A QR code is only text

A QR code is a square picture of black and white dots that stores a short piece of text. That is all. It has no security of its own: anyone can read it with any phone, and anyone can make a QR code with any text inside. A screenshot of a QR code works exactly like the original.

QR codes can still be read when part of them is dirty or covered, thanks to error correction: extra data that lets the reader rebuild missing parts. There are four levels:

LevelCan recover aboutEffect
L7% damageSmallest code
M15%A good default for screens
Q25%Bigger code
H30%Biggest; used for printed codes or codes with a logo on top

More text or a higher level means more, smaller dots, which are harder for a laptop camera to read in a dark hall. So: keep the text short. A ticket token of 100 to 150 characters scans easily on a phone screen.

3. Put a signed token in the code

What text should the QR hold? Three options:

Inside the QRCan someone forge one?Can the scanner check it without the server?
A counting ticket number: 1042Yes. Try 1043, 1044…No
A random secret: a UUID v4 (122 random bits)No, it is impossible to guessNo, it must look it up
A signed token: ticket id, event id, expiry + signatureNo, without the key nobody can signYes, it can check the signature and the event

A random secret is already safe against guessing. A signed token adds useful things: the scanner knows at once that the code is for this event and is not expired, and it can check the signature even without the network (section 7). The Plan's qr_code column can hold the token, or a hash of it.

HMAC token or JWS

A simple, short format is "payload, then signature", both Base64URL text:

package edu.campus.club.internal.ticket;

record TicketClaims(UUID ticketId, UUID eventId, Instant expiresAt) { }

final class TicketTokens {
    private static final Base64.Encoder B64 = Base64.getUrlEncoder().withoutPadding();
    private final byte[] secret;          // from env / secret store, never from Git
    private final Clock clock;

    TicketTokens(byte[] secret, Clock clock) {
        this.secret = secret.clone();
        this.clock = clock;
    }

    String issue(TicketClaims c) {
        String payload = B64.encodeToString("%s.%s.%d".formatted(
                c.ticketId(), c.eventId(), c.expiresAt().getEpochSecond()).getBytes(StandardCharsets.UTF_8));
        return "t1." + payload + "." + B64.encodeToString(hmac(payload));   // "t1" = format/key version
    }

    Optional<TicketClaims> verify(String token) {
        String[] parts = token.split("\\.");
        if (parts.length != 3 || !parts[0].equals("t1")) return Optional.empty();
        byte[] given;
        try { given = Base64.getUrlDecoder().decode(parts[2]); }
        catch (IllegalArgumentException e) { return Optional.empty(); }
        if (!MessageDigest.isEqual(hmac(parts[1]), given)) return Optional.empty();  // constant time
        TicketClaims c = parse(parts[1]);
        return c.expiresAt().isAfter(clock.instant()) ? Optional.of(c) : Optional.empty();
    }
    …
}

The standard alternative is a JWS (JSON Web Signature, the signed part of a JWT), made with a library such as Nimbus JOSE + JWT (Spring Security already uses it). JWS gives you a well-known format and a choice of algorithms, at the cost of a longer string.

HMAC (shared secret)

Short and fast. But the same key both signs and checks. If a scanner device holds the key, anyone who copies it from that device can make valid tickets. So with HMAC, only the server checks tokens.

Public-key signature (for example ES256 in a JWS)

The server signs with a private key; scanners check with the public key, which cannot sign. Safe to put on a door laptop for offline checks. Longer token.

The signature stops forgery (making a new ticket). It does not stop copying: a screenshot sent to a friend has a perfect signature. Copying is stopped by the one-time check-in (section 5).

4. Quotas without overselling (CLUB-3, CLUB-4)

200 seats, 600 clicks in the same second. The naive code reads, checks, then writes:

Event e = events.find(id);
if (e.ticketsSold() < e.ticketQuota()) {     // 600 threads all see 199 < 200 …
    e.sell();                                  // … and all sell. 799 tickets.
}

This is a race condition: the check and the write are two steps, and other requests run between them. The fix is to make the database do both in one atomic statement:

UPDATE club.events
SET tickets_sold = tickets_sold + 1
WHERE id = :eventId AND tickets_sold < ticket_quota;     -- 1 row: you got a seat. 0 rows: sold out

INSERT INTO club.tickets (id, event_id, user_id, qr_code, status, issued_at)
VALUES (:id, :eventId, :userId, :token, 'ISSUED', :now);  -- UNIQUE(event_id, user_id): one per student

PostgreSQL locks the event row during the UPDATE, so the 600 requests take turns on that one row, and the condition is checked again for each. Exactly 200 succeed. If the insert fails (the student already has a ticket), the whole transaction rolls back, including the +1. Also add CHECK (tickets_sold <= ticket_quota) as a last guard. For a few hundred seats this is enough; the registration rush (thousands per second) needed Redis (lesson 20).

Paid tickets: hold the seat

For a paid event, the student first goes to the payment gateway, which takes minutes. If we counted the seat only after PaymentConfirmed, 300 people could pay for 200 seats. So:

  1. Click "Buy": take the seat now with the atomic update, and save a reservation (status HELD, expires_at in 15 minutes). Then create the payment.
  2. PaymentConfirmed arrives from Kafka (deduped): turn the hold into an ISSUED ticket and make its QR token.
  3. Payment FAILED or EXPIRED, or the hold times out: give the seat back (tickets_sold - 1, with a condition so it happens once).

Cancelling (CLUB-7) also gives the seat back. The exact states are a decision for SPEC-club.md.

5. One-time check-in (CLUB-5)

At the door, the scanner sends the token to the server. The server checks the signature, the event, and then marks the ticket used with one conditional update:

@Transactional
CheckInResult checkIn(UUID eventId, String token, UUID staffId) {
    TicketClaims claims = tokens.verify(token).orElse(null);
    if (claims == null) return CheckInResult.invalid();              // forged, broken or expired
    if (!claims.eventId().equals(eventId)) return CheckInResult.wrongEvent();

    int changed = jdbc.sql("""
            UPDATE club.tickets
            SET status = 'USED', checked_in_at = :now, checked_in_by = :staff
            WHERE id = :id AND event_id = :event AND status = 'ISSUED' AND checked_in_at IS NULL
            """)
            .param("now", Timestamp.from(clock.instant()))
            .param("staff", staffId).param("id", claims.ticketId()).param("event", eventId)
            .update();
    if (changed == 1) return CheckInResult.welcome(claims.ticketId());
    return CheckInResult.rejected(tickets.whyNot(claims.ticketId()));   // "already used at 19:02", "cancelled"
}

Two doors scan the same screenshot at the same moment. Both send the token. The database runs the two updates one after the other: the first changes 1 row, the second finds checked_in_at already set and changes 0 rows. Only one person enters. Showing "already used at 19:02 by door 2" helps the staff talk to the student.

6. Making the QR image

On the server (Java)

The ZXing library makes a PNG. The browser just shows <img src="/api/v1/club/tickets/{id}/qr.png">. The image endpoint must check that the ticket belongs to the caller, and should say Cache-Control: no-store.

In the browser (TypeScript)

The API returns the token text; a small JavaScript QR library draws it. No image traffic, and the page can redraw it larger in a dark hall. The token is still only shown to its owner.

byte[] png(String token) throws WriterException, IOException {
    Map<EncodeHintType, Object> hints = Map.of(
            EncodeHintType.ERROR_CORRECTION, ErrorCorrectionLevel.M,
            EncodeHintType.MARGIN, 2);                       // the white border readers need
    BitMatrix matrix = new QRCodeWriter().encode(token, BarcodeFormat.QR_CODE, 320, 320, hints);
    ByteArrayOutputStream out = new ByteArrayOutputStream();
    MatrixToImageWriter.writeToStream(matrix, "PNG", out);   // from ZXing's "javase" artifact
    return out.toByteArray();
}

Either way, the token is the ticket, not the picture. Never put the student's name or email in the QR text: it would be readable by anyone who sees the screen.

7. Scanning at the door

Smart Campus is website only, so the door scanner is a web page on a laptop or a phone's browser. Two browser parts are involved:

  1. navigator.mediaDevices.getUserMedia({ video: { facingMode: "environment" } }) opens the camera (the back camera on a phone). It only works on a secure origin: HTTPS, or localhost in dev. The user must allow camera access.
  2. Something must find the QR code in the video frames:
    • the BarcodeDetector API, built into some browsers but not in every browser (check MDN's compatibility table before you rely on it), or
    • a JavaScript library (for example a JavaScript port of ZXing) as the fallback that works everywhere.
export async function startScanner(video: HTMLVideoElement, onCode: (text: string) => void) {
  video.srcObject = await navigator.mediaDevices.getUserMedia({ video: { facingMode: "environment" } });
  await video.play();

  if ("BarcodeDetector" in window) {
    const detector = new (window as any).BarcodeDetector({ formats: ["qr_code"] });
    const tick = async () => {
      const codes = await detector.detect(video);
      if (codes.length > 0) onCode(codes[0].rawValue);
      requestAnimationFrame(tick);
    };
    tick();
  } else {
    startLibraryScanner(video, onCode);     // fallback: a JS QR library
  }
}

Make the screen easy for the staff: a big green "Welcome" or red "Already used", a sound, and ignore the same code for two seconds so one phone is not sent ten times.

Offline scanning: the trade-off

Online (recommended first)

Every scan asks the server. Perfect "only once" across all doors. Needs Wi-Fi at the door.

Offline

The scanner checks the signature with a public key and keeps a local list of used tickets, then uploads it later. Works without network, but two offline doors can both let the same screenshot in. And an HMAC key must never be on the device.

8. Attendees, club roles, club approval

Attendee list and check-in count (CLUB-6)

SELECT count(*) FILTER (WHERE status IN ('ISSUED', 'USED')) AS tickets,
       count(*) FILTER (WHERE status = 'USED')              AS checked_in
FROM club.tickets
WHERE event_id = :eventId;

Names come from a local copy of user profiles (from UserProvisioned events) or identity's public API, because club may not read identity's tables. A live counter can poll this every few seconds; the list is only for the club's managers.

Per-club roles (C3, CLUB-2)

Resolution C3: Keycloak has realm roles like STUDENT and CLUB_MANAGER, but per-club permissions live in club_members.role. Being a manager of the Chess Club does not let you scan tickets for the Music Club. So a realm role alone is not enough; check the club too:

@Component("clubAccess")
public class ClubAccess {
    private final ClubMemberRepository members;

    public ClubAccess(ClubMemberRepository members) {
        this.members = members;
    }

    public boolean canManage(UUID clubId, Authentication auth) {
        UUID userId = UUID.fromString(auth.getName());            // JWT sub
        return members.roleOf(clubId, userId)
                .map(role -> role == ClubRole.PRESIDENT || role == ClubRole.OFFICER)
                .orElse(false);
    }
}

// in a controller
@PreAuthorize("@clubAccess.canManage(#clubId, authentication)")
@PostMapping("/api/v1/club/clubs/{clubId}/events/{eventId}/check-ins")
CheckInResponse checkIn(@PathVariable UUID clubId, …) { … }

Remember to check that the event really belongs to that club, or a manager of club A could pass club A's id with club B's event.

Club approval (CLUB-8)

C10 lists club approval as a table the spec must design. A simple way: clubs.status PENDING → APPROVED or REJECTED, changed only by ACADEMIC_ADMIN. Lists and event creation show and allow only APPROVED clubs, so "only recognised clubs appear".

10. Common mistakes

  • Read, check, then write for the quota. Use one conditional UPDATE.
  • Counting the paid seat only after payment. Hold the seat first, release it on failure or timeout.
  • A counting ticket number in the QR. Easy to forge. Use a signed token or a random secret.
  • Thinking the signature stops screenshots. It does not. The one-time check-in does.
  • Putting an HMAC key in the scanner page. Anyone can then sign tickets.
  • Checking only the realm role instead of the role in this club.
  • Personal data inside the QR text. Keep only ids, expiry and a signature.
  • Relying on BarcodeDetector everywhere. Have a library fallback.

11. Practice

  1. Open any QR generator, make a code with the text hello, and scan it with your phone. Then make one with 300 characters at level H and compare how dense it looks.

  2. In JShell, write issue and verify for the HMAC token above. Change one character of the payload and check that verify returns empty.

  3. In a scratch PostgreSQL database, create events(id, ticket_quota, tickets_sold) with quota 5. Open two psql windows and run the conditional update in both, with BEGIN but no commit in the first. What does the second one do? What happens after you commit the first?

  4. Make a small HTML page on localhost that opens your camera with getUserMedia. In the browser console, check whether "BarcodeDetector" in window is true in your browser.

  5. On paper: list the states of a paid ticket from "Buy" to "checked in", including payment failure, hold timeout and cancel with refund.

13. Test yourself

1. Why is the QR text a signed token and not just the ticket number?

A counting number can be guessed, so people could make fake tickets. A signed token cannot be made without the key, and it also tells the scanner the event and expiry.

2. A student sends a screenshot of their ticket to a friend. What stops both from entering?

The one-time check-in: the conditional UPDATE … WHERE checked_in_at IS NULL succeeds only once. The second scan changes zero rows and is rejected.

3. Why does UPDATE … WHERE tickets_sold < ticket_quota stop overselling when "read, check, write" does not?

The database checks the condition and changes the row in one atomic step, with a row lock. Requests take turns, and each sees the latest count. With read-check-write, many requests see the same old count between the read and the write.

4. Why must a paid ticket hold the seat before the payment?

Paying takes minutes. If seats were counted only after PaymentConfirmed, more people could pay than there are seats, and some would need refunds.

5. Why is an HMAC key dangerous on an offline scanner, but a public key is fine?

With HMAC, the same key signs and checks, so whoever copies it can make tickets. A public key can only check signatures; signing needs the private key, which stays on the server.

6. Why is the realm role CLUB_MANAGER not enough to scan tickets for an event?

It says "manages some club", not which one. Per-club permission lives in club_members.role (C3), so we must check the role in the event's own club.
