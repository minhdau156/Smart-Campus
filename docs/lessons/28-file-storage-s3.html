File uploads and S3 storage

Students post photos of second-hand books and of lost wallets. Where do the photos live, how does a 6 MB phone picture get there without passing through our Java app, and how do we make sure it is really a picture and does not tell the world where the student lives?

1. Why you need this in Smart Campus

  • MKT-1: a seller posts a book with photos, price and course. The Plan has a listing_images(id, listing_id, object_key) table: the database stores only the key of each photo, not the photo.
  • MKT-3/4: edit, mark as sold, delete a listing: its photos must be removed too.
  • MKT-5/6: reports and moderation: an admin may need to remove a bad photo.
  • LF-1/2: report a lost or found item with a photo (lost_found_items.image_key).
  • LF-4: claim an item with proof of ownership. Proof photos are private.
  • LF-6: archive after 60 days: what happens to the photos?

The Architecture says it plainly: "Uploads go straight to MinIO via pre-signed URLs, size and MIME type checked; images re-encoded." Spec decision Q6 replaced MinIO with RustFS in dev, because MinIO stopped publishing Docker images. Apps use the plain S3 API, so only the dev container changed.

2. Why files do not go in the database

PostgreSQL can store bytes (bytea). But for photos it is a poor fit:

  • Size: thousands of 3 MB photos make the database huge. Backups and restores become slow, and the database cache fills with pictures instead of useful rows.
  • Traffic: every photo view would go browser → gateway → Java → database and back, holding a database connection the whole time.
  • Tools: object stores are built for this job. They are cheap per gigabyte, stream big files, and can give out short-lived download links.

An analogy: the database is a library catalogue. It says "the book is on shelf 4B". It does not glue the book into the catalogue.

3. Buckets, keys, objects, and RustFS

S3 (Amazon Simple Storage Service) is a storage service whose HTTP API became a de facto standard. Many products speak the same API ("S3-compatible"), including RustFS.

Our Compose file already runs RustFS:

rustfs:

  image: rustfs/rustfs:1.0.6
  environment:
    RUSTFS_ACCESS_KEY: ${RUSTFS_ACCESS_KEY:?set in infra/.env}
    RUSTFS_SECRET_KEY: ${RUSTFS_SECRET_KEY:?set in infra/.env}
    RUSTFS_CONSOLE_ENABLE: "true"
  ports:
    - "127.0.0.1:9000:9000"      # the S3 API
    - "127.0.0.1:9001:9001"      # the web console

The dev access key and secret key are in infra/.env (copied from .env.example, gitignored). The S3 API is http://localhost:9000; the console at http://localhost:9001 lets you look at buckets and files.

4. S3 from Java: S3Client

We use the official AWS SDK for Java v2. It works with RustFS if we change two things: the endpoint (talk to localhost:9000, not to Amazon) and path-style access.

Virtual-hosted style (Amazon's default)

http://campus-marketplace.localhost:9000/listings/a.jpg: the bucket is part of the host name. Needs DNS tricks on localhost.

Path style (what we use in dev)

http://localhost:9000/campus-marketplace/listings/a.jpg: the bucket is the first part of the path. Works with one host name.

@ConfigurationProperties("campus.storage")
record StorageProperties(URI endpoint, String region, String accessKey, String secretKey, String bucket) { }

@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(StorageProperties.class)
class StorageConfig {

    @Bean
    S3Client s3Client(StorageProperties p) {
        return S3Client.builder()
                .endpointOverride(p.endpoint())                    // http://localhost:9000 in dev
                .region(Region.of(p.region()))                     // required by the SDK; RustFS accepts a fixed value
                .credentialsProvider(StaticCredentialsProvider.create(
                        AwsBasicCredentials.create(p.accessKey(), p.secretKey())))
                .forcePathStyle(true)
                .build();
    }

    @Bean
    S3Presigner s3Presigner(StorageProperties p) {
        return S3Presigner.builder()
                .endpointOverride(p.endpoint())
                .region(Region.of(p.region()))
                .credentialsProvider(StaticCredentialsProvider.create(
                        AwsBasicCredentials.create(p.accessKey(), p.secretKey())))
                .serviceConfiguration(S3Configuration.builder().pathStyleAccessEnabled(true).build())
                .build();
    }
}

The values come from configuration, so production can point at another S3-compatible store without code changes. The secret key comes from the environment, never from a committed file.

Check against the real container Newer SDK versions add extra checksum headers by default, and some S3-compatible stores handle them differently. If uploads to RustFS fail with checksum errors, read the SDK's documentation on request checksum settings. Always prove the setup with an integration test against the real RustFS image (lesson 10).

5. Presigned URLs

We do not want 6 MB photos to pass through the gateway and core-app. Instead, our server gives the browser a presigned URL: a normal S3 URL plus a signature, made with our secret key, that says "whoever holds this link may do this one thing (PUT this key, or GET this key) until this time". The browser uses it to talk to the object store directly. The secret key never leaves the server.

An analogy: a hotel key card that opens only room 412 and stops working at noon.

PresignedUpload presignPut(String key, String contentType) {
    PutObjectRequest put = PutObjectRequest.builder()
            .bucket(props.bucket())
            .key(key)                                   // chosen by US, never by the user
            .contentType(contentType)                   // the browser must send the same header
            .build();
    PresignedPutObjectRequest signed = presigner.presignPutObject(PutObjectPresignRequest.builder()
            .signatureDuration(Duration.ofMinutes(5))   // short life
            .putObjectRequest(put)
            .build());
    return new PresignedUpload(signed.url().toString(), clock.instant().plus(Duration.ofMinutes(5)));
}

Downloads work the same way with presignGetObject, for private files (section 8).

Because the browser on localhost:5173 talks to localhost:9000, a different origin, the store must allow it with CORS rules for that bucket (allowed origin, method PUT, header Content-Type). How to set CORS rules on RustFS must be checked in its docs when the module is built.

6. The upload flow: ask, upload, confirm

Browser                       core-app (marketplace)              RustFS :9000
   │ POST …/listings/{id}/uploads ─►│ check: my listing? < 5 photos?
   │   { contentType: image/jpeg }  │ key = tmp/{uploadId}; save pending_uploads row
   │◄── { uploadId, url, expiresAt }│
   │ PUT url  (the file bytes) ───────────────────────────────────────►│ stores tmp/{uploadId}
   │ POST …/uploads/{uploadId}/confirm ─►│ HEAD object: size OK?
   │                                │ GET bytes: really an image? re-encode,
   │                                │ strip metadata, make thumbnail
   │                                │ PUT listings/{id}/{imageId}.jpg + thumb ─►│
   │                                │ DELETE tmp/{uploadId} ───────────────────►│
   │                                │ INSERT listing_images (object_key)
   │◄── 201 { imageId, thumbUrl }   │
  1. Ask. The server checks rights (only the seller of this listing) and limits (for example at most 5 photos), creates a temporary key, and remembers it in a pending_uploads table with an expiry.
  2. Upload. The browser PUTs the file directly to RustFS with the presigned URL.
  3. Confirm. The browser says "done". The server does not believe the browser: it checks the real object (next section), makes the final clean image, and only then adds a listing_images row.

Note that a presigned PUT does not limit the size by itself. That is why the confirm step checks the size with a HEAD request before reading the file, and deletes anything too big.

7. Checking and cleaning images

Do not trust the name or the Content-Type

photo.jpg with Content-Type: image/jpeg can be an HTML page, a script or a 2 GB file. Check the real content: the first bytes of a file (the "magic number") tell its true type. JPEG starts with FF D8 FF, PNG with 89 50 4E 47. Even better: try to decode it as an image. If it does not decode, reject it.

Re-encode, which also removes EXIF

Phone photos carry EXIF metadata: camera model, time, and often the exact GPS position where the photo was taken. A photo of a book taken at home tells everyone where the student lives. Re-encoding means: decode the pixels, then write a brand new JPEG from the pixels only. The new file has no EXIF, no GPS, and no hidden extra content.

CleanImage clean(InputStream in, long size) throws IOException {
    if (size > MAX_BYTES) throw new CampusProblem(ProblemCode.VALIDATION_FAILED, "Photo is larger than 8 MB");
    try (ImageInputStream iis = ImageIO.createImageInputStream(in)) {
        Iterator<ImageReader> readers = ImageIO.getImageReaders(iis);
        if (!readers.hasNext()) throw new CampusProblem(ProblemCode.VALIDATION_FAILED, "Not a supported image");
        ImageReader reader = readers.next();
        try {
            reader.setInput(iis);
            if ((long) reader.getWidth(0) * reader.getHeight(0) > MAX_PIXELS) {   // stop "image bombs"
                throw new CampusProblem(ProblemCode.VALIDATION_FAILED, "Photo has too many pixels");
            }
            BufferedImage pixels = reader.read(0);
            BufferedImage main = resize(pixels, 1600);         // long side at most 1600 px
            BufferedImage thumb = resize(pixels, 320);         // for lists
            return new CleanImage(toJpeg(main), toJpeg(thumb)); // new files: pixels only, no EXIF
        } finally {
            reader.dispose();
        }
    }
}
  • Image bombs: a tiny file can claim 50 000 × 50 000 pixels and use gigabytes of memory when decoded. Read the width and height first, as above.
  • Orientation: phones often save the picture sideways and add an EXIF note "rotate 90°". Removing EXIF removes that note, so the photo appears sideways. Read the orientation before cleaning and rotate the pixels (a metadata library can read it).
  • Formats: Java's built-in ImageIO reads JPEG and PNG, but not every modern phone format (for example HEIC). The spec must say which formats we accept.
  • Thumbnails: make them once at upload, not on every page view. Lists show the 320 px thumbnail; the listing page shows the 1600 px version.

8. Private files, key names, cleanup

Public or private?

Marketplace listing photos

Shown to every logged-in student. Still, keep the bucket private and give out presigned GET links (for example valid for one hour), or serve them through a controlled path. Then a removed photo (MKT-6) stops working quickly.

Lost & found claim proof (LF-4)

A photo of an ID card or a receipt. Only the claimant and security staff may see it. Private bucket, a permission check, then a short presigned GET (a few minutes).

Never make a whole bucket "public read" just to make images easy.

Key naming

  • Build keys from our own ids: listings/{listingId}/{imageId}.jpg, lostfound/{itemId}/{imageId}.jpg, tmp/{uploadId}.
  • Never use the user's file name in the key. A name like ../../other/listing.jpg or a 2 000-character name causes trouble. Keep the original name only as text in the database if you want to show it.
  • Random ids in keys also mean nobody can guess the next photo's URL.
  • Prefixes per purpose (tmp/, listings/) make cleanup jobs and expiry rules simple.

Orphan cleanup

An orphan is a file that no database row points to. They appear when a user asks for an upload URL and never confirms, when a confirm crashes half-way, or when a listing is deleted. A nightly job (lesson 25: a lock, chunks, a time zone) cleans them:

  • delete tmp/… objects whose pending_uploads row expired a day ago,
  • delete objects of listings deleted more than N days ago,
  • for LF-6, decide in the spec whether archived items keep their photos.

Order matters: when deleting a listing, delete the database row (and publish the event) first, and let the job delete the files later. A missing file shows a broken image; a row pointing to a deleted file is worse than a file nobody points to.

10. Common mistakes

  • Streaming uploads through core-app when a presigned URL would do.
  • Trusting the file name or Content-Type. Decode the real bytes.
  • Storing the original phone photo. It keeps GPS data. Re-encode.
  • Keys made from user input. Build keys from your own ids.
  • Long-lived presigned URLs (days). Use minutes for uploads and private files.
  • Public buckets for convenience.
  • Forgetting path-style access with RustFS, then getting strange DNS errors.
  • Saving the database row before the file is checked. Confirm first.
  • Never cleaning tmp/. Storage grows forever.

11. Practice

  1. Start the infrastructure and open the RustFS console at http://localhost:9001. Log in with the keys from your infra/.env. Create a bucket scratch and upload a photo by hand.

    docker compose -f infra/docker-compose.yml up -d --wait
docker compose -f infra/docker-compose.yml ps rustfs

  2. In a scratch Maven project (not in the repo), add the AWS SDK v2 S3 module, build the S3Client above, and list the objects in scratch with listObjectsV2.

  3. Make a presigned PUT URL for tmp/test.jpg with content type image/jpeg, valid for 5 minutes. Upload with curl:

    curl -X PUT -H "Content-Type: image/jpeg" --data-binary "@photo.jpg" "<the presigned url>"

    Try again with Content-Type: image/png. Why does it fail now?

  4. Take a photo with your phone with location on. Look at its EXIF data with any EXIF viewer. Re-encode it with ImageIO.read + ImageIO.write and look again.

  5. On paper: write the pending_uploads table and the SQL of the cleanup job. What happens if the job runs while a user is uploading?

13. Test yourself

1. Why do photos go to RustFS and not into a bytea column?

Photos would make the database huge, slow backups, fill its cache, and every view would hold a database connection. An object store is built and priced for big files.

2. Why does the browser upload with a presigned URL instead of sending the file to our API?

The big bytes skip the gateway and core-app, so our app threads and memory stay free. The secret key stays on the server; the URL allows only one action for a few minutes.

3. Why does the server re-check the file at "confirm" instead of trusting the browser?

The browser can be changed by the user. It can upload a huge file or a non-image with an image name. Only the server's own check of the real object is trustworthy.

4. Why re-encode images even when they are valid JPEGs?

To remove EXIF data like the GPS position (privacy), remove any hidden extra content, and make the size and format predictable.

5. Why must keys never come from the user's file name?

A user could pick a name that overwrites another file or breaks paths. Keys built from our own random ids are safe, unique and cannot be guessed.

6. When deleting a listing, why delete the row first and the file later?

If the file is deleted first and the transaction then fails, a live listing points to a missing photo. A leftover file with no row is harmless and the cleanup job removes it.
