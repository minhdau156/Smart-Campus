Redis, Lua and the registration rush

At 08:00 the registration window opens and 5,000 students click "Register" in the same minute. How do we answer each of them in under half a second, and still never give away a seat twice? This is the hardest part of Smart Campus, and the reason registration-service is a separate app.

1. The rush problem

The Plan says course registration "crashes every semester" today. Our targets are written as non-functional requirements (NFRs):

IdRequirement (from the Plan)What it means for the design
NFR-1Registration stays up with 5,000 students at once, p95 under 500 ms 95 of every 100 answers must arrive in under 0.5 s, even at the peak. The Arch says "5,000 students registering at the same minute" and 99.9% availability during windows.
NFR-2Never overbook a section or double-enroll a student Correctness beats speed. A fast wrong answer is a bug.
NFR-5Run a load test before every registration window We must be able to prove NFR-1 and NFR-2 (lesson 21).

Why is this hard? Popular sections are a hot spot: hundreds of students want the same 60 seats in the same second. Everyone reads and changes one number. That is exactly where race conditions and slow locks appear.

The Plan's answer has five steps. Keep this picture in mind for the whole lesson:

1. Waiting roomPer-user rate limit. At peak, a queue ticket and a position.
→
2. Redis seat gateLua script: duplicate? seat left? decrement. Answer in ms.
→
3. Kafka queueregistration.requests, key = sectionId.
→
4. Worker + PostgreSQLFinal guard: unique keys, version. On failure, release the Redis seat.
→
5. Result202 now, then polling (C8). WebSocket later.

2. Race conditions

A race condition is a bug that appears only when two things happen at nearly the same time, and the result depends on who is faster. Two classic forms:

Check-then-act

Section CS101-01: 1 seat left

  Request A (Lan)                     Request B (Minh)
  ─────────────────                   ─────────────────
  SELECT seats_left → 1
                                      SELECT seats_left → 1
  1 > 0, so INSERT enrollment
                                      1 > 0, so INSERT enrollment
  UPDATE seats_left = 0
                                      UPDATE seats_left = 0

  Result: 2 students in 1 seat.  Overbooked (breaks NFR-2).

Each request was correct alone. The bug is the gap between the check and the action. Another request slipped into the gap.

Lost update

  A reads enrolled = 29          B reads enrolled = 29
  A writes enrolled = 30         B writes enrolled = 30     ← A's +1 is lost

  Two students enrolled, counter says one.

The fix for both is the same idea: the read and the write must be one indivisible (atomic) step, or the write must fail when the data changed since the read (a version check, lesson 19).

3. Database locks vs atomic Redis operations

PostgreSQL can make the steps safe, for example with SELECT … FOR UPDATE (lock the row until commit) or a conditional update UPDATE … SET enrolled = enrolled + 1 WHERE enrolled < capacity. These are correct. The problem is speed under a hot spot:

Only PostgreSQL on the hot path

Every request for CS101-01 waits for the same row lock, one after another. Each transaction holds a connection from a small pool (often 10–20 per app). With hundreds of requests per second on one row, the queue grows, the pool runs out, and all endpoints slow down, not only the popular section.

Redis first, PostgreSQL last

Redis keeps data in memory and runs commands one at a time on a single main thread, so each command (and each Lua script) is atomic. A seat check takes well under a millisecond. PostgreSQL is still the final truth, but it is written later, at a steady pace, by a worker.

This is Arch decision ADR-3: "Redis as the first seat gate, PostgreSQL as the final truth". The trade-off the Arch accepts: "two copies of seat counts need reconciling". We handle that in section 8.

4. Redis in 10 minutes

Redis is an in-memory key–value store. Our Compose stack runs redis:8.8.4-alpine3.23 on port 6379 (infra/docker-compose.yml). The platform already uses it for the gateway's per-IP rate limit (lesson 11). The types we need:

TypeLike…CommandsOur use (planned)
String / integerOne labelled box with a numberGET, SET, INCR, DECR, INCRBYseats:{sectionId} = seats left
SetA bag of unique namesSADD, SREM, SISMEMBERholders:{sectionId} = students holding a seat (dedupe)
HashA small form with fieldsHSET, HGET, HGETALLreq:{requestId} = status of one request
Sorted setA ranked listZADD, ZRANKan option for waiting-room order

TTL ("time to live") makes a key delete itself later: EXPIRE key 3600, or SET key value EX 3600 NX (set only if it does not exist, expire in 1 hour). We use TTLs for request status, waiting-room tickets and rate-limit counters, so old keys never pile up.

docker compose -f infra/docker-compose.yml exec redis redis-cli
127.0.0.1:6379> SET seats:{sec-1} 2
127.0.0.1:6379> DECR seats:{sec-1}        # (integer) 1
127.0.0.1:6379> SADD holders:{sec-1} lan  # (integer) 1 = added
127.0.0.1:6379> SADD holders:{sec-1} lan  # (integer) 0 = already there
127.0.0.1:6379> SET req:abc PENDING EX 60
127.0.0.1:6379> TTL req:abc               # seconds left
Why the curly braces in key names? In a Redis cluster, keys are spread over many nodes, and one script may only touch keys on one node. Redis hashes only the part inside {…} (a "hash tag"). So seats:{sec-1} and holders:{sec-1} always live together. We run a single Redis today (Sentinel in production, per Arch §8), but using hash tags from day one costs nothing.

5. Lua scripts: the seat gate

Each Redis command is atomic, but "check the set, then check the counter, then decrement, then add to the set" is four commands. Another client could run between them: check-then-act again. A Lua script fixes this. Redis runs the whole script as one step; nothing else runs until it ends. It is like a bank clerk who closes the door while serving one customer, so be quick: a script must be short and must never loop over big data.

-- KEYS[1] = seats:{sectionId}     seats left (integer)
-- KEYS[2] = holders:{sectionId}   students who hold a seat (set)
-- ARGV[1] = studentId
-- Returns: 1 reserved, 0 full, -1 already holds a seat, -2 section not loaded

if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return -1                                   -- duplicate click or retry
end

local left = redis.call('GET', KEYS[1])
if not left then
  return -2                                   -- not open, or Redis lost its data
end

if tonumber(left) <= 0 then
  return 0                                    -- full: answer SECTION_FULL at once
end

redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1

This is the Plan's step 2: "a Lua script atomically checks for a duplicate and decrements seats:{sectionId}. If no seat is left, the request is rejected immediately without touching the database." Because the whole script is one step, the race from section 2 cannot happen: the second request sees the first one's decrement.

EVAL, EVALSHA and Spring's RedisScript

EVAL "script" numkeys key… arg… sends the full script text every time. EVALSHA sha1 … sends only its SHA-1 fingerprint; Redis keeps a cache of scripts it has seen. If the cache is empty (for example after a restart), Redis answers NOSCRIPT. Spring Data Redis handles this for you: it tries EVALSHA first and falls back to EVAL.

package edu.campus.registration.internal;

@Component
class SeatGate {
    private static final RedisScript<Long> RESERVE =
            RedisScript.of(new ClassPathResource("redis/reserve-seat.lua"), Long.class);

    private final StringRedisTemplate redis;

    SeatGate(StringRedisTemplate redis) {          // constructor injection, no Lombok
        this.redis = redis;
    }

    SeatResult reserve(SectionId section, StudentId student) {
        String tag = "{" + section.value() + "}";
        Long code = redis.execute(RESERVE,
                List.of("seats:" + tag, "holders:" + tag),  // KEYS: always pass keys here,
                student.value().toString());                  // never build them inside Lua
        return SeatResult.fromCode(code);              // RESERVED, FULL, DUPLICATE, NOT_LOADED
    }
}

A matching release-seat.lua does the opposite (SREM the student, then INCR the seats, only if the student was in the set). We call it when the worker rejects a request or a student drops.

6. The front door: waiting room and per-user limit

Per-user rate limit (C14)

The gateway limits per IP (platform R1: 20 requests/s, burst 40). But many students share one campus Wi-Fi IP, and one bot can use many IPs. So C14 says: registration endpoints are limited per user, inside registration. The simplest version is a fixed-window counter in Redis, again as one Lua script:

local n = redis.call('INCR', KEYS[1])
if n == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])   -- the counter deletes itself after the window
end
return n                                   -- Java: if n > limit → 429

Over the limit, the service answers 429 with a Retry-After header and problem JSON with code: RATE_LIMITED (that code already exists in ProblemCode). The actual limit (for example 5 requests per second per student) is a number for the registration spec.

Waiting room tokens (REG-5)

Even with limits, 5,000 people at 08:00:00 is more than the backend may want to take in one second. A waiting room works like the ticket machine at a bank: take a number, sit down, and watch the screen. The Plan: "At peak, students receive a queue token and the page polls their position." A simple design with two counters:

wr:{windowId}:next      INCR  → each arriving student gets the next number (ticket)
wr:{windowId}:admitted  INCRBY N every second, by a scheduled job ("now serving up to …")

position = ticket − admitted        (≤ 0 means: you may register now)

Lan arrives → ticket 1204          admitted = 1000  → position 204
… 1 second later …                 admitted = 1200  → position 4
… 1 second later …                 admitted = 1400  → admitted ✓
  • POST /api/v1/registration/waiting-room → a random token, stored in Redis as wr:token:{token} → (studentId, ticket), with a TTL. The token is bound to the student, so it cannot be passed to a friend.
  • GET …/waiting-room/{token} → { "position": 204 }. The page polls this every few seconds (REG-5: "I know the system is working and don't refresh").
  • The register endpoint refuses a request whose ticket is not admitted yet.
  • N (students admitted per second) comes from load tests: it is the rate we proved the system can handle (lesson 21).

Both counters are single INCR/GET commands, so they are atomic and cost the same for 50 or 50,000 students.

7. The queue, the worker, 202 and polling

The API side

After the seat gate says RESERVED, the API puts a request (a command: "give Lan a seat in CS101-01") on the Kafka topic registration.requests. The key is the sectionId (Topics.REGISTRATION_REQUESTS, 12 partitions). Kafka keeps order per key, so all requests for one section are processed by one worker thread, in arrival order. Waitlists stay fair, and two requests for the same section never race inside the worker.

Then the API answers at once with 202 Accepted, not 201 Created: "I took your request; the result comes later" (ADR-7). This is decision C8: the result is read by polling, because the WebSocket host (notification) arrives later.

POST /api/v1/registration/requests
Authorization: Bearer eyJ…
Idempotency-Key: 7f9c2b6e-…                // required on POSTs that create enrollments (Arch §7)
{ "sectionId": "3f1c…" }

HTTP/1.1 202 Accepted
Location: /api/v1/registration/requests/a1b2…
{ "requestId": "a1b2…", "status": "PENDING" }

GET /api/v1/registration/requests/a1b2…     // the page asks every second
{ "requestId": "a1b2…", "status": "CONFIRMED" }          // or REJECTED + a reason code

If the seat gate says FULL, the API answers 409 with code: SECTION_FULL right away (a code the Arch names; the registration spec adds it to ProblemCode). Nothing reaches Kafka or PostgreSQL. This fast "no" is most of the traffic in a rush, so it must be cheap.

This is not the outbox, and that is on purpose

Lesson 08 says "never call kafkaTemplate.send in business code". Here the API has no database write at all, so there is nothing for an outbox to be atomic with. The two systems are Redis and Kafka. The API therefore waits for Kafka's acknowledgement before it answers 202, and if the send fails, it runs release-seat.lua and answers with an error. If the API crashes between the Redis decrement and the send, one seat is "stuck" in Redis: the sync check in section 8 finds it. The registration spec must confirm this design.

The request status lives in a Redis hash req:{requestId} with a TTL (for example one hour), written by the API (PENDING) and by the worker (CONFIRMED / REJECTED). Only the student who made the request may read it.

const result = useQuery({
  queryKey: ['registration-request', requestId],
  queryFn: () => api.getRequest(requestId),
  refetchInterval: (query) => (query.state.data?.status === 'PENDING' ? 1000 : false),
});

The worker side (C5)

The worker runs in registration-service (Arch §9: "api + worker profiles") and reads registration.requests. It writes to the database with the final guards from Plan step 4. Because registration-service cannot write the course schema, decision C5 gives it its own seat table, fed by SectionChanged events:

CREATE TABLE registration.section_seats (
    section_id  UUID PRIMARY KEY,              -- from course.events; no FK to course (C4)
    capacity    INT  NOT NULL CHECK (capacity >= 0),
    enrolled    INT  NOT NULL DEFAULT 0,
    version     BIGINT NOT NULL DEFAULT 0,     -- optimistic lock
    updated_at  TIMESTAMPTZ NOT NULL
);

CREATE TABLE registration.enrollments (
    id               UUID PRIMARY KEY,
    student_id       UUID NOT NULL,
    section_id       UUID NOT NULL,
    status           TEXT NOT NULL,            -- ENROLLED / DROPPED
    idempotency_key  TEXT NOT NULL UNIQUE,     -- a retried request cannot enroll twice
    created_at       TIMESTAMPTZ NOT NULL
);
-- The Plan has UNIQUE(student_id, section_id). A partial index keeps that rule for active
-- enrollments but still lets a student register again after a drop.
CREATE UNIQUE INDEX enrollments_one_active
    ON registration.enrollments (student_id, section_id) WHERE status = 'ENROLLED';
@KafkaListener(topics = "registration.requests", groupId = "registration-worker")
@Transactional
void on(SeatRequest req) {
    if (enrollments.existsByIdempotencyKey(req.idempotencyKey())) {
        return;                                          // a repeat (at-least-once, lesson 08)
    }
    RuleCheck check = rules.check(req.studentId(), req.sectionId());   // REG-3: clash, prerequisite, credit limit
    if (!check.ok()) {
        afterCommit.releaseSeatAndReject(req, check.reason());         // Plan step 4: give the Redis seat back
        return;
    }
    SeatRow seats = sectionSeats.get(req.sectionId());
    int changed = jdbc.update("""
            UPDATE registration.section_seats
               SET enrolled = enrolled + 1, version = version + 1, updated_at = ?
             WHERE section_id = ? AND version = ? AND enrolled < capacity""",
            Timestamp.from(clock.instant()), req.sectionId().value(), seats.version());
    if (changed == 0) {
        throw new SeatConflict(req);                     // version moved or full: retry or reject
    }
    enrollments.insert(req);                             // unique indexes = last guard
    events.publishEvent(enrollmentConfirmed(req));       // outbox → registration.events (key studentId)
    afterCommit.markConfirmed(req);                      // Redis req:{id} = CONFIRMED
}

Notice the layers. Redis already blocked most bad requests. The version check, the enrolled < capacity condition and the unique indexes catch anything Redis missed. Redis updates happen after commit (for example with a TransactionSynchronization), so Redis never shows a result that was rolled back. registration.requests is not replayable (Topics says so): it holds commands, and running them again would act again.

8. Drops, waitlist, overrides, sync, and restarts

Drop and waitlist promotion (REG-4, REG-6)

A drop is also sent through registration.requests with the same key (sectionId). So drops and new requests for one section are handled one at a time, in order. When a seat frees up:

  1. The worker marks the enrollment DROPPED, lowers enrolled and publishes EnrollmentDropped.
  2. If the section's waitlist is not empty, the seat goes straight to the first student on the waitlist (after the REG-3 checks again; if that student now has a clash, try the next one). Redis seats stays at 0, so a newcomer cannot jump the queue.
  3. If the waitlist is empty, after commit the worker runs release-seat.lua: Redis gets the seat back and the next click can take it.

Capacity changes and admin overrides (REG-9, REG-11)

  • REG-9 (raise capacity): course publishes SectionChanged with the new capacity. The registration consumer updates section_seats.capacity (version check) and then INCRBY seats:{id} delta in Redis (or gives the new seats to the waitlist first).
  • REG-11 (enroll manually with a reason): an academic admin's override goes through the same queue with an override flag and a required reason. The worker skips the capacity check, adds the student to holders, never lets Redis go below 0, and writes an audit row (NFR-3). Counting overrides separately keeps NFR-2 checkable: normal enrollments never exceed capacity.

Keeping Redis and PostgreSQL in sync

Two copies of a number will drift sometimes: a crash between a Redis change and a Kafka send, or between a DB commit and the Redis update. Most of our crashes leave Redis with fewer seats than reality (we under-sell, never over-sell), which is the safe direction. Still, we must see it. For each open section, a scheduled job compares:

expected Redis seats = section_seats.capacity − section_seats.enrolled − pending requests
drift                = Redis seats:{sectionId} − expected

It exports drift as a metric, and an alert fires when it is not 0 for a while. Arch §8 lists this alert ("Redis seat count and DB enrolled_count out of sync"), and platform criterion B3 says the seat-sync alert "is added by registration":

- alert: SeatCountOutOfSync
  expr: abs(registration_seat_drift) > 0
  for: 2m                       # short drift is normal while requests are in flight
  labels: { severity: page }
  annotations:
    summary: "Redis and DB seat counts differ for section {{ $labels.section }}"

Should the job fix the drift by itself? Fixing a number while requests are in flight can make it worse, so a safe first version alerts and gives admins a "resync this section" action. The spec decides.

What if Redis restarts?

Redis keeps data in memory. After a restart it may have lost recent writes, or everything if there is no persistence. (Redis can save to disk with snapshots (RDB) or an append-only file (AOF); with appendfsync everysec you lose at most about a second. Our dev container has no volume for Redis, so treat its data as lost on restart.) The rules:

  • Never guess. A missing seats: key returns -2, and the API answers 503 "registration paused, try again" instead of assuming the section is empty or full.
  • Rebuild from the truth. A loader reads section_seats, active enrollments and pending requests from PostgreSQL and writes seats: and holders: back. Then the gate opens again.
  • Correctness never depended on Redis. Even with wrong Redis data, the worker's version check and unique indexes stop overbooking. Redis only makes the answer fast.

10. Common mistakes

  • Doing GET then DECR from Java. Two commands = a gap = a race. Put check and change in one Lua script.
  • Building key names inside Lua. Pass every key in KEYS, so Redis (and a future cluster) knows which keys the script touches.
  • Long Lua scripts. While a script runs, Redis serves nobody else. No loops over big sets.
  • Treating Redis as the truth. It is a fast gate. PostgreSQL constraints decide.
  • Returning 201 before the worker ran. The honest answer is 202 + a status URL.
  • Keying registration.requests by studentId. Then two requests for the same section run in parallel in different partitions, and waitlist order is lost.
  • Releasing a Redis seat inside the DB transaction. If the transaction then rolls back, Redis and the DB disagree. Update Redis after commit.
  • Forgetting TTLs. Request statuses and tickets without a TTL fill memory over many semesters.
  • Assuming a missing key means "0 seats" or "full capacity". Missing means "unknown": pause and rebuild.

13. Test yourself

1. Why not just use SELECT … FOR UPDATE in PostgreSQL for every request?

It is correct but slow at a hot spot: every request for a popular section waits for the same row lock and holds a pooled connection while waiting. The pool runs out and every endpoint slows down. Redis answers the same question atomically in memory, in well under a millisecond.

2. Why must the duplicate check and the decrement be in one Lua script?

As separate commands, another request can run between them (check-then-act). Redis runs a script as one atomic step, so no other command can see a half-done state.

3. Why is registration.requests keyed by sectionId?

Kafka keeps order only within a partition, and the key picks the partition. With sectionId as the key, all requests and drops for one section are processed one by one in arrival order, so the waitlist is fair and the worker never races with itself on that section.

4. Why does the API answer 202 and not 201?

At that moment only Redis has reserved a seat. The enrollment row does not exist yet; the worker may still reject it (for example a prerequisite is missing). 202 plus a status URL is honest, and it keeps the answer fast (ADR-7, C8).

5. If Redis has wrong numbers, can a section be overbooked?

No. Redis is only the first gate. The worker's enrolled < capacity and version check, and the unique indexes, are the final guard (NFR-2). Wrong Redis data can cause wrong "full" answers or slow requests, which is why we alert on drift.

6. Why must a missing seats: key not be treated as "0 seats left"?

Missing can mean Redis restarted and lost data. Treating it as 0 would wrongly reject everyone; treating it as full capacity could hand out seats that are taken. The safe answer is "paused" until the loader rebuilds the keys from PostgreSQL.
