API gateway and rate limiting

The website talks to one address, localhost:8080. Behind it, a gateway sends each request to the right app and stops anyone who sends too many. This lesson explains how, and why the counter lives in Redis.

1. Why a gateway

Smart Campus has three backend apps: core-app (:8081), registration-service (:8082) and notification-service (:8083). The website should not know that. An API gateway is a single front door: it receives every request and forwards it to the right app. Think of a hotel reception: guests talk to one desk, and the desk calls the right department.

Browserwebsite on :5173 (dev)
→
gateway :8080route · rate limit · (later) check JWT · problem JSON
→
core-app :8081/api/v1/**
registration :8082/api/v1/registration/**
notification :8083/api/v1/notification/**, /ws/**

Things the gateway does once, for everyone:

  • Routing: one public address; apps can move or scale behind it (T13).
  • Rate limiting: stop floods before they reach the apps (T14, Arch §7).
  • Token check: verify the Keycloak JWT signature (planned in identity, lesson 17). Each service checks roles again (defence in depth).
  • Hiding disabled modules: a filter answers 404 (planned in shell).
  • Same error shape: problem JSON even when a backend is down (T13).

2. Routes, predicates, filters

We use Spring Cloud Gateway, the "server-webflux" variant (spec Tech Stack). It has three building blocks:

BlockQuestion it answersExample
RouteWhere does this request go?id registration, uri http://localhost:8082
PredicateDoes this route match the request?Path=/api/v1/registration/**
FilterWhat to change or check on the way in or out?add a header, rate-limit, rewrite the path
server:
  port: 8080

spring:
  cloud:
    gateway:
      server:
        webflux:                       # the 2025.x prefix for the WebFlux gateway
          routes:
            - id: registration
              uri: ${REGISTRATION_URI:http://localhost:8082}   # env var, so containers can override
              predicates:
                - Path=/api/v1/registration/**
            - id: notification
              uri: ${NOTIFICATION_URI:http://localhost:8083}
              predicates:
                - Path=/api/v1/notification/**,/ws/**
            - id: core
              uri: ${CORE_URI:http://localhost:8081}
              predicates:
                - Path=/api/v1/**          # the catch-all: must be LAST

The ${NAME:default} form reads an environment variable and falls back to the default. In the Compose apps profile (T15) the variables point to container names instead of localhost.

3. Route order, WebSocket and errors

The first match wins

/api/v1/registration/requests matches both /api/v1/registration/** and /api/v1/**. The gateway checks routes in order and uses the first one that matches. So the specific routes must come before the catch-all.

Catch-all first

/api/v1/** → core-app is checked first. Every registration request goes to core-app, which answers 404. Registration is "down" and nothing logs an error.

Specific first

/api/v1/registration/** and /api/v1/notification/** first, /api/v1/** last. To be safe, give the catch-all a higher order value too, and cover each route in GatewayRoutingIT.

WebSocket: /ws/**

A WebSocket starts as a normal HTTP request with an Upgrade header, then stays open so the server can push messages. The gateway can forward it like any route (T13 adds the route now). Nothing serves it until the notification module adds the STOMP endpoint (lesson 24).

Errors at the gateway

The gateway is a separate app, so platform-starter's Spring MVC problem handler does not run there (the gateway is WebFlux). T13 writes a reactive handler with the same JSON shape:

What happenedStatus
No route matches404 problem JSON
Backend refuses the connection (app down)503 problem JSON
Backend too slow504 problem JSON
Too many requests429 problem JSON, code RATE_LIMITED (T14)

Never an HTML error page: the website can always parse the answer.

4. Reactive basics: never block

The gateway runs on Spring WebFlux with the Netty server. Instead of one thread per request (like Spring MVC in our other apps), a few event-loop threads serve thousands of requests. A thread starts some I/O (like calling a backend), and instead of waiting, it goes to serve other requests. When the answer arrives, the work continues.

A waiter picture: an MVC waiter takes your order and stands in the kitchen until the food is ready. A reactive waiter takes your order, serves other tables, and comes back when the kitchen rings the bell. Few waiters, many tables, but only if no waiter ever stands and waits.

TypeMeaning
Mono<T>Zero or one value, arriving later (like a promise)
Flux<T>Zero to many values, arriving over time (a stream)
@Component
class GatewayHeaderFilter implements GlobalFilter {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest().mutate()
                .header("X-Gateway", "smart-campus")
                .build();
        return chain.filter(exchange.mutate().request(request).build());  // returns at once
    }
}
Never block an event-loop thread No Thread.sleep, no JDBC, no blocking HTTP client, no .block() inside a filter. One blocked thread stops many requests at once. Reactor even throws an error if you call block() on a Netty thread. Use reactive clients (the reactive Redis client, for example) and chain with map / flatMap.

5. Rate-limiting algorithms

Rate limiting means: each caller may send at most N requests per time unit. Above that, the gateway answers 429 Too Many Requests without calling the backend. It protects the apps from bots, bugs (a frontend stuck in a loop) and floods. Three classic ways:

AlgorithmHow it countsWeak spot
Fixed windowA counter per caller per second (or minute). Reset at the start of each window. Bursts at the edge: 20 requests at 0.99 s and 20 more at 1.01 s = 40 in 20 ms.
Sliding windowCount requests in the last N seconds, moving with time (exactly, or estimated from two windows). Smoother, but more data or math per caller.
Token bucketEach caller has a bucket of tokens. Each request takes a token. Tokens refill at a steady rate, up to a maximum. Allows a short burst on purpose, which is usually what you want.
Token bucket for one IP: refill 20 tokens/s, bucket size 40

 idle for a while    → bucket full: 40 tokens
 page load: 30 calls → 30 taken, 10 left      (burst allowed, all OK)
 next second         → +20 refilled → 30
 a bot: 100 calls/s  → 20/s get a token, the other 80/s get 429

Spring Cloud Gateway's Redis limiter uses the token bucket. Our defaults (spec R1): replenish rate 20 per second, burst 40, set in config.

6. RequestRateLimiter with Redis

The gateway's RequestRateLimiter filter asks a rate limiter "may this key make a request?" and a key resolver "who is this caller?". With RedisRateLimiter, each bucket lives in Redis and is updated by a small Lua script, so the "read tokens, take one, write back" step is atomic.

filters:
  - name: RequestRateLimiter
    args:
      redis-rate-limiter.replenishRate: 20     # tokens added per second
      redis-rate-limiter.burstCapacity: 40     # bucket size = biggest burst
      redis-rate-limiter.requestedTokens: 1    # cost of one request
      key-resolver: "#{@trustedProxyIpKeyResolver}"   # a bean, by name (SpEL)
  • burstCapacity: 0 blocks every request. requestedTokens above 1 makes a request "cost more", which lets you go below one request per second.
  • It needs the reactive Redis starter, spring-boot-starter-data-redis-reactive.
  • T14.3 applies it to all /api/v1/** routes as a default filter (a filter that every route gets), with the numbers read from config.
Why the state is in Redis, not in the gateway's memory In production the gateway runs as 2 to 4 replicas (Arch §8). With in-memory counters, each replica has its own bucket, so a caller gets 2 to 4 times the limit by spreading requests. With Redis, all replicas share one bucket per caller (spec R1). RateLimitIT proves it: two gateway instances, one budget.

7. Whose limit? The key resolver

A KeyResolver turns a request into a key string. Same key = same bucket. For platform the key is the client IP address.

@Bean
KeyResolver remoteIpKeyResolver() {
    return exchange -> Mono.justOrEmpty(exchange.getRequest().getRemoteAddress())
            .map(address -> address.getAddress().getHostAddress());   // "203.0.113.7"
}

If the resolver gives no key, the filter denies the request by default (a setting can change this). Better to refuse than to let an unknown caller in without a limit.

The X-Forwarded-For trust problem

In production, a load balancer or ingress sits in front of the gateway. Then the "remote address" is the proxy's IP, the same for every student, and everyone shares one bucket. Proxies add the real client IP in the X-Forwarded-For header:

X-Forwarded-For: 198.51.100.4, 10.0.0.12
                 └ client ─┘   └ proxy ┘   (each proxy appends the address it saw)

But anyone can send that header. A bot that writes a random X-Forwarded-For on every request would get a fresh bucket every time, and the limit would mean nothing.

Trust the header always

Key = first value of X-Forwarded-For. A bot sets it to random IPs and is never limited.

Trust only known proxies (T14.2)

TrustedProxyIpKeyResolver: use the remote address. Read X-Forwarded-For only if the remote address is in a configured trusted-proxy range, and then take the nearest address that is not a trusted proxy.

RateLimitIT covers this: a spoofed X-Forwarded-For from an untrusted source is ignored. (Spring Cloud Gateway also ships an XForwardedRemoteAddressResolver with a "max trusted index" option; T14 may build on it or write its own.)

8. The 429 answer and per-user limits

The Redis limiter answers 429 by default, but not in our problem JSON shape and without telling the client when to try again. T14.4 adds RateLimitedProblemFilter to fix both:

HTTP/1.1 429 Too Many Requests
Retry-After: 1
Content-Type: application/problem+json

{
  "type": "https://campus.edu/problems/rate-limited",
  "title": "Rate limited",
  "status": 429,
  "detail": "Too many requests. Try again in 1 second(s).",
  "code": "RATE_LIMITED",
  "traceId": "…"
}
  • Retry-After is a standard HTTP header. Here it holds whole seconds, at least 1. A good client (our website) waits that long before trying again, instead of hammering the server.
  • RATE_LIMITED already exists in ProblemCode (shared-kernel), so the frontend can show "Please slow down" for every module the same way.
  • Requests under the limit are not changed at all, and another IP is not affected by your limit. Both are cases in RateLimitIT.

Per-user limits for registration (planned)

Arch §7: "registration endpoints are limited per user, others per IP". Why? A whole dormitory may share one public IP, and during the rush hundreds of honest students would share one bucket. After identity exists, the key can be the user id from the JWT. The registration module adds that limit for its routes (map C14), together with the waiting room. T14.3 documents how a route replaces the default per-IP limit with its own.

10. Common mistakes

  • Catch-all route first. Registration and notification become unreachable.
  • Blocking in a gateway filter. JDBC, sleep or .block() freezes an event-loop thread.
  • Trusting X-Forwarded-For from anyone. The limit becomes useless.
  • In-memory rate limits with several replicas. Each replica gives the full budget.
  • A 429 without Retry-After. Clients guess and often retry at once, which makes the flood worse.
  • Copying Boot 3 / older gateway YAML. Keys and artifacts changed in Spring Cloud 2025.x; check the docs for our version.
  • Hard-coding localhost backend URLs. In containers the hosts are service names; read them from env vars.

  2. Token bucket on paper: replenish 20/s, burst 40. A client is idle, then sends 50 requests in 0.1 s, then 1 request every 40 ms for 2 s. How many 429 answers does it get?

  3. Look inside Redis while you think about keys (Redis runs in Compose already):

    docker compose -f infra/docker-compose.yml exec redis redis-cli ping

    After T14, send a burst through the gateway and run the scan again to see the limiter's keys.

  4. After T13 and T14, with all apps running, use the smoke script and then trigger the limit (Git Bash):

    bash infra/smoke.sh

  5. Spoof test: send -H "X-Forwarded-For: 1.2.3.4" with the burst. Does it give you a new bucket? It must not, because your machine is not a trusted proxy.

RouteA rule "these requests go to that app".
PredicateA test that decides if a route matches (e.g. the path).
FilterA step that changes or checks a request or response on the way.
Default filterA filter added to every route.
ReactiveA style where threads never wait; work continues when data arrives.

13. Test yourself

1. Why must /api/v1/registration/** come before /api/v1/**?

The gateway uses the first matching route. The catch-all also matches registration URLs, so if it came first, every registration request would go to core-app and get a 404.

2. Why is calling JDBC inside a gateway filter so harmful?

The gateway serves many requests on a few event-loop threads. A blocking call holds one of them, so all the requests waiting on that thread stop too. Under load the whole gateway freezes.

3. Why does Smart Campus prefer a token bucket over a fixed window?

A page load makes a short burst of calls, which a token bucket allows up to the burst size, while still holding the long-term rate. A fixed window can let through double the limit at the edge between two windows.

4. Why is the limiter state kept in Redis?

The gateway runs as several replicas. Counters in memory would give each replica its own budget. Redis gives all replicas one shared bucket per caller, and its Lua script makes each update atomic.

5. Why read X-Forwarded-For only from trusted proxies?

Any client can write that header. If it were always trusted, a bot could pick a new fake IP for every request and never be limited.

6. Why will registration use a per-user limit instead of per IP?

Many students can share one public IP (a dormitory, the campus Wi-Fi). During the rush a per-IP limit would block honest students. A per-user key, from the login token, is fair to each student and still stops one user's bot.
