Spring Boot 4 basics

Every backend app in Smart Campus is a Spring Boot app. Spring creates your objects, connects them, reads your settings, and switches on features just because a jar is on the classpath. This lesson shows how, using core-app and our own platform-starter.

1. What Spring Boot does

A backend app needs many parts: a web server, a database connection pool, JSON, Kafka clients, health checks, logging. Wiring them by hand is long and easy to get wrong.

Spring Framework gives an IoC container ("inversion of control"). Instead of your code creating its helpers with new, the container creates all objects and hands each one the helpers it needs. Think of a restaurant kitchen: the cook does not grow vegetables. They ask, and the ingredients arrive.

Spring Boot adds three things on top:

  • Starters: one dependency per feature (spring-boot-starter-webmvc, spring-boot-starter-jdbc …).
  • Auto-configuration: good default objects are created for you when a library is present (a DataSource when a JDBC driver and a URL exist).
  • Externalized configuration: settings in application.yml, environment variables or the command line, not in code.
@SpringBootApplication
public class CoreApplication {
    public static void main(String[] args) {
        SpringApplication.run(CoreApplication.class, args);
    }
}

@SpringBootApplication turns on auto-configuration and component scanning of the package edu.campus and every package below it.

2. Beans and dependency injection

A bean is an object that Spring creates and manages. By default there is one of each (scope "singleton"), shared by everyone who asks.

Two ways to make a bean

1. A stereotype on your class

Component scanning finds classes with these annotations:

  • @Component: a general bean
  • @Service: business logic (OutboxProbeService)
  • @Repository: database access
  • @RestController: HTTP endpoints (PingController)
  • @Configuration: a class that holds @Bean methods

2. A @Bean method

For objects you cannot annotate (JDK or library classes):

@Configuration(proxyBeanMethods = false)
class ClockConfiguration {
    @Bean
    Clock clock() {
        return Clock.systemUTC();
    }
}

proxyBeanMethods = false tells Spring not to wrap the class, because no @Bean method calls another one. It starts a little faster. You will see it on every configuration class in this project.

Constructor injection

Dependency injection (DI) = Spring passes the beans a class needs into it. The project rule: constructor injection only. If a class has one constructor, Spring uses it; no @Autowired is needed.

@Service
class OutboxProbeService {
    private final JdbcTemplate jdbc;
    private final ApplicationEventPublisher events;
    private final Clock clock;

    OutboxProbeService(JdbcTemplate jdbc, ApplicationEventPublisher events, Clock clock) {
        this.jdbc = jdbc;
        this.events = events;
        this.clock = clock;
    }
}

Why constructors and not @Autowired on fields?

  • Fields can be final: the object is complete and cannot change.
  • A test can call new OutboxProbeService(fakeJdbc, fakeEvents, fixedClock) with no Spring at all.
  • A long constructor is a warning sign: the class does too much.

If two beans of the same type exist, Spring cannot choose and startup fails ("expected single matching bean"). That is why Clock lives in its own configuration class: the controller test (PingControllerTest) can give its own fixed Clock without a clash.

3. Configuration and profiles

application.yml

Settings live in src/main/resources/application.yml. One file can hold several documents, separated by ---. A document with spring.config.activate.on-profile is used only when that profile is active.

spring:
  application:
    name: core-app
  datasource:
    username: core_app                 # the DB user for core-app (lesson 04)
  flyway:
    default-schema: platform
server:
  port: 8081
campus:
  version: "@project.version@"         # Maven fills this in while copying the file

---
spring:
  config:
    activate:
      on-profile: dev                  # your laptop + Docker Compose
    import: optional:file:../../infra/.env[.properties]
  datasource:
    url: jdbc:postgresql://localhost:5433/${POSTGRES_DB:campus}
    password: ${CORE_APP_DB_PASSWORD}  # read from infra/.env, never written here

---
spring:
  config:
    activate:
      on-profile: test                 # integration tests; Testcontainers gives the URL

${NAME:default} is a placeholder: the value of another setting or environment variable, with a default after the colon. The dev profile is switched on by the Maven plugin for spring-boot:run; the ITs use @ActiveProfiles("test").

Who wins?

Spring reads settings from many property sources. When two set the same key, the higher one wins:

  command line            --server.port=9000                 (highest)
  environment variables   SERVER_PORT=9000
  profile documents       the "dev" or "test" block of application.yml
  application.yml         the first block
  platform-starter        campus-platform-defaults.yml        (lowest, see section 5)

Environment variables use relaxed binding: campus.outbox.retry-interval can be set as CAMPUS_OUTBOX_RETRYINTERVAL (dots become _, dashes are dropped, upper case). Containers in T15 are configured this way.

Reading settings in code

@Value: one value

PingController(Clock clock,
    @Value("${spring.application.name}") String app,
    @Value("${campus.version}") String version)

Fine for one or two values (used in PingController).

@ConfigurationProperties: a group

@ConfigurationProperties("campus.outbox")
public record OutboxProperties(Duration retryInterval) {}

A typed record for a whole group. 30s becomes a Duration. Register it with @EnableConfigurationProperties(OutboxProperties.class). (Example only: today the retry job reads the value with a placeholder.)

4. Starters and auto-configuration

A starter is a dependency that brings a feature's libraries. Look at core-app's pom: spring-boot-starter-webmvc (Tomcat + Spring MVC), -actuator, -jdbc, -flyway, -kafka. You add the jar; Spring Boot does the setup.

Auto-configuration classes are normal @Configuration classes inside those jars, guarded by conditions:

ConditionCreates the beans only if …
@ConditionalOnClass(X.class)class X is on the classpath (the library is there)
@ConditionalOnBean(X.class)a bean of type X already exists
@ConditionalOnMissingBeanthe app has not made its own bean of this type
@ConditionalOnPropertya setting has a given value
@ConditionalOnWebApplication(type = SERVLET)the app is a Spring MVC (servlet) app

@ConditionalOnMissingBean is the key to "defaults you can replace": Boot creates a JdbcTemplate unless you made one yourself. Your bean always wins.

See what was switched on, and why Start the app with --debug (or set debug: true). Boot prints the condition evaluation report: every auto-configuration, matched or not, with the reason.

5. Inside platform-starter

backend/platform-starter is our own starter (T8). core-app only lists it in its pom, and gets problem JSON, a trace id, the outbox setup and the Modulith rules, with no annotation and no import. How does Spring find it? Through plain text files inside the jar:

1. Settings, very earlyMETA-INF/spring.factories → PlatformDefaultsEnvironmentPostProcessor adds campus-platform-defaults.yml at the lowest priority
→
2. BeansMETA-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports lists 3 auto-configurations
→
3. Conditionseach one switches on only if the app has the right libraries

Step 1: shared default settings

public class PlatformDefaultsEnvironmentPostProcessor implements EnvironmentPostProcessor {
    static final String FILE = "campus-platform-defaults.yml";

    @Override
    public void postProcessEnvironment(ConfigurableEnvironment environment, SpringApplication application) {
        List<PropertySource<?>> sources =
                new YamlPropertySourceLoader().load("platform-starter defaults", new ClassPathResource(FILE));
        sources.forEach(environment.getPropertySources()::addLast);   // LAST = lowest priority
    }
}

An EnvironmentPostProcessor runs before any bean exists, while Spring is still collecting settings. addLast puts our file at the bottom of the list, so every app can still override a value (core-app's test profile sets retry-interval: 2s, and it wins). It is like a parent pom, but for settings.

Step 2 and 3: conditional beans

@AutoConfiguration(afterName = "org.springframework.modulith.events.config.EventPublicationAutoConfiguration")
@ConditionalOnClass(FailedEventPublications.class)   // Modulith events library present
@ConditionalOnBean(FailedEventPublications.class)    // and Modulith really made the registry
@EnableScheduling
public class OutboxAutoConfiguration {
    @Bean
    OutboxRetryJob outboxRetryJob(FailedEventPublications failed) {
        return new OutboxRetryJob(failed);
    }
}

afterName makes Spring evaluate this class after Modulith's own auto-configuration. Otherwise @ConditionalOnBean could run too early and always say "no". ProblemHandlingAutoConfiguration uses @ConditionalOnWebApplication(type = SERVLET), so the planned WebFlux gateway (T13) does not get the MVC error handler.

The same spring.factories file also registers CampusModuleDetection for Spring Modulith (lesson 06).

6. REST, JSON and Actuator

A controller

@RestController
@RequestMapping("/api/v1/platform")
class PingController {

    record Ping(String app, String version, Instant time) {}

    @GetMapping("/ping")
    Ping ping() {
        return new Ping(app, version, clock.instant());
    }
}

@RestController means "every method's return value is the response body". Spring turns the Ping record into JSON: {"app":"core-app","version":"0.1.0-SNAPSHOT","time":"2026-09-07T08:00:00Z"}. Other annotations you will use: @PostMapping, @PathVariable, @RequestParam, @RequestBody, @Valid, @ResponseStatus(HttpStatus.CREATED). Lesson 09 covers API design and errors.

Jackson 3

The JSON library is Jackson. Boot 4 uses Jackson 3, whose packages start with tools.jackson (Jackson 2 used com.fasterxml.jackson). Spring Boot makes a JsonMapper bean you can inject (CoreApplicationIT does). Two details:

  • The annotations such as @JsonInclude still come from com.fasterxml.jackson.annotation (see ProblemBody in platform-starter).
  • Records and Instant work with no setup, and an Instant is written as ISO-8601 text. DomainEventJsonTest proves this with a plain JsonMapper.builder().build().

Actuator

Actuator (spring-boot-starter-actuator) adds operations endpoints under /actuator. core-app shows only two on the web:

management:
  endpoints:
    web:
      exposure:
        include: health, info
  endpoint:
    health:
      show-details: always   # dev and test only: show db, kafka … parts

GET /actuator/health answers {"status":"UP", …}. Docker Compose (T15) and the gateway smoke test use it. Actuator also collects metrics with Micrometer (request counts, JVM memory). They are not exposed on the web yet: T18 adds /actuator/prometheus (lesson 12).

7. Proxies: @Transactional and @Scheduled

What a proxy is

For some annotations, Spring does not give other beans your object directly. It gives a proxy: a wrapper object, like a receptionist in front of an office. Calls go through the receptionist, who does extra work before and after (open a transaction, commit or roll back), then calls the real method.

  Controller ──► [ proxy of OutboxProbeService ] ──► real OutboxProbeService.create()
                   BEGIN transaction                   INSERT …, publishEvent(…)
                   COMMIT, or ROLLBACK on an exception

@Transactional

@Transactional on a method means: everything in it runs in one database transaction (lesson 04). This is how the outbox works: the business row and the event row commit together (lesson 08). Rules to remember:

  • By default Spring rolls back on unchecked exceptions (RuntimeException, so also CampusProblem) and on Error. It commits on a checked exception, unless you set rollbackFor.
  • Private methods are never intercepted. Use public or package-private methods (OutboxProbeService.create is package-private and works).
The self-invocation trap A call from one method to another inside the same object does not go through the proxy. So its @Transactional is silently ignored.

No transaction!

@Service
class EnrollmentService {
    void confirmAll(List<UUID> ids) {
        ids.forEach(this::confirm);  // this = real object
    }
    @Transactional
    void confirm(UUID id) { … }
}

Fixes

  • Put @Transactional on the method that is called from outside (confirmAll).
  • Or move confirm to another bean and inject it.
  • Or use TransactionTemplate in code for full control.

@Scheduled

@Scheduled runs a bean method again and again, on a timer inside the app. It needs @EnableScheduling somewhere (here: OutboxAutoConfiguration).

@Scheduled(
        initialDelayString = "${campus.outbox.retry-interval}",
        fixedDelayString = "${campus.outbox.retry-interval}")   // 30s, or 2s in tests
public void resubmitFailed() {
    failed.resubmit(ResubmissionOptions.defaults());
}

fixedDelay waits the interval after each run ends; fixedRate starts on a fixed beat; cron = "0 0 2 * * *" with zone = "Asia/Ho_Chi_Minh" runs at 02:00 Vietnam time. Careful: with three copies of an app, the job runs in all three. Later modules (for example the planned lost-and-found archive job) must make jobs safe to run twice (lesson 25).

The Clock bean

Time is a dependency too. ClockConfiguration makes one Clock bean (Clock.systemUTC()), every class that needs the time injects it, and tests replace it with a fixed clock (lesson 01).

8. From Boot 3 to Boot 4

Most tutorials online are still for Spring Boot 3. Smart Campus uses Boot 4.1.3 (spec Q1). The differences you will meet in this code base:

AreaBoot 3 tutorials sayBoot 4 / this project
BaseSpring Framework 6Spring Framework 7
JSONJackson 2, com.fasterxml.jackson.databindJackson 3, tools.jackson.databind (annotations unchanged)
Web starterspring-boot-starter-webspring-boot-starter-webmvc
Flyway, Kafkaadd flyway-core / spring-kafkatheir own starters: spring-boot-starter-flyway, spring-boot-starter-kafka
Test sliceseverything in spring-boot-starter-testper-technology test starters, e.g. spring-boot-starter-webmvc-test for @WebMvcTest
Package namesorg.springframework.boot.test.autoconfigure.web.servlet.WebMvcTestorg.springframework.boot.webmvc.test.autoconfigure.WebMvcTest
Settings hookorg.springframework.boot.env.EnvironmentPostProcessororg.springframework.boot.EnvironmentPostProcessor

The main idea behind most changes: Boot 4 split its big auto-configuration jar into smaller modules, one per technology. So a feature often needs its own starter, and some classes moved to new packages. When a tutorial's import does not compile, search the Boot 4 docs or the migration guide for the new name, and check our code for an example first.

10. Common mistakes

  • @Autowired on fields. Use a constructor and final fields.
  • Calling new on a bean class inside production code. You get an object without its dependencies and without its proxy (so no transaction).
  • Self-invocation: calling a @Transactional method from the same class and expecting a transaction.
  • Catching an exception inside a @Transactional method and not rethrowing it. Spring sees no exception, so it commits half the work.
  • Writing passwords in application.yml. Use a placeholder and infra/.env (dev) or environment variables (containers).
  • Copying shared settings into each app. Shared defaults belong in campus-platform-defaults.yml; an app only overrides what is different.
  • Following a Boot 3 tutorial blindly. Check starter names, Jackson packages and test annotations against section 8.

13. Test yourself

1. Why does the project insist on constructor injection?

Fields can be final, so the object is always complete; tests can build the class with new and fakes, without Spring; and a long constructor shows that a class does too much.

2. Why does PlatformDefaultsEnvironmentPostProcessor use addLast?

addLast gives the shared defaults the lowest priority. Every app can still override any value in its own yml, environment or command line, like core-app's test profile does with a 2-second retry interval.

3. How does core-app get problem JSON without any annotation or import?

platform-starter's jar contains an AutoConfiguration.imports file that lists ProblemHandlingAutoConfiguration. Spring Boot reads that file at startup and, because the app is a servlet web app, creates the handler beans.

4. A method calls this.save(x), and save has @Transactional. Why is there no transaction?

The transaction is started by the proxy around the bean. A call through this goes straight to the real object and never passes the proxy, so nothing starts a transaction.

5. Why must OutboxAutoConfiguration run after Modulith's auto-configuration?

It uses @ConditionalOnBean(FailedEventPublications.class). That bean is made by Modulith. If our condition were checked first, the bean would not exist yet, and the retry job would never be created.

6. Why is the Clock a bean and not a static call?

As a bean it can be replaced: production gets the system clock, tests get a fixed one. A static Instant.now() cannot be replaced, so time-based rules cannot be tested reliably.
