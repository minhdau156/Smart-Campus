Load testing with k6

"It works on my machine with one user" says nothing about 08:00 on registration day. A load test sends thousands of fake students at the system and measures what happens. In this lesson you learn to write, run and read the Smart Campus registration rush test, and to check afterwards that no seat was given away twice.

1. Why you need this in Smart Campus

Three Plan requirements point straight at load testing:

IdRequirementHow the test proves it
NFR-1Registration stays up with 5,000 students at once, p95 under 500 msA threshold on the 95th percentile of response time, under a 5,000-student rush
NFR-2Never overbook a section or double-enroll a studentSQL checks on the database after the test
NFR-5Run a load test before every registration windowThe script is repeatable: one command, a clear pass or fail

The Arch adds: "A k6 load test against staging (5,000 virtual users on one section set) gates every release that touches registration." k6 is an open-source load testing tool from Grafana Labs. You write the test in JavaScript; k6 itself is a Go program, so one machine can simulate thousands of users.

A percentile needs a short explanation. "p95 = 480 ms" means: sort all response times; 95% of them are 480 ms or faster, 5% are slower. We use p95, not the average, because an average hides the slow students. If 90 answers take 100 ms and 10 take 4 s, the average looks fine (490 ms) while 1 in 10 students waits four seconds.

2. Kinds of performance tests

KindQuestion it answersShapeIn Smart Campus
SmokeDoes the script work at all?1–2 users, under a minuteRun after every change to the script or the API
LoadDo we meet targets at the expected traffic?Ramp up to normal peak, hold, ramp downNormal registration day traffic
StressWhere does it break, and how?Keep raising the load past the targetFinds the safe admission rate for the waiting room (lesson 20)
Spike (our "rush")Do we survive a sudden jump?From almost 0 to very high in seconds08:00, window opens: this is NFR-1
SoakDoes it slowly get worse?Medium load for hoursMemory leaks, growing Redis keys without TTL

Always start with a smoke test. A load test on a broken script only produces a big report of errors.

3. A first k6 script

A k6 script has three parts: options (how much load, and the pass/fail rules), an export default function (what one user does once: one iteration), and optional setup/teardown functions.

import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE = __ENV.BASE_URL || 'http://localhost:8080';   // the gateway

export const options = {
  vus: 2,                    // 2 virtual users
  duration: '30s',
  thresholds: {
    http_req_failed: ['rate<0.01'],     // under 1% errors
    http_req_duration: ['p(95)<500'],   // p95 under 500 ms: NFR-1's number
  },
};

export default function () {
  const res = http.get(`${BASE}/api/v1/platform/ping`);
  check(res, {
    'status is 200': (r) => r.status === 200,
  });
  sleep(1);                  // "think time": a real user pauses
}

check

Looks at one response and records pass/fail. A failed check does not stop the test or fail it. It shows up as a percentage at the end ("checks: 99.8%").

threshold

A pass/fail rule on a whole metric. If any threshold fails, k6 exits with a non-zero exit code, so a script or CI job can stop the release.

You can also put a threshold on the check rate: checks: ['rate>0.99']. That turns "99% of checks passed" into a real gate.

4. VUs vs arrival rate (and coordinated omission)

A virtual user (VU) is like one simulated person running your function in a loop. There are two ways to describe load:

Closed model: "N users"

Executors constant-vus, ramping-vus, per-vu-iterations. Each VU sends a request, waits for the answer, then continues. If the server slows down, the VUs send fewer requests. The load drops just when the system is in trouble.

Open model: "N arrivals per second"

Executors constant-arrival-rate, ramping-arrival-rate. k6 starts new iterations at a fixed rate, no matter how slow the server is, using free VUs from a pool. This is how real students behave: at 08:00 they arrive whether or not the server is fast.

The closed model has a hidden trap called coordinated omission. Imagine the server freezes for 5 seconds. In the closed model, every VU is stuck waiting, so nobody sends new requests during the freeze. Those 5 seconds produce only a few slow samples instead of hundreds. The p95 looks better than what real students would feel. The open model keeps sending; if no VU is free, k6 counts a dropped_iterations metric, which tells you the test itself could not keep up.

Rule for Smart Campus Use an arrival-rate executor for the rush. Use VU-based executors only for smoke tests or for "everyone presses at exactly 08:00:00" bursts, and read their latencies with care.

5. The registration rush script

Shape of the rush

NFR-1 says 5,000 students "at once"; the Arch says "at the same minute". A useful shape for 5,000 students, each arriving once:

arrivals per second
 250 │      ┌───────────────────┐
     │     /                     \
     │    /                       \
   0 └───/─────────────────────────\────►  time
        0s  5s                 20s  25s

 ramp up   0 → 250/s in 5 s   ≈   625 students
 hold      250/s for 15 s     ≈ 3,750 students
 ramp down 250 → 0/s in 5 s   ≈   625 students
                               = 5,000 students, front-loaded like a real opening

Each iteration is one student: register for one section, then poll the result (202 + polling, decision C8). Because of polling, one student makes several HTTP requests, so the server sees more than 250 requests per second.

Test data: students, tokens and sections

  • Students and tokens. Every request needs a JWT from Keycloak (lesson 16). Getting 5,000 tokens during the test would load-test Keycloak, not registration. So a seed script fetches them before the test and writes data/students.json. Two traps: access tokens live only 5 minutes in our design (Arch §5), so the test realm needs a longer lifetime or the seed must run right before the test; and the client used to get tokens without a browser must exist only in the test realm, never in production.
  • Sections. Seed a known set, for example 20 sections × 100 seats = 2,000 seats for 5,000 students. Many students must get SECTION_FULL. That tests the fast "no" path, which is most traffic on a real rush day.
  • A clean start. Reset the registration tables and Redis keys before each run, so results are comparable.

SharedArray loads a JSON file once and shares it between all VUs, so 5,000 VUs do not each keep their own copy in memory.

import http from 'k6/http';
import { check, sleep } from 'k6';
import { SharedArray } from 'k6/data';
import exec from 'k6/execution';

const BASE = __ENV.BASE_URL || 'http://localhost:8080';
const students = new SharedArray('students', () => JSON.parse(open('./data/students.json')));
const sections = new SharedArray('sections', () => JSON.parse(open('./data/sections.json')));

// 409 SECTION_FULL and 429 are expected answers, not failures.
http.setResponseCallback(http.expectedStatuses(200, 202, 409, 429));

export const options = {
  scenarios: {
    rush: {
      executor: 'ramping-arrival-rate',
      startRate: 0,
      timeUnit: '1s',
      preAllocatedVUs: 500,
      maxVUs: 3000,
      stages: [
        { target: 250, duration: '5s' },
        { target: 250, duration: '15s' },
        { target: 0, duration: '5s' },
      ],
    },
  },
  thresholds: {
    'http_req_duration{name:register}': ['p(95)<500'],   // NFR-1
    'http_req_duration{name:status}': ['p(95)<500'],
    http_req_failed: ['rate<0.001'],                     // 5xx and other unexpected codes
    checks: ['rate>0.999'],
    dropped_iterations: ['count==0'],                     // k6 kept the planned rate
  },
};

export default function () {
  const i = exec.scenario.iterationInTest;               // 0, 1, 2 … unique per student
  const student = students[i % students.length];
  const section = sections[i % sections.length];
  const headers = {
    Authorization: `Bearer ${student.token}`,
    'Content-Type': 'application/json',
    'Idempotency-Key': `${student.id}-${section.id}`,
  };

  const res = http.post(`${BASE}/api/v1/registration/requests`,
      JSON.stringify({ sectionId: section.id }),
      { headers, tags: { name: 'register' } });

  check(res, { 'register answered 202 or 409': (r) => r.status === 202 || r.status === 409 });
  if (res.status !== 202) return;

  const url = `${BASE}/api/v1/registration/requests/${res.json('requestId')}`;
  for (let attempt = 0; attempt < 30; attempt++) {        // at most ~30 s of polling
    sleep(1);
    const s = http.get(url, { headers, tags: { name: 'status' } });
    if (s.json('status') !== 'PENDING') {
      check(s, { 'final status known': (r) => ['CONFIRMED', 'REJECTED'].includes(r.json('status')) });
      return;
    }
  }
  check(null, { 'final status known': () => false });   // still PENDING: counts as a failure
}

Things to notice:

  • tags: { name: … } group requests, so thresholds can target one endpoint (http_req_duration{name:register}). Without a name tag, every status URL (each with a different id) would be its own group.
  • http.expectedStatuses: by default k6 counts every status ≥ 400 as "failed". In a rush, 409 SECTION_FULL is a correct answer.
  • The Idempotency-Key is the same if the same student retries the same section, as a real client would do (Arch §7).
  • "Every request answered": the last check fails if a request stays PENDING too long. Fast 202s with lost results would be a hidden failure.

For an "everyone at exactly 08:00:00" burst, add a second scenario with the per-vu-iterations executor (vus: 5000, iterations: 1). It is closer to the Arch's words "5,000 virtual users", but remember the coordinated-omission caveat.

6. Running it and watching Grafana

k6 in Docker against the Compose stack

You do not need to install k6. Run the official grafana/k6 image with a pinned tag (platform rule: no latest). Attach it to the Compose network, so it can reach the gateway by its service name. Our Compose project is named smart-campus, so the default network is smart-campus_default.

docker run --rm -i `
  --network smart-campus_default `
  -v "${PWD}/load-tests/k6:/scripts" `
  -e BASE_URL=http://gateway:8080 `
  grafana/k6:<pinned-tag> run /scripts/registration-rush.js
Trap: the per-IP rate limit All k6 traffic comes from one IP address. The gateway's per-IP limit (platform R1: 20 requests/s, burst 40) would answer almost everything with 429, and you would be testing the limiter, not registration. The limit is set in config, so the test environment needs a load-test setting (higher limit, or k6 sending traffic past it in a controlled way). Never switch it off in production.

Laptop numbers are not production numbers

On your laptop, k6, Kafka, PostgreSQL, Redis and four Java apps share the same CPU. The Arch runs production on Kubernetes with up to 20 registration replicas. So:

  • On Compose (map assumption 2: "the k6 rush test runs against Compose first"), the test proves correctness (NFR-2) and finds obvious slowness. Use a smaller shape if needed.
  • The real NFR-1 pass/fail number comes from a production-like staging environment, which is part of the later shipping phase.

Watch Grafana during the test

k6 tells you what the users felt. Grafana (http://localhost:3000, observability profile) tells you why. Keep it open during the run:

PanelWhat a problem looks like
Request rate and p95 per route ("Platform overview", T18)p95 climbs while the rate stays flat: something is queueing
5xx rate and 429 rateAny 5xx is a bug; many 429s may mean the limiter is in the way

k6 can also send its own metrics to Prometheus (with a Prometheus remote-write output), so k6 latency and server metrics appear on one Grafana time line. Check the k6 docs for the current option name before you set it up.

7. Reading results and checking correctness

The end-of-test summary

  ✓ register answered 202 or 409
  ✓ final status known

  checks.........................: 100.00% ✓ 7012   ✗ 0
✓ dropped_iterations.............: 0
✓ http_req_duration{name:register}: avg=61ms  med=38ms  p(90)=142ms p(95)=231ms max=1.2s
✓ http_req_duration{name:status}..: avg=12ms  med=9ms   p(90)=21ms  p(95)=30ms  max=410ms
✓ http_req_failed................: 0.00%
  http_reqs......................: 9871   375/s
  iterations.....................: 5000
  vus_max........................: 620

(example numbers for illustration only)

Read it in this order: (1) Did every threshold pass (the ✓ marks)? (2) Is dropped_iterations 0, so the load was really applied? (3) Look at p95 and max: a max of many seconds with a good p95 still deserves a look in Grafana. (4) Are iterations = 5,000? Save the summary (k6's handleSummary function can write it as JSON) so you can compare runs before every window (NFR-5).

The correctness check: the part most teams forget

A fast test that oversold a section is a failed test. After the run, wait until the worker's Kafka lag is 0, then run SQL checks (table names from lesson 20, planned):

-- 1. NFR-2: no section has more normal enrollments than seats
SELECT s.section_id, s.capacity, count(e.id) AS enrolled
  FROM registration.section_seats s
  JOIN registration.enrollments e
    ON e.section_id = s.section_id AND e.status = 'ENROLLED'
 GROUP BY s.section_id, s.capacity
HAVING count(e.id) > s.capacity;

-- 2. NFR-2: no student is enrolled twice in one section
SELECT student_id, section_id, count(*)
  FROM registration.enrollments
 WHERE status = 'ENROLLED'
 GROUP BY student_id, section_id
HAVING count(*) > 1;

-- 3. The counter matches the real rows (no lost update)
SELECT s.section_id, s.enrolled, count(e.id) AS real_count
  FROM registration.section_seats s
  LEFT JOIN registration.enrollments e
    ON e.section_id = s.section_id AND e.status = 'ENROLLED'
 GROUP BY s.section_id, s.enrolled
HAVING s.enrolled <> count(e.id);

Two more checks, done by a small script that also reads Redis and the k6 JSON summary:

  • No lost seats: with 5,000 students and 2,000 seats, every section must end full. A section with free seats while students were told SECTION_FULL means seats leaked in Redis (under-selling is a bug too).
  • Every request answered: number of 202 answers in k6 = number of CONFIRMED + REJECTED results. Redis seats: for each section = capacity − enrolled (drift 0).
Get-Content load-tests/k6/verify-rush.sql | docker compose -f infra/docker-compose.yml exec -T postgres `
  psql -U postgres -d campus -v ON_ERROR_STOP=1

(User and database names come from your infra/.env.)

9. Common mistakes

  • Only looking at the average. Use p95 (and look at max).
  • Using VUs for a rush. Closed-model tests hide slowness (coordinated omission). Use arrival rates.
  • Counting 409 as an error, or counting 500 as fine. Set expectedStatuses carefully.
  • Skipping the correctness check. Speed without NFR-2 is worthless.
  • Getting tokens inside the test. You end up testing Keycloak.
  • Forgetting the per-IP limiter and "proving" that everything returns 429.
  • Running k6 on the same small machine and trusting the absolute numbers. Compare runs with each other; get the real number on staging.
  • No name tags on URLs with ids. Thousands of tiny metric groups, and thresholds that match nothing.
  • Not resetting data. The second run finds every section already full and looks amazingly fast.

  4. On paper: calculate how many students arrive with stages 0→400/s in 10 s, 400/s for 10 s, 400→0 in 10 s. Is that more or less than 5,000?

  5. On paper: write one more SQL check that finds students who were enrolled in two sections with overlapping times (REG-3). Which module's data would you need?

12. Test yourself

1. Why do we measure p95 and not the average response time?

The average hides the slow tail. A few students waiting many seconds barely move the average, but they are exactly the people NFR-1 protects. p95 tells you what almost everyone experiences.

2. Why is an arrival-rate executor better than a fixed number of VUs for the rush?

Real students arrive whether the server is fast or slow. With fixed VUs, a slow server makes VUs wait and send less, so the test reduces the load exactly when it matters and under-reports latency (coordinated omission).

3. All thresholds passed. Why is the test still not finished?

Thresholds measure speed and HTTP errors. NFR-2 is about correctness: you must still check the database for oversold sections, double enrollments and counters that do not match, and check that every accepted request got a final result.

4. Why should tokens be prepared before the test instead of during it?

Logging in 5,000 users during the test puts the load on Keycloak and mixes its latency into our numbers. We want to measure registration. Preparing tokens also keeps the test repeatable.

5. Why must 409 SECTION_FULL be an "expected" status?

With more students than seats, many correct answers are 409. If k6 counted them as failures, http_req_failed would be huge and hide the real problems (5xx, timeouts).

6. Why can a laptop run not prove NFR-1 for production?

On a laptop, k6 and every service share one CPU, and there is one replica of each app. Production has separate machines and up to 20 registration replicas. The laptop run proves correctness and catches big regressions; the official number comes from a production-like environment.
