Security hardening (OWASP)

Smart Campus holds grades, phone numbers, photos and payments for thousands of students. This lesson walks through the most common ways web apps get broken into, shows where each one could happen in Smart Campus, and gives the habit that stops it.

1. The OWASP Top 10, mapped to Smart Campus

OWASP (Open Worldwide Application Security Project) is a non-profit community. Every few years it publishes the Top 10: the ten most important risk categories for web apps, based on real data. The newest edition is the 2025 list. Check owasp.org/Top10 for the exact wording; the short names below follow it.

#Category (2025)Example in Smart CampusSection
A01Broken Access Control (now includes SSRF)A student reads another student's grade by changing the id2
A02Security MisconfigurationKeycloak in start-dev mode in production; Swagger UI open to the world5

Security is not one feature you add at the end. It is a set of small habits in every module. Each section below ends with the habit.

2. Broken access control: IDOR and SSRF

IDOR

Access control is "who may do what to which row". It is number one on the list because it is easy to forget one check. The classic bug is IDOR (insecure direct object reference): the URL contains an id, and the server never checks that the row belongs to the caller.

IDOR

@GetMapping("/api/v1/grade/grades/{id}")
@PreAuthorize("hasRole('STUDENT')")
GradeView get(@PathVariable UUID id) {
    return grades.findById(id)
        .orElseThrow(...);       // any student, any grade
}

Owner in the query

@GetMapping("/api/v1/grade/grades/{id}")
@PreAuthorize("hasRole('STUDENT')")
GradeView get(@PathVariable UUID id, @AuthenticationPrincipal Jwt jwt) {
    UUID me = UUID.fromString(jwt.getSubject());
    return grades.findByIdAndStudent(id, me)
        .orElseThrow(() -> new CampusProblem(ProblemCode.NOT_FOUND,
                "Grade %s not found".formatted(id)));
}

Random UUIDs make ids hard to guess, but that is not access control: ids leak in links, logs and screenshots. Other IDOR spots to check: a club manager editing another club's event, a seller marking someone else's listing as sold, a student closing someone else's lost-item claim, a lecturer exporting a roster for a section they do not teach.

Habit: every endpoint with an id gets a test "other user's id → 404".

SSRF

SSRF (server-side request forgery) happens when our server fetches a URL that a user gave. The attacker gives an internal address, like http://keycloak:8080/admin/… or a cloud metadata address, and our server, which sits inside the private network, fetches it for them. In the 2025 list SSRF is part of A01.

Where could Smart Campus fetch a user's URL? "Import a book photo from a link" in the marketplace, a link preview in announcements, a club's external event page. Best answer: do not build these features; uploads go straight to storage (section 4). If one is ever needed:

  • allow only https and a short allowlist of hosts;
  • resolve the host name and refuse private and loopback IP ranges (10.x, 172.16–31.x, 192.168.x, 127.x, 169.254.x);
  • do not follow redirects, set a short timeout and a size limit.

3. Injection and XSS

SQL injection

Injection means user text is treated as code. With SQL, a search for ' OR '1'='1 could change the meaning of the query. The fix is always the same: bind parameters. The SQL text has ? placeholders, and the values are sent separately, so the database never reads them as SQL.

// BAD: the user's text becomes part of the SQL
jdbc.query("SELECT id, title FROM marketplace.listings WHERE title ILIKE '%" + q + "%'", mapper);

// GOOD: a placeholder, value bound separately
jdbc.query("SELECT id, title FROM marketplace.listings WHERE title ILIKE ?", mapper, "%" + q + "%");

One trap: you cannot bind a column name. Our API convention allows ?sort=createdAt,desc (Arch §7). Never paste that into ORDER BY. Map it through a fixed list:

private static final Map<String, String> SORT_COLUMNS = Map.of(
        "createdAt", "created_at",
        "price", "price_amount");

String column = SORT_COLUMNS.get(sortField);
if (column == null) {
    throw new CampusProblem(ProblemCode.VALIDATION_FAILED, "Cannot sort by " + sortField);
}
String direction = "desc".equalsIgnoreCase(sortDir) ? "DESC" : "ASC";

The same idea applies to OpenSearch queries (lesson 29): build them with the client's query objects, not by joining JSON strings.

XSS in React

XSS (cross-site scripting) is injection into the page: an attacker's text runs as JavaScript in another user's browser, where it can steal tokens or act as that user. React protects you by default: {listing.description} is shown as text, never run as HTML. You lose this protection when you step around React:

Dangerous

<div dangerouslySetInnerHTML={{ __html: listing.description }} />

<a href={club.website}>Website</a>   // "javascript:…" link

Safe

<p style={{ whiteSpace: "pre-line" }}>{listing.description}</p>

<a href={safeHttpUrl(club.website)}>Website</a>
// allow only http: and https: URLs

If an announcement really needs rich text (bold, lists), sanitize the HTML with a well-known library such as DOMPurify before showing it, and still keep a strict Content Security Policy (section 5). Habit: a code review flags every dangerouslySetInnerHTML.

4. File uploads

The marketplace (book photos, MKT-1) and lost & found (item photos, LF-1) accept files. A file from a user is untrusted input that is also large. The Arch (§8) sets the rules: "uploads go straight to storage via pre-signed URLs, size and MIME type checked; images re-encoded". In dev the storage is RustFS (S3-compatible, spec Q6).

5. Configuration, secrets and dependencies

Misconfiguration

Many break-ins use no clever bug, only a setting left in "dev mode". Checks for Smart Campus:

  • Keycloak runs start-dev in Compose. Production uses start with HTTPS, a fixed hostname and a strong admin password, and the admin console is not reachable from the internet.
  • Actuator: today core-app exposes only health and info, and show-details: always is set only in the dev profile. Keep it that way: never expose env or heapdump publicly.
  • Swagger UI and /v3/api-docs: useful in dev; in production, hide them or put them behind login.
  • Errors: rule E1 already makes every error problem JSON with no stack trace (platform T8). That also covers A10: when something unexpected happens, the answer is a clean 500 and the request is refused ("fail closed"), never "let it through".
  • CORS: never * together with credentials (lesson 17).
  • Ports: Compose binds every port to 127.0.0.1, so other machines on your Wi-Fi cannot reach your dev database. Keep that.

Security headers

HTTP response headers can tell the browser to be stricter. Spring Security adds some by default on API responses (for example X-Content-Type-Options: nosniff and cache control). The SPA's HTML is served by Nginx in production (Arch §8), so these go in its config:

HeaderWhat it does
Content-Security-PolicyLists where scripts, styles and API calls may come from. Stops most XSS even if a bug slips in. Start with default-src 'self' and add Keycloak's origin for login.
Strict-Transport-Security"Always use HTTPS for this site." (HSTS)
X-Content-Type-Options: nosniffThe browser must not guess file types (helps with uploads).
frame-ancestors 'none' (in CSP)Our pages cannot be shown inside another site's frame (clickjacking).
Referrer-PolicyLimits how much of our URL is sent to other sites.

Secrets

A secret is anything that gives access: DB passwords, the Keycloak admin password, the payment gateway key, the QR ticket signing key. The spec's "Never" list says: never commit secrets. Today:

  • Compose reads passwords from infra/.env, which is in .gitignore. The template with fake values is infra/.env.example.
  • core-app's dev profile imports ../../infra/.env, so no password is written in application.yml.
  • In production: Kubernetes Secrets or Vault (Arch §8, lesson 31).
If a secret is ever committed Deleting the line is not enough: it stays in git history and in every clone. Change the secret (rotate it) first, then clean up.

Vulnerable dependencies (supply chain)

Most of our running code is not ours: Spring, Kafka clients, React, hundreds of npm packages. A known hole in any of them is our hole. Platform task T20 (spec criterion C1) adds two scanners to CI:

  • OWASP Dependency-Check: compares our Maven and npm libraries with public vulnerability databases (it needs an NVD API key, plan open question 3).
  • Trivy: scans the file system and the 4 app images, including the operating system packages in the base image.

Any HIGH or CRITICAL finding fails the build unless it is in a reviewed suppression file. Adding a suppression is on the spec's "Ask first" list. Other supply chain habits already in the spec: pin every version (no latest, no ranges), commit lock files, use npm ci, and ask before adding a new dependency.

6. Logins, rate limits and webhooks

Authentication failures

Our best defence here: we never handle passwords. Keycloak does (lesson 16). In Keycloak we should turn on its brute-force detection (lock or slow down after many wrong passwords), set a password policy, and require a second factor (OTP) for powerful roles like SYSTEM_ADMIN and ACADEMIC_ADMIN. Short access tokens (5 minutes) limit the damage of a stolen token.

Rate limiting

Rate limiting caps how many requests one caller can send in a time window. It protects against bots, scraping and simple denial of service (map C14):

  • Per IP at the gateway for all /api/v1/** routes: default 20 requests/second with a burst of 40, state in Redis, answer 429 + Retry-After (platform R1, task T14, lesson 11).
  • Per user for registration: keyed by the JWT sub, because thousands of students may share one campus IP (registration module).
  • The waiting room during registration windows (REG-5) also stops bots that try to grab seats.

Webhook signature checks

When a student pays for a club ticket, the payment gateway (VNPay or MoMo) calls our webhook to say "paid". Anyone on the internet can call that URL. If we believe any call, an attacker gets free tickets. The provider signs each call with a shared secret using an HMAC (a hash mixed with a secret key; the provider's docs say which algorithm and which fields). We recompute it and compare:

boolean isValid(String signedData, String receivedHex, byte[] secret) throws GeneralSecurityException {
    Mac mac = Mac.getInstance("HmacSHA512");                  // use the algorithm the provider documents
    mac.init(new SecretKeySpec(secret, "HmacSHA512"));
    byte[] expected = mac.doFinal(signedData.getBytes(StandardCharsets.UTF_8));
    byte[] received = HexFormat.of().parseHex(receivedHex);
    return MessageDigest.isEqual(expected, received);         // constant-time compare
}
  • Constant-time compare (MessageDigest.isEqual): a normal equals stops at the first wrong byte, and the time difference can leak the answer.
  • After the signature, also check the amount and order id against our own database, and make the handler idempotent (the provider retries; lesson 08).
  • Never trust the browser's return URL ("payment success" page) as proof of payment. Only the signed server-to-server call counts. More in lesson 26.

7. Logs and personal data

Logging without personal data

Logs are copied to Loki (platform T17), kept for weeks, and read by many people. So they must help debugging without becoming a leak (A09 covers both sides: log enough to notice attacks, but log safely).

Do not log

Tokens or the Authorization header, passwords, full names, emails, phone numbers, grades, payment card or wallet data, photos, whole request bodies.

Do log

The user id (the UUID sub), traceId, the module, the action, ids of rows, the problem code, and security events: failed logins (Keycloak), 403s, bad webhook signatures, rate-limit hits.

log.info("grade published sectionId={} count={}", sectionId, grades.size());   // ids and counts
// NOT: log.info("published {}", grades)  → would print every student's mark

The audit log (NFR-3: "an audit log of grade and enrollment changes") is a different thing: a table that records who changed what and when, kept on purpose, with access limited to admins. Do not use normal logs as the audit trail.

Personal-data protection

Smart Campus stores personal data of real people, many of them young adults. Vietnam has national rules on personal data protection, and newer, stricter rules have been introduced in recent years. This lesson does not give legal advice: the university's legal or data protection team must say which rules apply and what they require. The engineering habits that support almost any such rules are:

  • Collect only what you need (data minimization). Does the marketplace really need a phone number, or is in-app messaging enough?
  • Use data only for the stated purpose. Grades are for the student and their lecturers, not for the search index.
  • Ask and record consent where needed, for example before showing a phone number to buyers (AUTH-2).
  • Let people see and correct their data, and delete what is no longer needed (the lost & found 60-day archive job, LF module, is an example of a retention rule).
  • Protect it: access control, encryption in transit (HTTPS) and at rest, and backups that are protected too.
  • Be ready to react to a breach: know who to tell, and how fast. Logs and traces must make it possible to find what was accessed.
  • Know where data is stored: choosing a cloud region is a legal question as well as a technical one (lesson 31).

8. Light threat modeling with STRIDE

Threat modeling means asking "what can go wrong?" before building. It finds design flaws (A06, Insecure Design) that no scanner can find. You do not need a big process. Draw the flow of one feature, then for each arrow ask the six STRIDE questions:

SSpoofingCan someone pretend to be another user?A bot registers for a friendKeycloak login, JWT sub as the student id, never a body field

RRepudiationCan someone deny they did it?"I never dropped that course"Audit log with user id, time, traceId (NFR-3)
IInformation disclosureCan someone see what they should not?See other students' enrollmentsOwnership checks; 404 for others' rows

Habit for Smart Campus: every SPEC-<module>.md gets a short "Threats" table like this one for its riskiest flow (payment webhook, grade entry, QR scan, uploads). Ten minutes in the spec saves a week of fixes later.

10. Common mistakes

  • Checking the role but not the owner (IDOR).
  • Building SQL with +, or pasting a sort field into ORDER BY.
  • Using dangerouslySetInnerHTML on user text.
  • Trusting the file name or Content-Type of an upload.
  • Committing .env, or "fixing" a leaked secret without rotating it.
  • Suppressing a scanner finding to make CI green without a review.
  • Comparing signatures with equals instead of a constant-time compare.
  • Logging whole objects (they may hold grades, phones or tokens).
  • Leaving dev settings in production: start-dev, open Swagger, detailed health.

13. Test yourself

1. Our ids are random UUIDs. Why do we still need ownership checks?

Hard to guess is not the same as forbidden. Ids appear in links, logs, screenshots and shared URLs. Only a server-side check that the row belongs to the caller is access control.

2. Why does binding parameters stop SQL injection, and why does it not help with ORDER BY?

Bound values are sent apart from the SQL text, so they can never change the query's structure. But placeholders can only stand for values, not for column names, so sort fields must be mapped through an allowlist.

3. Why do uploads go straight to storage with a pre-signed URL, and why re-encode images?

Our services never carry large untrusted bytes, and the URL only allows one object, one size and a short time. Re-encoding throws away anything that is not a real image, including hidden scripts and location metadata.

4. Why must the payment webhook check a signature, and why compare in constant time?

Anyone can call the webhook URL; the signature proves it came from the provider and was not changed. A normal compare stops early on the first difference, and that timing can help an attacker guess a valid signature.

5. Why log the user's UUID but not their name or email?

The UUID is enough to investigate (it links to the profile for people allowed to see it), while names, emails and grades in logs would spread personal data to every log reader and backup.

6. Scanners and tests exist. Why also do threat modeling?

Scanners find known bugs in code and libraries. They cannot find a design that is wrong, like a refund flow with no limit or a registration API with no plan against bots. Only thinking about the design finds those.
