1. Why you need this in Smart Campus

Smart Campus has 14 modules. Ten of them (identity, course, timetable, grade, announcement, payment, club, marketplace, lostfound, search) plus shell and platform live in one Spring Boot app: core-app. If any class could call any other class, after a few months nobody could change grade without breaking club.

So we draw walls inside the app. Each module has a small public part and a large private part. Spring Modulith is a Spring library that knows where the walls are and fails the build when code climbs over one. You will meet this every time you add a class to core-app.

2. Monolith, microservices, modular monolith

There are three common ways to cut a backend:

StyleWhat it isGoodHard
MonolithOne app, one deploy, no inside walls Simple to run and debugGrows into a tangle; every change can break anything
MicroservicesMany small apps, each with its own deploy and database Each part scales and ships aloneNetwork calls everywhere, many moving parts, hard for one small team
Modular monolithOne app, but split inside into modules with checked walls Simple to run, clean boundariesAll modules scale together

An everyday picture: a monolith is one big open-plan office. Microservices are separate buildings across the city. A modular monolith is one building with locked rooms and a reception desk at each door.

Smart Campus mixes them (Arch ADR-1) A modular monolith (core-app) plus two extracted services: registration-service (it must survive 5,000 students clicking at the same minute, so it scales alone) and notification-service (WebSocket, push and email have a different load shape). One team, fewer moving parts, and only the two parts that really need it pay the price of a separate service.
gateway :8080one entry point
→
core-app :8081platform, identity, shell, course, timetable, grade, announcement, payment, club, marketplace, lostfound, search
registration-service :8082the registration rush
notification-service :8083inbox, WebSocket, push, email

Because the walls inside core-app are real, a module could later be moved out into its own service with much less pain. That is a nice side effect, not a plan.

3. A module is a top-level package

Spring Modulith looks at the package of the main class (edu.campus, from CoreApplication). Every package directly below it is one application module:

backend/core-app/src/main/java/edu/campus/
├── CoreApplication.java          ← the root package: edu.campus
├── platform/                     ← module "platform"  (exists, T6)
│   ├── package-info.java         ← @ApplicationModule(displayName = "Platform")
│   ├── PingController.java       ← API part (root package of the module)
│   ├── ModuleApiGroups.java
│   └── internal/                 ← private to platform
│       └── OutboxProbeService.java …
├── course/                       ← module "course"    (planned, module 4)
│   ├── SectionLookup.java        ← API: other modules may use it
│   └── internal/ …               ← private
└── grade/                        ← module "grade"     (planned, module 7)

The project rule (spec, "Conventions"): one Modulith module = one top-level package, and the package name is the module id. The same id is used for the database schema (course), the API prefix (/api/v1/course) and the OpenAPI group. One name everywhere makes it easy to find things.

@ApplicationModule(displayName = "Platform")
package edu.campus.platform;

import org.springframework.modulith.ApplicationModule;

A package-info.java is a special Java file that holds annotations and Javadoc for a whole package. @ApplicationModule is optional (the package is a module anyway), but it is the natural place for the module's display name and its rules.

4. Public API and internal packages

Inside a module there are two kinds of classes:

  • The API: public types in the module's root package (edu.campus.course). Other modules may use them.
  • Internals: everything in sub-packages (edu.campus.course.internal, …internal.jdbc). Only the module itself may use them.
Modulith's rule, and our naming rule By default, Modulith treats every sub-package of a module as hidden, whatever its name. Smart Campus adds a naming convention on top: put private code in a sub-package called internal, so a reader sees at once that it is private. Our own ArchUnit rule (InternalPackageRule) checks exactly that name.

Reaching inside

package edu.campus.grade.internal;

import edu.campus.course.internal.SectionRepository; // ✗

class GradeService {
    // reads course's tables through its repository
}

Using the door

package edu.campus.grade.internal;

import edu.campus.course.SectionLookup;  // ✓ API

class GradeService {
    // asks course a question through its API
}

Named interfaces

Sometimes a module wants to share more than its root package, for example a package of event payload records. A named interface opens one sub-package on purpose:

// edu/campus/course/events/package-info.java
@org.springframework.modulith.NamedInterface("events")
package edu.campus.course.events;

Now other modules may use edu.campus.course.events, but still not edu.campus.course.internal. Use this rarely: every opened door is a promise you must keep.

The database follows the same walls

Each module owns one PostgreSQL schema (lesson 04). Its Flyway migrations live in db/migration/<schema>/ and touch only that schema. There are no foreign keys across schemas (map C4). If grade needs a section id, it stores a bare UUID and keeps its own small copy of the facts it needs.

5. How our modules are found

Modulith's default rule is "every direct sub-package of the main class's package". In T6 this caused a surprise: shared-kernel's classes live in edu.campus.kernel, and platform-starter's in edu.campus.starter. Both are below edu.campus, so Modulith thought they were modules. Then platform using edu.campus.kernel.event.Topics looked like a module reaching into another module's sub-package, and verify() failed.

The fix is a small detection strategy in platform-starter:

public class CampusModuleDetection implements ApplicationModuleDetectionStrategy {

    static final Set<String> LIBRARIES = Set.of("edu.campus.kernel", "edu.campus.starter");

    private final ApplicationModuleDetectionStrategy defaults =
            ApplicationModuleDetectionStrategy.directSubPackage();

    @Override
    public Stream<JavaPackage> getModuleBasePackages(JavaPackage rootPackage) {
        return defaults.getModuleBasePackages(rootPackage)
                .filter(pkg -> !LIBRARIES.contains(pkg.getName()));  // libraries, not modules
    }
}

It reuses the default rule and only removes the two libraries. A new package such as edu.campus.grade still becomes a module automatically, so nothing can slip past the checks. The strategy is registered in the starter's META-INF/spring.factories, so core-app needs no setting at all (T8.6).

6. verify(): the build checks the walls

class ModularityTest {

    private final ApplicationModules modules = ApplicationModules.of(CoreApplication.class);

    @Test
    void modulesFollowTheRules() {
        modules.verify();      // throws Violations if any rule is broken
    }
}

ApplicationModules.of(…) reads the compiled classes (it uses ArchUnit under the hood; no Spring context, no Docker, so it is fast). verify() then checks:

  • No access to another module's internals.
  • No cycles between modules (A uses B and B uses A). The map already removed one planned cycle: course does not consume registration events (C17).
  • Allowed dependencies, if a module lists them with @ApplicationModule(allowedDependencies = …).

Proving the check works (spec P3)

A test that always passes proves nothing. So T6 keeps a fixture in the test sources that is wrong on purpose:

backend/core-app/src/test/java/fixture/boundary/
├── alpha/AlphaService.java       uses beta.BetaApi (allowed) AND beta.internal.BetaSecret (NOT allowed)
└── beta/
    ├── BetaApi.java              beta's public API
    └── internal/BetaSecret.java  beta's private class
@Test
void modulithVerifyFailsWhenAModuleUsesAnotherModulesInternalPackage() {
    ApplicationModules fixtureModules = ApplicationModules.of(FIXTURE, INCLUDE_TEST_CLASSES);

    assertThatThrownBy(fixtureModules::verify)
            .isInstanceOf(Violations.class)
            .hasMessageContaining("BetaSecret");
}

The same test file also runs our InternalPackageRule (plain ArchUnit) against the fixture and against the real app. Two independent checks for the same wall: if one tool changes behavior in a new version, the other still catches the problem. More about ArchUnit in lesson 10.

7. How modules talk to each other

There are two allowed doors (Arch §4):

DoorUse it forExample (planned)
Public Java API (a direct method call) Asking a question right now grade asks course "does section X exist?"
An event on Kafka Saying "this happened", so others can react later course publishes SectionChanged; timetable updates its read model

Events inside one module vs across modules (spec D5)

Spring Modulith has a handy annotation for listening to events in the same app:

package edu.campus.club.internal;

@Component
class TicketStatsUpdater {

    @ApplicationModuleListener              // club listens to a club event: OK
    void on(DomainEvent<TicketIssued> event) { … }
}

@ApplicationModuleListener is a short form of three things: run after the sender's transaction commits, run asynchronously (on another thread), and run in a new transaction.

Smart Campus rule D5 An in-process listener (@ApplicationModuleListener, @EventListener, @TransactionalEventListener) may only handle events of its own module. Events from another module are always read from Kafka, even when both modules run inside core-app. Only Kafka keeps the history, so only Kafka lets a read model be replayed. An ArchUnit rule (T12.3, planned) fails the build otherwise. The full story is in lesson 08.

Publishing stays the same in every module: call ApplicationEventPublisher.publishEvent(new DomainEvent<>(…)) inside the business transaction. Modulith's event registry (the outbox) stores it and sends it to Kafka after the commit.

8. Module tests and the Documenter

Testing one module alone

A full @SpringBootTest starts every module. Modulith offers @ApplicationModuleTest: put it on a test class inside a module's package, and it starts only that module's beans (by default). If the module needs a bean from another module, the test fails, which tells you about a hidden dependency.

package edu.campus.course;

@ApplicationModuleTest                     // boots only the "course" module
@Import(TestcontainersConfiguration.class)
class CourseModuleIT {

    @Autowired SectionLookup sections;

    @Test
    void findsASectionById() { … }
}

Other bootstrap modes exist (for example, also start the direct dependencies). Modulith's test library also has a Scenario helper to check "when I do X, event Y is published". No module uses these yet; platform has full-app tests only.

Drawing the map: the Documenter

Modulith can write diagrams of the modules and their dependencies:

class ModuleDocsTest {
    @Test
    void writeModuleDocs() {
        new Documenter(ApplicationModules.of(CoreApplication.class))
                .writeDocumentation();          // diagrams + one "canvas" page per module
    }
}

The files go into a folder under target/ (PlantUML diagrams and an overview page per module). Because they come from the real code, they are never out of date. The Documenter lives in Modulith's docs library; check that it is on the test classpath before you add this test. Nice for a README or a review once several modules exist.

One OpenAPI group per module (T9)

The module list is also used for API docs. ModuleApiGroups asks Modulith for the modules and makes one springdoc group per module, so course will get /v3/api-docs/course with no code change:

public static List<GroupedOpenApi> groupsFor(ApplicationModules modules) {
    return modules.stream()
            .map(ModuleApiGroups::groupFor)        // group = module id, packages = module package
            .sorted(Comparator.comparing(GroupedOpenApi::getGroup))
            .toList();
}

Details in lesson 09.

10. Common mistakes

  • Making a class public in internal "just to use it" from another module. Java public does not open a Modulith wall. Add a method to the module's API instead.
  • Putting shared helpers in a module. If every module needs it and it has no Spring code, it belongs in shared-kernel (ids, money, time, events, errors).
  • Listening in-process to another module's event. It works today and breaks replay forever. Read it from Kafka (D5).
  • Joining across schemas in SQL ("just for a report"). Use the other module's API or build a read model from events.
  • "Fixing" the boundary fixture. AlphaService is wrong on purpose. If you fix it, the test that proves P3 stops proving anything.
  • Creating a module by accident. A new package directly under edu.campus is a new module, with its own walls and its own API group.

11. Practice

  1. Run only the architecture tests (fast, no Docker):

    .\mvnw.cmd -pl backend/core-app -am test "-Dtest=ModularityTest,BoundaryViolationTest" "-Dsurefire.failIfNoSpecifiedTests=false"

  2. Break a wall on purpose (this is what T6 did once by hand):

    • add a public class Secret in backend/core-app/src/main/java/edu/campus/platform/internal/;
    • add backend/core-app/src/main/java/edu/campus/demo/Demo.java that calls new edu.campus.platform.internal.Secret().

    It compiles (Java is happy), but run step 1 again and read the Violations message. Then delete both new files.

  3. Read ModularityTest: why are there tests that say kernel and starter are not modules? What would break without CampusModuleDetection?

  4. Start core-app (see lesson 03) and open http://localhost:8081/swagger-ui.html. Find the group selector. How many groups are there today, and why?

  5. On paper: design the packages for the planned course module. What goes in edu.campus.course (API) and what in edu.campus.course.internal? Which of its facts should other modules learn by API call, and which by event?

13. Test yourself

1. Why did Smart Campus not choose full microservices for every module?

One team would have to run and debug 14 networked apps. Most modules have the same small load. Only registration (huge rush) and notification (different delivery work) need to scale alone, so only those two are separate (ADR-1).

2. Why is a Java public class in course.internal still not usable by grade?

Java visibility and module walls are different things. Modulith decides by package: types in a module's sub-packages are internal, whatever their Java modifier. verify() fails if another module uses them.

3. What problem does CampusModuleDetection solve?

The shared libraries live in edu.campus.kernel and edu.campus.starter, so the default rule saw them as modules, and using kernel.event.Topics looked like a violation. The strategy removes those two packages from the module list but keeps the default rule for everything else.

4. Why keep a fixture that is wrong on purpose?

To prove the check really fails on a violation (P3). Without it, a misconfigured verify() could pass forever and nobody would notice.

5. timetable and course both run in core-app. Why may timetable not use @ApplicationModuleListener for SectionChanged?

An in-process listener cannot be replayed. timetable is a read model that must be rebuildable from history, which only Kafka keeps. Also, one delivery path for all cross-module events is simpler (D5).

6. Why is it useful that OpenAPI groups come from the Modulith module list?

A new module gets its API docs group automatically, and the groups always match the real modules that verify() checks. Nobody has to remember to add a group by hand.
