Payments, webhooks and idempotency

A student pays 50 000 VND for a club event ticket. Money moves in a system we do not control, messages arrive late, twice, or are faked. This lesson shows how to take payments so that nobody pays without a ticket, and nobody gets a ticket without paying.

1. Why you need this in Smart Campus

CLUB-4 says a student gets a free or paid ticket. CLUB-7 says they can cancel and get a refund before the deadline. The Architecture says a payment gateway (for example VNPay or MoMo) confirms payment with a webhook, and club consumes PaymentConfirmed. But no module produced that event. Resolution C7 created a new module for it: payment ★ (module 10, in core-app, schema payment). It publishes PaymentConfirmed and PaymentRefunded.

clubstudent wants a paid ticket
→
paymentcreates a payment, redirects to the gateway, verifies the webhook
→
KafkaPaymentConfirmed
→
clubissues the QR ticket (lesson 27)

Assumption 4: external systems are stubbed. In dev we use the provider's sandbox (a test copy of their system with fake money) or a mock webhook (section 8).

2. The redirect flow

We never see card or bank details. The student types them on the gateway's own page. Our job is to send them there with the right order, and to learn the result. Most Vietnamese gateways work like this (names of fields differ, so always follow the provider's official docs):

Browser            Smart Campus (payment)             Payment gateway
   │ POST /api/v1/payment/payments ──►│
   │   (Idempotency-Key: …)           │ save payment PENDING
   │◄── 201 { redirectUrl } ──────────│ build URL: order ref, amount,
   │                                  │ return URL, expiry, + signature
   │ ── browser goes to redirectUrl ──────────────────────────────►│
   │                                  │          student pays      │
   │                                  │◄── IPN / webhook (server to server, signed)
   │                                  │ verify, mark PAID, outbox event
   │                                  │── "received" answer ───────►│
   │◄── browser sent back to return URL (signed query string) ─────│
   │ GET /api/v1/payment/payments/{id} → "PAID"
  1. Our backend saves a payments row with status PENDING and a unique order reference (the id the gateway will send back to us).
  2. It builds the gateway URL with the amount, the order reference, a return URL and an expiry time, and signs it with a secret key shared only with the gateway.
  3. The browser goes to the gateway. The student pays there.
  4. The gateway calls our webhook (VNPay calls it IPN: Instant Payment Notification) directly from its servers, and also sends the browser back to our return URL.

Return URL vs webhook (IPN)

Return URL (browser comes back)

Travels through the student's browser. The student can edit it, bookmark it, or never arrive (closed the tab, phone battery died, network lost). Use it only to show a nice "checking your payment…" page.

Webhook / IPN (server to server)

The gateway's server calls our server. It is signed, and gateways retry it if we do not answer. This is the only message that may change a payment to PAID.

An analogy: the return URL is the customer saying "I paid, look at my phone screen". The webhook is the bank calling the shop directly. You give the goods based on the bank's call.

So the return page does not trust its query string. It polls our own API, GET /api/v1/payment/payments/{id}, until the status is final, and shows the result.

3. Checking the signature

Anyone on the internet can send a POST to our webhook URL. To know the message really comes from the gateway, gateways sign it with an HMAC: a hash of the message mixed with a secret key that only we and the gateway know. Without the key, nobody can make a valid signature, and changing one character of the message breaks it.

The general steps (the exact field list, order and hash, for example HMAC-SHA256 or HMAC-SHA512, come from the provider's docs):

  1. Take the fields the provider lists, in the exact order and format they describe.
  2. Compute the HMAC with our secret.
  3. Compare it with the signature in the message using a constant-time compare.
package edu.campus.payment.internal.gateway;

final class SignatureVerifier {
    private final SecretKeySpec key;
    private final String algorithm;                     // e.g. "HmacSHA512", from the provider's docs

    SignatureVerifier(byte[] secret, String algorithm) {
        this.key = new SecretKeySpec(secret, algorithm);
        this.algorithm = algorithm;
    }

    boolean isValid(String signedData, String receivedHex) {
        byte[] expected = hmac(signedData);
        byte[] received;
        try {
            received = HexFormat.of().parseHex(receivedHex.toLowerCase(Locale.ROOT));
        } catch (IllegalArgumentException notHex) {
            return false;
        }
        return MessageDigest.isEqual(expected, received);   // constant time
    }

    private byte[] hmac(String data) {
        try {
            Mac mac = Mac.getInstance(algorithm);
            mac.init(key);
            return mac.doFinal(data.getBytes(StandardCharsets.UTF_8));
        } catch (GeneralSecurityException e) {
            throw new IllegalStateException("HMAC not available", e);
        }
    }
}
Why constant time? String.equals stops at the first different character. An attacker who measures the answer time very precisely can guess the signature one character at a time (a timing attack). MessageDigest.isEqual takes the same time whatever the input.

A valid signature is not the end. After it, also check:

  • the order reference exists in our payments table,
  • the amount equals what we saved (never trust an amount from the message alone),
  • the result code really means "success" (gateways send webhooks for failures too).

Then answer the gateway in the format its docs require. If we do not answer correctly, it will retry, which is fine because we are idempotent (section 5).

4. The payment state machine

A state machine is a list of states and the only moves allowed between them. Writing it down stops impossible changes like "REFUNDED → PAID".

                ┌──► PAID ──► REFUND_PENDING ──► REFUNDED
   PENDING ─────┼──► FAILED          (gateway confirms the refund)
                └──► EXPIRED   (nobody paid before the deadline)
enum PaymentStatus {
    PENDING, PAID, FAILED, EXPIRED, REFUND_PENDING, REFUNDED;

    boolean canMoveTo(PaymentStatus next) {
        return switch (this) {
            case PENDING -> next == PAID || next == FAILED || next == EXPIRED;
            case PAID -> next == REFUND_PENDING;
            case REFUND_PENDING -> next == REFUNDED || next == PAID;   // refund rejected
            case FAILED, EXPIRED, REFUNDED -> false;                   // final states
        };
    }
}

In SQL, make each move a conditional update, so two threads cannot both "win":

UPDATE payment.payments
SET status = 'PAID', paid_at = :now, provider_txn_ref = :txnRef
WHERE id = :id AND status = 'PENDING';        -- 1 row = we moved it; 0 rows = already final

A hard case: paid after it expired

Our payment expires after 15 minutes, but a slow bank confirms at minute 16. The money is gone from the student's account. Do not ignore it. Record it (for example status PAID with a "late" flag, or a separate state the spec defines), then either give the ticket if seats remain or start a refund automatically. Decide this in SPEC-payment.md and SPEC-club.md.

5. Webhooks that arrive many times

Gateways retry webhooks until they get the "received" answer. Network problems can also deliver the same webhook twice. Exactly like Kafka events (lesson 08), the handler must be idempotent:

CREATE TABLE payment.payments (
    id               UUID PRIMARY KEY,
    order_ref        TEXT NOT NULL UNIQUE,        -- what we send to the gateway
    payer_id         UUID NOT NULL,
    purpose_type     TEXT NOT NULL,               -- e.g. CLUB_TICKET
    purpose_id       UUID NOT NULL,               -- e.g. the ticket reservation id (bare UUID)
    amount           NUMERIC(19, 0) NOT NULL,     -- VND has no decimals
    currency         CHAR(3) NOT NULL,
    status           TEXT NOT NULL,
    provider         TEXT NOT NULL,               -- VNPAY, MOMO, MOCK
    provider_txn_ref TEXT,
    expires_at       TIMESTAMPTZ NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL,
    paid_at          TIMESTAMPTZ,
    UNIQUE (provider, provider_txn_ref)           -- one gateway transaction, one payment
);
@Transactional
WebhookAnswer handle(GatewayNotice notice) {
    if (!verifier.isValid(notice.signedData(), notice.signature())) {
        return WebhookAnswer.badSignature();                // log the order ref, never the secret
    }
    Payment p = payments.findByOrderRef(notice.orderRef()).orElse(null);
    if (p == null) return WebhookAnswer.unknownOrder();
    if (!p.amount().equals(notice.amount())) return WebhookAnswer.wrongAmount();

    if (notice.success() && payments.markPaid(p.id(), notice.txnRef(), clock.instant())) {
        events.publishEvent(PaymentEvents.confirmed(p, clock.instant()));   // outbox, same tx
    } else if (!notice.success()) {
        payments.markFailed(p.id(), clock.instant());       // WHERE status = 'PENDING'
    }
    return WebhookAnswer.received();                        // also for a repeat: "yes, we have it"
}

markPaid returns true only when the conditional update changed one row. A second copy changes zero rows, so no second event is published. And because the event goes through the outbox, it is sent if and only if the payment became PAID.

6. Money in VND

Never use double for money: 0.1 + 0.2 is not exactly 0.3 in binary. Our shared-kernel already has a Money record built on BigDecimal:

public record Money(BigDecimal amount, Currency currency) {
    public Money {
        …
        int decimals = currency.getDefaultFractionDigits();      // VND → 0, USD → 2
        amount = amount.setScale(decimals, RoundingMode.UNNECESSARY);  // throws if too many decimals
    }
    public static Money of(String amount, String currencyCode) { … }
}
  • VND has no minor unit. There is no "0.5 đồng". Money.of("50000.5", "VND") throws instead of rounding: a hidden rounding in money code is a bug.
  • Is Money.of("50000", "VND") equal to Money.of("50000.0", "VND")? Yes. The text "50000.0" is written with one decimal, but its value is whole, so setScale(0, UNNECESSARY) works and both become 50000. Read MoneyTest.java to see the exact rules.
  • Some gateways want the amount in a special form (for example a whole number, sometimes multiplied by a factor). Do this conversion in one adapter method per provider, with a unit test, never spread around the code.
  • In SQL, store NUMERIC plus the currency code, never a float.

7. Idempotency-Key, events, refunds, reconciliation

Our own POST needs an Idempotency-Key

The Architecture's API conventions say: an Idempotency-Key header is required on POSTs that create enrollments, tickets or payments. The student double-clicks "Pay", or the network drops the answer and the browser retries. Without a key we would create two payments.

CREATE TABLE payment.idempotency_keys (
    user_id       UUID NOT NULL,
    idem_key      TEXT NOT NULL,                 -- a UUID the browser makes once per click
    request_hash  TEXT NOT NULL,                 -- hash of the request body
    payment_id    UUID NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (user_id, idem_key)
);
  • Same key, same body → return the same payment again (same status code, same body). No new row.
  • Same key, different body → reject with problem JSON (for example 409 or 422, decided in the spec). The client reused a key by mistake.
  • Key missing → 400 problem JSON.

Events

PaymentConfirmed and PaymentRefunded are published with publishEvent (the outbox, spec D1). club consumes them from Kafka with the processed_events dedupe (D2), even though both modules run in core-app (D5). The payload carries ids and facts: payment id, purpose type and id, payer id, amount. Which topic and key they use is decided in SPEC-payment.md (the existing campus.events topic is keyed by aggregateId).

Refunds (CLUB-7)

  1. club checks its own rule: is it before the cancellation deadline? Is the ticket unused?
  2. club cancels the ticket and asks payment for a refund, through payment's public API (club depends on payment, so it may call it).
  3. payment moves PAID → REFUND_PENDING and calls the gateway's refund API. Refunds can take time and can fail, so this is a state, not one call.
  4. When the gateway confirms, REFUND_PENDING → REFUNDED and PaymentRefunded goes out through the outbox. Notification tells the student.

Reconciliation job

What if the webhook never arrives (our server was down for an hour, and the gateway gave up)? A scheduled reconciliation job asks the gateway directly about every payment that is still PENDING after some minutes, using the provider's "query transaction" API, and applies the answer through the same idempotent code as the webhook. It also moves old unpaid payments to EXPIRED. Run it with the patterns from lesson 25 (SKIP LOCKED, chunks, a time zone). A daily check of our totals against the provider's report is also common in real shops.

8. The mock webhook and secrets

A real sandbox must call our webhook from the internet, but in dev our app is on localhost, which the gateway cannot reach. So for most dev work we use a mock gateway (assumption 4): a dev-only page and endpoint that pretend to be the gateway. The important trick: the mock signs its webhook with the dev secret and calls the real webhook endpoint. So the signature check, the amount check and the idempotency code all run in dev and in tests.

@RestController
@Profile("dev")
@RequestMapping("/api/v1/payment/dev/mock-gateway")
class MockGatewayController {
    private final MockGateway mock;

    MockGatewayController(MockGateway mock) {
        this.mock = mock;
    }

    @PostMapping("/{orderRef}/pay")          // "student clicks Pay" on the fake page
    void pay(@PathVariable String orderRef, @RequestParam boolean success) {
        mock.sendSignedWebhook(orderRef, success);   // builds + signs a notice, POSTs to our webhook
    }
}

Integration tests (lesson 10) do the same with a fixed clock: send the webhook twice, send one with a wrong signature, send one with a wrong amount.

Never log secrets

  • The gateway secret comes from environment variables or a secret store, never from Git (infra/.env is gitignored for this reason).
  • Do not log full webhook bodies or URLs with signatures. Log the order reference, the result and "signature valid: yes/no".
  • The webhook endpoint has no JWT (the gateway has no user), so it is public at the gateway. The HMAC is its only proof. Keep it behind the per-IP rate limit (lesson 11).

10. Common mistakes

  • Marking PAID from the return URL. The browser can lie or never come back.
  • Comparing signatures with equals. Use MessageDigest.isEqual.
  • Trusting the amount in the webhook. Compare it with the amount you saved.
  • Publishing PaymentConfirmed on every webhook copy. Publish only when the conditional update changed a row.
  • Using double or float for money. Use Money and NUMERIC.
  • Calling the gateway inside a long database transaction. A slow network call holds locks. Save first, call outside the transaction, then save the result.
  • Ignoring payments that never got a webhook. Add a reconciliation job.
  • Committing the secret key or printing it in logs.

11. Practice

  1. Read Money.java and MoneyTest.java in backend/shared-kernel. Write down what Money.of("1000.5", "VND") does and why. Run the tests:

    .\mvnw.cmd -pl backend/shared-kernel test

  2. In a scratch Java file (JShell works: run jshell), compute an HMAC-SHA256 of the text "orderRef=A1&amount=50000" with the key "dev-secret", and print it as hex with HexFormat.of().formatHex(...). Change one character and see the whole result change.

  3. Draw the state machine on paper and add the "paid after expired" case. Which events go out, and what does the student see?

  4. Write the test list (names only) for the webhook handler: valid, repeated, bad signature, unknown order, wrong amount, failure code, late payment.

  5. Open the official developer docs of one Vietnamese gateway (VNPay or MoMo). Find: the hash algorithm, the list of signed fields, the IPN answer format, and the sandbox URL. Do not copy secrets anywhere.

13. Test yourself

1. Why must only the webhook, not the return URL, mark a payment as PAID?

The return URL goes through the student's browser, which can be edited or may never come back. The webhook comes from the gateway's server, is signed, and is retried until we answer.

2. The signature is valid. Why still compare the amount?

A valid signature proves the gateway sent the message, not that it matches our order. A bug or a tricked flow could report a smaller amount for our order reference. We give goods only for the amount we asked for.

3. The same webhook arrives three times. Why is only one PaymentConfirmed published?

The update is conditional (WHERE status = 'PENDING'). Only the first copy changes a row, and the event is published only in that case, in the same transaction (outbox).

4. Why does Money.of("1000.5", "VND") throw instead of rounding?

VND has no decimals, so the value is wrong input. Silent rounding would hide a bug and could move real money in a way nobody notices.

5. Why does the mock gateway sign its webhook and call the real endpoint?

So the real verification, amount check and idempotency code run in dev and tests. A mock that skipped them would test nothing important.

6. Why do we need a reconciliation job if we already have webhooks?

Webhooks can be lost: our server may be down longer than the gateway retries. The job asks the gateway about stuck PENDING payments so no paid student is left without a ticket.
