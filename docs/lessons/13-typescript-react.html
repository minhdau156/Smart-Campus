2. TypeScript basics and strict mode

TypeScript (TS) is JavaScript plus types. A type says what shape a value has. The TypeScript compiler checks your code before it runs, then removes the types. The browser only ever sees plain JavaScript. A good picture: types are a spell checker for your data.

let credits: number = 3;
const code: string = "CS101";
let isOpen: boolean = true;
const tags: string[] = ["core", "year-1"];

function totalCredits(sections: { credits: number }[]): number {
  return sections.reduce((sum, s) => sum + s.credits, 0);
}

totalCredits([{ credits: 3 }, { credits: "4" }]);
//                                ^^^ error: string is not assignable to number

Often you do not write the type: TS infers it. const code = "CS101" already has type "CS101". Write types on function parameters and on exported things; let TS infer the rest.

interface or type?

Both give a name to an object shape:

interface Section {
  id: string;
  code: string;
  capacity: number;
  room?: string;          // ? = optional: string or undefined
  readonly createdAt: string;
}

type SectionId = string;                      // type can name ANY type…
type SeatStatus = "OPEN" | "FULL" | "CLOSED"; // …including a union (next section)
interfacetype
Object shapesYesYes
Unions, tuples, primitivesNoYes
Extendinterface A extends Btype A = B & { … }

A simple rule: use type by default (it can do everything you need here), and use interface when you want to say "this is an object contract". Be consistent inside one module. Most of our API types will be generated anyway (lesson 14).

Strict mode

The spec rule is strict: true in tsconfig.json and no any. Strict mode turns on many checks. The most important one is strictNullChecks: null and undefined are not hidden inside every type.

function roomLabel(s: Section): string {
  return s.room.toUpperCase();
  //     ^^^^^^ error: 's.room' is possibly 'undefined'
}

function roomLabelFixed(s: Section): string {
  return s.room?.toUpperCase() ?? "Room not set";   // ?. and ?? handle undefined
}

Without strict mode this compiles, and the page crashes for every section that has no room yet.

3. Unions, narrowing, unknown, generics

Union types and narrowing

A union A | B means "either A or B". TS then forces you to check which one you have before you use it. That check is called narrowing.

type RegistrationResult =
  | { status: "ENROLLED"; sectionId: string }
  | { status: "WAITLISTED"; position: number }
  | { status: "REJECTED"; code: string };

function message(r: RegistrationResult): string {
  switch (r.status) {
    case "ENROLLED":
      return `You got a seat in ${r.sectionId}`;   // here TS knows sectionId exists
    case "WAITLISTED":
      return `You are number ${r.position} on the waitlist`;
    case "REJECTED":
      return `Not possible: ${r.code}`;
  }
}

If someone later adds a fourth status, TS reports that message no longer returns a string in every case. The compiler helps you find every place to update. Other ways to narrow: typeof x === "string", x instanceof ProblemError, "field" in x, and if (x) for null checks.

unknown instead of any

any: turns checking off

const body: any = await res.json();
body.sectoinId.trim();   // typo, no error, crash at runtime

unknown: "check before use"

const body: unknown = await res.json();
if (isProblem(body)) {
  show(body.code);        // safe after the check
}

Data from outside (JSON from the network, localStorage, a caught error) is unknown until you check it. A type guard is a function that does the check and tells TS the result:

function isProblem(x: unknown): x is { code: string; status: number } {
  return typeof x === "object" && x !== null && "code" in x && "status" in x;
}

Generics

A generic is a type with a parameter, written in angle brackets. It lets one function or type work for many types, without losing information. You already know Array<string> (same as string[]).

type Page<T> = {
  items: T[];
  page: number;
  totalItems: number;
};

function firstItem<T>(page: Page<T>): T | undefined {
  return page.items[0];
}

const sections: Page<Section> = await loadSections();
const s = firstItem(sections);   // TS infers T = Section, so s is Section | undefined

The backend has the same idea: DomainEvent<P> in shared-kernel is generic in its payload type (lesson 08).

4. Components, JSX and props

React builds a page from components. A component is a function that returns what should be on screen. Like LEGO bricks: small pieces, combined into bigger ones. The spec says: function components only.

type SectionCardProps = {
  code: string;
  title: string;
  seatsLeft: number;
};

export function SectionCard({ code, title, seatsLeft }: SectionCardProps) {
  return (
    <article className="section-card">
      <h3>{code}: {title}</h3>
      {seatsLeft > 0
        ? <p>{seatsLeft} seats left</p>
        : <p className="full">Full</p>}
    </article>
  );
}
  • JSX is the HTML-like syntax inside JavaScript. It is turned into normal function calls at build time. Files with JSX end in .tsx.
  • { } inside JSX means "a JavaScript expression here". You cannot write an if statement inside; use ? : or &&.
  • Use className, not class (a reserved word in JavaScript).
  • A component name starts with a capital letter: <SectionCard /> is a component, <section> is an HTML tag.

Props ("properties") are the inputs of a component, like the parameters of a function. They flow down, from parent to child, and the child must not change them.

<SectionCard code="CS101" title="Programming 1" seatsLeft={12} />
<SectionCard code="CS102" title="Data structures" seatsLeft="12" />
{/*                                               ^^^^ error: string is not number */}

5. State, events and forms

State is data that belongs to a component and can change over time, like the text in a search box. When state changes, React calls your component again and updates the screen. You create state with the useState hook (hooks are functions whose names start with use; they give components extra powers).

import { useState } from "react";

export function SeatPicker() {
  const [seats, setSeats] = useState(1);      // current value + a function to change it
  return (
    <div>
      <button type="button" onClick={() => setSeats(seats - 1)} disabled={seats <= 1}>−</button>
      <span>{seats}</span>
      <button type="button" onClick={() => setSeats(seats + 1)}>+</button>
    </div>
  );
}

Rules of hooks: call them only at the top level of a component (not inside if or loops), and only from components or other hooks. ESLint checks this for you.

Never change state directly (seats++ or list.push(x)). Always call the setter with a new value: setList([...list, x]). React compares the old and new value to decide what to redraw.

Controlled forms

In a controlled input, React state is the single source of truth: the input shows the state, and every key press updates the state.

import { useState } from "react";

type ReportFormProps = { onSubmit: (title: string) => void };

export function ReportForm({ onSubmit }: ReportFormProps) {
  const [title, setTitle] = useState("");
  const tooShort = title.trim().length < 3;

  return (
    <form
      onSubmit={(e) => {
        e.preventDefault();          // stop the browser from reloading the page
        onSubmit(title.trim());
        setTitle("");
      }}
    >
      <label>
        What did you lose?
        <input value={title} onChange={(e) => setTitle(e.target.value)} />
      </label>
      <button type="submit" disabled={tooShort}>Report</button>
    </form>
  );
}

Notice two things. tooShort is not state: it is derived from title, so it is just calculated on each render. And the form does not call the API itself; it gives the value to its parent through the onSubmit prop, which makes it easy to test (lesson 14).

6. Lists, keys, composition, context

Lists and keys

export function SectionList({ sections }: { sections: Section[] }) {
  if (sections.length === 0) return <p>No sections found.</p>;
  return (
    <ul>
      {sections.map((s) => (
        <li key={s.id}>{s.code}</li>     {/* key: a stable, unique id */}
      ))}
    </ul>
  );
}

The key tells React which item is which between renders. Use the database id (our ids are UUIDs). Do not use the array index: when a student drops a section from the middle of the list, the indexes shift and React can show the wrong data in the wrong row.

Composition with children

Instead of one giant component with many options, build small ones and put them inside each other. The special prop children is whatever you put between the tags:

import type { ReactNode } from "react";

export function Card({ title, children }: { title: string; children: ReactNode }) {
  return (
    <section className="card">
      <h2>{title}</h2>
      {children}
    </section>
  );
}

// usage
<Card title="My week">
  <SectionList sections={mySections} />
</Card>

Context: data many components need

Passing the same prop through five levels ("prop drilling") is tiring. Context lets a parent provide a value that any child below can read. Use it for things that are truly global for a part of the page: the current user, the language, the theme. Do not use it for every piece of state.

import { createContext, useContext } from "react";
import type { ReactNode } from "react";

type Locale = "vi" | "en";
const LocaleContext = createContext<Locale | null>(null);

export function LocaleProvider({ locale, children }: { locale: Locale; children: ReactNode }) {
  return <LocaleContext.Provider value={locale}>{children}</LocaleContext.Provider>;
}

export function useLocale(): Locale {
  const locale = useContext(LocaleContext);
  if (locale === null) throw new Error("useLocale must be used inside LocaleProvider");
  return locale;
}

The small hook useLocale hides the null check, so every caller gets a real Locale and a clear error if the provider is missing.

7. useEffect and data fetching

useEffect runs code after React has drawn the screen. It is for synchronising with something outside React: a browser API, a timer, a WebSocket subscription, the page title.

useEffect(() => {
  document.title = `${unread} new messages`;
}, [unread]);           // dependency list: run again only when unread changes

useEffect(() => {
  const id = setInterval(refreshClock, 1000);
  return () => clearInterval(id);    // cleanup: runs before the next effect and on unmount
}, []);

Many tutorials load data with useEffect. It works for a demo, but look at what you must write to do it correctly:

const [data, setData] = useState<Ping | null>(null);
const [error, setError] = useState<unknown>(null);
const [loading, setLoading] = useState(true);

useEffect(() => {
  let ignore = false;                       // avoid a race: old answer arriving late
  fetch("/api/v1/platform/ping")
    .then((r) => r.json())
    .then((d) => { if (!ignore) setData(d); })
    .catch((e) => { if (!ignore) setError(e); })
    .finally(() => { if (!ignore) setLoading(false); });
  return () => { ignore = true; };
}, []);
Why not to fetch data in useEffect
  • No cache: every component that needs the same data asks the server again; going back to a page shows a spinner again.
  • Races: without the ignore flag, a slow old answer can overwrite a newer one.
  • Boilerplate: loading, error, retry and refresh logic, copied into every screen.
  • Double calls in development: React's StrictMode mounts components twice in dev on purpose, so you see two requests.
The Smart Campus stack (Capability Map, assumption 6) uses TanStack Query for server data instead. It solves all four problems. See lesson 14.

8. Vite and the project layout

Vite is the build tool. It has two jobs:

npm run devA dev server on http://localhost:5173. Very fast start; when you save a file the page updates at once (hot module replacement).
npm run buildType-checks, then bundles and minifies everything into dist/: small static files any web server can serve.

The /api proxy

In development the page comes from Vite (:5173) but the API is the gateway (:8080). A browser treats two ports as two different origins and would block the calls (CORS). The fix is a proxy: the page calls /api/… on Vite, and Vite forwards the request to the gateway. For the browser it is all one origin.

import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      "/api": "http://localhost:8080",     // the gateway: the single entry point
    },
  },
});
Browserfetch("/api/v1/platform/ping")
→
Vite :5173path starts with /api → forward

Because the code always uses relative URLs like /api/v1/…, the same build also works in production, where a web server sits in front of the gateway.

VITE_ environment variables

Vite reads .env files and gives your code only the variables whose names start with VITE_, through import.meta.env:

VITE_APP_NAME=Smart Campus
const appName = import.meta.env.VITE_APP_NAME;
if (import.meta.env.DEV) console.debug("dev mode");
Never put a secret in a VITE_ variable The value is copied into the JavaScript bundle at build time. Anyone can read it with "View source". API keys, passwords and client secrets stay on the server. (The VITE_ prefix exists exactly so that other env vars on your machine are not leaked by accident.)

This follows the Architecture's src/{shell, modules/<id>, shared}. A module folder uses the same id as the backend module and the API prefix, so /api/v1/course/… ↔ src/modules/course/.

  • kebab-case file names (spec rule): section-card.tsx, use-sections.ts. Windows does not care about upper/lower case in file names, but Linux CI does; all-lowercase names avoid "works on my machine" import errors.
  • Named exports (spec rule): export function SectionCard, then import { SectionCard } from "./section-card". The name is the same everywhere, and rename tools and search work. (React's lazy() expects a default export; lesson 18 shows the small adapter the shell uses.)
  • import type for things that are only types: import type { ReactNode } from "react". The import disappears from the output.

10. Common mistakes

  • Using any to "make the error go away". Use unknown and narrow, or fix the type. The spec forbids any.
  • Changing state in place (list.push, obj.x = 1). React may not redraw. Create a new array or object.
  • Storing derived values in state (for example isValid next to title). They get out of sync. Calculate them during render.
  • Using the array index as key in lists that can change order.
  • Fetching data in useEffect in feature code. Use TanStack Query.
  • Writing http://localhost:8080 in components. Always use relative /api/… URLs; the proxy handles dev.
  • Secrets in VITE_ variables. They end up in the public bundle.
  • Editing files in src/shared/api/generated/. The next gen:api overwrites them, and CI fails because the files differ.

13. Test yourself

1. Why does the spec forbid any but allow unknown?

any switches type checking off, so typos and wrong shapes crash only at runtime. unknown also accepts any value, but TS forces you to check it before use, so the check happens in the code where it belongs.

2. Why is a discriminated union (status: "ENROLLED" | …) better than one object with many optional fields?

Each case says exactly which fields exist. After a switch on status, TS knows the fields, and when a new case is added, the compiler shows every place that does not handle it yet. Optional fields allow impossible mixes, like a rejected result with a seat.

3. Why must list items have a stable key, and why not the index?

React uses the key to match items between renders. If an item is removed in the middle, indexes shift, so React may reuse the wrong row (with its input text or focus). A database id stays with the same item.

4. Why do we not load server data in useEffect in Smart Campus?

You would have to write caching, race protection, loading/error state and retries by hand on every screen, and StrictMode makes extra calls in dev. TanStack Query does all of this in one tested place.

5. Why does the frontend call /api/v1/… and not http://localhost:8080/api/v1/…?

A relative URL keeps the browser on one origin, so there are no CORS problems. In dev the Vite proxy forwards it to the gateway; in production the web server does. The same code works in both without changes.

6. Why kebab-case file names and named exports?

Windows ignores letter case in file names but Linux CI does not, so mixed-case names can work locally and fail in CI. Named exports keep one name for each thing in every file, which makes search, rename and auto-import reliable.
