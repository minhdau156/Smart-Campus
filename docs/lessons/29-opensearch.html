Search with OpenSearch

A student types "giai tich" without accents and expects to find the book "Giải tích 1" for their course, cheapest first. SQL LIKE '%…%' cannot do that well. A search engine can. This lesson explains how it works and how Smart Campus will feed it from Kafka.

1. Why you need this in Smart Campus

MKT-2: "As a buyer, I want to search and filter by course, title and price, so I find a cheap copy quickly." The capability map adds cross-module search over sections, listings and lost-and-found items. The search module (module 14) is special:

  • It owns no source data. It has no PostgreSQL schema (look at infra/postgres/init/01-schemas-and-users.sh: there is no search schema). It owns only OpenSearch indexes.
  • It is a read model built from events: course.events and campus.events (ListingCreated, ListingSold, ItemReported, …).
  • Resolution C16: it "can be dropped and replayed at any time".

Why not just SQL? WHERE title ILIKE '%giai tich%' cannot use a normal index (it reads every row), does not ignore accents, does not handle typos, and cannot rank "best match first". A search engine is built for exactly these jobs.

2. The inverted index

A book's index at the back lists words and the pages they appear on. A search engine does the same for documents: an inverted index maps each term (a word after cleaning) to the list of documents that contain it.

Documents                         Inverted index (term → documents)
 1: "Giải tích 1 - bản mới"        giai  → 1, 3
 2: "Vật lý đại cương"             tich  → 1, 3
 3: "Bài tập giải tích"            1     → 1
                                   ban   → 1
                                   moi   → 1
                                   vat   → 2       bai → 3
                                   ly    → 2       tap → 3 …

Query "giai tich" → terms giai, tich → documents 1 and 3 → rank them

Finding documents is now a quick lookup per term, not a scan of every row. The work moved from search time to index time: every document is cut into terms when it is saved.

OpenSearch is an open-source search engine (a fork of Elasticsearch, built on the Apache Lucene library). You talk to it with JSON over HTTP. Our Compose file runs one node:

opensearch:
  image: opensearchproject/opensearch:3.10.0
  environment:
    discovery.type: single-node
    DISABLE_SECURITY_PLUGIN: "true"      # dev only: no login, no TLS
  ports:
    - "127.0.0.1:9200:9200"

3. Documents and mappings

A document is one JSON object, like one row. An index is a collection of documents, like a table. The mapping is the index's schema: it says the type of every field. The most important choice is text vs keyword:

TypeWhat happensUse forExample
textCut into terms by an analyzer. Good for "contains these words"Full-text searchtitle, description
keywordKept as one exact value. Good for equal, filter, sort, countIds, codes, statusescourseId, status
long, date, …Numbers and times; range queries and sortPrice, timeprice, createdAt

A field can have both, with a sub-field: title as text for searching, and title.raw as keyword for exact sort.

PUT /listings-v1
{
  "settings": { "analysis": { … see next section … } },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "id":          { "type": "keyword" },
      "title":       { "type": "text", "analyzer": "vi_folded",
                       "fields": { "raw": { "type": "keyword" } } },
      "description": { "type": "text", "analyzer": "vi_folded" },
      "courseId":    { "type": "keyword" },
      "courseCode":  { "type": "keyword" },
      "price":       { "type": "long" },
      "status":      { "type": "keyword" },
      "createdAt":   { "type": "date" }
    }
  }
}

"dynamic": "strict" rejects documents with unknown fields, so a typo in our code fails loudly instead of quietly creating a new field. You cannot change a field's type in an existing index; you create a new index and fill it again (section 7).

4. Analyzers and Vietnamese accents

An analyzer turns text into terms. It has a tokenizer (cuts the text into pieces) and token filters (change each piece). The same analyzer is used for the documents and for the user's query, so both sides become the same terms.

Many students type Vietnamese without accents ("toan" for "Toán"). The asciifolding filter turns letters with accents into plain ASCII letters, so both become toan. It also turns đ into d.

"settings": {
  "analysis": {
    "filter": {
      "vi_fold": { "type": "asciifolding", "preserve_original": true }
    },
    "analyzer": {
      "vi_folded": {
        "type": "custom",
        "tokenizer": "standard",
        "filter": [ "lowercase", "vi_fold" ]
      }
    }
  }
}
"Toán Cao Cấp"  ─standard─►  Toán | Cao | Cấp
                ─lowercase─► toán | cao | cấp
                ─vi_fold──►  toán + toan | cao | cấp + cap   (preserve_original keeps both)

With preserve_original, the accented form is kept too. So "Toán" and "toan" both match, and a query typed with the right accents also matches the exact form. You can test any analyzer with the _analyze API (see Practice).

Limits of folding Folding can mix up words that differ only by accents (for example "bàn" table and "bán" sell both become "ban"). For a book market that is usually fine. The standard tokenizer cuts Vietnamese into syllables, not words; phrase queries help keep syllables together. Plugins with real Vietnamese word splitting exist, but adding one is a spec decision.

5. The query DSL and BM25

OpenSearch queries are JSON (the query DSL, a small language for queries). The main pieces:

  • match: full-text search in one field.
  • multi_match: the same in several fields, with weights (title^3 means a match in the title counts 3 times more).
  • bool: combine queries. must = must match and adds to the score; filter = must match but does not change the score and can be cached; should = nice to have; must_not = exclude.
  • fuzziness: "AUTO": allow small typos ("giai tihc" still finds "giai tich").
GET /listings/_search
{
  "query": {
    "bool": {
      "must": [
        { "multi_match": { "query": "giai tich", "fields": ["title^3", "description"],
                           "fuzziness": "AUTO" } }
      ],
      "filter": [
        { "term":  { "status": "AVAILABLE" } },
        { "term":  { "courseId": "4b1c…" } },
        { "range": { "price": { "lte": 100000 } } }
      ]
    }
  },
  "sort": [ { "_score": "desc" }, { "id": "asc" } ],
  "size": 20
}

Rule: yes/no conditions go in filter (status, course, price range). Only the words the user typed go in must. This keeps the score meaningful and the query fast.

How the score is computed: BM25

OpenSearch ranks with BM25 by default. In simple words, a document scores higher when:

  • the query term appears often in it (term frequency), but with less extra gain each time, so repeating a word 50 times does not win;
  • the term is rare in the whole index (inverse document frequency): "giai tich" tells more than "sach" (book), which is in every listing;
  • the field is short: a match in a 4-word title means more than in a 300-word description.

6. Paging with search_after

from + size works like SQL OFFSET: deep pages get slow, and OpenSearch limits how deep you can go by default. For "load more" lists, use search_after, the search-engine version of keyset pagination (lesson 25):

  1. Sort by something with a unique tie-breaker: _score, then id.
  2. Each hit in the answer has a sort array, for example [7.31, "a91e…"].
  3. For the next page, send the last hit's array as "search_after": [7.31, "a91e…"].

If documents change between pages, results can shift. For a stable view across pages, OpenSearch offers a point in time (PIT) to use with search_after. For a marketplace list, small shifts are usually acceptable.

7. Building the index from Kafka

The search module listens to events and keeps the index up to date. It never reads the marketplace tables (no cross-module reads, D3).

marketplaceListingCreated, ListingSold via outbox
→
Kafkacampus.events, key = aggregateId
→
search consumerbuild a document, bulk write
→
OpenSearchalias listings

Idempotent by design

Use the listing id as the document id. Writing the same document twice just overwrites it with the same content, so duplicate events are harmless. Because campus.events is keyed by aggregateId, events of one listing arrive in order. For extra safety against old events overwriting new ones, OpenSearch supports external versioning: send a version number with each write, and it rejects a write with an older version. Where to keep dedupe state, given that search has no PostgreSQL schema, is a decision for SPEC-search.md.

The bulk API

Writing documents one HTTP call at a time is slow. The bulk API sends many actions in one request (as NDJSON: one JSON object per line). A Kafka listener that receives a batch of records can turn it into one bulk call. Important: a bulk call can partly fail. Its answer has "errors": true and a status per item; check every item, and do not acknowledge the Kafka batch if an item failed for a reason that a retry can fix.

Aliases: rebuild with zero downtime

An alias is a second name that points to an index. The app always searches listings, which points to listings-v1. To change a mapping or rebuild:

  1. Create listings-v2 with the new mapping.
  2. Replay: a new consumer group reads the topics from the beginning (retention.ms=-1, D5) and fills listings-v2.
  3. When it has caught up, move the alias in one atomic call: 
    POST /_aliases
{ "actions": [
  { "remove": { "index": "listings-v1", "alias": "listings" } },
  { "add":    { "index": "listings-v2", "alias": "listings" } } ] }
  4. Delete listings-v1 later.

Users never see an empty index. This is exactly the "drop and replay" promise of C16, done without downtime.

Eventual consistency

A seller saves a listing. The outbox sends the event, the consumer indexes it, and OpenSearch makes it searchable after its refresh (about once per second by default). So for a short time, the listing exists but search cannot find it. This is eventual consistency: correct soon, not instantly. Design the UI for it: after "Save", show the listing page (read from marketplace's own API), not a search result.

8. The Java client and lost-and-found matching

The opensearch-java client builds requests with typed builders. A sketch (method names can differ between client versions; check the client's docs for the version you add):

package edu.campus.search.internal;

@Component
class ListingSearch {
    private final OpenSearchClient client;

    ListingSearch(OpenSearchClient client) {
        this.client = client;
    }

    List<ListingDoc> search(String text, String courseId, long maxPrice) throws IOException {
        SearchResponse<ListingDoc> response = client.search(s -> s
                .index("listings")                                     // the alias
                .query(q -> q.bool(b -> b
                        .must(m -> m.multiMatch(mm -> mm
                                .query(text).fields("title^3", "description").fuzziness("AUTO")))
                        .filter(f -> f.term(t -> t.field("status").value(FieldValue.of("AVAILABLE"))))
                        .filter(f -> f.term(t -> t.field("courseId").value(FieldValue.of(courseId))))
                        .filter(f -> f.range(r -> r.field("price").lte(JsonData.of(maxPrice))))))
                .size(20),
                ListingDoc.class);
        return response.hits().hits().stream().map(Hit::source).toList();
    }
}

Spring Data OpenSearch is another option with repositories. Either way, wrap OpenSearch behind the search module's own API, so other modules never depend on the client library.

Matching lost and found items (LF-3)

LF-3: "be notified when a found item matches my report". Ways to find candidates for a new FOUND item among open LOST reports:

  • Hard filters: same category, status OPEN, lost time before found time and within N days.
  • Text similarity: a multi_match on title and description with the folded analyzer, or OpenSearch's more_like_this query ("find documents similar to this one").
  • Place: same building or campus area as a keyword, or a distance query if the spec stores coordinates.
  • Take only results above a score threshold, and suggest them to the owner, who must still claim with proof (LF-4). Never hand an item over automatically.
A dependency to decide The capability map says search depends on lostfound, not the other way round, and the Architecture says search publishes no events. So either lostfound does simple matching in its own PostgreSQL schema (filters + PostgreSQL full-text search), or the spec allows search to publish a "possible match" event. This is an "Ask first" decision for SPEC-lostfound.md.

10. Common mistakes

  • Mapping ids and statuses as text. Filters then match parts of words. Use keyword.
  • Putting filters in must. They change the score and are not cached. Use filter.
  • Different analyzers for index and query, so "toan" never meets "toán".
  • Letting OpenSearch guess the mapping (dynamic mapping). Define it, and use "dynamic": "strict".
  • Searching the real index name instead of the alias. Then a rebuild needs a code change.
  • Treating search as the source of truth. It is a copy. Read the listing page from marketplace.
  • Ignoring per-item errors in a bulk answer.
  • Deep from paging. Use search_after.

13. Test yourself

1. Why is an inverted index faster than ILIKE '%giai tich%'?

ILIKE with a leading % must read every row. The inverted index already lists the documents for each term, so the search is a few lookups. The work was done once, at index time.

2. Why must the same analyzer run on the documents and on the query?

Matching compares terms. If documents become "toan" but the query stays "Toán", the terms differ and nothing matches.

3. Why do status and price go in filter, not in must?

They are yes/no conditions. In filter they do not distort the relevance score, and OpenSearch can cache them, so queries are faster.

4. How do aliases make "drop and replay" (C16) possible without downtime?

The app searches the alias. We build a new index from a replay while the old one still serves users, then move the alias in one atomic call. Users never see an empty or half-built index.

5. Why is it safe if the search consumer receives ListingCreated twice?

The document id is the listing id, so the second write overwrites the same document with the same content. Ordering per listing comes from the Kafka key; external versions can reject old writes.

6. A seller saves a listing and searches for it at once, but it is missing. Is this a bug?

No. Search is eventually consistent: the event must go through the outbox, Kafka, the consumer and the index refresh. The UI should show the new listing from marketplace's own API.
