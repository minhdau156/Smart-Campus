1. Why you need this in Smart Campus

The backend and the frontend are written in two languages (Java and TypeScript). If a backend developer renames seatsLeft to availableSeats, a hand-written frontend type is now wrong, and nobody notices until a student sees an empty page. Smart Campus closes this gap with a chain of generated files:

Java controllerrecord Ping(String app, …)
→
OpenAPI JSONdocs/api/core-app-platform.json
(T9, exists)
→
TS typessrc/shared/api/generated/
(T19.5, planned)
→
Screenscompile errors if the shape changed

A change in the backend now breaks the frontend build, not the student's page. T19 also writes one shared client that turns every error into a typed ProblemError, so all 14 modules show errors the same way. This closes spec criteria P2 (lint, test, build pass) and the frontend part of A1.

2. fetch and async/await

fetch is the browser's built-in function for HTTP calls. It returns a Promise: an object that says "the answer will come later". await waits for it, inside a function marked async. Like ordering at a café: you get a ticket (the Promise), and you wait for your number (await).

async function loadPing(): Promise<unknown> {
  const res = await fetch("/api/v1/platform/ping", {
    headers: { Accept: "application/json" },
  });
  if (!res.ok) {                              // res.ok = status 200–299
    throw new Error(`HTTP ${res.status}`);
  }
  return res.json();                          // also a Promise: reading the body takes time
}
The big fetch surprise fetch does not throw for 404, 409 or 500. It only throws when the network fails (server down, no internet). You must check res.ok or res.status yourself. Forgetting this is the most common bug in API code.

Also note Promise<unknown>: res.json() can return anything. The next section makes it typed.

3. Types generated from OpenAPI

Since T9, a test exports the core-app OpenAPI document to docs/api/, sorted and stable, and the normal build fails if the committed file is out of date. Here is part of the real file:

"paths" : {
  "/api/v1/platform/ping" : {
    "get" : {
      "operationId" : "ping",
      "responses" : {
        "200" : { "content" : { "application/json" : {
                    "schema" : { "$ref" : "#/components/schemas/Ping" } } } },
        "default" : { "content" : { "application/problem+json" : {
                    "schema" : { "$ref" : "#/components/schemas/Problem" } } } }
…
"Problem" : {
  "required" : [ "code", "detail", "status", "title", "traceId", "type" ], …

openapi-typescript is a command-line tool that reads this file and writes a .ts file with only types (no runtime code, so it adds nothing to the bundle). T19.5 adds it as the gen:api script:

"scripts": {
  "gen:api": "openapi-typescript ../../docs/api/core-app-platform.json -o src/shared/api/generated/core-app-platform.ts"
}

When more apps and modules export their own JSON files, the script will cover all of docs/api/*.json (T19.5 decides how: one command per file, or a small loop). The output looks roughly like this (shortened):

export interface paths {
  "/api/v1/platform/ping": {
    get: operations["ping"];
  };
}
export interface components {
  schemas: {
    Ping: {
      app?: string;
      /** Format: date-time */
      time?: string;
      version?: string;
    };
    Problem: {
      code: string;
      detail: string;
      errors?: components["schemas"]["FieldError"][];
      status: number;
      title: string;
      traceId: string;
      type: string;
    };
  };
}

Look closely: Ping's fields are optional (?) because the Java record does not mark them as required, while Problem's fields are required because T9 listed them in required. The generated types tell the truth about the contract, so a good backend contract gives a good frontend type. Also, time is a string: JSON has no date type; you convert it with new Date(time) where you need it.

You use the types by indexing into them:

import type { components } from "./generated/core-app-platform";

export type Ping = components["schemas"]["Ping"];
export type Problem = components["schemas"]["Problem"];

4. The problem-JSON client (T19.6)

Every error from every Smart Campus app is RFC 7807 problem JSON with content type application/problem+json and our extra fields code and traceId (lesson 09). T19.6 writes src/shared/api/http.ts: a small wrapper around fetch, typed by the generated paths, that turns any problem response into a ProblemError with code, traceId and, for 429, retryAfter. The task does not add a fetch library; it is our own small file. A sketch of the idea:

import type { components, paths } from "./generated/core-app-platform";

type Problem = components["schemas"]["Problem"];

export class ProblemError extends Error {
  readonly status: number;
  readonly code: string;                     // "NOT_FOUND", "RATE_LIMITED", …
  readonly traceId: string | undefined;
  readonly retryAfter: number | undefined;   // seconds, from the Retry-After header (429)

  constructor(status: number, problem: Partial<Problem>, retryAfter?: number) {
    super(problem.detail ?? `HTTP ${status}`);
    this.name = "ProblemError";
    this.status = status;
    this.code = problem.code ?? "UNKNOWN";   // e.g. an HTML error page from a proxy
    this.traceId = problem.traceId;
    this.retryAfter = retryAfter;
  }
}

async function toProblemError(res: Response): Promise<ProblemError> {
  const isProblem = res.headers.get("Content-Type")?.includes("application/problem+json");
  const body: unknown = isProblem ? await res.json() : {};
  const header = res.headers.get("Retry-After");
  const retryAfter = header !== null && /^\d+$/.test(header) ? Number(header) : undefined;
  return new ProblemError(res.status, body as Partial<Problem>, retryAfter);
}

// The JSON type of a GET path's 200 answer, read from the generated paths.
type GetJson<P extends keyof paths> = paths[P] extends {
  get: { responses: { 200: { content: { "application/json": infer Body } } } };
} ? Body : never;

export async function get<P extends keyof paths>(path: P): Promise<GetJson<P>> {
  const res = await fetch(path, { headers: { Accept: "application/json" } });
  if (!res.ok) throw await toProblemError(res);
  return (await res.json()) as GetJson<P>;
}

Three things are worth understanding here:

  • P extends keyof paths means the path string itself is checked. get("/api/v1/platform/pong") is a compile error, because that path is not in the OpenAPI file. get("/api/v1/platform/ping") returns Promise<Ping> with no type written by hand. (Paths with {id} parameters need a bit more work; T19 starts with what ping needs.)
  • infer Body is TypeScript "pattern matching" on a type: "if it has this shape, give me the part called Body". You will rarely write this yourself; it lives in one shared file.
  • The Retry-After header may be a number of seconds or an HTTP date. Our gateway limiter answers 429 (spec R1); the sketch only accepts whole seconds and ignores anything else.

Showing messages by code

The rule from the backend is: switch on code, never on the message text. detail is for humans and can change; code is a stable contract (ProblemCode in shared-kernel: INTERNAL_ERROR, VALIDATION_FAILED, NOT_FOUND, CONFLICT, RATE_LIMITED; later modules add codes such as SECTION_FULL).

import { ProblemError } from "./http";

export function problemText(error: unknown): string {
  if (!(error instanceof ProblemError)) return "Network problem. Check your connection.";
  switch (error.code) {
    case "NOT_FOUND":
      return "We could not find this.";
    case "VALIDATION_FAILED":
      return "Please check the highlighted fields.";
    case "RATE_LIMITED":
      return `Too many requests. Try again in ${error.retryAfter ?? 1} s.`;
    default:
      return `Something went wrong. Please quote this id: ${error.traceId ?? "n/a"}`;
  }
}

export function ProblemMessage({ error }: { error: unknown }) {
  return <p role="alert">{problemText(error)}</p>;
}

Showing the traceId matters: a student can send it to support, and a developer finds the exact trace and logs in Grafana (lesson 12). When the shell module adds vi/en translations, these texts move into translation files, keyed by the same codes.

5. TanStack Query: reading data

TanStack Query (formerly "React Query") manages server state: data that lives on the server and that the page shows a copy of. It handles loading and error states, caching, retries, refresh, and removes duplicate requests. It is part of the Smart Campus frontend stack (Architecture and Capability Map). T19 itself does not list it as a subtask; it comes in with the first screens that load data. Examples below use the v5 API; check the docs for the version that gets pinned.

import { createRoot } from "react-dom/client";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { ProblemError } from "./shared/api/http";
import { App } from "./shell/app";

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,          // data counts as fresh for 30 s: no refetch in that time
      retry: (failures, error) =>  // retry network/5xx errors, never 4xx
        !(error instanceof ProblemError && error.status < 500) && failures < 2,
    },
  },
});

createRoot(document.getElementById("root")!).render(
  <QueryClientProvider client={queryClient}>
    <App />
  </QueryClientProvider>,
);
import { useQuery } from "@tanstack/react-query";
import { get } from "../shared/api/http";
import { ProblemMessage } from "../shared/api/problem-message";

export function usePing() {
  return useQuery({
    queryKey: ["platform", "ping"],                     // the cache key
    queryFn: () => get("/api/v1/platform/ping"),        // how to load it
  });
}

export function PingStatus() {
  const ping = usePing();
  if (ping.isPending) return <p>Checking the server…</p>;
  if (ping.isError) return <ProblemMessage error={ping.error} />;
  return <p>{ping.data.app} {ping.data.version} is up</p>;   // data is Ping here
}
  • Query key: an array that names the data, like a label on a box in the cache. Put every input into it: ["course", "sections", { semester, page }]. Two components with the same key share one request and one cache entry.
  • Loading and error states: check isPending and isError first. After those checks, TS knows data is defined. Always show something for all three states.
  • staleTime: how long data is "fresh". Fresh data is shown without asking the server. Stale data is still shown at once, then refreshed in the background. A course list can be fresh for minutes; seat counts during the registration rush much less.

Put each useQuery in a small custom hook (usePing, useSections) inside the module folder. Screens then never see URLs or keys.

6. TanStack Query: changing data

Reading is a query. Creating, updating or deleting is a mutation. After a change on the server, the cached lists are old, so you invalidate them: mark them stale so they are fetched again.

import { useMutation, useQueryClient } from "@tanstack/react-query";

export function useCreateReport() {
  const queryClient = useQueryClient();
  return useMutation({
    // post(): a sibling of get() in http.ts for POST requests (not shown)
    mutationFn: (title: string) => post("/api/v1/lostfound/reports", { title }),
    onSuccess: () => {
      // every query whose key STARTS with ["lostfound", "reports"] is refetched
      return queryClient.invalidateQueries({ queryKey: ["lostfound", "reports"] });
    },
  });
}

export function NewReport() {
  const create = useCreateReport();
  return (
    <>
      <ReportForm onSubmit={(title) => create.mutate(title)} />
      {create.isPending && <p>Saving…</p>}
      {create.isError && <ProblemMessage error={create.error} />}
    </>
  );
}

Copying server data into useState

Load once, store in state, update by hand after each change. Two screens soon show different numbers.

Let the cache own server data

useQuery to read, useMutation + invalidateQueries to change. useState is only for UI state (open/closed, text being typed).

Hierarchical keys make invalidation easy: ["registration"] would refresh everything of that module, ["registration", "enrollments", studentId] only one student's list.

7. Vitest and Testing Library

Vitest is the test runner. It uses the same config and transforms as Vite, so TypeScript and JSX work with no extra setup. jsdom is a fake browser in Node, so components can render without opening Chrome. T19.3 sets both up:

test: {
  environment: "jsdom",
  setupFiles: ["./src/test-setup.ts"],   // e.g. extra matchers like toBeDisabled()
},

Tests live next to the code: http.ts → http.test.ts, report-form.tsx → report-form.test.tsx (spec: src/**/*.test.tsx).

Testing the client (T19.6: "unit-test a 409 and a 429")

import { afterEach, expect, it, vi } from "vitest";
import { get, ProblemError } from "./http";

function problem(status: number, body: object, headers: Record<string, string> = {}) {
  return new Response(JSON.stringify(body), {
    status,
    headers: { "Content-Type": "application/problem+json", ...headers },
  });
}

afterEach(() => vi.unstubAllGlobals());

it("turns a 409 into a ProblemError with code and traceId", async () => {
  vi.stubGlobal("fetch", vi.fn().mockResolvedValue(problem(409, {
    type: "https://campus.edu/problems/conflict", title: "Conflict", status: 409,
    detail: "Section S1 has no seats left", code: "CONFLICT", traceId: "4bf92f3577b34da6a3ce929d0e0e4736",
  })));

  const error = await get("/api/v1/platform/ping").catch((e: unknown) => e);

  expect(error).toBeInstanceOf(ProblemError);
  expect(error).toMatchObject({ status: 409, code: "CONFLICT", traceId: "4bf92f3577b34da6a3ce929d0e0e4736" });
});

it("reads Retry-After on a 429", async () => {
  vi.stubGlobal("fetch", vi.fn().mockResolvedValue(
    problem(429, { code: "RATE_LIMITED", status: 429 }, { "Retry-After": "3" })));

  await expect(get("/api/v1/platform/ping")).rejects.toMatchObject({ code: "RATE_LIMITED", retryAfter: 3 });
});

vi.stubGlobal replaces the global fetch with a fake for this test, and vi.unstubAllGlobals puts the real one back. No server, no network: the test is fast and always gives the same result.

Testing a component like a user

Testing Library has one idea: test what the user sees and does, not the inside of the component. You find elements the way a user (or a screen reader) would: by role and accessible name.

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { expect, it, vi } from "vitest";
import { ReportForm } from "./report-form";

it("sends the trimmed title when the user submits", async () => {
  const user = userEvent.setup();
  const onSubmit = vi.fn();
  render(<ReportForm onSubmit={onSubmit} />);

  const button = screen.getByRole("button", { name: "Report" });
  expect(button).toBeDisabled();

  await user.type(screen.getByRole("textbox", { name: /what did you lose/i }), "  Blue umbrella ");
  await user.click(button);

  expect(onSubmit).toHaveBeenCalledWith("Blue umbrella");
});
QueryWhen nothing matchesUse it for
getByRole(…)throws at onceThings that must be there now (first choice)
findByRole(…)waits, then throws (returns a Promise)Things that appear later, e.g. after a query loads
queryByRole(…)returns nullChecking that something is not there

Prefer ByRole, then ByLabelText, then ByText. Use data-testid only as a last resort. A test that finds a button by role also checks that the button is accessible. user-event types and clicks like a real user (focus, key presses), which is closer to reality than firing one raw event. toBeDisabled() comes from @testing-library/jest-dom, loaded in the setup file (check its docs for the Vitest import).

Components that use TanStack Query

Give each test its own fresh QueryClient with retry: false, so tests do not share a cache and errors appear at once:

import type { ReactElement } from "react";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { render, screen } from "@testing-library/react";

export function renderWithQuery(ui: ReactElement) {
  const client = new QueryClient({ defaultOptions: { queries: { retry: false } } });
  return render(<QueryClientProvider client={client}>{ui}</QueryClientProvider>);
}

it("shows the app name from ping", async () => {
  vi.stubGlobal("fetch", vi.fn().mockResolvedValue(Response.json({ app: "core-app", version: "0.1.0" })));
  renderWithQuery(<PingStatus />);
  expect(await screen.findByText(/core-app 0\.1\.0 is up/)).toBeInTheDocument();
});

8. ESLint, Prettier and the "up to date" check

ESLint: finds bugs

Hooks called inside an if, missing effect dependencies, unused variables, any (via typescript-eslint). npm run lint.

Prettier: formats

Spaces, quotes, line breaks. No discussions about style in reviews. npm run format. Like Spotless on the Java side.

They must not fight: ESLint's style rules are switched off (commonly with eslint-config-prettier) and Prettier owns formatting. The generated folder is excluded from linting (T19.5): it is not our code and we never edit it.

export default [
  { ignores: ["dist", "src/shared/api/generated"] },
  // … typescript-eslint, react-hooks, prettier configs …
];

Proving the generated files are up to date

A generated file in Git can go stale: someone changes a controller, exports the JSON, but forgets gen:api. CI (T20) catches this in two steps, one per side:

# backend job (T20.2)
- run: ./mvnw verify -Pexport-openapi
- run: git diff --exit-code docs/api

# frontend job (T20.3)
- run: npm --prefix frontend/web ci
- run: npm --prefix frontend/web run gen:api
- run: git diff --exit-code

git diff --exit-code prints the differences and exits with code 1 if there are any. A non-zero exit code fails the CI step. So the rule is simple: regenerate, then the working tree must be unchanged. If it changed, the committed file was stale, and the PR is red until you run the command and commit the result. (The backend side is already checked in every normal build since T9: OpenApiExportIT compares the export with the committed file.)

10. Common mistakes

  • Not checking res.ok. fetch does not throw for 4xx/5xx. Always go through http.ts.
  • Writing API types by hand. They drift from the backend. Use the generated ones; if a type is wrong, fix the Java side (for example mark a field as required) and regenerate.
  • Editing generated files. Your change is overwritten and CI fails.
  • Showing detail or matching on message text. Use code for logic and translations.
  • Forgetting an input in the query key. Page 2 then shows page 1's cached data.
  • Forgetting to invalidate after a mutation. The list still shows old data.
  • Retrying 4xx errors. A 409 or 404 will not fix itself; retrying only adds load (and a 429 makes the rate limit worse).
  • Testing implementation details (state values, CSS classes) instead of what the user sees. Such tests break on every refactor.
  • Calling the real backend in unit tests. Stub fetch; tests must run without Docker.

12. Words to know

WordMeaning in simple words
PromiseAn object for a value that will arrive later.
async/awaitSyntax to wait for a Promise in readable, top-to-bottom code.
OpenAPIA standard JSON file describing every endpoint, input and answer.
Code generationA tool writing code (here, types) from another file, so nobody types it by hand.
Problem JSONThe RFC 7807 error body, application/problem+json, with our code and traceId.
Server stateData that lives on the server; the page only shows a cached copy.
Query keyThe array that names one piece of cached data.
StaleCached data that may be old and will be refreshed.
MutationA request that changes data on the server (POST, PUT, PATCH, DELETE).
InvalidateMark cached data as stale so it is fetched again.
Stub / mockA fake replacement (here for fetch) used in a test.
jsdomA fake browser inside Node, used by tests.
Role (ARIA)What an element is for a screen reader: button, textbox, alert…
Exit codeThe number a command returns: 0 = success, anything else = failure.

13. Test yourself

1. Why generate TypeScript types from the OpenAPI file instead of writing them?

Hand-written types drift from the backend silently. Generated types change when the backend contract changes, so a breaking change shows up as a compile error in the frontend build (and in CI), not as a broken page for students.

2. Why does the client turn every error into one ProblemError class?

All 14 modules then handle errors the same way: one instanceof check, then switch on code. The traceId and retryAfter are always in the same place, and the logic is tested once (T19.6) instead of in every screen.

3. Why switch on code and not on detail?

code is a stable machine contract from ProblemCode. detail is a human sentence that can be reworded or translated at any time, which would silently break the frontend logic.

4. Why must every input of a query (page, filter, id) be part of the query key?

The key is how TanStack Query finds data in the cache. If page 2 has the same key as page 1, the cache returns page 1's data, and invalidation cannot target the right entries.

5. Why do Testing Library tests find elements by role and name?

That is how users and screen readers find them, so the test checks real behaviour and also proves the element is accessible. Tests that use roles survive refactors of class names and internal structure.

6. How does gen:api + git diff --exit-code prove the types are up to date?

CI regenerates the types from the committed JSON. If the result differs from the committed types, git diff --exit-code returns 1 and the job fails. So a PR cannot be merged with stale generated files.
