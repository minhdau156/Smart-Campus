Testing: JUnit, Testcontainers, ArchUnit

In Smart Campus a task is "done" only when ./mvnw verify is green. This lesson shows the kinds of tests we write, the tools for each, and the rules that keep the tests honest.

1. Why you need this in Smart Campus

Many Smart Campus promises cannot be seen by clicking around: "an event is never lost", "a student is never enrolled twice", "a module never reads another module's tables". The only way to know they hold, today and after every change, is a test that fails when they break.

The project's Definition of Done (tasks/todo.md): ./mvnw verify is green, with no new suppressions and no disabled tests. So tests are not extra work at the end; they are how a task is finished.

2. The test pyramid: Test vs IT

              ▲  few, slow, real everything
             ╱ ╲      smoke script (curl through the gateway)          infra/smoke.sh (planned)
            ╱   ╲
           ╱ IT  ╲    integration tests: real Postgres/Kafka/Redis    *IT  → failsafe
          ╱───────╲
         ╱  unit   ╲  plain Java, Spring slices, architecture rules   *Test → surefire
        ╱───────────╲
       many, fast (milliseconds), no Docker

Write many fast unit tests and fewer slow integration tests. A unit test tells you exactly which method broke. An integration test tells you the pieces really work together (SQL is valid, Kafka really gets the record).

Both kinds live in src/test/java. Only the name decides who runs them.

3. JUnit 5 and AssertJ

JUnit 5 (JUnit Jupiter) runs the tests. AssertJ writes the checks in a readable, chained style. A good test has three parts: arrange (set up), act (call one thing), assert (check the result).

@Test
void byNameFailsForAnUnknownTopic() {
    assertThatIllegalArgumentException()
            .isThrownBy(() -> Topics.byName("grades"))
            .withMessageContaining("grades");
}

Many cases, one test: @ParameterizedTest

One method, run once per row. Great for tables, like the Arch §6 topic table:

@ParameterizedTest
@CsvSource({
    "REGISTRATION_REQUESTS, registration.requests, 12, sectionId,   false",
    "REGISTRATION_EVENTS,   registration.events,    6, studentId,   true",
    …
})
void topicMatchesTheArchitectureTable(
        Topics topic, String name, int partitions, String keyField, boolean replayable) {
    assertThat(topic.topicName()).isEqualTo(name);
    assertThat(topic.partitions()).isEqualTo(partitions);
    …
}

JUnit converts each CSV value to the parameter type (here even the enum Topics).

Grouping: @Nested

An inner class marked @Nested groups tests about one situation, and the report reads like a sentence. Our code does not use it yet; it is handy once a domain class has many rules:

class SectionTest {
    @Nested
    class WhenFull {
        @Test void refusesANewStudent() { … }
        @Test void putsTheStudentOnTheWaitlist() { … }
    }
}
Name tests as facts Our names say what must be true: aRolledBackProbeIsNeverPublished, sharedKernelIsALibraryNotAModule. When one fails, the name alone tells you which promise broke.

4. Control time and helpers: Clock, fakes, mocks

A fixed Clock

Project rule: never call Instant.now(); ask for a Clock. In a test you pass a clock that never moves, so the result is the same on every run:

public static Clock fixedAt(String isoInstant) {
    return Clock.fixed(Instant.parse(isoInstant), ZoneOffset.UTC);
}

Clocks is shared with other modules through the shared-kernel test-jar. PingControllerTest does the same with a test bean and then checks the exact time "2026-09-07T08:00:00Z" in the answer.

Fakes vs mocks

Fake

A small, real, simple version of a dependency, e.g. an in-memory repository built on a HashMap. You check the result.

Mock

A generated stand-in (Mockito) that you program ("when called with X, return Y") and then ask "were you called?". You check the interaction.

Mockito comes with spring-boot-starter-test, but no Smart Campus test uses it yet. The project prefers real objects, a fixed Clock, small fakes, and real infrastructure in Testcontainers. Mocks are fine at a boundary you cannot run, like a payment gateway or a push service. Too many mocks test your guesses about the code, not the code. (In a Spring test, Spring's @MockitoBean replaces a bean with a mock; the older @MockBean is not used in Boot 4.)

5. Spring tests: slices and full app

KindWhat startsSpeedSmart Campus example
Plain JUnitNothing; you call newFastestTopicsTest, ProbeTopicTest, ModularityTest

@WebMvcTest(PingController.class)        // org.springframework.boot.webmvc.test.autoconfigure
class PingControllerTest {

    @TestConfiguration
    static class FixedClock {
        @Bean Clock clock() { return Clock.fixed(Instant.parse("2026-09-07T08:00:00Z"), ZoneOffset.UTC); }
    }

    @Autowired private MockMvcTester mvc;        // AssertJ-style MockMvc: no real HTTP

    @Test
    void pingReturnsAppVersionAndTime() {
        var result = mvc.get().uri("/api/v1/platform/ping").exchange();
        assertThat(result).hasStatusOk();
        assertThat(result).bodyJson().extractingPath("$.time").isEqualTo("2026-09-07T08:00:00Z");
    }
}
Boot 4 moved the test slices In Spring Boot 4 each slice comes from its own test starter and package. @WebMvcTest needs spring-boot-starter-webmvc-test and lives in org.springframework.boot.webmvc.test.autoconfigure. Old Boot 3 tutorials show other package names; trust the code in this repo.

Context caching: Spring keeps a started app context and reuses it for every test class with the same configuration. That is why OutboxIT uses exactly the same annotations as CoreApplicationIT: the app and its containers start once for both. A small difference (another profile, an extra bean) means a second, slow start.

6. Real infrastructure: Testcontainers, Awaitility

Testcontainers + @ServiceConnection

Testcontainers starts real Docker containers from a test. No shared test database, no "works on my machine": every run gets a fresh PostgreSQL and Kafka, with the same image tags as infra/docker-compose.yml.

@TestConfiguration(proxyBeanMethods = false)
public class TestcontainersConfiguration {

    @Bean
    @ServiceConnection                       // Spring reads URL, user, password from it
    PostgreSQLContainer postgres() {
        return new PostgreSQLContainer("postgres:19.0-alpine3.24");
    }

    @Bean
    @ServiceConnection                       // sets the Kafka bootstrap servers
    KafkaContainer kafka() {
        return new KafkaContainer("apache/kafka:4.4.0");
    }
}
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@ActiveProfiles("test")
@Import(TestcontainersConfiguration.class)
class CoreApplicationIT { … }

@ServiceConnection means the test profile needs no datasource URL or Kafka address. Redis comes the same way when the gateway tests need it (T14). One trap from T7: the Testcontainers DB user is a superuser, so a permission problem that would fail against Compose can hide in tests. CoreApplicationIT.modulithDoesNotCreateTablesItself guards that one case.

Waiting for async results: Awaitility

The outbox sends to Kafka after the commit, on another thread. A test cannot check right away, and Thread.sleep(5000) is both slow and flaky. Awaitility checks again and again until the condition is true, or fails after a limit:

// wait until the publication is marked complete, at most 10 s
await().atMost(Duration.ofSeconds(10)).until(() -> completionDate(id) != null);

// O2: for the WHOLE period, nothing may arrive (proves an absence)
await().during(twoRelayIntervals())
       .atMost(twoRelayIntervals().plusSeconds(10))
       .until(() -> topic.recordsWithKey(id.toString()).isEmpty());

atMost = "wait until it becomes true". during = "it must stay true for this long". The second one is how you test "nothing happens".

7. Architecture tests

Some rules are about the shape of the code, not its behavior. These tests read the compiled classes and fail the build if the shape is wrong.

  • Spring Modulith verify() (ModularityTest): no module uses another module's internals; no cycles (lesson 06).
  • ArchUnit: a library for writing your own rules in Java. Our InternalPackageRule says "no class may use a package named internal of another module".
static ArchRule noAccessToOtherModulesInternals(String root) {
    return classes()
            .that().resideInAPackage(root + "..")
            .should(notUseOtherModulesInternals(root))     // a custom ArchCondition
            .as("classes should not use another module's internal package");
}

A rule that never fails proves nothing, so BoundaryViolationTest runs both checks against a fixture that is wrong on purpose and asserts they throw (spec P3). The small helper methods are also unit-tested with a @ParameterizedTest (InternalPackageRuleTest). T12 (planned) adds the next rule the same way: no in-process listener on another module's events (D5), with its own violation fixture.

Two more "shape" tests in core-app: NoOwnPlatformConfigTest (core-app must not repeat the starter's outbox settings) and OpenApiExportIT (the committed API docs match the code). Rules written as tests cannot be forgotten.

8. TDD, coverage and flaky tests

Red, green, refactor

1. RedWrite a small test for the next behavior. Run it. See it fail for the right reason.
→
2. GreenWrite the simplest code that makes it pass.
→
3. RefactorClean up names and duplication. Tests stay green.

Seeing the test fail first matters: it proves the test can fail. The task notes record this habit, for example in T5 "golden test and table test both seen failing", and in T9 the export check was "seen failing with a tampered file".

Coverage with JaCoCo

JaCoCo records which lines the tests ran. Every build writes a report to target/site/jacoco/index.html in each module (root pom.xml). shared-kernel has a gate: under 90% line coverage the build fails (T4.6). Other modules set their own gate in their spec. Coverage shows what is not tested; a high number does not prove the tests check the right things.

The rules that keep tests honest

Never (spec "Boundaries") Never delete a failing test, or add @Disabled, to get to green. Never lower a coverage gate without asking first.

A flaky test passes sometimes and fails sometimes with no code change. The causes are almost always time (Instant.now(), sleep), order (tests sharing data), or async work. The spec's policy: a flaky test is fixed, or quarantined with an issue link; it is never silently deleted. Typical fixes in this project: a fixed Clock, Awaitility instead of sleep, and a unique key per test (each OutboxIT test uses its own probe id, so tests do not see each other's records).

10. Common mistakes

  • Naming an integration test …Test. Surefire runs it in the fast phase, and .\mvnw.cmd test suddenly needs Docker.
  • Thread.sleep in tests. Use Awaitility.
  • Instant.now() in code under test. Inject a Clock.
  • Tests that depend on each other's data. Use unique ids per test.
  • Small config differences between IT classes. Each difference starts another app context and more containers.
  • Mocking everything. Then the test only repeats the code. Prefer real objects and real infrastructure.
  • A rule test with no failing example. Keep a fixture that proves it fails.
  • Making a test green by weakening it. Fix the code, or change the spec first.

11. Practice

  1. Run the fast tests, then open a coverage report:

    .\mvnw.cmd test
start backend\shared-kernel\target\site\jacoco\index.html

  2. Red on purpose: in TopicsTest, change 12 to 13 in the CSV row for REGISTRATION_REQUESTS. Run the test and read the AssertJ message. Undo it.

  3. With Docker running, run only core-app's ITs and watch the containers start:

    .\mvnw.cmd -pl backend/core-app -am verify -DskipUTs
docker ps

  4. Read OutboxIT.o2_aRolledBackProbeIsNeverPublished. Why does it use during(...) and not just atMost(...)?

  5. TDD exercise (scratch branch): add a method Topics.replayableTopics() that returns the names of the replayable topics. Write the test first, see it fail, then make it pass. Throw the branch away afterwards (changing Topics is a spec change).

13. Test yourself

1. Why are integration tests named *IT and run by a different plugin?

So .\mvnw.cmd test stays fast and needs no Docker, while verify still runs everything. Failsafe also lets the build clean up after the ITs before it reports failure.

2. Why does the project test against a real PostgreSQL and Kafka instead of mocks?

The risky parts are exactly the interactions: SQL, transactions, Kafka acknowledgements. A mock only returns what you told it, so it cannot find those bugs. T7 found a real duplicate this way.

3. Why should a test never call Thread.sleep(5000) to wait for Kafka?

On a fast machine it wastes time; on a slow CI machine 5 s may not be enough and the test becomes flaky. Awaitility waits only as long as needed, up to a limit.

4. What does BoundaryViolationTest prove that ModularityTest cannot?

That the checks really fail on a violation. A passing verify() on clean code could also mean the check is switched off or misconfigured.

5. Why do OutboxIT and CoreApplicationIT use exactly the same annotations?

Spring caches the application context by its configuration. Same configuration = the app and its containers start once and are reused, which saves a lot of time.

6. A test fails sometimes on CI. Why is @Disabled not allowed?

It hides a real problem (in the test or the code) and removes a safety net silently. The rule is to fix it, or quarantine it with an issue link so it is tracked.
