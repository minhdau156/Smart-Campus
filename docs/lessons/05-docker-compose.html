Docker, Compose and Dockerfiles

One command starts seven programs on your laptop: Postgres, Redis, Kafka, Keycloak, OpenSearch, RustFS and Mailpit. This lesson explains how Docker and Docker Compose do that, how to debug them, and how our own apps will become container images in T15.

1. Why Docker

Without Docker, every developer would install seven servers by hand, each a different version with different settings. "It works on my machine" would be a daily problem.

Docker runs programs in containers: isolated boxes that carry the program and everything it needs. Docker Compose starts many containers together from one YAML file. Our file is infra/docker-compose.yml:

docker compose -f infra/docker-compose.yml up -d --wait    # start all, wait until healthy
docker compose -f infra/docker-compose.yml down             # stop and remove (data stays)

Like a shipping container: the port does not care what is inside, it handles every box the same way. Docker does not care if the box holds Postgres or Kafka.

2. Images, containers, layers, tags

Image

A read-only package: a small Linux file system with the program, at one exact version. Like a recipe, or a class in Java. Example: postgres:19.0-alpine3.24.

Container

A running copy of an image, with its own writable layer, network and processes. Like a cake made from the recipe, or an object made from a class. You can run many from one image.

Layers

An image is a stack of layers. Each layer holds the file changes of one build step. Images share layers they have in common, and Docker caches layers: if a step and everything before it did not change, the old layer is reused. This is why our app image (section 7) copies the big libraries first and our small code last.

Tags: always pinned

The part after : is the tag. Our compose file pins every tag exactly:

Never use latest latest is just a name that moves to each new release. Today it means 19.0, next month something else, and the same compose file gives a different setup. The spec forbids floating tags everywhere, including Docker.

3. Ports and the Compose network

Publishing ports

  postgres:
    ports:
      - "127.0.0.1:5432:5432"     # host-address : host-port : container-port

A container has its own network. ports opens a door from your computer into it. 127.0.0.1 means only your computer can use the door, not other devices on your Wi-Fi. Our dev passwords are simple, so this matters.

Service names are host names

Compose puts all services of a project on one private network (here smart-campus_default, from name: smart-campus). Inside it, each service name is a host name. This is the most important rule for T15:

App on your laptop(spring-boot:run)
Postgres: localhost:5432
Kafka: localhost:9092
App in a container(profile apps, T15)
Postgres: postgres:5432
Kafka: kafka:29092

Inside a container, localhost means that container itself, not your laptop. Keycloak already uses the in-network address: KC_DB_URL: jdbc:postgresql://postgres:5432/keycloak.

Kafka is special: it tells clients where to connect next ("advertised listeners"). So it has two client listeners: EXTERNAL://localhost:9092 for programs on your laptop and INTERNAL://kafka:29092 for containers (lesson 07).

4. Volumes and .env

Volumes keep data

A container's own files disappear when the container is removed. A volume is storage that Docker keeps separately:

    volumes:
      - postgres-data:/var/lib/postgresql                     # named volume: the database files
      - ./postgres/init:/docker-entrypoint-initdb.d:ro         # bind mount: our folder, read-only
…
volumes:
  postgres-data:
  kafka-data:
  opensearch-data:
  rustfs-data:
  • A named volume (postgres-data) is managed by Docker. It survives down and is deleted only by down -v.
  • A bind mount (./postgres/init) shows a folder from the repo inside the container. The Postgres image runs the scripts there only when its data folder is empty, which is how our schemas and users are created once (lesson 04).

Settings and secrets: .env

Passwords are not written in the compose file. Compose reads them from infra/.env (next to the compose file), and puts them in with interpolation:

    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?copy infra/.env.example to infra/.env}
      CORE_APP_DB_PASSWORD: ${CORE_APP_DB_PASSWORD:?set in infra/.env}
  • ${NAME} = the value from .env or your shell. ${NAME:?message} = stop with this message if it is missing or empty.
  • $$ = a real $ for the container's own shell (used in the healthcheck).
  • infra/.env.example is the template and is in git. infra/.env holds your values and is gitignored. First time: copy the example.
  • core-app's dev profile reads the same file (spring.config.import: optional:file:../../infra/.env[.properties]), so a password is written in exactly one place.

5. Healthchecks, depends_on, profiles

Healthchecks

"Running" is not "ready". Postgres runs for a few seconds before it accepts connections. A healthcheck is a command Docker repeats to ask "are you ready?":

    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U \"$${POSTGRES_USER}\" -d \"$${POSTGRES_DB}\""]
      interval: 5s
      timeout: 5s
      retries: 20

Each service has one (redis-cli ping, Kafka's API-versions tool, OpenSearch's cluster health …). The Keycloak image has no curl, so its check sends a tiny HTTP request with plain bash. up --wait returns only when every container is healthy, so a script can safely start the apps next.

depends_on

    depends_on:
      postgres:
        condition: service_healthy    # wait for the healthcheck, not just the start

In T15 each app container will wait like this for Postgres, Kafka and Redis.

Profiles

A Compose profile marks services that start only when asked. Services without a profile always start. The plan:

6. Everyday commands

All commands start with docker compose -f infra/docker-compose.yml. Below, that part is shortened to dc.

7. Our app image (T15)

Today our apps run with spring-boot:run. In T15 they also run as containers, built from one shared Dockerfile, infra/docker/spring-app.Dockerfile (planned). A Dockerfile is the recipe for an image. T15 asks for:

  • a multi-stage build: stage 1 unpacks the jar, stage 2 is the small final image;
  • the layers of the Spring Boot jar copied dependencies first, our code last;
  • a pinned Eclipse Temurin 21 JRE base (a JRE runs Java; it cannot compile);
  • a non-root user, and the jar path as a build argument;
  • a healthcheck on /actuator/health.

Here is a sketch of that shape. It is not the final file: T15 writes it and pins the real base tag.

# ---- stage 1: unpack the layered jar ----
FROM eclipse-temurin:<exact 21 JRE tag> AS extract
WORKDIR /build
# the jar path, e.g. backend/core-app/target/core-app-0.1.0-SNAPSHOT.jar
ARG JAR_FILE
COPY ${JAR_FILE} application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

# ---- stage 2: the image we ship ----
FROM eclipse-temurin:<exact 21 JRE tag>
WORKDIR /app
RUN groupadd --system app && useradd --system --gid app app
# big layers that rarely change first ...
COPY --from=extract /build/extracted/dependencies/ ./
COPY --from=extract /build/extracted/spring-boot-loader/ ./
COPY --from=extract /build/extracted/snapshot-dependencies/ ./
# ... our small, often-changing code last
COPY --from=extract /build/extracted/application/ ./
# run as a normal user, not root
USER app
HEALTHCHECK CMD curl -fs http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "-jar", "application.jar"]

(In a Dockerfile, a # comment must be on its own line.)

Why each part

PartWhy
Multi-stageThe unpack step and its leftovers stay in stage 1. Only the final files reach the shipped image.
-Djarmode=tools … extract --layersSpring Boot's jar can unpack itself into its layers (the root pom turned layers on in T2). Each layer becomes one Docker layer.
Dependencies firstChange one line of Java → only the small application layer is rebuilt. The libraries come from the cache (T15.5 checks this).
Pinned JRE tagSame reason as everywhere: the same build tomorrow. A JRE is smaller than a JDK.
Non-root userIf someone breaks into the app, they are not root inside the container. T15.5 checks id -u is not 0.
HEALTHCHECKDocker knows when the app is ready. Check that the base image really has curl; if not, T15 must use another way (the Keycloak check in our compose file shows a bash-only trick). The port depends on the app (8081 for core-app).

Other T15 details: a .dockerignore so only the built jars are sent to Docker (not the whole repo); memory limits per container plus JAVA_TOOL_OPTIONS with -XX:MaxRAMPercentage, so Java sizes its memory from the container limit; and only the gateway's port 8080 is published. The build runs after Maven:

.\mvnw.cmd package -DskipTests
docker compose -f infra/docker-compose.yml --profile apps up -d --build --wait

The spec chose a plain Dockerfile over Cloud Native Buildpacks because it is easier to read and to add the OpenTelemetry agent to later (T16).

8. Testcontainers and Windows tips

Testcontainers: Docker inside your tests

Testcontainers is a Java library that starts containers from a test. Our ITs use it to get a real Postgres and a real Kafka:

@Bean
@ServiceConnection
PostgreSQLContainer postgres() {
    return new PostgreSQLContainer("postgres:19.0-alpine3.24");   // same tag as Compose
}

@Bean
@ServiceConnection
KafkaContainer kafka() {
    return new KafkaContainer("apache/kafka:4.4.0");
}

Compose

Long-lived, for you and for spring-boot:run. Fixed ports. Data kept in volumes.

Testcontainers

Short-lived, one fresh set per test run. Random free ports, given to Spring by @ServiceConnection. Removed after the tests. Same images, so tests match dev.

So .\mvnw.cmd test needs no Docker, but .\mvnw.cmd verify (which runs the *IT classes) needs Docker Desktop running. The two do not share data, and Compose can be up or down while ITs run.

Windows tips

  • Docker Desktop must be running before docker or the ITs work. On Windows it uses WSL 2 (a real Linux kernel inside Windows).
  • Memory: the infra uses about 2.2 GB at peak (T3). WSL 2 memory can be limited in %UserProfile%\.wslconfig ([wsl2], memory=8GB); leave enough for Docker, the IDE and the apps.
  • Line endings: a shell script with Windows line endings (CRLF) fails inside a Linux container. Our .gitattributes keeps files in LF (only .cmd/.bat use CRLF), which protects infra/postgres/init/01-schemas-and-users.sh.
  • Port already in use: a Postgres installed on Windows may already hold 5432. Find it with Get-NetTCPConnection -LocalPort 5432 and stop that service.
  • The space in C:\Smart Campus: always quote paths in scripts.
  • From a container to your laptop: use host.docker.internal (T18's Prometheus will reach spring-boot:run apps this way).

10. Common mistakes

  • Using localhost inside a container to reach another service. Use the service name (postgres, kafka:29092).
  • Running down -v by accident. It deletes every volume: all local data, topics and users.
  • Expecting a new password in .env to apply. The init script runs only on an empty volume.
  • Using latest or a short tag like 21. Pin the exact tag.
  • Committing infra/.env. It is gitignored for a reason.
  • Publishing ports on 0.0.0.0 (the default when you write only "5432:5432"). Keep 127.0.0.1:.
  • Copying the app code before the libraries in a Dockerfile. Every code change then rebuilds all layers.
  • Running the app as root in the image.
  • Running Compose apps and spring-boot:run apps at the same time. They want the same ports.

11. Practice

  1. First time only, create your settings file, then start everything and time it:

    if (-not (Test-Path infra/.env)) { Copy-Item infra/.env.example infra/.env }
Measure-Command { docker compose -f infra/docker-compose.yml up -d --wait }
docker compose -f infra/docker-compose.yml ps

  2. Find the network and the volumes Compose created:

    docker network ls
docker volume ls

  3. Prove the "service name" rule. From inside the Redis container, reach Postgres by name, then try localhost:

    docker compose -f infra/docker-compose.yml exec redis sh -c "nc -z postgres 5432 && echo reachable"
docker compose -f infra/docker-compose.yml exec redis sh -c "nc -z localhost 5432 || echo not-here"

    (If nc is missing in the image, try the same idea with another container.)

  4. Open Mailpit's web page at http://localhost:8025 and RustFS's console at http://localhost:9001. Which service answers on which port?

  5. Follow Kafka's log in one window. In another, pause and unpause Kafka, and watch dc ps change. Then read how OutboxIT uses the same trick.

  6. On paper: write the core-app service block for the apps profile. Which datasource URL, Kafka address and healthcheck does it need? What goes in depends_on?

13. Test yourself

1. Why does an app in a container use postgres:5432, while spring-boot:run uses localhost:5432?

localhost always means "this machine". For an app on your laptop, the published port on your laptop leads to Postgres. Inside a container, localhost is the container itself, so it must use the service name, which Compose's network turns into Postgres's address.

2. You changed CORE_APP_DB_PASSWORD in infra/.env and now core-app cannot log in. Why?

The user and its password were created by the init script on the first start, when the volume was empty. The script does not run again. Either set the old password back, or run down -v (deletes all local data) and start again.

3. Why does up --wait matter in scripts and CI?

It returns only when every healthcheck passes. Without it, the next step (starting an app, running a smoke test) could run while Postgres or Kafka is still starting, and fail randomly.

4. Why does the planned Dockerfile copy dependencies before our application code?

Docker reuses cached layers until the first step that changed. Libraries rarely change, our code changes often. With code last, a code change rebuilds only the small top layer.

5. Why must the app container not run as root?

If an attacker finds a hole in the app, they get the rights of the process. As a normal user they can do much less inside the container, and it is harder to escape to the host.

6. Why do Testcontainers use the same image tags as the compose file?

So tests run against exactly the versions developers use. A test that passes on a different Postgres or Kafka version proves little about the real setup.
