Reliable events: outbox, dedupe, replay

How do we save data in PostgreSQL and tell other modules about it through Kafka, without ever losing a message or acting on it twice? This is the most important idea in the Smart Campus backend.

1. Why you need this in Smart Campus

Smart Campus modules do not call each other's tables. When something important happens, a module publishes an event (a short message that says "this happened"). Other modules listen and react. For example:

  • registration confirms a seat → publishes EnrollmentConfirmed → timetable adds the class to the student's week, and notification sends "You got the seat!".
  • course moves a class to another room → publishes ScheduleChanged → timetable updates, students get a message.
  • payment gets money for a club event → publishes PaymentConfirmed → club creates the ticket.

If one of these events is lost, a student pays and gets no ticket. If an event is sent for a change that never happened, a student sees a class they are not in. If it is applied twice, a student gets two emails or two tickets. This lesson shows the three tools that stop all three problems.

2. The dual-write problem

The simple way looks like this:

@Transactional
void confirm(Enrollment e) {
    repository.save(e);                          // 1. write to PostgreSQL
    kafkaTemplate.send("registration.events", …); // 2. write to Kafka
}                                                // 3. COMMIT

This is a dual write: two writes to two different systems. There is no transaction that covers both PostgreSQL and Kafka. So things can go wrong in the gaps:

What goes wrongResultName
Kafka send works, then the COMMIT fails (for example a constraint error) Other modules react to an enrollment that does not existPhantom event
COMMIT works, but Kafka is down, or the app crashes before the send The enrollment exists, but nobody hears about itLost event
You move the send after the commit Fixes phantoms, but a crash between commit and send still loses the eventLost event
Key point You cannot make two different systems commit together "by being careful". You need a design where there is only one write that matters.

3. The transactional outbox

The idea: do not send to Kafka inside the business transaction. Save the event in a database table instead, in the same transaction as the business data. That table is the "outbox", like the tray on an office desk where you put letters to be posted later.

1. Business transactionINSERT enrollment
INSERT event into outbox table
COMMIT (both or neither)
→
2. Relay (after commit)Read unsent events
Send each to Kafka
→
3. Kafka acknowledgesMark the outbox row completed

Now look at the failure cases again:

  • Rollback → the outbox row is rolled back too → nothing is ever sent. No phantom.
  • Kafka down or app crash after commit → the row is still in the table, not completed → the relay tries again later. Nothing is lost.

The only write that "decides" is the single database commit. Everything after it is retry work.

4. The outbox in Spring Modulith

We do not write our own outbox table and relay. Spring Modulith already has one, called the Event Publication Registry. This is spec decision D1, and task T7 tested it with a real PostgreSQL and a real Kafka.

@Transactional
UUID create(String note) {
    Instant now = clock.instant();
    OutboxProbe probe = new OutboxProbe(UUID.randomUUID(), note, now);

    jdbc.update("INSERT INTO platform.outbox_probe (id, note, created_at) VALUES (?, ?, ?)",
            probe.id(), probe.note(), Timestamp.from(probe.createdAt()));   // business row

    events.publishEvent(new DomainEvent<>(                                 // Modulith saves this
            UUID.randomUUID(), EVENT_TYPE, 1, now, probe.id().toString(), probe)); // in event_publication

    return probe.id();
}

What happens, step by step:

  1. publishEvent(...) is a normal Spring call. Modulith catches it and writes one row into platform.event_publication, using the same database connection, so it is part of the same transaction.
  2. The method ends → Spring commits. Both rows are saved, or neither.
  3. After the commit, a background thread sends the event to Kafka with KafkaTemplate.
  4. When Kafka says "stored" (acks=all), the row gets a completion_date and status COMPLETED.
  5. If Kafka does not answer, the row becomes FAILED. Our OutboxRetryJob sends FAILED rows again every 30 seconds. At startup, all unfinished rows are sent again too.
Status of one row in platform.event_publication

  PUBLISHED ──► PROCESSING ──► COMPLETED        (happy path)
                    │
                    └──► FAILED ──► RESUBMITTED ──► PROCESSING ──► COMPLETED
                         (Kafka down,            (OutboxRetryJob,
                          or stuck > 5 min)       every 30 s)

The settings for all of this live in one place, so every app gets the same behavior:

spring:
  modulith:
    events:
      jdbc:
        schema-initialization:
          enabled: false          # Flyway creates the table, not Modulith (T7 trap)
      republish-outstanding-events-on-restart: true
      staleness:
        processing: 5m            # stuck "in flight" too long → FAILED → retried
  kafka:
    producer:
      acks: all                   # "done" only when Kafka really stored it
campus:
  outbox:
    retry-interval: 30s

5. At least once, never exactly once

The outbox guarantees no lost events and no phantom events. It does not guarantee "exactly one copy". T7 proved this with a real test:

  1. The app sends the event. Kafka is frozen (docker pause) and does not answer.
  2. After the producer timeout, the row is marked FAILED.
  3. Kafka wakes up and stores the request it was holding → copy 1.
  4. The retry job sends the FAILED row again → copy 2, with the same eventId.

This is not a bug in Modulith. Any system that retries after a timeout has this problem: when you get no answer, you cannot know if the other side got the message. So the rule in distributed systems is:

Smart Campus rule (spec O3, decided at Checkpoint B) Delivery is at least once. Every copy of an event has the same eventId. Consumers must make repeats harmless.

6. The idempotent consumer

Idempotent means "doing it twice has the same result as doing it once". Pressing a lift button five times still calls the lift once. Our consumers become idempotent by remembering which events they already handled (spec D2, built in T11):

CREATE TABLE notification.processed_events (
    event_id     UUID PRIMARY KEY,         -- the eventId from the envelope
    processed_at TIMESTAMPTZ NOT NULL
);
@KafkaListener(topics = "registration.events", groupId = "notification")
@Transactional
void on(DomainEvent<EnrollmentConfirmed> event) {
    boolean firstTime = processedEvents.tryInsert(event.eventId());  // INSERT … ON CONFLICT DO NOTHING
    if (!firstTime) {
        return;                       // seen before: skip, but still acknowledge
    }
    inbox.add(event.payload().studentId(), "You got the seat!");      // the side effect
}                                     // COMMIT: marker row + side effect together

Why it works: the "I have seen this" row and the side effect are saved in the same transaction. Either both are saved, or neither. So:

  • Copy 2 arrives → the insert hits the primary key → we skip. Side effect happened once.
  • The app crashes in the middle → both are rolled back → Kafka gives the event again → we process it for the first time. Still once.

Not idempotent

UPDATE seats SET taken = taken + 1 on every event. Two copies → two seats taken.

Idempotent

Check processed_events first, or write absolute values: INSERT … ON CONFLICT (enrollment_id) DO NOTHING.

Emails and push messages An email cannot be "rolled back". If the app crashes after sending the email but before the commit, the student may get the email twice. That is why notification sending is designed as "save to inbox and outbox first, then send" and is marked not replayable (next section).

7. The event envelope and keys

Every event in Smart Campus is wrapped in the same "envelope", from shared-kernel:

public record DomainEvent<P>(
        UUID eventId,        // unique per event; the dedupe key (D2)
        String type,         // "EnrollmentConfirmed": past tense
        int schemaVersion,   // raise it when the payload changes in a breaking way (D4)
        Instant occurredAt,
        String aggregateId,  // which thing changed, e.g. a section id
        P payload) { … }

The Kafka message key decides ordering: Kafka keeps messages in order only inside one partition, and the key picks the partition. So the key is chosen per topic, in Topics (spec D6):

TopicPartitionsKeyWhy this key
registration.requests12sectionIdRequests for one section are handled in arrival order (fair waitlist)
registration.events6studentIdOne student's enroll/drop events stay in order
course.events3sectionIdChanges to one section stay in order
grade.events3studentIdOne student's grades stay in order
campus.events3aggregateIdEverything else

Trace information (traceparent) travels in Kafka headers, not in the payload, so business data stays clean (lesson 12).

8. Replay: rebuilding a read model

Some modules keep a read model: a copy of data from other modules, shaped for fast reading. timetable (a student's week) and search are read models. Because our event topics keep all history (retention.ms=-1), we can throw a read model away and build it again from the start of the topic (spec D5, built in T12):

  1. Stop the consumer.
  2. Delete its derived tables and its processed_events rows.
  3. Reset its Kafka consumer group to the earliest offset.
  4. Start it again. It reads every event from the beginning and rebuilds the same rows.

Two rules make replay safe:

  • Cross-module events always come from Kafka, even between two modules in the same core-app. An in-process Spring listener cannot be replayed. An ArchUnit test will fail the build if someone listens in-process to another module's event.
  • Only read-model consumers are replayable. A consumer that sends emails is registered as non-replayable, otherwise a replay would email every student again. registration.requests is also non-replayable: it holds commands ("give me a seat"), not facts.

10. Common mistakes

  • Calling kafkaTemplate.send inside business code. Always use publishEvent, so the outbox is used.
  • Publishing outside a transaction. Without @Transactional, the event and the data are not saved together.
  • Using a new random eventId on retry. Then consumers cannot see that it is a repeat. The id is set once, when the event is created.
  • Doing the dedupe check and the side effect in two transactions. A crash between them loses the event or doubles it.
  • Putting whole entities from another module in the payload. Send ids and the facts that changed.
  • Letting Modulith create its own table. Flyway owns all tables. Keep schema-initialization.enabled: false.

12. Words to know

WordMeaning in simple words
Dual writeWriting the same change to two systems with no shared transaction. Unsafe.
OutboxA database table where events wait until they are sent to Kafka.
RelayThe background worker that reads the outbox and sends to Kafka.
Event Publication RegistrySpring Modulith's built-in outbox (event_publication table).
ExternalizationModulith's word for "send this event to an outside broker like Kafka".
Acknowledge (ack)Kafka's answer "I stored it".
At-least-onceEvery event arrives, but maybe more than once.
IdempotentDoing it again changes nothing more.
Read modelA copy of data built from events, shaped for fast reads.
ReplayReading a topic again from the start to rebuild a read model.
Phantom eventAn event about a change that was rolled back.

13. Test yourself

1. Why is it not enough to call kafkaTemplate.send after the commit?

The app can crash (or Kafka can be down) between the commit and the send. The data is saved but the event is lost forever, because nothing remembers that it still has to be sent.

2. A transaction saves an enrollment and calls publishEvent, then throws. What reaches Kafka?

Nothing. The event_publication row was written in the same transaction, so it is rolled back with the enrollment. There is nothing for the relay to send (spec O2).

3. Why can't the outbox promise exactly one copy?

When Kafka does not answer in time, the sender cannot know if Kafka stored the message or not. To avoid losing it, it sends again, which can create a second copy. Only the consumer can remove repeats.

4. Why must the processed_events insert be in the same transaction as the side effect?

If they are separate, a crash between them either marks an event "done" without doing it (lost) or does it without marking it (done twice on retry). Together, they are all-or-nothing.

5. Why must timetable read course.events from Kafka even though both modules run inside core-app?

Because only Kafka keeps the history. An in-process listener cannot be replayed, so the read model could never be rebuilt. One delivery path is also simpler to reason about (spec D5).

6. Why is registration.requests keyed by sectionId and not by studentId?

Kafka keeps order per key. Keying by section puts all requests for one section in one partition, in arrival order, so seats and the waitlist are given out fairly.
