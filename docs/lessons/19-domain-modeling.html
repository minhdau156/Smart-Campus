Domain modeling: aggregates and rules

How do we turn "a section has 60 seats" and "two classes can never share a room at the same time" into Java classes and SQL tables that make breaking these rules impossible? This lesson uses the course module as the example, but every module uses the same ideas.

1. Why you need this in Smart Campus

The domain is the real-world area the software is about. For us that is a university: courses, sections, rooms, students, grades. Domain modeling means choosing the classes, fields and methods that describe this world, and putting the business rules in the right place.

The course module (module 4) has rules like these, from the Plan's user stories:

  • REG-7: an academic admin creates courses and sections with a capacity, a lecturer and a schedule.
  • REG-9: during registration, the admin can raise a capacity or open a new section.
  • TT-4: a lecturer reports a cancelled or rescheduled class, and students are told automatically.
  • TT-5: rooms and time slots are assigned "without clashes", so no two classes share a room at once.

If these rules live in random places (a controller here, a SQL query there, a React form there), one day someone adds a new endpoint and forgets one rule. Then a section gets capacity -5, or two lectures are booked into room B4-201 at 07:30 on Monday. Domain modeling puts each rule in one place that every path must go through.

2. One language for the team (ubiquitous language)

Ubiquitous language means "the same words everywhere": in the user stories, in conversations, in class names, in table names and in event names. If the admin says "section" and the code says ClassGroup, every discussion needs a translation, and translations create bugs.

3. Entity, value object, aggregate

Domain-driven design (DDD) gives us three building blocks. Think of a library:

Entity

Has an identity that stays the same while its data changes. A library member is still the same person after changing their phone number. In Smart Campus: Section, Course, Room. Two sections with the same capacity are still two different sections.

Value object

Has no identity. It is equal to another one when all its values are equal, like two 50,000 VND notes. It never changes; you replace it. In Smart Campus: Money, TimeRange, WeeklySlot, typed ids. Java records are perfect for this.

An aggregate is a small group of entities and value objects that are saved together and checked together. One entity is the root, the only door into the group. Outside code may hold a reference to the root (by its id), never to the inner parts. Think of an order and its order lines: you never change one line without going through the order, because the order must check its total.

Aggregate "Section"  (one transaction = one aggregate)

  ┌───────────── Section (root, entity) ─────────────┐
  │ id: SectionId        capacity: 60                │
  │ courseId: CourseId   semesterId: SemesterId      │   other aggregates are
  │ lecturerId: UUID     status: OPEN                │   referenced by ID only:
  │ version: 7                                       │     CourseId → Course
  │                                                  │     RoomId   → Room
  │  weeklySlots: [ WeeklySlot(MON 07:30-09:30, R1), │
  │                 WeeklySlot(THU 13:00-15:00, R2) ]│   (value objects inside)
  │  meetings:    [ Meeting(2027-01-04 …, SCHEDULED),│
  │                 Meeting(2027-01-07 …, CANCELLED)]│   (entities inside)
  └──────────────────────────────────────────────────┘

Rules of thumb for aggregates:

  • Small. A Course does not contain all its sections. They are separate aggregates that point to the course by CourseId.
  • Reference others by id. This is the same rule as "no cross-schema foreign keys" (C4), one level smaller.
  • One aggregate per transaction (as a default). If a change must touch two aggregates, often one changes now and the other reacts to an event.

Typed ids

Every id is a UUID. If all ids are plain UUID, nothing stops you from passing a student id where a section id is expected. shared-kernel gives us TypedId, so each module writes tiny id records:

package edu.campus.course;

import edu.campus.kernel.id.Ids;
import edu.campus.kernel.id.TypedId;
import java.util.UUID;

public record SectionId(UUID value) implements TypedId {
    public SectionId {
        Ids.requireId(value, "SectionId");   // null is rejected at once
    }

    public static SectionId newId() {
        return new SectionId(Ids.newId());
    }
}

Now enroll(SectionId, StudentId) cannot be called with the arguments swapped: the compiler stops you. In the database and on the wire, it is still a plain UUID (value()).

4. Invariants and rich models

An invariant is a rule that must be true always, not only "after validation". Examples for a section:

  • capacity is at least 1;
  • a weekly slot starts before it ends (already true for every TimeRange);
  • a cancelled section cannot get new meetings;
  • a meeting can only be moved if it is not in the past.

The trick: make it impossible to create or change the object in a bad state. The constructor checks the first state. Every method that changes state checks the rule before it changes anything. There are no public setters.

package edu.campus.course.internal;

record WeeklySlot(DayOfWeek day, LocalTime start, LocalTime end, RoomId room) {
    WeeklySlot {
        Objects.requireNonNull(day, "day");
        Objects.requireNonNull(room, "room");
        if (!start.isBefore(end)) {
            throw new IllegalArgumentException("A slot must start before it ends: %s-%s".formatted(start, end));
        }
    }
}
package edu.campus.course.internal;

final class Section {
    private final SectionId id;
    private final CourseId courseId;
    private final SemesterId semesterId;
    private UUID lecturerId;             // a user from identity: bare UUID, no FK (C4)
    private int capacity;
    private SectionStatus status;
    private final List<Meeting> meetings;
    private long version;                // optimistic lock, see section 7

    Section(SectionId id, CourseId courseId, SemesterId semesterId, UUID lecturerId, int capacity) {
        this.id = Objects.requireNonNull(id, "id");
        this.courseId = Objects.requireNonNull(courseId, "courseId");
        this.semesterId = Objects.requireNonNull(semesterId, "semesterId");
        this.lecturerId = Objects.requireNonNull(lecturerId, "lecturerId");
        this.capacity = requireValidCapacity(capacity);
        this.status = SectionStatus.OPEN;
        this.meetings = new ArrayList<>();
    }

    /** REG-9: raise (or lower) the capacity. Returns the fact that happened. */
    SectionChanged changeCapacity(int newCapacity, Instant now) {
        requireNotCancelled();
        this.capacity = requireValidCapacity(newCapacity);
        return SectionChanged.from(this, now);
    }

    /** TT-4: the lecturer cancels one class. */
    ScheduleChanged cancelMeeting(MeetingId meetingId, String reason, Instant now) {
        Meeting meeting = findMeeting(meetingId);
        if (meeting.endsBefore(now)) {
            throw new CampusProblem(ProblemCode.CONFLICT, "This class is already over");
        }
        meeting.cancel(reason);
        return ScheduleChanged.from(this, now);
    }

    private static int requireValidCapacity(int capacity) {
        if (capacity < 1) {
            throw new CampusProblem(ProblemCode.VALIDATION_FAILED, "Capacity must be at least 1");
        }
        return capacity;
    }
    // requireNotCancelled(), findMeeting(…), getters …
}

Note three things. now comes in as a parameter (the service takes it from an injected Clock, never Instant.now()), so tests can control time. The methods return an event: the change and the fact "this happened" are created together. And the errors use CampusProblem, so the web layer turns them into problem JSON (lesson 09). Today ProblemCode has only VALIDATION_FAILED, CONFLICT and a few others; the Arch also names SCHEDULE_CONFLICT, which the course spec would add.

Rich model vs anemic model

Anemic model

The class is only fields with getters and setters. All rules live in "service" classes. Any code can call section.setCapacity(-5). To know the rules, you must read every service.

Rich model

The class has behaviour: changeCapacity, cancelMeeting, reschedule. The rules live next to the data. The application service only loads, calls one method, saves and publishes.

@Service
class SectionService {
    private final SectionRepository sections;
    private final ApplicationEventPublisher events;
    private final Clock clock;

    SectionService(SectionRepository sections, ApplicationEventPublisher events, Clock clock) {
        this.sections = sections;
        this.events = events;
        this.clock = clock;
    }

    @Transactional
    void changeCapacity(SectionId id, int newCapacity) {
        Section section = sections.get(id);                              // 1. load
        Instant now = clock.instant();
        SectionChanged fact = section.changeCapacity(newCapacity, now);  // 2. rules
        sections.save(section);                                          // 3. save (version check)
        events.publishEvent(new DomainEvent<>(UUID.randomUUID(),           // 4. outbox (lesson 08)
                "SectionChanged", 1, now, id.value().toString(), fact));
    }
}

5. The course aggregates

Here is a proposed split for the course schema. The Plan's table list (§4) has courses, course_prerequisites, semesters, sections and section_schedules. Rooms have no table in the Plan, which the capability map lists as gap C10 ("rooms (TT-5)").

Aggregate (root)Inside itInvariants it protectsStory
Coursecode, name, credits, list of prerequisite CourseIds code is unique; credits > 0; a course is not its own prerequisite; no prerequisite cycles (CS201 needs CS101 needs CS201)REG-7
Semestercode, start date, end datestart before end; codes uniqueREG-7
Sectioncapacity, lecturer id, status, weekly slots, meetings capacity ≥ 1; slots valid; no changes when cancelled; past meetings cannot moveREG-7, REG-9, TT-4
Roomcode (e.g. "B4-201"), building, seatscode uniqueTT-5

Some rules need data from more than one aggregate. "No two meetings in one room at the same time" looks at many sections. "No prerequisite cycles" looks at many courses. One aggregate cannot protect these alone, because it does not hold the other data. For these set rules, we use a check in the service plus a database constraint (next section).

Smart Campus rule C17: no enrolled_count in course The Plan's sections table has enrolled_count, and Arch §4 says course consumes EnrollmentConfirmed to update it. But registration also consumes SectionChanged from course. Both together make a dependency cycle. So the capability map decided: course.sections has no enrolled_count. Live seat counts come from registration, which keeps its own section_seats table (C5, lesson 20).

This has a real effect on the model. When an admin lowers a capacity from 60 to 40, Section cannot check "but 52 students are already enrolled", because it does not know that number. The course spec must decide what happens: either registration simply stops giving seats until enrolled < capacity, or the UI asks registration first. Knowing which module owns which data tells you where a rule can live.

6. Room clashes: two guards

TT-5 says no two classes share a room at once. Two meetings clash when their time ranges overlap and they use the same room. shared-kernel already has the overlap check:

public record TimeRange(Instant start, Instant end) {
    /** True if the two ranges share at least one instant. */
    public boolean overlaps(TimeRange other) {
        return start.isBefore(other.end) && other.start.isBefore(end);
    }
}

The end is not included (a "half-open" range). So 07:30–09:30 and 09:30–11:30 touch but do not overlap. That is what we want: one class can end at 09:30 and the next one start at 09:30 in the same room.

Guard 1: the check in Java

Weekly slots are in local wall-clock time ("Monday 07:30"). To compare real times, the service turns each slot into dated meetings for the semester, using the university's time zone (ZoneId.of("Asia/Ho_Chi_Minh"), never the server's default). Then it asks the repository for meetings in the same room in that period and checks each one:

List<Meeting> wanted = slot.meetingsBetween(semester.startDate(), semester.endDate(), CAMPUS_ZONE);
for (Meeting m : wanted) {
    meetings.findActiveInRoom(m.room(), m.time())          // SQL uses the index below
            .stream()
            .filter(other -> other.time().overlaps(m.time()))
            .findFirst()
            .ifPresent(other -> {
                throw new CampusProblem(ProblemCode.CONFLICT,
                        "Room %s is already used by section %s at %s".formatted(m.room(), other.sectionId(), other.time()));
            });
}

This gives a clear error message ("Room B4-201 is already used by CS101-02 on Monday 07:30"). But it has a gap: two admins can check at the same moment, both see "free", and both save. This is a check-then-act race (more in lesson 20).

Guard 2: a PostgreSQL exclusion constraint

A UNIQUE constraint says "no two rows have equal values". An exclusion constraint is more general: "no two rows where this operator is true". With && (the "overlaps" operator for ranges), the database itself refuses the second booking, even when two transactions run at the same time.

-- One row per real class on a date. tstzrange = range of "timestamp with time zone".
CREATE TABLE course.section_meetings (
    id          UUID PRIMARY KEY,
    section_id  UUID NOT NULL REFERENCES course.sections (id),   -- same schema: FK allowed
    room_id     UUID NOT NULL REFERENCES course.rooms (id),
    during      TSTZRANGE NOT NULL,                              -- '[start, end)', end not included
    status      TEXT NOT NULL DEFAULT 'SCHEDULED',               -- SCHEDULED / CANCELLED
    created_at  TIMESTAMPTZ NOT NULL,
    CONSTRAINT meeting_not_empty CHECK (NOT isempty(during)),
    CONSTRAINT no_room_double_booking
        EXCLUDE USING gist (room_id WITH =, during WITH &&)
        WHERE (status <> 'CANCELLED')                            -- cancelled classes free the room
);

How to read the constraint: "for two rows that are not cancelled, it must never be true that the room_ids are = and the during ranges && (overlap)." PostgreSQL builds a GiST index to check this fast. When it fails, the error has SQLSTATE 23P01 (exclusion_violation), which the service maps to a 409 problem.

Two details to know

1. Mixing = on a UUID column with && on a range in one GiST index needs the btree_gist extension. Our app user core_app has no right to create extensions, so the Postgres init script (run as the admin user) would have to run CREATE EXTENSION btree_gist. That is an infra change to agree on first.

2. tstzrange(a, b) uses the bounds [) by default: start included, end not included. This matches TimeRange, so Java and SQL agree on "touching is not overlapping".

Guard 1: Java checkFriendly message, names the other section. Can miss a race.
+
Guard 2: DB constraintNever misses, even with two admins at once. Error is less friendly.
=
ResultGood errors in normal use, and correctness always.

Why store dated meetings and not only weekly slots? Because TT-4 changes single dates: "the class on 1 Feb is cancelled", "the class on 8 Feb moves to Wednesday". A weekly slot cannot express that. Generating the meetings of one semester (about 15 weeks × 1–3 slots) is small. The course spec will confirm this design.

7. Optimistic locking

During the rush, two admins may open the same section page. Admin A raises the capacity to 80. Admin B, who still sees the old page, changes the lecturer and saves the old capacity 60 with it. A's change is silently lost: a lost update.

Optimistic locking stops this without holding database locks while people think. Each row has a version number. Every update says "only if the version is still the one I read", and adds 1:

UPDATE course.sections
   SET capacity = :capacity, lecturer_id = :lecturerId, status = :status,
       version = version + 1
 WHERE id = :id
   AND version = :versionIReadEarlier;     -- 0 rows updated = someone else was faster

If 0 rows change, the service throws CampusProblem(ProblemCode.CONFLICT, "This section was changed by someone else. Reload and try again.") → HTTP 409. (With JPA, a @Version field does the same thing for you.) The client can send the version it loaded, for example in an If-Match header or in the request body.

It is called "optimistic" because it hopes conflicts are rare and only checks at the end. A "pessimistic" lock (SELECT … FOR UPDATE) would block the second admin until the first one finishes. For admin screens, optimistic is the right choice. The same version also travels in events, so consumers can ignore old news (lesson 22).

8. Domain events and the public API

Domain events

A domain event is a fact that already happened, so its name is in the past tense: SectionChanged, ScheduleChanged, never ChangeSection (that would be a command). course publishes them to course.events, keyed by sectionId, so all changes to one section stay in order (Topics.COURSE_EVENTS, spec D6).

Event (planned)WhenWho listens (planned)
SectionChangedSection created, capacity changed (REG-9), lecturer changed, section opened/closed/cancelled registration (updates section_seats, C5), timetable, grade (who is the lecturer)
ScheduleChangedSlots assigned (TT-5), one class cancelled or moved (TT-4) timetable (TT-1, TT-3), notification (TT-2: "your class moved")
public record SectionChanged(
        SectionId sectionId,      // the Kafka key for course.events (Topics reads this field)
        CourseId courseId,
        String courseCode,        // a few facts consumers need, so they don't call back
        SemesterId semesterId,
        UUID lecturerId,
        int capacity,
        String status,
        long version) { }         // consumers keep only the newest version

Notice the payload carries the section's whole public state, not only "the capacity went from 60 to 80". Consumers can then simply "save the latest version". This is easier to make idempotent than a delta like "+20". It still carries ids and facts only, never the full entity with its internal parts (platform rule).

Public API vs internal

In core-app, the module's package root edu.campus.course is its public API. Anything in edu.campus.course.internal is private, and Spring Modulith's verify() fails the build if another module imports it (lesson 06).

edu.campus.course                     ← public: other core-app modules may use these
├── SectionId, CourseId, SemesterId, RoomId    (typed ids)
├── SectionChanged, ScheduleChanged            (event payloads)
├── CourseCatalog                              (a small read interface, if needed)
└── internal/                         ← private: only course uses these
    ├── Section, Meeting, WeeklySlot, Course, Room
    ├── SectionService, SectionRepository
    └── web/SectionController

Keep the public API small. Every public type is a promise you must keep. And remember: registration-service is a separate app. It cannot call any Java method in core-app. It only sees course.events on Kafka. How the event classes are shared with it (a small contract library, or each consumer keeping its own copy of the JSON shape) is a question for the course spec.

10. Common mistakes

  • Public setters on aggregates. setCapacity(int) lets anyone skip the rules. Use intention-revealing methods like changeCapacity.
  • Validating only in the controller. Bean Validation on a request DTO is good for "field is missing", but the invariants must live in the model, or a Kafka consumer or batch job will bypass them.
  • Huge aggregates. Putting all sections inside Course means every capacity change locks and loads the whole course.
  • Trusting the Java clash check alone. Without the exclusion constraint, two admins can still double-book a room.
  • Using the server's time zone. Use Asia/Ho_Chi_Minh explicitly when turning "Monday 07:30" into an Instant.
  • Adding enrolled_count back to course "just for display". That breaks C17. Ask registration for seat counts.
  • Event names in the present or imperative tense (UpdateSection). Events are facts: past tense.
  • Calling Instant.now() inside the model. Pass now in from an injected Clock.

13. Test yourself

1. Why is WeeklySlot a value object but Section an entity?

A section keeps its identity while its capacity or lecturer changes; other modules refer to it by id. A slot is just "Monday 07:30–09:30 in B4-201": two slots with the same values are the same thing, and to change one you replace it.

2. Why check invariants in the constructor and methods instead of in the controller?

Because the controller is only one way in. Kafka consumers, jobs, imports and future endpoints also change sections. If the class itself refuses bad states, no path can create one.

3. Why do we need the exclusion constraint if the Java code already checks for clashes?

The Java check reads, then writes. Two transactions can both read "free" before either writes (check-then-act race). The database constraint is checked at write time, with proper locking inside PostgreSQL, so the second booking always fails.

4. Why can't the Section aggregate stop an admin from lowering capacity below the number of enrolled students?

Because, by decision C17, course does not store how many students are enrolled. That number belongs to registration. A rule can only live where its data lives, so this rule must be handled by registration or by asking it.

5. Why does SectionChanged carry the full public state and a version, not only the changed field?

Consumers can then just keep the newest version. Repeats and old events are easy to ignore (compare versions), and a replay rebuilds the same result. A delta like "+20 seats" applied twice would be wrong.

6. Why must the time zone be explicit when making meetings from weekly slots?

"Monday 07:30" means 07:30 in Vietnam. A server running in UTC would otherwise create meetings seven hours off, and the clash checks and timetables would all be wrong.
