Lesson 18 · Part 2: Feature modules

App shell: routing, lazy modules, i18n

Smart Campus is a "super-app": one website that holds many small apps (timetable, registration, clubs, marketplace…). The shell is the frame around them: the menu, the routes, the language and the layout. Modules plug in; admins switch them on and off.

1. What a shell is

Think of a shopping mall. The mall gives the doors, the corridors, the signs and the lights. Each shop is its own business. A shop can close without closing the mall. In Smart Campus:

  • the mall is the shell: login, header, menu, language switch, layout, error pages;
  • each shop is a feature module: timetable, registration, marketplace…;
  • the sign at the entrance is the module manifest list: which shops are open, and for whom.

Arch ADR-8 chose "plugin manifest + lazy-loaded frontend modules" for three reasons: modules can be toggled per university (AUTH-5), the first download stays small, and a module's code loads only when someone opens it. The accepted trade-off: "manifest and routes must stay in sync". You will see below how to make that safe.

2. The module manifest

A manifest is a small description of a module: its id, name, icon, route, API prefix, who may see it, and its order in the menu. This is the example from the Arch (§7):

{
  "id": "marketplace",
  "name": "Book Market",
  "icon": "book",
  "route": "/marketplace",
  "apiPrefix": "/api/v1/marketplace",
  "requiredRoles": ["STUDENT"],
  "enabled": true,
  "order": 60
}

On the backend, every module implements one small interface. The shell collects all of them (Spring gives you every bean of a type as a List) into a registry.

public record ModuleManifest(String id, String name, String icon, String route,
                             String apiPrefix, Set<String> requiredRoles, int order) {}

public interface CampusModule {
    ModuleManifest manifest();
}
@Component
class MarketplaceModule implements CampusModule {
    @Override
    public ModuleManifest manifest() {
        return new ModuleManifest("marketplace", "Book Market", "book", "/marketplace",
                "/api/v1/marketplace", Set.of("STUDENT"), 60);
    }
}

Feature modules depend on shell (it comes before them in the build order), so they may use its public interface. Spring Modulith's verify() checks this (lesson 06).

GET /api/v1/modules

Map decision C1 fixed the path to /api/v1/modules (the Plan said /api/modules). It returns the modules that are enabled and that the caller's roles allow (Arch §5, step 5):

@GetMapping("/api/v1/modules")
List<ModuleManifest> modules(Authentication auth) {
    Set<String> roles = auth.getAuthorities().stream()
            .map(GrantedAuthority::getAuthority)
            .filter(a -> a.startsWith("ROLE_"))
            .map(a -> a.substring("ROLE_".length()))
            .collect(Collectors.toSet());
    return registry.all().stream()
            .filter(m -> toggles.isEnabled(m.id()))                         // AUTH-5
            .filter(m -> m.requiredRoles().isEmpty()
                      || !Collections.disjoint(m.requiredRoles(), roles))  // any one role is enough
            .sorted(Comparator.comparingInt(ModuleManifest::order))
            .toList();
}
A hidden menu item is not security The list only decides what the menu shows. A student can still type /api/v1/grade/sections/… by hand. The real protection is @PreAuthorize and ownership checks in each module (lesson 17).

3. Toggles and the gateway 404 filter

AUTH-5: "As a system admin, I want to enable or disable modules per university, so that features roll out gradually." A feature toggle is an on/off switch stored as data, so changing it needs no redeploy. A likely design (the shell spec will decide): a table in the shell schema with one row per module id and an enabled flag, and an admin screen for SYSTEM_ADMIN.

When a module is off, its API must also be off. The Arch says: "a disabled module's endpoints return 404 via a gateway filter". A global filter in Spring Cloud Gateway runs for every request, before routing (lesson 11):

@Component
class DisabledModuleFilter implements GlobalFilter, Ordered {

    private final ModuleToggles toggles;        // a cached copy of "which ids are on"

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getPath().value();     // /api/v1/marketplace/listings
        String moduleId = ModulePaths.moduleIdOf(path);            // "marketplace", or null
        if (moduleId != null && !toggles.isEnabled(moduleId)) {
            return problems.write(exchange, ProblemCode.NOT_FOUND); // 404 problem JSON, same as an unknown route
        }
        return chain.filter(exchange);
    }

    @Override
    public int getOrder() { return -10; }                           // early, before routing
}
  • Why 404 and not 403? For the caller, a disabled module should look exactly like a module that does not exist.
  • How does the gateway know the toggles? It must not ask the database on every request. Options: poll an internal shell endpoint every few seconds and cache the answer, or listen to a ModuleToggled event on campus.events. A few seconds of delay after a toggle is fine.
  • Some ids can never be turned off: platform, identity, shell itself (/api/v1/modules).

4. React Router: nested routes and layouts

A router maps the URL in the address bar to a screen, without reloading the page. React Router lets routes be nested: a parent route draws the frame, and puts the child screen into an <Outlet /> (a hole in the frame). A parent that only draws a frame is called a layout.

URL: /registration/windows/42

  "/"  → <ShellLayout>            header, menu, language switch
           └── <Outlet>
                 ":moduleId/*" → <ModuleOutlet>     finds "registration" in the manifest list
                                   └── registration's own routes:  "windows/:id" → <WindowPage>
import { createBrowserRouter } from "react-router";

export const router = createBrowserRouter([
  {
    path: "/",
    element: <ShellLayout />,              // the frame: header + menu + <Outlet />
    errorElement: <ShellErrorPage />,       // if the frame itself fails
    children: [
      { index: true, element: <HomePage /> },
      { path: "auth/callback", element: <LoginCallback /> },   // lesson 16, step 4
      { path: ":moduleId/*", element: <ModuleOutlet /> },      // every feature module
      { path: "*", element: <NotFoundPage /> },
    ],
  },
]);

Notice: the shell does not list timetable, grade… as routes. One route, :moduleId/*, serves them all. The /* at the end lets the module keep its own child routes. This keeps the shell small and makes "add a module" a change inside the module's folder.

5. Lazy modules and a menu from the manifest

Code splitting means Vite cuts the app into several JavaScript files (chunks). React.lazy loads a chunk only when the component is first drawn. Suspense shows a fallback (a spinner) while the chunk downloads. A student who never opens the marketplace never downloads its code.

import { lazy, type ComponentType, type LazyExoticComponent } from "react";

// The ONE place that links a manifest id to code. Each import() becomes its own chunk.
// React.lazy needs a default export; our rule is named exports, so we adapt it here.
export const moduleScreens: Record<string, LazyExoticComponent<ComponentType>> = {
  timetable: lazy(() =>
    import("../modules/timetable/routes").then((m) => ({ default: m.TimetableRoutes }))),
  registration: lazy(() =>
    import("../modules/registration/routes").then((m) => ({ default: m.RegistrationRoutes }))),
  marketplace: lazy(() =>
    import("../modules/marketplace/routes").then((m) => ({ default: m.MarketplaceRoutes }))),
};
export function ModuleOutlet() {
  const { moduleId } = useParams();
  const { data: modules, isPending } = useModules();     // TanStack Query: GET /api/v1/modules
  if (isPending) return <PageSpinner />;

  const allowed = modules?.some((m) => m.id === moduleId) ?? false;
  const Screen = moduleId ? moduleScreens[moduleId] : undefined;
  if (!allowed || !Screen) return <NotFoundPage />;      // disabled, not allowed, or unknown

  return (
    <ModuleErrorBoundary moduleId={moduleId!}>              // section 8
      <Suspense fallback={<PageSpinner />}>
        <Screen />
      </Suspense>
    </ModuleErrorBoundary>
  );
}

The manifest type comes from the generated OpenAPI types (platform T19, lesson 14), so the frontend and backend cannot drift apart silently. The menu is just a list drawn from the same data:

type ModuleManifest = components["schemas"]["ModuleManifest"];   // generated, do not edit

export function MainMenu({ modules }: { modules: ModuleManifest[] }) {
  const { t } = useTranslation();
  return (
    <nav aria-label={t("shell.menu")}>
      <ul>
        {modules.map((m) => (
          <li key={m.id}>
            <NavLink to={m.route}>
              <ModuleIcon name={m.icon} aria-hidden="true" />
              {t(`modules.${m.id}`, { defaultValue: m.name })}
            </NavLink>
          </li>
        ))}
      </ul>
    </nav>
  );
}
Keeping the manifest and the routes in sync (ADR-8's trade-off) Write one small Vitest test: every id that the backend can return (a list exported from the OpenAPI file or a fixture) must have a key in moduleScreens, and every key must be a known id. Then a forgotten module fails CI instead of showing a blank page.

6. Vietnamese and English (NFR-8)

NFR-8: "use the app in Vietnamese or English, so international students can use it too". i18n (internationalization: "i", 18 letters, "n") means building the app so the language can change. Two different jobs:

Words: translation files

Every sentence the user sees lives in a JSON file per language, under a key. A library such as react-i18next picks the right one. No text is hard-coded in components.

Numbers, dates, money: Intl

The browser's built-in Intl API knows that Vietnamese writes 1.500.000 ₫ and English writes ₫1,500,000. Never format these by hand.

import i18n from "i18next";
import { initReactI18next } from "react-i18next";
import vi from "./locales/vi.json";
import en from "./locales/en.json";

void i18n.use(initReactI18next).init({
  resources: { vi: { translation: vi }, en: { translation: en } },
  lng: "vi",                       // default for a Vietnamese university
  fallbackLng: "en",               // a missing Vietnamese key shows English, not the raw key
  interpolation: { escapeValue: false },   // React already escapes text
});
{ "shell": { "menu": "Danh mục chính", "logout": "Đăng xuất" },
  "registration": { "seatsLeft": "Còn {{count}} chỗ" } }

{ "shell": { "menu": "Main menu", "logout": "Log out" },
  "registration": { "seatsLeft_one": "{{count}} seat left", "seatsLeft_other": "{{count}} seats left" } }

English needs plural forms (_one, _other); Vietnamese does not change the noun. i18next uses the language's plural rules to choose.

export function formatVnd(amount: string, locale: string): string {
  // The API sends money as a decimal string + currency (never a float). VND has 0 decimals.
  return new Intl.NumberFormat(locale, { style: "currency", currency: "VND" }).format(Number(amount));
}
formatVnd("150000", "vi-VN");   // "150.000 ₫"
formatVnd("150000", "en");      // "₫150,000"

export function formatClassTime(isoUtc: string, locale: string): string {
  // The API sends UTC (spec rule). Show campus time, whatever the phone's own time zone is.
  return new Intl.DateTimeFormat(locale, {
    weekday: "long", hour: "2-digit", minute: "2-digit", timeZone: "Asia/Ho_Chi_Minh",
  }).format(new Date(isoUtc));
}
  • When the language changes, also set <html lang="vi"> or "en". Screen readers use it to choose a voice.
  • Error messages: show a translated text chosen by the problem JSON code (SECTION_FULL → errors.SECTION_FULL), not the English detail (lesson 09: clients switch on the code).
  • Keycloak's login page has its own language setting. The OIDC request can pass ui_locales=vi so the login page matches.

7. Phone-first layout and accessibility (NFR-7)

NFR-7: "use the app on my phone screen". There is no mobile app (map assumption 3). The website itself must work well on a phone. Most students will open it on a phone, often in a hurry between classes or during the registration rush.

Mobile-first means you write the CSS for the small screen first, then add rules for wider screens with media queries (@media (min-width: …)).

.shell {
  display: grid;
  grid-template-rows: auto 1fr auto;      /* header / content / bottom menu */
  min-height: 100dvh;                      /* dvh: the real visible height on phones */
}
.shell-menu {                              /* phone: a bar at the bottom, easy for thumbs */
  position: sticky; bottom: 0;
  display: flex; justify-content: space-around;
}
.shell-menu a { min-width: 48px; min-height: 48px; }   /* big enough to tap */

@media (min-width: 768px) {                /* tablet and desktop: menu on the left */
  .shell {
    grid-template-columns: 240px 1fr;
    grid-template-rows: auto 1fr;
  }
  .shell-menu { position: static; flex-direction: column; grid-row: 2; }
}
  • Use flex for a row or column of things, grid for two-way layouts like the shell or a week timetable.
  • The page must never scroll sideways. Wide tables (rosters) scroll inside their own box.
  • Test at 360 px width in the browser's device mode, not only on your large screen.

Accessibility basics

Accessibility (a11y) means people with different abilities can use the app: with a screen reader, only a keyboard, low vision, or a shaking hand. WCAG 2.2 is the standard. The basics cost little if you do them from the start:

RuleIn the shell
Use the right HTML element<nav> for the menu, <button> for actions (not a clickable <div>), <table> for the timetable grid
Every input has a label<label htmlFor>; icons-only buttons get aria-label
Keyboard works everywhereTab through the menu; focus is visible; after a route change, move focus to the page heading
Enough colour contrastDo not show "section full" with colour only; add text or an icon
Announce changesRegistration result "pending → confirmed" in an aria-live="polite" region
Language set<html lang> matches the chosen language

8. Error boundaries

If a React component throws while drawing, React removes the whole page by default. One broken module must not take the shell down. An error boundary is a component that catches drawing errors in its children and shows a fallback instead. It is like a fuse in a house: one room goes dark, not the whole building.

import { Component, type ErrorInfo, type ReactNode } from "react";

type Props = { moduleId: string; children: ReactNode };

// Error boundaries must still be class components in React.
export class ModuleErrorBoundary extends Component<Props, { failed: boolean }> {
  state = { failed: false };

  static getDerivedStateFromError() {
    return { failed: true };
  }

  componentDidCatch(error: Error, info: ErrorInfo) {
    console.error(`module ${this.props.moduleId} crashed`, error, info.componentStack);
  }

  render() {
    return this.state.failed ? <ModuleCrashed id={this.props.moduleId} /> : this.props.children;
  }
}
  • Where: one around each module (in ModuleOutlet), plus the router's errorElement for the shell itself.
  • What they do not catch: errors in event handlers and in async code (like a failed fetch). Those are handled where they happen; API errors arrive as problem JSON through TanStack Query.
  • A real case for lazy modules: after a new deploy, old chunk file names are gone. A user with the old page open clicks "Marketplace" and the import() fails. The boundary should offer a "Reload" button, which loads the new version.

10. Common mistakes

  • Treating the menu as security. Hiding a link protects nothing; the API must check.
  • Importing a module statically (import { MarketplaceRoutes } from …) in the shell. That puts it back in the main bundle and kills lazy loading.
  • Hard-coded text like "Đăng xuất" inside a component. Every string goes in the translation files.
  • Formatting money with string tricks or using JavaScript floats for amounts. Use Intl.NumberFormat and decimal strings.
  • Showing times in the phone's time zone. A student abroad still needs campus time for classes.
  • Desktop-first CSS that is "fixed later" for phones. Start at 360 px.
  • No error boundary per module. One crash then blanks the whole app.
  • The gateway asking the database for toggles on every request. Cache them.

13. Test yourself

1. If the menu already hides a disabled module, why do we also need the gateway 404 filter?

The menu is only what the browser shows. Anyone can call the API directly. The filter makes the module's API truly unavailable, and 404 makes it look like it does not exist.

2. Why does the shell have one :moduleId/* route instead of one route per module?

Then adding a module means adding its folder and one registry line, not editing the shell's router. The manifest list from the server decides what is reachable.

3. Why use React.lazy per module?

Each module becomes its own chunk, so the first page is small and fast on a phone, and code for modules a student never opens is never downloaded (ADR-8).

4. Why use Intl instead of writing our own money and date formatting?

Each locale has different separators, symbol positions and date orders. Intl already knows them, and it also converts UTC times to campus time with timeZone.

5. Why design for the phone first in Smart Campus?

There is no mobile app (assumption 3), and most students use phones, especially during the registration rush. Adding space for big screens is easier than squeezing a desktop layout.

6. Why put an error boundary around each module and not only one around the app?

With one boundary at the top, any module crash replaces the whole app with an error page. Per-module boundaries keep the menu and other modules working.
