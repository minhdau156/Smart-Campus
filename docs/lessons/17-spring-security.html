Spring Security with JWT and roles

Lesson 16 gave the web app a token. Now every Smart Campus service must check that token, turn Keycloak roles into Spring rules, and still answer the harder question: "is this your grade?". You will use this in the identity module and then in every module after it.

1. Defence in depth

The Arch (§8, Security) gives three layers. Each one catches what the one before cannot:

1. GatewayChecks the JWT signature and expiry. Bad token → 401 at the door.
→
2. Each serviceChecks the JWT again and the role with @PreAuthorize
→
3. Row-level check"A student reads only their own grades; a lecturer grades only their sections"

Why check the token twice? Because the gateway is not the only way in. A misconfigured route, a test tool inside the cluster, or a future service-to-service call can reach core-app directly. Like a hospital: the main door has a guard, but the medicine room still has its own lock. This idea is called defence in depth.

Spring Security is the library that does layers 1 and 2 for us. Layer 3 is our own code, because only our module knows who owns a grade.

2. The filter chain

A servlet filter is code that runs before your controller, for every request. It can look at the request, change it, or stop it. Spring Security is a chain of filters: each one does one job, then passes the request on.

HTTP request
   │
   ▼
┌───────────────────────── SecurityFilterChain ─────────────────────────┐
│ CorsFilter                  → answers or checks browser CORS rules     │
│ BearerTokenAuthenticationFilter → reads "Authorization: Bearer …",      │
│                                  checks the JWT, sets the user         │
│ ExceptionTranslationFilter  → turns "no user" into 401, "no right" 403 │
│ AuthorizationFilter         → URL rules (permitAll, authenticated …)   │
└────────────────────────────────────────────────────────────────────────┘
   │
   ▼
DispatcherServlet → @RestController (+ @PreAuthorize on methods)

When a filter accepts the token, it puts an Authentication object in the SecurityContext: a place, tied to the current request, that says "this request is user X with these authorities". Later code reads it from there.

You do not write the filters. You configure them with a SecurityFilterChain bean:

@Configuration
@EnableMethodSecurity                                // turns on @PreAuthorize
class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http, JwtAuthenticationConverter jwtConverter) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health/**", "/actuator/info").permitAll()
                .requestMatchers("/api/v1/*/ping").permitAll()       // smoke checks (platform T13)
                .anyRequest().authenticated())                       // everything else needs a token
            .oauth2ResourceServer(rs -> rs.jwt(jwt -> jwt.jwtAuthenticationConverter(jwtConverter)))
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable());                           // see section 5
        return http.build();
    }
}

STATELESS means the server keeps no login session. Every request brings its own token. This is what lets us run 20 copies of registration-service during the rush: any copy can serve any request.

Deny by default Write the few public paths first, and end with anyRequest().authenticated(). A new endpoint is then protected even if you forget it. The opposite style ("protect these paths") fails open.

3. JWT resource server and Keycloak roles

A resource server is an API that accepts access tokens (lesson 16, section 2). Spring Boot sets one up from a few properties:

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://localhost:8180/realms/campus      # the "iss" every token must have
          jwk-set-uri: http://localhost:8180/realms/campus/protocol/openid-connect/certs
          audiences: campus-api                               # the "aud" every token must contain

With this, Spring downloads and caches the public keys, checks the signature, exp, iss and aud, and rejects anything else with 401.

From realm_access.roles to authorities

Spring Security calls each permission an authority (a string). By default it reads the scope claim and makes SCOPE_openid and so on. Keycloak puts roles somewhere else: in realm_access.roles (Arch §7). So we write a small converter: a class that turns a JWT into authorities.

public final class KeycloakRealmRoles implements Converter<Jwt, Collection<GrantedAuthority>> {

    // Map C3: the only realm roles Smart Campus knows. Keycloak's own roles are ignored.
    static final Set<String> CAMPUS_ROLES = Set.of(
            "STUDENT", "LECTURER", "FACULTY_STAFF", "ACADEMIC_ADMIN",
            "SECURITY_STAFF", "SYSTEM_ADMIN", "CLUB_MANAGER");

    @Override
    public Collection<GrantedAuthority> convert(Jwt jwt) {
        Map<String, Object> realmAccess = jwt.getClaimAsMap("realm_access");
        if (realmAccess == null || !(realmAccess.get("roles") instanceof Collection<?> roles)) {
            return List.of();                                   // no roles: still a valid user
        }
        return roles.stream()
                .map(String::valueOf)
                .filter(CAMPUS_ROLES::contains)                 // drops "default-roles-campus" etc.
                .<GrantedAuthority>map(role -> new SimpleGrantedAuthority("ROLE_" + role))
                .toList();
    }
}
@Bean
JwtAuthenticationConverter jwtAuthenticationConverter() {
    var converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(new KeycloakRealmRoles());
    return converter;                       // principal name stays "sub" (the Keycloak user id)
}

Why the ROLE_ prefix? Spring's hasRole('STUDENT') looks for the authority ROLE_STUDENT. hasAuthority('ROLE_STUDENT') means the same.

4. @PreAuthorize and ownership checks

Method security puts the rule on the method itself. Spring checks it before the method runs. If the rule is false, the method never runs.

@PostMapping("/api/v1/course/sections")
@PreAuthorize("hasRole('ACADEMIC_ADMIN')")                  // REG-7: only the academic office
SectionView create(@Valid @RequestBody NewSection body) { … }

@GetMapping("/api/v1/announcement/posts")
@PreAuthorize("isAuthenticated()")                          // every logged-in user
Page<PostView> feed(Pageable page) { … }

@PostMapping("/api/v1/announcement/posts")
@PreAuthorize("hasAnyRole('FACULTY_STAFF', 'LECTURER', 'ACADEMIC_ADMIN')")
PostView publish(@Valid @RequestBody NewPost body) { … }

Roles alone are not enough

A role says what kind of person you are. It does not say which rows are yours. Every student has the role STUDENT. If the only rule is hasRole('STUDENT'), any student can read any other student's grades by changing an id in the URL. This bug has a name: IDOR (insecure direct object reference; see lesson 30).

Role check only

@GetMapping("/api/v1/grade/students/{studentId}/grades")
@PreAuthorize("hasRole('STUDENT')")
List<GradeView> grades(@PathVariable UUID studentId) {
    return grades.forStudent(studentId);   // anyone's!
}

Role + ownership

@GetMapping("/api/v1/grade/grades/me")
@PreAuthorize("hasRole('STUDENT')")
List<GradeView> myGrades(@AuthenticationPrincipal Jwt jwt) {
    UUID me = UUID.fromString(jwt.getSubject());
    return grades.forStudent(me);          // only mine
}

Two good habits:

  • Take the user id from the token, not from the request. A /me endpoint cannot be pointed at someone else.
  • Put the owner in the query. WHERE id = ? AND student_id = ? returns nothing for other people's rows. Return 404, not 403, so you do not even say "this grade exists".

For a lecturer, the rule is "only the sections I teach". You can call a bean from the expression:

@PutMapping("/api/v1/grade/sections/{sectionId}/grades")
@PreAuthorize("hasRole('LECTURER') and @sectionAccess.teaches(authentication, #sectionId)")
void enterGrades(@PathVariable UUID sectionId, @Valid @RequestBody GradeSheet sheet) { … }

@Component("sectionAccess")
class SectionAccess {
    private final LecturerSections lecturerSections;       // grade's local projection of course data (C4)

    boolean teaches(Authentication auth, UUID sectionId) {
        UUID lecturerId = UUID.fromString(auth.getName()); // getName() = sub
        return lecturerSections.isAssigned(lecturerId, sectionId);
    }
}

Note that grade cannot read the course schema (C4, no cross-schema access). It keeps its own small copy of "who teaches which section", built from course.events (lesson 08).

5. The gateway, CORS and CSRF

The reactive side

Our gateway uses Spring Cloud Gateway on WebFlux (reactive, non-blocking; see lesson 11). WebFlux has no servlet filters, so Spring Security has a reactive twin: SecurityWebFilterChain with ServerHttpSecurity. The ideas are the same; the names change.

@Configuration
@EnableWebFluxSecurity
class GatewaySecurityConfig {

    @Bean
    SecurityWebFilterChain gateway(ServerHttpSecurity http) {
        return http
            .authorizeExchange(ex -> ex
                .pathMatchers("/actuator/health/**", "/api/v1/*/ping").permitAll()
                .pathMatchers(HttpMethod.OPTIONS, "/**").permitAll()   // CORS pre-flight has no token
                .anyExchange().authenticated())
            .oauth2ResourceServer(rs -> rs.jwt(Customizer.withDefaults()))
            .csrf(ServerHttpSecurity.CsrfSpec::disable)
            .build();
    }
}

The gateway only checks "is this a real, unexpired token for us". It does not check roles per endpoint: it does not know the business rules. It passes the Authorization header on to the service, which checks again (layer 2).

CORS

Browsers block JavaScript from one origin (scheme + host + port) from reading answers from another origin, unless the server says it is allowed. This rule is CORS (Cross-Origin Resource Sharing). In Smart Campus:

  • Dev: Vite at localhost:5173 proxies /api to the gateway (platform T19). The browser sees one origin, so no CORS is needed.
  • Prod (planned): the SPA and /api are served under one domain by the Ingress (lesson 31). Again one origin.
  • If they ever differ, configure CORS once, at the gateway, with an exact list of origins. Never * together with credentials.

Keycloak is a different origin, but that is fine: the login is a full-page redirect, and the token call is allowed by the client's webOrigins setting (lesson 16).

Why CSRF matters less here

CSRF (cross-site request forgery) is when an evil site makes your browser send a request to our site, and the browser automatically adds our cookie. With bearer tokens, the browser adds nothing automatically: our JavaScript must put the token in the header, and the evil site cannot read our memory. So for a pure bearer-token API, CSRF protection can be turned off. Be careful: as soon as you use cookies for login (the BFF pattern, section 8), CSRF protection is needed again.

6. 401 vs 403 as problem JSON

StatusMeaningExampleWhat the web app does
401 Unauthorized (really "unauthenticated")"I do not know who you are"No token, expired token, bad signatureRefresh the token or send the user to login
403 Forbidden"I know you, but you may not do this"A STUDENT calls a LECTURER endpointShow "You do not have access". Logging in again will not help.

Platform rule E1: every error is application/problem+json with code and traceId (lesson 09). Spring Security's default 401 and 403 are empty bodies, so we plug in two small handlers:

http.exceptionHandling(ex -> ex
        .authenticationEntryPoint(problemWriter.forStatus(401, "UNAUTHENTICATED"))   // + WWW-Authenticate: Bearer
        .accessDeniedHandler(problemWriter.forStatus(403, "FORBIDDEN")));

// 401 body:
{"type":"https://campus.edu/problems/unauthenticated","title":"Unauthenticated","status":401,
 "detail":"Token expired","code":"UNAUTHENTICATED","traceId":"4bf92f…"}

UNAUTHENTICATED and FORBIDDEN are not in ProblemCode yet. Today it has INTERNAL_ERROR, VALIDATION_FAILED, NOT_FOUND, CONFLICT and RATE_LIMITED. Identity would add them.

Real trap in this repo CampusProblemHandler (platform T8) has a catch-all @ExceptionHandler(Exception.class) that returns 500. A failed @PreAuthorize throws AccessDeniedException inside the controller call, so this catch-all would grab it and answer 500 instead of 403. The fix: add a specific handler for AccessDeniedException (→ 403) and AuthenticationException (→ 401), and write a test that proves it.

7. Testing with jwt()

You do not need a running Keycloak to test security. The spring-security-test library has a jwt() helper that puts a fake, already-checked JWT on a MockMvc request.

@Test
void lecturerOfTheSectionCanEnterGrades() throws Exception {
    mvc.perform(put("/api/v1/grade/sections/{id}/grades", SECTION)
                    .with(jwt()
                            .jwt(j -> j.subject(LECTURER_ID.toString())
                                       .claim("realm_access", Map.of("roles", List.of("LECTURER"))))
                            .authorities(new KeycloakRealmRoles()))      // use OUR converter
                    .contentType(APPLICATION_JSON)
                    .content(sheetJson))
       .andExpect(status().isNoContent());
}

@Test
void studentGetsProblem403() throws Exception {
    mvc.perform(put("/api/v1/grade/sections/{id}/grades", SECTION)
                    .with(jwt().authorities(new SimpleGrantedAuthority("ROLE_STUDENT")))
                    .contentType(APPLICATION_JSON).content(sheetJson))
       .andExpect(status().isForbidden())
       .andExpect(jsonPath("$.code").value("FORBIDDEN"));
}

@Test
void noTokenGets401() throws Exception {
    mvc.perform(get("/api/v1/grade/grades/me")).andExpect(status().isUnauthorized());
}
  • .authorities(...) with fixed values skips your converter. Pass the converter itself (first test), or unit-test KeycloakRealmRoles on its own.
  • Test the three cases for every protected endpoint: no token (401), wrong role (403), right role but someone else's row (404).
  • One integration test (a *IT, lesson 10) can run a real Keycloak with Testcontainers, import the realm JSON, get a real token, and call the API. That proves the issuer, audience and keys are wired correctly.

For the reactive gateway, WebTestClient has a matching mockJwt() helper.

8. Tokens in the browser

The Arch says: "tokens never stored in localStorage (memory + refresh via secure cookie or BFF)". Why? Any JavaScript on the page can read localStorage. One XSS bug (lesson 30) or one bad npm package would let an attacker copy every token and use it from their own computer.

Plan A: an OIDC library, tokens in memory

  • Do not write PKCE yourself. Use a proven, standards-following OIDC client library (for example oidc-client-ts, or Keycloak's own keycloak-js; the OpenID Foundation keeps a list of certified libraries). It handles state, PKCE, the callback, expiry and logout.
  • Keep tokens in memory (a JavaScript variable). They are lost on page reload, so the library does a silent login: it asks Keycloak again with prompt=none. If the Keycloak session is still alive, a new token comes back without a login page.
  • Renew silently before expiry: about a minute before the 5-minute token ends, the library gets a new one (Arch §5, step 6).
import { UserManager, WebStorageStateStore, InMemoryWebStorage } from "oidc-client-ts";

export const userManager = new UserManager({
  authority: "http://localhost:8180/realms/campus",     // discovery finds the other URLs
  client_id: "campus-web",
  redirect_uri: `${window.location.origin}/auth/callback`,
  post_logout_redirect_uri: window.location.origin,
  scope: "openid profile email",
  userStore: new WebStorageStateStore({ store: new InMemoryWebStorage() }),   // memory, not localStorage
  automaticSilentRenew: true,
});

The API client from platform T19 then adds Authorization: Bearer to each call, and on a 401 it tries one silent renew before sending the user to login.

Plan B: the BFF pattern

BFF (Backend for Frontend)

A small server (the gateway can play this role) does the OIDC login as a confidential client and keeps the tokens on the server. The browser only gets an HttpOnly, Secure, SameSite session cookie that JavaScript cannot read. Stolen-token risk is much lower.

The trade-off

The gateway becomes stateful: it needs a shared session store (for example Redis) for its replicas. CSRF protection comes back because cookies are sent automatically. One more moving part to build and run.

The identity spec must choose. Plan A is simpler and fits a stateless gateway. Plan B is the safer choice recommended by the IETF's current draft on OAuth for browser-based apps. Either way, the rest of this lesson (services checking JWTs) stays the same.

10. Common mistakes

  • Trusting the gateway alone. Each service must check the token too.
  • Only role checks on endpoints with ids. Add ownership: /me endpoints and owner-filtered queries.
  • Forgetting @EnableMethodSecurity. Then every @PreAuthorize is silently ignored. Have one test that expects a 403.
  • hasRole('ROLE_STUDENT'). hasRole adds the prefix itself. Write hasRole('STUDENT').
  • 500 instead of 403 because a catch-all exception handler swallows AccessDeniedException (section 6).
  • Turning CSRF off while using login cookies. Off is only safe for bearer-token APIs.
  • Tokens in localStorage (Arch §8 forbids it).
  • Reading the user id from the request body instead of the token.

13. Test yourself

1. The gateway already checks every token. Why must core-app check it again?

The gateway may not be the only way in (misconfiguration, internal calls, tests in the cluster). Defence in depth: each service protects itself. Also, only the service knows the role rules for its endpoints.

2. Why is hasRole('STUDENT') not enough for reading grades?

Every student has that role, so it does not say which grades are theirs. Without an ownership check, any student could read others' grades by changing an id (IDOR).

3. Why do we write our own converter for Keycloak roles?

Spring reads the scope claim by default. Keycloak puts roles in the nested realm_access.roles claim. The converter reads that claim and maps each known role to a ROLE_… authority.

4. Why can we disable CSRF for the API, and when must it come back?

CSRF abuses credentials the browser sends by itself (cookies). Bearer tokens are added by our code, so a foreign site cannot make the browser send them. If we switch to cookie sessions (BFF), the browser sends credentials automatically again, so CSRF protection is needed.

5. Why answer 404 instead of 403 when a student asks for someone else's grade?

403 says "this exists, but not for you", which leaks information. 404 from an owner-filtered query treats other people's rows as if they did not exist.

6. Why keep tokens in memory instead of localStorage?

Any script on the page can read localStorage, so one XSS bug could steal tokens that keep working elsewhere. Memory is harder to reach and disappears with the tab; the Keycloak session gives a new token silently when needed.
