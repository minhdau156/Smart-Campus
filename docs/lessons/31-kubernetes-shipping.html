1. From Compose to Kubernetes

Compose starts containers on one machine, and you tell it what to do. Kubernetes (often "K8s") runs containers on a group of machines (a cluster), and you tell it what you want: "always 2 copies of registration-service, version 3f9c2ab". A controller then works all the time to make reality match. If a machine dies, it starts the lost copies elsewhere. This style is called declarative: you describe the goal, not the steps. A thermostat is the same idea: you set 22 °C and it keeps working to reach it.

The Arch (§8) gives the production picture:

Web SPAVite dev serverNginx container behind Ingress, assets on a CDN
Gateway1 containerDeployment, 2–4 replicas
core-app1 containerDeployment, 2–4 replicas, HPA on CPU
registration-service1 container2 replicas normally; HPA up to 20 on CPU + Kafka lag; pre-scaled before each window

Keycloak1 container2 replicas, own PostgreSQL

2. Pods, Deployments, Services, Ingress

  internet
     │  https://campus.example.edu
     ▼
 ┌─────────┐   /        → web (Nginx, the SPA)
 │ Ingress │   /api/**  → gateway        (also /ws/** for WebSocket)
 └────┬────┘
      ▼
 ┌──────────────┐   stable name + load balancing      ┌──── Pod ────┐
 │ Service      │ ──────────────────────────────────► │ gateway     │
 │ "gateway"    │                                      └─────────────┘
 └──────────────┘                                      ┌──── Pod ────┐
                                                       │ gateway     │  ← both made by the
                                                       └─────────────┘    "gateway" Deployment
      gateway → Service "core-app" → core-app Pods, Service "registration-service" → …
  • Pod: the smallest unit; one or more containers that run together on one machine and share a network address. Usually one app container per Pod. Pods are disposable: they get new names and addresses when replaced.
  • Deployment: "keep N Pods of this template running". It also does rolling updates (section 5).
  • Service: a fixed name and address in front of a changing set of Pods. The gateway calls http://core-app:8081 and never needs to know Pod addresses. This is why our gateway reads backend URLs from env (platform T13.2).
  • Ingress: rules for traffic from outside the cluster (host names, paths, TLS). An ingress controller must be installed to make them work. Newer clusters may use the Gateway API, the successor to Ingress; check what your cluster offers.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: registration-service
spec:
  replicas: 2
  selector:
    matchLabels: { app: registration-service }
  template:                                   # the Pod template
    metadata:
      labels: { app: registration-service }
    spec:
      containers:
        - name: app
          image: registry.example.edu/campus/registration-service:3f9c2ab   # git SHA, never "latest"
          ports: [{ containerPort: 8082 }]
          resources:
            requests: { cpu: 500m, memory: 768Mi }  # what the scheduler reserves
            limits:   { memory: 768Mi }             # above this the container is killed
---
apiVersion: v1
kind: Service
metadata:
  name: registration-service
spec:
  selector: { app: registration-service }     # sends traffic to Pods with this label
  ports: [{ port: 8082, targetPort: 8082 }]

Requests and limits matter for Java: the JVM sizes its heap from the container's memory limit. Our Dockerfile (platform T15) caps the heap, and the plan notes the memory each container needs. Keep the limit and the heap setting in agreement, or the Pod is killed for using too much memory (OOMKilled).

3. ConfigMap and Secret

The same image must run in dev, staging and production. Only configuration changes. Spring Boot reads environment variables automatically (SPRING_DATASOURCE_URL overrides spring.datasource.url), so Kubernetes only has to set env vars.

apiVersion: v1
kind: ConfigMap
metadata: { name: registration-config }
data:
  SPRING_PROFILES_ACTIVE: prod
  SPRING_KAFKA_BOOTSTRAP_SERVERS: campus-kafka-bootstrap:9092
  SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_ISSUER_URI: https://auth.campus.example.edu/realms/campus
---
apiVersion: v1
kind: Secret
metadata: { name: registration-secrets }
type: Opaque
stringData:
  SPRING_DATASOURCE_PASSWORD: "…"            # NEVER in git: created by the pipeline or a vault

# in the Deployment's container:
envFrom:
  - configMapRef: { name: registration-config }
  - secretRef:    { name: registration-secrets }
A Secret is not encrypted by default Kubernetes stores Secret values in base64, which is an encoding, not encryption. Protect them with access rules, encryption at rest in the cluster, or an external store like Vault (Arch §8: "Secrets in Kubernetes Secrets or Vault, never in the repo"). Same rule as infra/.env today (lesson 30).

4. Probes and Actuator health groups

A probe is a check that Kubernetes runs against each container again and again. There are three kinds, and they answer different questions:

ProbeQuestionIf it failsSpring Boot endpoint
Startup"Have you finished starting?"Keep waiting (up to a limit), then restart. Other probes wait until it passes./actuator/health/liveness
Liveness"Are you stuck beyond repair?"Restart the container/actuator/health/liveness
Readiness"Can you take traffic right now?"Stop sending traffic (no restart)/actuator/health/readiness

Spring Boot Actuator has these two health groups built in. They turn on automatically when the app detects Kubernetes, or with one property. Today core-app exposes /actuator/health (platform T6); Compose's healthcheck uses it.

management:
  endpoint:
    health:
      probes:
        enabled: true                 # /actuator/health/liveness and /readiness
      group:
        readiness:
          include: readinessState, db # no DB → stop traffic to this Pod, do not restart it
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8082 }
  periodSeconds: 5
  failureThreshold: 30              # up to 150 s to start (Flyway, Kafka, JIT warm-up)
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8082 }
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8082 }
  periodSeconds: 5
Never put external systems in liveness If liveness included the database, a 30-second database hiccup would make Kubernetes restart every Pod at once, and the restart itself would make the outage worse. Restarts cannot fix the database. External checks belong in readiness (and even there, think: if every Pod becomes unready, the whole service answers 503).

5. Rolling updates and graceful shutdown

NFR-6 asks for deploys "without downtime". A Deployment does a rolling update: it replaces Pods a few at a time. New Pods must be ready before old Pods are removed.

replicas: 2   maxSurge: 1   maxUnavailable: 0

 time ─────────────────────────────────────────────────────────────►
 v1 ●  v1 ●                    start 1 new Pod (surge)
 v1 ●  v1 ●  v2 ○              v2 starting…  (startup probe)
 v1 ●  v1 ●  v2 ●              v2 ready      (readiness probe passes)
 v1 ◌  v1 ●  v2 ●              stop one v1   (graceful shutdown)
       v1 ●  v2 ●  v2 ○        next v2 starting…
             v2 ●  v2 ●        done: never fewer than 2 ready Pods

Note the middle of the picture: v1 and v2 run at the same time. That is normal, and it has consequences for the database (section 8) and for events (old and new consumers in the same group).

Graceful shutdown

When a Pod must stop, Kubernetes sends SIGTERM (a polite "please stop") and, at about the same time, removes the Pod from the Service. These two happen in parallel, so for a moment new requests can still arrive. Then, after terminationGracePeriodSeconds (default 30 s), it kills the process for good.

  1. preStop sleep (a few seconds): wait until the Pod is out of the Service, so no new requests come.
  2. Spring graceful shutdown: stop accepting new requests, finish the ones in progress, within a time limit.
  3. Kafka: listeners stop, the consumer leaves its group, and its partitions move to the other Pods. An event that was half-processed is delivered again to another Pod, which is safe because consumers deduplicate by eventId (spec D2, lesson 08).
  4. Outbox: an event saved but not yet sent stays in event_publication and is sent later (resubmission job or restart). No event is lost.
# application.yml
server:
  shutdown: graceful                       # recent Boot versions default to this; we set it explicitly
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s        # max time to finish in-flight work

# Pod spec
terminationGracePeriodSeconds: 40          # > preStop (10 s) + Spring's 20 s
containers:
  - name: app
    lifecycle:
      preStop:
        exec: { command: ["sh", "-c", "sleep 10"] }

6. Autoscaling for the registration rush

NFR-1: 5,000 students registering in the same minute, p95 under 500 ms. A HorizontalPodAutoscaler (HPA) changes the number of replicas of a Deployment based on a metric. "Horizontal" means more copies, not bigger copies.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: registration-service }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: registration-service }
  minReplicas: 2
  maxReplicas: 20                          # Arch §8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 60 }   # % of the CPU *request*

Three things the Arch already thought about:

  • Pre-scale before each window. An HPA reacts after load arrives, and a new JVM needs time to start and warm up. A rush that peaks in the first seconds is over before new Pods are ready. So a scheduled job raises minReplicas shortly before the registration window opens, and lowers it after.
  • Kafka lag as a metric. CPU does not show a growing queue. Scaling on consumer lag needs an external metrics source (for example a Prometheus adapter, or a tool like KEDA). Platform's open question about measuring lag in seconds (T18) feeds into this.
  • Partitions limit consumers. registration.requests has 12 partitions (spec O5). In one consumer group, each partition goes to at most one consumer, so more than 12 worker Pods would sit idle. The Arch splits registration-service into "api" and "worker" profiles: the API part can grow to 20, the worker part is capped by the partition count.

The k6 rush test (lesson 21) against staging proves the settings before every release that touches registration (Arch §8).

7. Images, registries and Helm

Pushing images to a registry

Compose builds images on your machine. A cluster pulls them from a container registry (a server that stores images, like GitHub Container Registry or a cloud provider's registry). Map C12: image push is deferred to this phase. The CI flow becomes:

1. Build./mvnw verify, layered jars, one Dockerfile for all 4 apps
→
2. ScanTrivy on each image (spec C1); HIGH/CRITICAL fails
→
3. Tag + pushTag = git commit SHA. Same image goes to staging, then prod
→
4. Deployhelm upgrade with that tag
docker tag campus/registration-service:dev registry.example.edu/campus/registration-service:3f9c2ab
docker push registry.example.edu/campus/registration-service:3f9c2ab

Why the commit SHA as the tag? It never moves: 3f9c2ab is always the same code. A tag like latest can point to different images on different days, so you can never be sure what is running (and the spec forbids it). Build once, promote the same image from staging to production.

Helm: charts and values

Writing ~10 YAML files per app, three times (dev, staging, prod), is a lot of copy-paste. Helm is a package manager for Kubernetes. A chart is a folder of YAML templates with holes; a values file fills the holes. Like a form letter: one template, different names and addresses.

infra/helm/campus/                 (planned)
├── Chart.yaml                     name, version of the chart
├── values.yaml                    defaults
├── values-staging.yaml            only what differs in staging
├── values-prod.yaml               only what differs in prod
└── templates/
    ├── _helpers.tpl               shared snippets (labels, names)
    ├── app-deployment.yaml        ONE template, used for all 4 Spring apps
    ├── app-service.yaml
    ├── registration-hpa.yaml
    ├── ingress.yaml
    └── configmap.yaml
image:
  registry: registry.example.edu/campus
  tag: "3f9c2ab"                 # set by CI with --set image.tag=…
apps:
  gateway:              { replicas: 2, port: 8080 }
  core-app:             { replicas: 2, port: 8081 }
  registration-service: { replicas: 2, port: 8082, hpa: { max: 20 } }
  notification-service: { replicas: 2, port: 8083 }
ingress:
  host: campus.example.edu
{{- range $name, $app := .Values.apps }}
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ $name }}
spec:
  replicas: {{ $app.replicas }}
  template:
    spec:
      containers:
        - name: app
          image: "{{ $.Values.image.registry }}/{{ $name }}:{{ $.Values.image.tag }}"
          ports: [{ containerPort: {{ $app.port }} }]
---
{{- end }}
helm upgrade --install campus infra/helm/campus \
  -f infra/helm/campus/values-prod.yaml \
  --set image.tag=3f9c2ab \
  --wait                                 # wait until rollouts are ready

helm history campus                       # every release is numbered
helm rollback campus 41                   # go back to release 41 if needed

Ports here match the dev ports from the spec (gateway 8080, core-app 8081, registration 8082, notification 8083), so the apps need no new settings. The Arch mentions Argo CD as an alternative: instead of CI running helm upgrade, a tool inside the cluster watches a git repo and applies changes itself ("GitOps").

8. Migrations and the data layer

Running Flyway at deploy time

Today each app runs Flyway at startup, on its own schema only (spec: one history table per schema). In Kubernetes there are two common choices:

Keep it at app startup

Simple, and it is what we already do. When several Pods start at once, Flyway uses a database lock so only one migrates and the others wait. The startup probe must allow enough time for a long migration.

A separate step before the rollout

A Kubernetes Job (for example a Helm pre-upgrade hook) runs the migration once; the Pods start only if it succeeds. Clear logs and one clear failure point. More setup.

Expand / contract: schema changes with no downtime

During a rolling update, old and new Pods share one database (section 5). And a rollback puts the old code back on the new schema. So every migration must work with both versions of the code. The pattern is called expand / contract (or "parallel change"). Example: rename marketplace.listings.title to name.

ReleaseMigrationCode
1. ExpandADD COLUMN name (nullable); copy title into itWrites both columns, still reads title
2. Switch(none, or add NOT NULL once filled)Reads and writes name; still writes title for safety
3. ContractDROP COLUMN titleOnly name

A rename done in one step (RENAME COLUMN) would break every old Pod still running during the rollout. The same idea applies to events: a breaking payload change gets a new schemaVersion (spec D4), and consumers accept both versions for a while.

Managed vs self-hosted infrastructure

Our apps are stateless and easy to replace. The stateful parts (they keep data) are the hard ones to run: backups, failover, upgrades, disks. The Arch lists both options:

PartManaged (a provider runs it)Self-hosted in the cluster (Arch §8)
PostgreSQLCloud database serviceCloudNativePG operator, primary + read replica
KafkaCloud Kafka serviceStrimzi operator, 3 brokers
RedisCloud Redis serviceRedis Sentinel
Object storageS3 or a compatible serviceAn S3-compatible server (RustFS replaced MinIO in dev, spec Q6)
Keycloak(usually self-run)2 replicas with its own PostgreSQL

An operator is a program in the cluster that knows how to run one kind of system (create, back up, fail over, upgrade). Managed costs more money and less work, and it is usually the safer choice for a small team. Self-hosted gives control and may help keep data in a chosen place (a legal question too; see lesson 30). Because our apps use plain protocols (JDBC, Kafka, S3 API), the choice changes configuration, not code.

10. Common mistakes

  • Using latest as the image tag. You cannot tell or roll back what runs.
  • The database in the liveness probe. One DB blip restarts everything.
  • No readiness probe. Traffic reaches Pods that are still starting: errors on every deploy.
  • No preStop pause / graceful shutdown. Requests in progress fail during each rollout.
  • Breaking migrations (rename or drop in one step) during a rolling update.
  • Relying on depends_on habits. Kubernetes starts everything at once; apps must retry connections.
  • Memory limit and JVM heap out of step: the Pod is OOMKilled under load.
  • More consumers than partitions, expecting more throughput.
  • Secrets in values files committed to git. Values hold settings; secrets come from the pipeline or a vault.

13. Test yourself

1. Why does a failing readiness probe stop traffic, while a failing liveness probe restarts the container?

Not ready can be temporary (starting, a dependency is slow), and a restart would not help. Liveness failing means the process is stuck in a way only a restart can fix. Mixing them up causes needless restarts or traffic to broken Pods.

2. Why must database migrations be backward compatible during a rolling update?

Old and new Pods run at the same time against the same database, and a rollback runs old code on the new schema. A migration that only the new code understands breaks the old Pods.

3. Why tag images with the git SHA and not latest?

A SHA always means the same code, so you know exactly what runs, the same image moves from staging to prod, and a rollback is precise. latest changes over time.

4. Why pre-scale registration before the window instead of trusting the HPA?

The HPA reacts after load rises, and new JVM Pods need time to start and warm up. The rush peaks in the first seconds, so capacity must already be there.

5. Why is a Pod stopped during a rollout not a problem for Kafka events?

Unsent events stay in the outbox and are sent later; half-processed messages are delivered again to another consumer, and consumers deduplicate by eventId. At-least-once plus idempotent consumers make restarts safe.

6. Why does choosing managed or self-hosted Postgres not change our Java code?

The apps talk plain JDBC and read the URL and password from configuration. Only the ConfigMap and Secret change; the image stays the same.
