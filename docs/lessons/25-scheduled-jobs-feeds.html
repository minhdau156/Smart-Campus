Scheduled jobs and targeted feeds

2. @Scheduled: delay, rate, cron, zone

Spring can call a method on a timer. You switch it on with @EnableScheduling (our platform-starter already does this for the outbox retry job), then mark a method with @Scheduled. There are three kinds of timer:

SettingMeaningUse it for
fixedDelay = "PT30S"Wait 30 s after the last run ended, then run again"Keep checking" jobs. Runs never overlap.
fixedRate = "PT30S"Start every 30 s, counted from the last startMeasurements at a steady beat. A slow run can make runs pile up.
cron = "0 0 2 * * *"Run at clock times. Spring's cron has 6 fields: second, minute, hour, day, month, weekday"Every night at 02:00"

A real example from our code, already built in platform task T8:

@Scheduled(
        initialDelayString = "${campus.outbox.retry-interval}",
        fixedDelayString = "${campus.outbox.retry-interval}")
public void resubmitFailed() {
    failed.resubmit(ResubmissionOptions.defaults());
}

Time zones

A cron like "02:00" needs a time zone. Without one, Spring uses the server's zone, and servers in containers are often on UTC. 02:00 UTC is 09:00 in Vietnam, in the middle of the school day. Always say the zone:

@Scheduled(cron = "0 0 2 * * *", zone = "Asia/Ho_Chi_Minh")   // 02:00 Vietnam time
void archiveOldItems() { … }

Inside the job, never call Instant.now(). Inject the app's Clock (core-app/.../platform/ClockConfiguration.java, which is UTC) and call clock.instant(). Tests can then use a fixed clock and say "it is now 61 days later". Store times as TIMESTAMPTZ (an exact moment). Turn "8:00 on Monday, Vietnam time" into an Instant when the user saves the form:

Instant publishAt = LocalDateTime.parse("2026-12-07T08:00")
        .atZone(ZoneId.of("Asia/Ho_Chi_Minh"))
        .toInstant();                                // 2026-12-07T01:00:00Z

3. Many replicas: who runs the job?

In production, core-app runs with 2 to 4 replicas (Architecture §8). Each replica has its own timer. So at 02:00, every replica starts the same job. For the archive job that means three copies all updating the same rows; for a "send reminder" job it means three emails. Two standard fixes:

A lock: only one replica runs

ShedLock is a small library. Before the job starts, it tries to take a named lock (a row in a shedlock table). Only the replica that gets it runs the job; the others skip this round.

@Scheduled(cron = "0 0 2 * * *", zone = "Asia/Ho_Chi_Minh")
@SchedulerLock(name = "lostfound-archive",
               lockAtMostFor = "PT30M")
void archiveOldItems() { … }

lockAtMostFor frees the lock if the replica dies mid-job. It is a third-party library, so check that its version supports our Spring Boot line before adding it (an "Ask first" change).

Row locks: all replicas share the work

Each replica takes a batch of rows with SELECT … FOR UPDATE SKIP LOCKED. FOR UPDATE locks the rows it picked; SKIP LOCKED means "if another replica already locked a row, skip it, do not wait". So two replicas never take the same row.

SELECT id FROM announcement.announcements
WHERE status = 'SCHEDULED' AND publish_at <= :now
ORDER BY publish_at
LIMIT 100
FOR UPDATE SKIP LOCKED;

No extra library, and the work spreads over replicas. Needs one transaction per batch.

Rule of thumb: for "work through a queue of rows", use SKIP LOCKED. For "one global task" (build a nightly report), use a lock like ShedLock.

4. Idempotent jobs in chunks

Even with a lock, a job can crash half-way, or run twice (a lock can expire while a very slow job is still running). So write every job so that running it again is harmless (idempotent, like the consumers in lesson 08):

  • Ask "which rows still need work?" every time (WHERE status = 'OPEN' AND …), never "continue from row 5 000".
  • Change state with a condition: UPDATE … SET status = 'ARCHIVED' WHERE id = ? AND status = 'OPEN'. Doing it twice changes nothing the second time.
  • Work in chunks (for example 500 rows per transaction). One huge transaction holds locks for a long time, and a failure at the end throws away all the work.

PostgreSQL's UPDATE has no LIMIT, so pick the chunk in a subquery:

@Component
class ArchiveJob {
    private static final int CHUNK = 500;
    private final JdbcClient jdbc;
    private final TransactionTemplate tx;
    private final Clock clock;

    ArchiveJob(JdbcClient jdbc, TransactionTemplate tx, Clock clock) {
        this.jdbc = jdbc;
        this.tx = tx;
        this.clock = clock;
    }

    @Scheduled(cron = "0 0 2 * * *", zone = "Asia/Ho_Chi_Minh")
    void archiveOldItems() {
        Instant cutoff = clock.instant().minus(Duration.ofDays(60));
        int changed;
        do {
            changed = tx.execute(status -> jdbc.sql("""
                    UPDATE lostfound.lost_found_items SET status = 'ARCHIVED'
                    WHERE id IN (SELECT id FROM lostfound.lost_found_items
                                 WHERE status = 'OPEN' AND created_at < :cutoff
                                 LIMIT :chunk FOR UPDATE SKIP LOCKED)
                    """)
                    .param("cutoff", Timestamp.from(cutoff))
                    .param("chunk", CHUNK)
                    .update());
        } while (changed == CHUNK);      // a smaller chunk means we are done
    }
}

If the search module must hide archived items, the job also publishes an event per item (for example ItemArchived) through the outbox, in the same transaction. That is a decision for SPEC-lostfound.md.

5. Scheduled publish (ANN-5)

A post can be saved now and go live later. Store the wish, and let a job make it happen:

CREATE TABLE announcement.announcements (
    id           UUID PRIMARY KEY,
    author_id    UUID NOT NULL,                   -- bare UUID, no FK to identity (C4)
    title        TEXT NOT NULL,
    body         TEXT NOT NULL,
    urgent       BOOLEAN NOT NULL DEFAULT false,  -- ANN-4: push it
    target_type  TEXT NOT NULL,                   -- ALL, FACULTY, COHORT, SECTION
    target_key   TEXT,                            -- faculty id, cohort code or section id; NULL for ALL
    status       TEXT NOT NULL,                   -- DRAFT, SCHEDULED, PUBLISHED
    publish_at   TIMESTAMPTZ,                     -- when it should go live
    published_at TIMESTAMPTZ,                     -- when it really went live
    created_at   TIMESTAMPTZ NOT NULL
);
CREATE INDEX ON announcement.announcements (publish_at) WHERE status = 'SCHEDULED';

The last line is a partial index: it only contains scheduled rows, so it stays tiny and the job's query is fast.

@Scheduled(fixedDelay = 30, timeUnit = TimeUnit.SECONDS)
void publishDue() {
    boolean more;
    do {
        more = tx.execute(status -> {
            Instant now = clock.instant();
            List<Announcement> due = repository.lockDue(now, 100);   // FOR UPDATE SKIP LOCKED
            for (Announcement a : due) {
                repository.markPublished(a.id(), now);             // WHERE status = 'SCHEDULED'
                events.publishEvent(AnnouncementEvents.published(a, now));  // outbox row, same tx
            }
            return due.size() == 100;
        });
    } while (more);
}

Why this is safe: the status change and the outbox row commit together, so the event goes out if and only if the post became PUBLISHED. If two replicas run at the same second, SKIP LOCKED gives them different rows. A post may go live up to 30 seconds late; that is acceptable for announcements.

Why not a timer per post? You could schedule one in-memory timer for each post. But timers vanish when the app restarts, and every replica would have its own. A row in the database survives restarts and is shared.

6. Audience targeting (ANN-1, ANN-2)

The Plan stores one target per post: target_type (ALL / FACULTY / COHORT / SECTION) and a target_id. A cohort is a code like "K2024", not a UUID, so the sketch above uses a text target_key. The feed needs to know, for the current user:

  • their faculty and cohort: from the user's profile (the identity module's public API, or claims in the JWT; decided in SPEC-identity.md),
  • their sections: the announcement module may not read registration's tables (no cross-schema access, D3). So it keeps a small local copy, built from EnrollmentConfirmed / EnrollmentDropped events on Kafka: a read model (lesson 22).

There are two classic ways to build a feed:

Fan-out on read

Store each post once. When a student opens the feed, ask "posts whose target matches me". Cheap to post, a bit more work per read. Good for our size.

Fan-out on write

When a post goes live, insert one row per recipient into a feed_items table. Very fast reads, but posting to "all" writes tens of thousands of rows, and new students do not see old posts. Usually used by very large social networks.

SELECT a.id, a.title, a.urgent, a.published_at, a.target_type
FROM announcement.announcements a
WHERE a.status = 'PUBLISHED'
  AND (   a.target_type = 'ALL'
       OR (a.target_type = 'FACULTY' AND a.target_key = :facultyId)
       OR (a.target_type = 'COHORT'  AND a.target_key = :cohort)
       OR (a.target_type = 'SECTION' AND a.target_key = ANY(:mySectionIds)))
ORDER BY …                                         -- next section
LIMIT 20;

An index on (target_type, target_key, published_at DESC) helps each branch. For ANN-2, the server must also check that the lecturer teaches that section before saving. Never trust the section id from the form alone.

7. Feed order and keyset pagination (ANN-3)

Ordering by relevance

"Relevant to me" can be a simple, explainable rule. For example: urgent first; then the more specific the target, the higher (my section > my cohort > my faculty > everyone); then newest first. Turn it into a number in SQL:

ORDER BY a.urgent DESC,
         CASE a.target_type WHEN 'SECTION' THEN 3 WHEN 'COHORT' THEN 2
                            WHEN 'FACULTY' THEN 1 ELSE 0 END DESC,
         a.published_at DESC,
         a.id DESC                                  -- tie-breaker: makes the order total

The last column matters: two posts can have the same time. Without a unique tie-breaker, the order between them can change between two requests, and pages repeat or skip rows.

A purely "rank by score" feed can bury new posts under old urgent ones. Many feeds only keep "urgent" on top for a few days. Decide the exact rule in the spec, and write a test for it.

Offset vs keyset pagination

Offset (?page=3&size=20)

LIMIT 20 OFFSET 60. Easy, and you can jump to page 50. But the database still reads and throws away the first 60 rows, so deep pages are slow. And when a new post arrives while you scroll, every row moves down one place: you see one post twice.

Keyset, also called cursor (?after=…)

Remember the sort values of the last row you showed, and ask for rows "after" it. The index jumps straight there, so page 50 is as fast as page 1. New posts at the top do not shift anything. But you cannot jump to "page 50".

For a simple newest-first feed, keyset looks like this. PostgreSQL compares the two values together (a row comparison):

WHERE (a.published_at, a.id) < (:lastPublishedAt, :lastId)
ORDER BY a.published_at DESC, a.id DESC
LIMIT 20

The client gets an opaque cursor (for example Base64 of those two values) and sends it back as ?after=…. With the relevance order above, the cursor holds all four sort values. Because urgent and the rank are sorted the same direction (DESC) as the rest, one row comparison still works.

Project rule The Architecture's API conventions use ?page=0&size=20 with content, page and totalElements. A feed with a cursor is a deliberate exception. Write it down in SPEC-announcement.md and ask before using it.

8. Read counts (ANN-6)

Resolution C10 lists "announcement reads (ANN-6)" as a table the module spec must design. The usual shape is one row per (announcement, user):

CREATE TABLE announcement.announcement_reads (
    announcement_id UUID NOT NULL REFERENCES announcement.announcements(id),  -- same schema: FK allowed
    user_id         UUID NOT NULL,
    read_at         TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (announcement_id, user_id)          -- one read per person, ever
);
INSERT INTO announcement.announcement_reads (announcement_id, user_id, read_at)
VALUES (:announcementId, :userId, :now)
ON CONFLICT DO NOTHING;

The browser can call this many times (every time the post scrolls into view). The primary key makes repeats harmless.

Counting:

  • SELECT count(*) … WHERE announcement_id = ? uses the primary key index, because announcement_id is its first column. Fine for a few thousand rows.
  • For very popular posts, keep a read_count column on the announcement and add 1 only when the insert really inserted a row (the insert returns "1 row"; a conflict returns "0"), in the same transaction. Then the counter never counts one person twice.
  • "312 of 450 students read it" also needs the audience size. For a section that comes from the local enrollment copy; for a faculty or cohort, from identity data.

10. Common mistakes

  • A cron with no zone. The job runs at the wrong hour in a UTC container.
  • Forgetting that every replica runs @Scheduled. Use a lock or SKIP LOCKED.
  • Calling Instant.now() in jobs. Tests cannot move time. Use the injected Clock.
  • Publishing the event outside the status-change transaction. Then an event can go out for a post that is not published, or the other way round.
  • One giant transaction for the whole archive. Work in chunks.
  • No tie-breaker in ORDER BY. Pages repeat or skip rows.
  • Counting reads with read_count = read_count + 1 on every view. One student scrolling twice counts twice.
  • Trusting the target from the form. Check that a lecturer owns the section.

11. Practice

  1. Read OutboxRetryJob.java and OutboxAutoConfiguration.java in backend/platform-starter. Is it fixedDelay or fixedRate? Why is that the right choice for a retry job?

  2. Write these as Spring cron strings (6 fields): every day 07:30; every Monday 08:00; every 15 minutes. Then check them against the Spring reference.

  3. In psql, open two terminals. In both, run BEGIN; and the same SELECT … LIMIT 2 FOR UPDATE SKIP LOCKED on a small test table you create in your own scratch database. See that the second terminal gets different rows.

  4. In the same scratch database, create 100 000 fake posts. Compare EXPLAIN ANALYZE for OFFSET 90000 LIMIT 20 and for the keyset query. Which one reads fewer rows?

  5. On paper: design the cursor for the relevance feed. Which four values go in it? What happens if a new urgent post arrives while a student is on page 3?

13. Test yourself

1. Why must the publish job write the status change and the event in one transaction?

So that both happen or neither happens. If they were separate, a crash could leave a published post with no event (notification never pushes it) or an event for a post that is still scheduled.

2. Three replicas run the 02:00 archive job. Why is it still correct with SKIP LOCKED and WHERE status = 'OPEN'?

SKIP LOCKED gives each replica different rows, and the status condition means a row archived once is never picked again. The work is shared and nothing is done twice.

3. Why does the cron need zone = "Asia/Ho_Chi_Minh"?

Without it, Spring uses the server's zone. Containers often use UTC, which is 7 hours behind Vietnam, so "02:00" would run at 09:00 local time.

4. Why is keyset pagination better than offset for a live feed?

It does not read and throw away earlier rows, so deep pages stay fast. And new posts at the top do not shift the rows, so the student does not see duplicates while scrolling.

5. Why does the feed keep its own copy of "my sections" instead of asking registration's tables?

Modules may not read another schema (D3, ADR-6). The local copy is built from Kafka events, can be rebuilt by replay, and keeps the feed working even if registration is busy.

6. How does the reads table stop one student from being counted twice?

Its primary key is (announcement_id, user_id). A second insert for the same pair is ignored by ON CONFLICT DO NOTHING, and a counter is only increased when a row was really inserted.
